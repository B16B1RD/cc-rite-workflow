# 列挙・全称主張を持つ記述は書き直しでは収束しない — 撤去だけが指摘面を消す

## 概要

散文やコメントが「この 2 field を env で渡す caller は X のみ」「以降の caller は番号を持たない」のように call site を数え上げたり、「〜だけが X を持つ」「どの経路でも Y されない」と全称・唯一性を断定すると、対象が 1 つ増えるだけでその文は偽になる。実態に合わせて書き直しても、次のサイクルで別の主張が偽になって再指摘される。**列挙は「完成させる」ではなく「置かない」が唯一の収束解**である。

## 詳細

### 観測された再生産の連鎖

PR #2094 は同一の失敗様式を 5 サイクル連続で再生産した。場所は毎回違うのに、指摘の形は同一だった。

| cycle | 場所 | 採った対処 | 次 cycle での結果 |
|---|---|---|---|
| 1 | skill 側の散文 | 実態に合わせて書き換え | 別の主張が偽と判明 |
| 2 | 同じ散文 | 2 reviewer が独立に「削除」を推奨 | — |
| 2 | docs の「値の出所」列挙 | 欠けていた 1 ケースを補完 | 実測で**別の**欠落が出現 |
| 3 | 列挙を撤去し実装 header への SoT ポインタへ差し替え | — | 指し先の header 自身が 2 規則を述べておらず不完全 |
| 4 | 基準語（「直接 source する caller」）へ置換 | — | その基準で grep した集合（3 件）と記述（2 件）が食い違う |
| 5 | header に「これが上記 4 ケース以外の唯一の帰結」と補完 | — | **前々 cycle で撤去したのと同じ網羅性断定の形**が再入 |

### 段階ごとの落とし穴

**1. 列挙の補完は 2 回目で機構ごと撤去する。** 同じ機構への 2 度目の指摘は、パッチではなく機構の撤去を検討する合図（fix.md の Simplification-First Escalation trigger と同旨）。列挙を保つ限り、対象が増えるたびに次のサイクルで偽になる。副次的な効果もある — 列挙を 2 言語で並行維持していると、片方だけ更新した瞬間に非対称が生まれるが、撤去すればそのクラスごと消える。

**2. 基準語へ置き換えても様式は基準側へ移動する。** 「call site が `2>/dev/null` で捨てるから届かない」という形式ベースの説明を撤去し「直接 source する caller」という基準にしても、その基準で選んだ集合が実 grep 結果と食い違えば同じ指摘が返る。**基準を書いたら、その基準で実際に grep して件数と集合の一致を確認してから commit する**。

**3. SoT ポインタ化は指し先の完全性を先に検証する。** docs 側で「複製するな」と宣言した以上、**指し先に無い情報は読者にとって存在しない**。ポインタを張る前に指し先を完結させること。順序を逆にすると、列挙撤去の判断自体は正しいのに読者の情報欠落を生む。

**4. SoT を完結させる作業と、網羅性を断定する作業は別物。** 前者は必要、後者は不要。指し先を完結させる過程で「これが唯一の帰結」と書き足すと、撤去したのと同じ形式が再入する。

**5. 撤去は grep で残存 0 を確認して終わる。** 指摘された行だけを直すと、同じクラスが別の行に残って次の cycle で返る。指摘のクラスを言語化し（例: 「caller 名・件数・呼び出し形への言及」）、そのクラスを機械的に検索して一掃する。

**6. 規則とその反例を同じ diff で導入しない。** 「caller を列挙して説明しない」と書きながら同一ファイルの 2 箇所で列挙していると、保守者は「規則に従って直す」か「規則を無効と見なす」の二択を迫られる。適用しきれないなら規則の scope を明示する（「本コメントでは」等）。

### 書き換えの型

列挙を条件へ変換すると、対象が何個あっても正しい記述になる。

```
✗ 「この 2 field を env で渡す caller は open / iterate のみ」
✓ 「env override も flow-state 読み取りも伴わない更新経路では既定値へ巻き戻るため読み戻す」

✗ 「call site が 2>/dev/null で捨てるから届かない」
✓ 「helper が rc=0 を返すため、捨てるか rc ゲートで握るかに関わらず届かない」
```

後者は call site を数えずに済み、remedy も正しく導ける。前者の形は (a) 数え間違える (b) 別形式の call site を見落とす (c) follow-up Issue のスコープを no-op にする、を同時に招いた。

### 関連する観測

- **設計文書の「優先順位表」は正常系の列挙であって全経路の列挙ではない。** 表を散文化すると、表が扱わない失敗経路（parse 不能 → 既定値へ倒れる等）が落ちる。散文化する際は実装の失敗経路を別途 grep して補う。
- **「stale 記述を是正する」変更が、同じ文の中に別の不正確さを持ち込む。** 削除した挙動の記述を書き換える際、新しい文が例外を N 個に閉じた列挙として提示したが、実装には N+1 番目の経路があった。しかも同じ PR 自身がその経路に WARNING とテストを実装していた。
