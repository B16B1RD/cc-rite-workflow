# 列挙・全称主張を持つ記述は書き直しでは収束しない — 撤去だけが指摘面を消す

## 概要

散文やコメントが「この 2 field を env で渡す caller は X のみ」「以降の caller は番号を持たない」のように call site を数え上げたり、「〜だけが X を持つ」「どの経路でも Y されない」と全称・唯一性を断定すると、対象が 1 つ増えるだけでその文は偽になる。実態に合わせて書き直しても、次のサイクルで別の主張が偽になって再指摘される。**列挙は「完成させる」ではなく「置かない」が唯一の収束解**である。

## 詳細

### 観測された再生産の連鎖

PR #2094 は同一の失敗様式を 5 サイクル連続で再生産した。場所は毎回違うのに、指摘の形は同一だった。

| cycle | 場所 | 採った対処 | 次 cycle での結果 |
|---|---|---|---|
| 1 | skill 側の散文 | 実態に合わせて書き換え | 別の主張が偽と判明 |
| 2 | 同じ散文 | 2 reviewer が独立に「削除」を推奨 | — |
| 2 | docs の「値の出所」列挙 | 欠けていた 1 ケースを補完 | 実測で**別の**欠落が出現 |
| 3 | 列挙を撤去し実装 header への SoT ポインタへ差し替え | — | 指し先の header 自身が 2 規則を述べておらず不完全 |
| 4 | 基準語（「直接 source する caller」）へ置換 | — | その基準で grep した集合（3 件）と記述（2 件）が食い違う |
| 5 | header に「これが上記 4 ケース以外の唯一の帰結」と補完 | — | **前々 cycle で撤去したのと同じ網羅性断定の形**が再入 |

### 段階ごとの落とし穴

**1. 列挙の補完は 2 回目で機構ごと撤去する。** 同じ機構への 2 度目の指摘は、パッチではなく機構の撤去を検討する合図（fix.md の Simplification-First Escalation trigger と同旨）。列挙を保つ限り、対象が増えるたびに次のサイクルで偽になる。副次的な効果もある — 列挙を 2 言語で並行維持していると、片方だけ更新した瞬間に非対称が生まれるが、撤去すればそのクラスごと消える。

**2. 基準語へ置き換えても様式は基準側へ移動する。** 「call site が `2>/dev/null` で捨てるから届かない」という形式ベースの説明を撤去し「直接 source する caller」という基準にしても、その基準で選んだ集合が実 grep 結果と食い違えば同じ指摘が返る。**基準を書いたら、その基準で実際に grep して件数と集合の一致を確認してから commit する**。

**3. SoT ポインタ化は指し先の完全性を先に検証する。** docs 側で「複製するな」と宣言した以上、**指し先に無い情報は読者にとって存在しない**。ポインタを張る前に指し先を完結させること。順序を逆にすると、列挙撤去の判断自体は正しいのに読者の情報欠落を生む。

**4. SoT を完結させる作業と、網羅性を断定する作業は別物。** 前者は必要、後者は不要。指し先を完結させる過程で「これが唯一の帰結」と書き足すと、撤去したのと同じ形式が再入する。

**5. 撤去は grep で残存 0 を確認して終わる。** 指摘された行だけを直すと、同じクラスが別の行に残って次の cycle で返る。指摘のクラスを言語化し（例: 「caller 名・件数・呼び出し形への言及」）、そのクラスを機械的に検索して一掃する。

**6. 規則とその反例を同じ diff で導入しない。** 「caller を列挙して説明しない」と書きながら同一ファイルの 2 箇所で列挙していると、保守者は「規則に従って直す」か「規則を無効と見なす」の二択を迫られる。適用しきれないなら規則の scope を明示する（「本コメントでは」等）。

### 書き換えの型

列挙を条件へ変換すると、対象が何個あっても正しい記述になる。

```
✗ 「この 2 field を env で渡す caller は open / iterate のみ」
✓ 「env override も flow-state 読み取りも伴わない更新経路では既定値へ巻き戻るため読み戻す」

✗ 「call site が 2>/dev/null で捨てるから届かない」
✓ 「helper が rc=0 を返すため、捨てるか rc ゲートで握るかに関わらず届かない」
```

後者は call site を数えずに済み、remedy も正しく導ける。前者の形は (a) 数え間違える (b) 別形式の call site を見落とす (c) follow-up Issue のスコープを no-op にする、を同時に招いた。

### 多ケースの帰結説明も同じクラス — 常に成立する 1 つの規則へ畳む

列挙の対象は call site だけではない。**helper が入力によって何通りに分岐するか**を散文で説明しようとすると、同じ再生産が起きる。

PR #2095 の cycle 1 は「アンカー仕様を引用した指摘がどう分類されるか」を 1 文に潰して 3 ファイルへ複製した。実測すると帰結は 5 通りに分岐し、しかも句読点の位置という文書では表現しづらい要因で割れた。記述で追随するのをやめ、**入力に依らず常に成立する 1 つの authoring 規則**（対象文字列を書かない）へ畳むのが正解だった。多ケースの帰結説明は SoT 1 箇所に委ね、他所では再掲しない。

このとき **1 箇所だけ直すと新たな未同期を作る**点に注意する。同一命題が 3 ファイルに複製されている状態で 1 箇所にだけ限定句を付けると、残り 2 箇所が偽のまま残り「二重定義の未同期」を新規に生む。既存複製の同期更新は simplification-first の対象外（機構の追加ではない）であり、3 箇所同時に直すのが最小修正になる。

**Simplification-First は実測で net-negative になる**: 同 PR の cycle 2 では「前 cycle の fix が導入した箇所への指摘は機構ごと削除・単純化を先に検討する」に従い、3 ファイルすべてで削除 + 短い置換となって develop からの net diff が元に戻った。追加パッチを重ねていれば、その追加物が次 cycle の新たな指摘対象面になっていた。

**判定基準を 1 箇所に適用したら、同じ基準が当たる箇所を全部 grep する**: 同 cycle 1 では対比の一方を「実例として不適格」と判定して除去したが、もう一方に同じ基準を適用しなかった。cycle 2 で 2 reviewer が独立に検出した。「A を直したが同型の B を直していない」は次 cycle で必ず出る。

### 「実装の挙動を散文で説明する」修正は、具体化する方向に進めると不正確さが増える

PR #2135 は同じ様式を helper の内部分岐の説明で 3 cycle 連続再生産した。

| cycle | 書いた内容 | 指摘 |
|---|---|---|
| 1 | 「全 head で converging_or_descending を返していた」 | helper は結果 3 件未満の間 `need_3_cycles` を返すため、実際に該当するのは head 4 以降だけ |
| 2 | 「武装する cycle 4 以降の head では」「cycle 1〜3 の head は `need_3_cycles`」 | head 1 の reason は `no_results_file` であって `need_3_cycles` ではない / armed head の閉じた列挙が head 6 を落とす |
| 3 | 列挙をやめ「判定の下りた head では一度も発散と判定しなかった」「判定は結果が 3 件揃うまで降りる」 | 収束 |

3 cycle 費やして到達した形は、最初より**抽象的**である。具体化するほど分岐条件の記述精度が要求され、そこで外す。**helper の内部分岐を散文で名指しするとき、分岐条件まで正しく書けないなら名指ししない**方が構造的に安全。

対象の helper は 0 件系だけで `no_results_file` / `results_dir_missing` / `no_file_after_pin` / `run_boundary_unresolved` の 4 分岐を持ち、dir と pin の状態で決まる。**reason enum を散文で列挙すると、その分岐条件まで正しく書かない限り必ず不正確になる**。

**reviewer の実測が割れたときも、争点を記述から外せることが多い**: cycle 3 では armed head の範囲について tech-writer と他 4 名の実測が対立した。差は「その run で結果が何件保存されたか」という docs からは検証できない事実に帰着する。head 番号を名指ししない記述にすれば**どちらが正しくても成立する** — tech-writer と error-handling の両者が独立に同じ回避策を推奨していた。討論で決着しない対立は、争点そのものを記述から外して解く。

### 関連する観測

- **設計文書の「優先順位表」は正常系の列挙であって全経路の列挙ではない。** 表を散文化すると、表が扱わない失敗経路（parse 不能 → 既定値へ倒れる等）が落ちる。散文化する際は実装の失敗経路を別途 grep して補う。
- **「stale 記述を是正する」変更が、同じ文の中に別の不正確さを持ち込む。** 削除した挙動の記述を書き換える際、新しい文が例外を N 個に閉じた列挙として提示したが、実装には N+1 番目の経路があった。しかも同じ PR 自身がその経路に WARNING とテストを実装していた。

### 加筆の梯子は「条件列挙 → 案内先 → 削除」で降りる

PR #2150 では、利用者向けの委譲案内について同じ 1 文へ 4 cycle 連続で指摘が付いた。指摘はすべて正当だったが、対応が毎回「条件を足す」だったため文面が 126 → 452 文字へ **3.6 倍に膨張**し、Issue が置き換える対象として名指しした「診断の羅列」そのものを再生した。しかも列挙は必ず漏れた（3 経路のうち 2 つしか書けていなかった）。

降り方には順序がある:

1. **条件の列挙をやめ、案内先を書く** — 「対象にならなかった場合は再実行時の報告と次回セッション開始時の警告が案内します」。案内先が条件に依らず有限個に閉じるなら、条件ではなく案内先を書けば全経路をカバーでき、かつ列挙より短い。**正確さと簡潔さはトレードオフではなく、参照する軸を変えれば両立する**
2. **案内先も経路ごとに違うなら、案内を書かない** — cycle 6 で、自動回収が外れる 3 経路（未マージ / dirty / 記録漏れ）はそれぞれ案内先が違い、1 つに名指しすると必ずどれかで外れることが判明した。**条件も案内先も列挙できないときは、退路そのもの（手動コマンド）を示して案内を書かない**。3 名の reviewer が独立に同じ経路の誤りを検出し、全員が削除を推奨した

### 撤退の判断は「同じ箇所への 2 回目の指摘」で下す

Simplification-First の Escalation trigger は「前 cycle の fix が導入した箇所への指摘」で発火する。しかし実務上は、**同じ箇所への 2 回目の指摘**の時点で加筆をやめ、「その機構ごと削除して根から消せないか」を先に検討すべきだった。cycle 4「条件が足りない」→ cycle 5「条件が多すぎる / 存在しない案内先」→ cycle 6「案内先が経路で違う」と、加筆・言い換えを繰り返しても指摘は終わらず、最終的に解になったのは削除だった。

**「X されます」型の断定を書く前に、その X が利用者に届く経路（surface）まで辿る。** 同 PR では次回セッション開始時の WARNING を案内先として書いたが、その stderr は session-start hook がログファイルへリダイレクトしており利用者には表示されない。存在しない可視シグナルを待たせると、無警告を「正常」と読ませる誤誘導になる。
