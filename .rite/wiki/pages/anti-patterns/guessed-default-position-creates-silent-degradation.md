# 位置決めを外部データから取る設計で「取れなかったら既定値を仮定する」と、無言の縮退になる

## 概要

テーブルのヘッダー行から列位置を決める、設定ファイルからインデックスを引く、といった「位置を外部データから取る」処理では、取得に失敗したときの分岐が要る。そこで**既定値を仮定して続行する**と、上流のデータが少し変わっただけで別の場所を黙って走査し、検出結果が 0 に倒れる。ハードコードした既定値と実データの位置がたまたま一致している間はテストも緑のままなので、発見が遅れる。

## 詳細

PR #2070 では、wiki index のテーブルからサマリー列の位置をヘッダー行で決める処理に、ヘッダーを検出できないときの既定列 fallback があった。見出し語が drift すれば別の列を走査するが、警告は出ない。しかも fixture のサマリー列が常にハードコード fallback と同じ位置にあったため、**ヘッダー由来の列位置決定そのものが pin されていなかった**。

外部データから位置を取ると決めた時点で、整合的な失敗時の振る舞いは「推測して続行」ではなく**「スキップして surface」**である。推測を選ぶなら、推測したこと自体を出力契約に載せる必要がある。

同型の縮退が rc の畳み込みでも起きる。`git cat-file -e` は「ref 自体が無い」と「ref 内に path が無い」を**どちらも rc=128** で返す。存在プローブでこれを畳むと、壊れた ref が「ファイル不在」と同じ静かな縮退になる。ref 自体の存在は `git rev-parse --verify` で先に確かめて分離する。

同 PR ではもう 2 つの関連観察がある。**同じファイルを読む複数の検出器は判定 regex を共有する** — 片方だけが狭いと、その形式のデータで片方だけ無言で 0 件になり、もう片方が正常に動き続けるため他カテゴリからも異常が見えない。そして **markdown テーブルの列パースは、リンクテキスト内の未エスケープ記号で列数が合わなくなる** — split の前にリンクスパンをマスクすると実データの列数不一致が消える。

**適用条件**: ヘッダー・設定・外部インデックスから位置や境界を決める処理を書くとき。取得失敗時の分岐に既定値を置く前に、「既定値で走った結果が 0 件だったとき、それが実体なのか縮退なのかを読み手が区別できるか」を確認する。
