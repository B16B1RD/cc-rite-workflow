# 機械強制の anchor を強制される側が選べる値にすると、2 層の gate が同一の誤りで同時に無効化される

## 概要

gate が「何を基準に判定するか」の anchor（commit SHA、PR 番号、タイムスタンプ等）を、**gate される側が渡す値**に取ると、その値の選択を誤ったときに gate は誤りを検出せず追認する。さらに悪いのは、複数の層が同じ anchor 選択の誤りを共有している場合で、独立に設計したはずの多層防御が**一斉に**無効化される。

## 詳細

PR #2130 で、5 cycle の差分スコープを消化したあとのフルレビューで、security / prompt-engineer が独立に検出した最重要指摘。

**何が起きたか**: 8.0.4 positive 層の判定 anchor である `--commit-sha` は、LLM が会話コンテキストの別ステップの出力から選ぶ値だった。helper は**形状検査（桁数）しか行わず、実 HEAD と突き合わせない**。

cycle 2 以降で 2 つの状況が同時に起きると:

1. 区間ごと skip（本 cycle の結果が保存されない）
2. 前 cycle の SHA を拾う（現 cycle 分が無いので LLM が手近な値へ手を伸ばす）

**marker 層と positive 層という 2 層の機械強制が、同一の誤りで同時に無効化される**。どちらの層も「前 cycle の値でも形式的には妥当」なので通ってしまう。

**設計上の非対称**: marker 層には値の選択規則が 4 文がかりで書かれていたのに、同じ段落で新規導入した SHA 側には選択規則が一切無かった。**既存 anchor に選択規則を書いた経験があるのに、新しい anchor には適用しなかった**。

**なぜ気づきにくいか**: anchor を「呼び出し側が渡す」設計は、helper を疎結合に保つ自然な形である。helper がリポジトリ状態を直接読まないほうがテストしやすく、hermetic でもある。その疎結合性がそのまま「強制される側が判定基準を選べる」という穴になる。

**対処**:

1. **新しい機械強制を設計したら、その anchor が「強制される側が選べる値」になっていないかを問う**。答えが yes なら、それは gate ではなく自己申告である
2. 可能なら anchor を**強制される側が選べない源**から取る（実 HEAD を helper 自身が読む、など）。疎結合性より gate の実効性を優先する
3. どうしても渡す設計にするなら、**形状検査ではなく実体との突き合わせ**を入れる（渡された SHA が実 HEAD の prefix か、等）
4. 既存 anchor に選択規則が書かれているなら、**新しい anchor にも同じ密度で書く**。片方だけ規則があるのは、規則が必要だと分かっていながら適用漏れした痕跡である
5. 多層防御を名乗るなら、**各層の anchor が独立しているか**を確認する。同じ値・同じ選択経路を共有していれば層数は 1 と数える

**判定の目安**: gate の判定式に現れる値を 1 つずつ辿り、「この値は誰が決めるか」を答える。答えが「gate される側」の値が 1 つでもあれば、その値の誤選択で gate 全体が無効化されうる。
