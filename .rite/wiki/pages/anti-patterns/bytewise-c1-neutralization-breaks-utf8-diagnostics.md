# 0x80-0x9F をバイト単位で潰す制御文字の中和は、UTF-8 の日本語を壊して診断を読めなくする

## 概要

C1 制御文字の範囲 0x80-0x9F は UTF-8 の継続バイトと重なるため、バイト単位で ? にすると日本語ロケールの git やシェルの原因行が文字化けする。整形式 UTF-8 列の継続バイトだけを残し、それ以外を潰す判定にすれば、制御文字の中和を保ったまま本文を読める。

## 詳細

端末に 8-bit の CSI（0x9B）を届かせないために、診断に載せる stderr の 0x80-0x9F を `LC_ALL=C tr` でまとめて ? にしていた。ところが「ディ」（e3 83 87）や「ホ」（e3 83 9b）のように、日本語の継続バイトの多くはこの範囲に入る。日本語ロケールの git が出す「そのようなファイルやディレクトリはありません」は ? の並びになり、運用者が失敗の原因を読めなくなった。

**直し方**: 0x80-0x9F のバイトを、U+00A0 以上を表す整形式 UTF-8 列の継続バイトなら残し、それ以外は ? にする。「それ以外」とは、単独のバイト、途中で切れた列、overlong、サロゲート、U+10FFFF 超、U+0080-U+009F（0xC2 0x80-0x9F）の 2 バイト目を指す。先頭バイトごとに 1 つ目の継続バイトの範囲が違う（C2 は A0-BF、E0 は A0-BF、ED は 80-9F、F0 は 90-BF、F4 は 80-8F）点を落とすと、overlong 経由の U+009B を通してしまう。

- 呼び出し側を緩いモード（C0 と DEL だけを潰すモード）へ差し替えると、単独の 0x9B まで素通しになる。中和の目的そのものに反するので採らない。
- 判定が正しいかは、厳格な UTF-8 デコーダを基準実装にした差分ファズで確かめると網羅できる。先頭バイト × 継続バイトの全組み合わせとランダム列を比べる。
- 前提は UTF-8 端末になる。latin1 端末では、残した継続バイトが C1 として読まれうる。ツール自身の日本語の診断文も同じ前提に立っているなら、整合は取れている。
- 整形式判定で本文を通すと、U+202E（bidi override）や U+200B（ゼロ幅スペース）などの Unicode 書式制御文字も通る。旧実装は偶然潰していた。対象を C0 / C1 に限るなら、契約にその旨を書いておく。

**awk で書くときの落とし穴**

- 出力を `out = out c` で 1 バイトずつ積み上げると、mawk では入力長の 2 乗で遅くなる（1MB で約 20 秒、gawk は 0.2 秒）。さらに、全入力を読み終えるまで何も出さない。ストリームを扱うフィルタは、判定したその場で printf する。
- バイト単位の処理は `LC_ALL=C` に頼る。ところが onetrue-awk の一部の版（2023 年秋の短い期間）は、C ロケールでも UTF-8 単位で length / substr を処理した。gawk / mawk / BSD awk のそれぞれで、実際に動かして確かめる。
- `RS` を入力に現れないバイト（前段の tr で必ず置換されるもの）にして全入力を 1 レコードで読み、`printf "%s"` で出す。こうすると末尾改行の有無を含めてバイトを落とさず、足しもしない。

**共有 helper の契約を変えるときの注意**: 中和 helper のモード 1 つを変えただけでも、そのモードを使う全 call site の出力が一斉に変わる。宣言した規模が小さくても、call site の数を数えて波及範囲を確かめる。
