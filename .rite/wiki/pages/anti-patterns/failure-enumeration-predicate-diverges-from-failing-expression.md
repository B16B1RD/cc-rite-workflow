# 失敗の原因を列挙する条件は失敗する式と同じ述語で書き、「特定できません」の既定文言で覆わない

## 概要

失敗の原因を名指しする列挙の条件が失敗する式と別の述語だと、同じ欠陥クラスの隣接ケースが列挙から漏れる。そのずれを既定文言で覆うと、既定文言は到達しにくい経路でだけ働き、案内先の妥当性を誰も確かめない。

## 詳細

### 起きたこと

照合キーの式は `.loc // (.file + ":" + ...)` で、`loc` が null / false でも `file` と連結して失敗する。一方、失敗の原因を列挙する条件は `has("loc") | not`（キーの有無）で書かれていたため、`loc: null` かつ `file` が文字列でない要素は照合を壊すのに列挙されなかった。列挙が 0 件のときの既定文言は「和集合の一時ファイルを確認してください」と案内していたが、そのファイルは同じプロセスの EXIT trap で終了時に削除され、人が読む時点では存在しなかった。

### 対処

- 列挙の述語を失敗する式と同じ falsy 判定（`.loc | not`）に揃え、列挙を失敗集合と 1 対 1 にする。
- 揃えると既定文言の分岐はほぼ到達しなくなるので、分岐ごと削除する。テストで固定できない分岐を残さない。
- 列挙の jq 自体のエラーは捨てずに stderr に出す（`2>/dev/null` で握らない）。

### 正しさの確かめ方

述語の一致は、入力の形ごとの真理値表（`loc` と `file` の値の組み合わせすべてで「式がエラーになる」と「列挙に出る」が一致するか）で確かめられる。テストで含む側だけを固定すると、列挙を広げる変異（照合を壊さない要素まで列挙する）は生き残るので、必要なら否定側の対照も置く。

### 失敗経路の案内先

失敗時の診断で案内する場所は、プロセス終了後も残るもの（結果 JSON・ログ）にする。一時ファイルは trap で消える前提で作られているので、案内先にしない。
