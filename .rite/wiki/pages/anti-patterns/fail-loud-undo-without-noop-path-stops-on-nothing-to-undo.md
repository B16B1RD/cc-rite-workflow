# 取り消し処理を fail-loud 化するときは、取り消す対象が無い no-op 経路を先に分けないと存在しない操作の失敗として止まる

## 概要

dry-run の後始末（git merge --abort など）の失敗を検出して止めるように直すと、元の操作が no-op で終わり取り消す対象が最初から無い経路でも取り消しが失敗し、事実と逆の診断と復旧案内を出して止まる。前段の判定と実行対象が別の参照を見ている手順では、この no-op 経路が実際に到達する。

## 詳細

**何が起きるか**: 手順書の bash で `git merge --no-ff --no-commit` を dry-run として実行し、結果を記録した後に `git merge --abort` で取り消す。取り消しの失敗を黙って通さないよう `git merge --abort || { ERROR; exit 1; }` に直すと、取り込みが「Already up to date.」で終わった場合に問題が出る。この場合 git は MERGE_HEAD を作らないので、abort は「There is no merge to abort (MERGE_HEAD missing)」で失敗する。手順は「取り込み途中の状態が残っている」と診断して止まるが、実際には何も残っていない。

**復旧案内が堂々巡りになる**: 案内は「abort する → MERGE_HEAD が無いことを確認する → やり直す」だが、この条件は最初から満たされている。案内どおりにやり直すと同じ ERROR に戻り、先へ進めない。直す前の版はこの状態を成功として通していたので、fail-loud 化によって新しく入った誤停止である。

**なぜ到達するか**: 前段の判定と実行対象が別の参照を見ていると、判定は「取り込みが必要」と言い、実行側では取り込むものが無い、という食い違いが起きる。例えば、前段は `origin/main` と `origin/develop` の祖先関係で乖離を判定するが、実行は `git pull` 後のローカル develop に取り込む。ローカルに未 push の back-merge があれば、前段では乖離ありと判定され、実行側では no-op になる。

**レビューで見落としやすい点**: 複数の reviewer がこの挙動を同じように実測していても、「文書どおりに進めば到達しない」と評価が分かれやすい。判断を分けたのは、前段が `origin/*` を見て実行がローカル branch を見ている、という参照の差に気付いたかどうかだった。到達可能性を評価するときは、各段が読む参照（リモート追跡か、ローカルか、作業ツリーか）を並べて比べる。

**どう直すか**:
- 取り消しの前に、取り消す対象（MERGE_HEAD など）が存在するかで分岐する。
- さらに、元の操作が no-op だった事実（`git merge-base --is-ancestor` で「すでに含まれている」と分かる状態）を独立に検出し、正しい診断で止める。
- 存在チェックで no-op を黙って成功扱いにすると、後続工程で差分のない操作を作らせる元の欠陥に戻る。止まり方の正しさ（診断と案内が実際の状態と一致すること）まで直す。
