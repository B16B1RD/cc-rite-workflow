# 失敗の印との一致でその回だけ抑止する設計は後続の書き込みで崩れる — 抑止した時点で印を消して回収を完了させる

## 概要

失敗の記録と現在の state がバイト単位で一致するときだけ抑止する設計は、「以後の書き込みは正当な作業の再開である」という前提に依存する。実際には印を残したまま state を書き換える処理があり、1 回目は抑止できても一致が崩れた後に回収済みの state が作業中へ戻る。抑止した時点で印そのものを消して回収を完了させると、後続の書き込みの種類に依存しなくなる。

## 詳細

**崩れ方**: 中断時に「この state は回収済み」という印を残し、再開の入口では印と state が一致するときだけ作業中として読むのを抑止する。一致の判定は、その後の書き込みがすべて正当な作業の再開であれば成り立つ。ところが、終了時の非 active 化や、削除済みの作業ツリーへの参照の自動クリアのように、印を残したまま同じ state を書き換える処理がある。1 回目の再開では一致して抑止できても、こうした書き込みで一致が崩れた後の再開では、回収済みの state が作業中として扱われる。2 名の reviewer が別々の経路で独立に実測した。

**テストが届かなかった理由**: fixture の state がレビュー履歴を持っていなかったため、終了時の処理が state を丸ごと削除し、問題の経路に届いていなかった。fixture が本番で普通に起きる状態（終了時の処理を生き延びる state、削除済みの作業ツリーへの参照）を含むかを確認する。

**収束した形**: 抑止を「一致したその回だけ」にせず、抑止した時点で印そのものを消して回収を完了させる。以後の書き込みが何であっても、印が無いので再び抑止の判定に入らない。

**判定の位置**: 判定は、同じ state を書き換える最初の処理（削除済み作業ツリーへの参照のクリアなど）より前に置く。後ろに置くと、判定の時点で既に一致が崩れている。

**棄却した代案**: 終了時の処理に印を消させる案は、開始時の処理が失敗したときに印を残すという別の契約を壊すため採らなかった。印の寿命を変えるときは、印を読む側だけでなく、印の存在に依存する他の契約も列挙する。

**テストの確かめ方**: 本番で普通に起きる状態を fixture に入れたうえで、修正前の実装でそのテストが落ちることを確かめた。fixture を足しただけでは、それが問題の経路に届いているかは分からない。
