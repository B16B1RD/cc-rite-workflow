# 開始・終了の対で囲む除外をラッチで実装すると、未閉鎖のまま EOF に達した経路が無音で全行を落とす

## 概要

走査対象から一定の範囲を除外するとき、開始トークンでフラグを立て終了トークンで倒す「ラッチ」は自然な実装だが、**終了トークンが現れないまま入力が尽きる経路**を誰も検査していない。その場合ラッチは立ったままなので、開始トークン以降の全行が除外され、しかも「除外した」という事実がカウンタにも WARNING にも残らない。無音の 0 件を塞ぐために入れた機構が、反対側から同じ無音の 0 件を作る。

## 詳細

起点事例では、記法例として書かれた HTML コメントを走査対象から落とすためにラッチを導入した。閉じタグ `-->` が同一行に無い入力（あるいは書きかけの記述）では、そこから EOF までの全エントリが黙って消える。error-handling / test / security の 3 名が別々の攻撃面から同じ行に到達しており、独立検出の重なりが単独レビュアーの確信度より強い証拠になった。

この構造は HTML コメントに固有ではない。**コードフェンス・YAML frontmatter・引用ブロックなど「開始と終了の対で囲む」除外はすべて同型**である。したがって対処も個別の特例ではなくクラス単位で書ける — 起点事例の修正は `in_comment || in_fence` の 1 述語で「未閉鎖の除外開始トークン」というクラスごと閉じた。述語の長さは変わらないまま、フェンス側の同型欠陥も同時に塞げている。特例を積み増す修正は次 cycle の指摘を再生産する（[修正案が失敗モードの交換で割れたら、その機構は測るべき量を測っていない](../heuristics/split-reviewer-recommendations-signal-removal.md) と同じ Simplification-First の判断）。

あわせて、この欠陥は検出失敗ガードの条件設計とも噛み合う。`entries == 0`（全滅形）を条件にしたガードは、「エントリを 1 件数えた後にラッチが立つ」部分欠損では entries>=1 となり構造的に発火できない（[全滅形だけを想定したガード条件は部分欠損形を必ず取り逃す](./total-failure-only-guard-misses-partial-loss.md)）。判定をラッチ変数自身へ置くと両方を覆える。

**適用条件**: 開始・終了トークンの対で範囲を囲む除外規則を追加・変更するとき。除外規則の追加と EOF 終端検査は必ずセットで書く。

### 兄弟 helper から除外規則を移すときは、未閉鎖の検出も一緒に移す

同じファイルを読む兄弟 helper の除外規則（HTML コメントブロックの除外）を新しい走査へ移すとき、除外だけを移し、未閉鎖を EOF で検出して検査失敗に倒す側を移し忘れることがある。そうすると、除外が検査の失敗を「問題なし」として通す。状態を持つ除外は、閉じなかったときに黙って以降を捨てる。

除外の境界を固定するテストは、除外の外側に検出すべき行を置いて期待件数を非ゼロにする。期待 0 件のテストは、除外が閉じない変異でも通る。

観測された事例では、blocking の指摘が cycle ごとに 4 → 2 → 0 件と収束した。指摘の多くは「新しく足した除外・限定が、入力の異常（未閉鎖コメント・旧形式）で黙って検出を落とす」類だった。除外を足すときに fail-loud 側と境界テストを同時に足せば、1 cycle で閉じる。
