# 「規約を守っている印」を除外条件にすると、印を持つ違反が検査から消える

## 概要

規約の遵守を測る静的チェックを書くとき、「もう対応済みの行」を除外したくなる。その除外条件に**遵守の印そのもの**（中和ヘルパーの関数名など）を使うと、同一行に印と違反が同居するケースが構造的に検査対象から外れる。規約のガードが自分自身の違反を見落とす形になる。

## 詳細

起点事例では、診断スニペットが外部由来の値を中和しているかを測るテストが `grep -v 'neutralize_ctrl'` で行を落としていた。ところが違反行の一部は同一行に `neutralize_ctrl` を含んでいた（片方の値だけ中和して他方を生で出す形）ため、検査対象から外れていた。

同じ作業で、その見落としは実害を生んでいる。**stderr の診断行には中和を通す一方、隣接する stdout の契約行は生のまま残す**という非対称が残り、リポジトリ自身が「Asymmetric Fix Transcription」として記録している型を再生産した。さらに**診断行を足すこと自体が新しい攻撃面になる**ケースも観測された — 「読出失敗の理由が消えるのは良くない」という正しい動機で入れた `sed "s|^|  ${page}: |"` が、外部由来のパスを sed のプログラム文字列へ補間する形になっており、区切り文字 `|` をパスに含めると s コマンドを終端でき、GNU sed の `e` コマンドで残りがシェルへ渡る。**変数を sed の式側へ入れてはならない。式は定数にして、変数は別行で中和して出す。**

関連して、**診断本文を運ぶ変数にセンチネル値を入れない**。同 PR ではパストラバーサル gate が `_polluted=1` と代入したため「検出行: 1」とだけ出て、どのパスが弾かれたかが失われた。sed インジェクション修正が守ろうとした「なぜ弾かれたかが消える」状態を、その修正と同じ commit で作っていた。

**適用条件**: 規約遵守を測る静的チェック・parity テストを書くとき。除外は「印の有無」ではなく「そもそも検査対象でないこと」（対象外ファイル・対象外構文）で表現する。
