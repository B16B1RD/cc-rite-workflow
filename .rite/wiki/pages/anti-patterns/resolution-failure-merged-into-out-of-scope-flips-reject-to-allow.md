# 検査先の解決に失敗した入力を「対象外」に合流させると、拒否していた入力が許可に変わる

## 概要

ガードの判定前に対象を解決する処理を置き換えるとき、解決の失敗理由（存在しない / 対象でない）を区別しないと、以前は例外で拒否していた入力が「対象外 = 許可」の経路に流れる。判定不能は拒否に倒し、除外判定と許可判定は同じ正規化で比べる。

## 詳細

HEAD を動かす git 操作を検査する hook で、検査先ディレクトリの解決を `os.chdir` から `git -C <dir> rev-parse` に置き換えた。`chdir` は存在しないディレクトリで例外を出し、結果として拒否していた。`git -C` は「存在しない」と「リポジトリでない」をどちらも非ゼロ終了で返す。そのため、存在しないディレクトリが「リポジトリ外なので対象外」に合流し、許可に変わった。

- 解決の失敗は理由ごとに分ける。「対象外と確認できた」ときだけ素通しし、「判定できない」ときは拒否に倒す（正常を確認できなければ止める）。
- 解決手段を置き換える変更では、旧実装が例外という形で拒否していた入力を列挙し、新実装でも拒否されるかを確かめる。例外による拒否は、コードに明示されていないので見落としやすい。
- 除外集合を文字列一致で判定し、許可側の検査が symlink を resolve して比べると、除外の範囲が symlink の先まで広がる。除外判定と許可判定は同じ正規化（resolve するならどちらも）で比べる。
- 同じ hook に引数パーサを新しく足すときは、兄弟パーサが持つ値付きオプションの扱いを引き継ぐ。例えば `-S[<keyid>]` のように値を省略できるオプションが欠けると、後ろのオプションを読み飛ばす。その結果、拒否すべき形を通し、正規の形を誤った理由で拒否する。
