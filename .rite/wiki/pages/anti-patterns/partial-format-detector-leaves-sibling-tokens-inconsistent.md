# 検出文法が一部の表記だけを見るとき、同じ画面の別表記が検査外に残って整合が壊れたままゲートは通る

## 概要

`#NNNN` だけを検出する文法の下で番号を直すと、同じカードにある `#` なしの裸番号が検査外に残り、修復後のプレースホルダと食い違う。表示テキストの番号は同一表示単位の全表記を一度に見る。

## 詳細

番号参照を成果物から除去する検出器は、通常「識別子として読める形」だけを文法に持つ。`#` + 3〜4 桁のような形である。この形を持たない表記——コマンド引数の裸の数字、ブランチ名に埋まった数字——は検査の外にある。

除去や置換を「検出器が指した箇所」だけで進めると、検査外の表記が元のまま残る。実測例では、デモ動画のターミナルカードが 17 行目に `/rite:open 1234`、19 行目に `feat/issue-1234-add-auth` を持ち、18 行目の出力だけがプレースホルダ `Issue #123` に直された。レンダリングされる映像では 1 枚のカードの中で 2 つの番号が食い違うが、検出器は `#` 付きしか見ないので findings 0 で通る。

**ゲートが通ることは整合の証拠にならない**。検出器の文法が部分的であるほど、通過は「その文法に触れる箇所が無い」以上を意味しない。

対処は範囲の取り方にある。番号を含む表示テキストを直すときは、**検出器が指した行ではなく、同一表示単位（同じターミナルカード・同じ scene・同じ図）の全表記**を一度に見る。単位の中で番号が何を指しているか（Issue か PR か）を確定させてから、単位ごと整合させる。

このとき、置換先の仕様が単位内で矛盾を生むことがある。実測例では「8 箇所すべてをプレースホルダ `#123` にする」という指示に従うと、同一カードに `Issue #123` と `Draft PR #123` が並び、Issue と PR が同番号だと主張することになった。プレースホルダは 1 つしか許可されていないため、両方を別番号にはできない。

この衝突では **仕様の字面より単位内の整合を採る**。実測例では、残骸の実体が番号ではなく主語（`PR`）の欠落だったので、PR 参照は主語だけを戻して番号を置かなかった。修復の種類（主語を戻す / 括弧を閉じる / 空白を消す）が仕様の意図と一致していれば、置換先の個数指定から外れることは逸脱として明示すれば足りる。判断を明示せずに字面へ従うと、通るゲートと壊れた画面が同時に残る。
