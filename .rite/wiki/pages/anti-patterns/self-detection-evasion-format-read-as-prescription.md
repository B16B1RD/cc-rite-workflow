# 自身の検出を避けるために崩した書式は、読者に「こう書け」と読まれる

## 概要

検出ゲートの仕様を記述する文書は、その仕様が検出する文字列を本文に書いた瞬間に自分自身が検出対象になる。これを避けるために記入例の書式を崩す（記号を全角に置き換える、区切りを分断する等）のは実務上必要な退避だが、**退避であることを書かなければ、読者にはその崩れた形が規定の記入形式に見える**。模倣した記入は検出層に拾われず、その指摘は降格して、ゲート自身が守るはずの受入基準が破れる。

## 詳細

**発生条件**: ワークフロー定義を同じワークフローで開発する構成のように、規約文書自身がその規約の検査対象になるドメイン。この構成では退避そのものが避けられないため、条件は例外ではなく常態である。

**実測**: PR #2095 は検出アンカーの正規形を仕様として本文に引用する必要があったため、矢印記号を全角にして検出 regex に full match しないようにした。この退避が無ければ、アンカー仕様を引用しただけの記述が実測済み指摘として恒久的に blocking 化する。一方、退避である旨を書かないままだと、読者が全角矢印を「規定の記入形式」と読んで模倣し、その記入は検出されない — 結果として本来 blocking であるべき指摘が降格し、ゲートの受入基準を裏側から破る。cycle 3 の指摘はこの経路を突いた。

**対処**: 退避した箇所には次の 2 つを必ず併記する。

1. **退避である旨**（「この行は本文自身が検出されるのを避けるため記号を置き換えている」）
2. **正しい記入形式**（実際に記入するときはどう書くのか）

片方だけでは足りない。1 だけでは読者は正しい形を知らないままになり、2 だけでは「なぜ本文と例が違うのか」が説明されず、どちらが正なのか判断できない。

**設計上の代替**: 退避が必要な箇所が増えるなら、書式を崩すのではなく**検出層の走査範囲を marker 近傍へ閉じる**ほうが根本的である。ただし検出層の変更が Non-goal の PR では退避が唯一の選択肢になるため、そのときは併記でしのぐ。

**混同しやすい別問題**: 「例が主張を否定している」（例そのものが間違っている）とは別のクラスである。ここでの例は**意図的に**正規形から外してあり、外してある事実が伝わらないことが欠陥にあたる。
