# 新しい種類の行を既存の照合キーへ合流させると、キーが一意でない行が黙って落ちる・誤って除外される

## 概要

既存の重複除去や台帳照合のキーに新しい種類の行を合流させると、キーが行ごとに一意でない場合に行が黙って落ち、別の記録と同じキーを共有すると無関係な処分で候補が除外される。合流前は全件を運んでいた経路（map）が、合流後にキーで畳む経路（reduce）を通るようになったときに起きやすい。

## 詳細

### 起きたこと

レビューの事前フィルタが除外した行を、採否判定の候補へ合流させた。候補の重複除去はキー（reviewer と位置）で畳む reduce で、同じ JSON に同じ reviewer・同じ位置の行が 2 つあると、後の行が黙って消えた。さらに、その行のキーが別の種類の記録（スコープ外処分が reviewer をキーに書く台帳行）と同じ形だったため、判定前の候補が無関係な処分で除外された。

### 対処

- 同じ JSON 内で同じキーになる 2 行目以降に出現順の添字（`#2` など）を付けて行ごとに一意にする。1 行しかない位置のキーは変えないので、既存の台帳照合は壊れない。
- 別の種類の記録と照合キーの形を共有しない。新しい行には専用の接頭辞付きキー（`guardrail:<reviewer>:<位置>` など）を与え、照合はそのキーでだけ行う。
- 検証を緩めて通した入力（位置が空・`-`・null の行）は、除外・prior の写し・原文の所在確認の各照合で一意かを 1 か所ずつ確かめる。一意でなければ機械照合から外し、同じ出典の行だけを使う。位置の無い候補の紐づけは分類役の判断に任せる（既存のスコープ外処分の規則と同じ扱いにすると構造が増えない）。

### 入力を消す側も確かめる

読み側に「この種類の行も候補にする」と足したら、その入力ファイルを消す側（セッション開始時の孤児回収・マージ後の退避判定）が同じ種類の行を持つファイルを保持するかも確かめる。読み側だけ直すと、新しい行だけを持つファイルが削除され、候補が届く前に消える。
