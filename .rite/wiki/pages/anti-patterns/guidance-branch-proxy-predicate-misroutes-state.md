# 停止後の案内を振り分ける判定に補助的な一覧の有無を使うと、案内が主張する状態を取り違える

## 概要

手順が止まった後の案内を「出力があれば A、なければ B」と分けるとき、判定に使ったコマンドが案内の前提とする状態そのものを見ていないと、無関係な要素が混ざった状態で誤った案内に振り分けられ、後段の検証を飛ばして先へ進ませてしまう。

## 詳細

リリース用スキルの復旧手順で、取り込み済みの develop を検出して止まる分岐を追加したとき、停止後の案内を `git log origin/develop..develop` の出力の有無で 2 つに分けた。案内 (1) は「ローカルにだけある back-merge が origin 側の判定とずれている」、案内 (2) は「origin/develop 自体が main を含み復旧は済んでいる」と主張する。

しかしこのコマンドが判定しているのは「ローカルにだけあるコミットがあるか」で、案内が分けたい「origin/develop 自体が origin/main を含むか」ではない。origin/develop が既に main を含み、ローカルに無関係な未 push コミットが 1 件あるだけで出力が非空になり、案内 (1) へ振り分けられる。実行者は誤った原因説明を受け、無関係なコミットの扱いを判断させられ、やり直すと事前チェックは通るため、案内 (2) で行うはずのツリー不変検証を一度も通らずにリリースへ戻る。さらに正常な再現状態でも、back-merge の第 2 親から到達する main 側のコミットが一覧に混ざり、「ローカルコミット」という説明自体が誤読を招いた。

対策は、分岐の判定を案内が主張する状態を直接問う述語（この例では `git merge-base --is-ancestor origin/main origin/develop`）に置き換え、補助的な一覧（`--first-parent` で main 側を除いたもの）はその状態が意味を持つ分岐の中で確認用に表示することである。

見分け方: 案内の各分岐の冒頭文が主張する状態を 1 つずつ書き出し、判定コマンドの真偽がその状態と同値かを確かめる。「その状態なら出力がある」だけで逆向き（出力があればその状態）が成り立たないなら、判定は代用品になっている。
