# 手順の再実行列は通常経路の強制層を飛ばさず、再実行の範囲と初回判断の保持を同じ文で書く

## 概要

やり直しで再実行する工程の列を散文で書くと、通常経路が通る検査工程が抜けて後段の検査が古い入力に当たったり、足した工程が初回に決着した判断まで作り直したりする。列は通常経路の順序に揃え、再実行の対象と保持する判断を同じ文で書き、順序の前提は helper 側で検査して機械的に失敗させる。

## 詳細

### 抜けの形 — 強制層を飛ばす

reviewer の出力が契約に違反したときに「その reviewer だけを出し直し、A → B → C を同じ cycle 内で再実行する」と書いた列が、通常経路では必ず通る強制層（実測ゲート・帰結クラスの降格）を含んでいなかった。再実行後の最終検査は、強制層を通る前の JSON に対して走り、判定対象がずれた。同じファイルの兄弟の再実行列は強制層を含んでおり、非対称だった。

列を直すだけでは次の抜けを防げない。最終検査の helper 側で「強制層を通った痕跡（例: ゲート適用記録）が JSON に在ること」を前提として検査し、無ければ失敗させると、列から工程が抜けても機械的に止まる。

### 足しすぎの形 — 決着済みの判断を作り直す

抜けを埋めるために、通常経路の矛盾検出・議論・事実確認の工程を再実行列へ足すと、今度は「何を再実行するのか」が決まらなくなる。字義どおりに読むと全 reviewer の出力を集め直し、初回に決着した矛盾を再検出して、同じ質問を利用者へもう一度出す経路や、検証済みの主張を数え直す経路ができる。

再実行列に工程を足すときは、同じ文に次の 2 点を書く:

- 再実行の対象範囲（例: 出し直した reviewer の指摘と、それと既存の指摘との矛盾検出だけ）
- 初回に確定した判断を保持するか（利用者の選択・議論の結論・事実確認の判定）

### 再試行の枠も書く

再実行列が再試行の回数カウンタをどう進めるかを書かないと、読み方によって再試行の枠が変わる。列と同じ場所に、再実行が再試行 1 回に数えられるかを書く。
