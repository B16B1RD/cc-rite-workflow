# 検査と使用は同一の式に畳む

## 概要

「入力を検査してから使う」を 2 つの式（guard と抽出、validate と transform）に分けた瞬間、3 種類の欠陥が同時に生える。個別にパッチすると 3 件の指摘になるが、1 本の式に畳めば 3 つとも構造的に消え、行数も分岐も減る。

## 詳細

PR #2126 の cycle 2 で「健全性 guard（`jq -e all(...)`）＋ 抽出（`jq -r [...]`）」の二重機構を導入したところ、cycle 3 で 3 件の blocking がすべてこの二重性に起因した。

**(a) 検査述語と使用側条件がずれても気付けない**: 検査を「`.reviewer` が非 null」、使用側を `select(type == "string")` と書いた。型が非文字列の要素は検査を通り、使用側で無音 drop される。ずれは目視でしか見つからず、しかも述語の内部矛盾がそれを示していた — `false` は jq の `//` が欠損扱いするため偶然弾かれるのに、`123` や配列は通る。「false は拒否するが 123 は受理する」という契約を意図して設計する者はいない。

**(b) 2 本目の fail-safe が到達不能コードになる**: 検査が真を返した後の抽出は構造的に失敗しえないため、抽出側に置いた `|| emit_full ...` は到達しない。それを唯一 pin していたテストは、fixture が guard 側に先に捕まるようになって**空振り**していた（TC は名乗った経路に到達していないのに、結果だけを見る assertion のため green のまま）。

**(c) 診断が構造的にゼロ行になる**: 検査が「不正あり」で*正常終了*する主経路（述語が偽になるだけ）では jq は stderr に何も書かない。`2>"$err"` + `head -3 "$err"` 形の診断イディオムをコピーすると、この経路だけが「対象は出るが原因が永久に出ない」状態になる。しかも見た目は他の経路と同一なので気付けない。

**畳んだ形**（1 本の jq が `OK\t{値}` か `BAD\t{違反 id 列}` を返す）:

- 使用側の条件がそのまま検査述語になるので (a) が構造的に消える
- fail-safe が 1 本になるので (b) が消える
- 違反要素の id を同じ式の中で列挙できるので (c) も消える（stderr に依存しない原因行が作れる）

**関連する一般則**: `$err` に原因を求めてよいのは「外部コマンドが異常終了した」経路だけである。述語が偽になっただけの経路では jq も grep も正常終了するので stderr は空になる。診断出力を書くときは、**その経路で stderr に何かが入る保証があるか**を経路ごとに確認する。無い経路では原因を自前で作る。

**判定の目安**: 「guard を足す」修正を思いついたら、それが「二重機構を足す」修正でもあることを確認する。使用側の条件を検査述語として書き写しているなら、畳める。
