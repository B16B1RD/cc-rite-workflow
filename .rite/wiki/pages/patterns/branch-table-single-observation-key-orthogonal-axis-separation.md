# 分岐表は判定キーを 1 つの観測量へ統一し、直交軸は表から出して独立段落に書く

## 概要

散文手順（LLM が runtime で読むワークフロー定義）の欠陥は、個々の文が誤っているのではなく、**複数の正しい文が同時に成立したときの優先順位が書かれていない**ことに現れる。分岐表を書くときの型が 2 つある: (1) 全分岐の条件キーを 1 つの観測量へ揃える、(2) 判定軸の異なる条件は表の行にしない。

## 詳細

### 1. 条件キーを 1 つの観測量へ統一する

一方を「節見出しの有無」、他方を「中身の形式」で条件付けると、**見出しは無いが旧形式で登録済み**のような実在形状がどちらの分岐にも一意に落ちない。字義実行すると新旧形式が混在し、それは他方の分岐が禁じている状態になる。検証 helper が形式非依存だと、混在は lint でも検出されない。

- 「見出しの有無」と「中身の形式」は**別の観測量**である。統一できないなら precedence を 1 文で明示する。
- 分岐条件を書いたら「**その条件が偽になる実在形状**」をプロジェクト自身の test fixture から探す。本リポジトリでは既存テストが該当形状を検証していた。
- 散文や HTML コメント内の形式例は判定根拠から明示的に除外する（成果物側に旧宣言が残っている場合がある）。

判定表の key も同様で、4 行が判定値（0 件 / VERIFIED / CONTRADICTED / UNVERIFIED）を key にしているのに 1 行だけ観測（コマンド失敗）を key にすると、その行は他行と同時該当して判別子を要求する。

### 2. 直交軸は表の行にしない

「すべて VERIFIED」と「自己矛盾候補あり」は別軸の判定なので同時に真になりうるが、表形式は暗黙に排他を示唆するため優先規則が書かれない。直交する条件は表から外し、表の直下に「**上表のいずれの行に該当した場合でも**〜」で始まる独立段落として書く。

**直交性を宣言するときは「何と直交し、何とは直交しないか」を両方書く。** 判定の軸だけが直交していて発火条件は上書きしない、という区別を落とすと、対象外のはずの入力でも検査が走る。

### 3. 「同じ〜に載せる」は先行詞の発火条件まで書く

表の各行は独立に到達しうるため、他行が作るオブジェクト（AskUserQuestion 等）を指す指示は、その行が発火しない経路で宙に浮く。「**あれば相乗り、無ければ本項目だけで新規に発行**」まで書き切る。

### 4. 分岐表は行列として埋め漏れを確認する

ある分岐の適用手順欄に「既存行の更新」を書き忘れると、その分岐に落ちるリポジトリでは更新が永久に実行されず、代わりに新規追加が走って同一キーの行が二重化する。**列（手順）× 行（分岐）の行列として埋め漏れを確認**し、「この分岐では起こらない」と思った手順が本当に起こらないか上流の判定を追う。

分岐表に手順名を並べるときは**依存グラフのトポロジカル順**にする。「用意 → 使用」の順序は自明に見えて逆順を書きやすく、逆順だと成果物が壊れる。

### 5. 1 つの検出に処理指示を 1 つだけ持たせる

同じクラスに対し「本文を書き換える」「指摘に留める」「3 値の処理へ流す」が優先規則なしで並存すると解が決まらない。検出と処理を 1:1 に畳み、他の記述には合流先を明記する。
