# 構造化レコードの部分更新は全行再生成へ置き換え、同定述語をキー位置まで anchor する

## 概要

構造化データ（GFM テーブル行等）の部分更新は「どの列か」の解決を必ず要求する。行の同定をキー一致にして誤爆を防いでも、同定後の**列の特定を位置で行えば、既に列がずれている行では誤ったセルを破壊する**（実データで 298 行中 16 行が該当）。**行全体を規定形式で再生成すれば列を数える必要が消え、既存の壊れた行も更新のたびに漸次是正される（healing）。**

ただし全行再生成は**同定の一意性を前提にする**ため、単純化と同時に述語を強くしなければ破壊的になる。

## 詳細

### 同定述語はキーの出現位置まで anchor する

部分更新を全行再生成へ単純化したとき、対象行を決める述語が「キーを**含む**行」のままだった。実データにはサマリー列に他レコードへの相互参照リンクを持つ行があり、**1 キーが最大 3 行に一致**した。全行再生成は一意性を前提にしているため、別レコードを丸ごと上書きして消す経路が開く。しかも同じ手順が「列位置を数えるな」と書いていたため、唯一の識別シグナルを契約側が禁じていた。

- 述語は**キーの出現位置（第 1 セル等）まで anchor する**。「キーを含む」で書くと、そのキーが本文中に相互参照として現れるデータで必ず誤爆する。
- 複数一致は fallback（1 件目を採る）ではなく **fail-loud で中止**する。silent に誤った行を書き換える経路を残さない。

### 対象範囲はレンダラの解釈に委ねない

「テーブル行」を対象と書くと GFM のブロック意味論に依存する。実 index の節内には空行が 2 本あり、GFM は先頭ブロックだけをテーブルと解釈するため、登録行 298 のうち **135 行が段落として描画**されていた。厳格に読むとその 135 行は重複ガードと重複削除の両方から漏れ、更新のたびに行が増える。

**対象範囲は位置ベース（見出しから次の見出しまで + 行頭文字）で定義する。** 「レンダラがテーブルとみなす行」は実データの些細な瑕疵（空行 1 本）で集合が変わる。あわせて瑕疵そのものを次サイクルで直す healing 手順を入れると、対象集合が収束する。

### optional フィールドを唯一の値ソースにしない

「値はすべて frontmatter から取る」と SoT を一本化したが、当該フィールドは schema 上 optional で**実データの 55%（164/298）が持っていなかった**。全行再生成と組み合わせると、それらのレコードでカタログ側の蓄積値が空で上書きされる。

- SoT を宣言する前に、そのフィールドが **schema 上必須か / 実データの充足率**を確認する。
- optional なら値ソースを順序付き（SoT → 当サイクル生成値 → 既存値保持）にし、**空文字での上書きを明示的に禁止**する。
- SoT 側を補完する手順を上流ステップに追加しないと、「SoT を更新してから実行せよ」という指示が不在フィールドに空振りする。

### 判定述語は全手順で同一の対象集合に揃える

「重複ガードはテーブル行を見る」「行同定はリンク一致で見る」と述語が分かれていると、節の外に残す旧形式行の扱いが未定義になる。同じデータを扱う複数手順の述語は**対象集合まで含めて一致させる**（「節内のテーブル行」のように範囲を明示する）。意図的に残すデータがあるなら、各手順がそれを対象に含むか除くかを 1 箇所で宣言する。

### 「写し」と宣言したデータの更新元を 1 つに固定する

「index は frontmatter の写し」と書きながら、更新手順の値の出所を「frontmatter + 今回のサマリー」と 2 系統にすると、写しが原本より新しくなる読みが成立する。**SoT を宣言したら、その SoT 以外から値を取る経路を手順に残さない。** 派生値を変えたい場合は「先に SoT を更新してから写しを再生成する」と順序で書く。

### 複数レビュアーが別の言葉で同一箇所を指したら両方の失敗経路をカバーする

同定述語の欠陥を、2 名は「キー列 anchor の欠落」として、1 名は「GFM 解釈依存」として報告した。前者だけ直すと 135 行漏れが残り、後者だけ直すと相互参照リンクの誤爆が残る。**それぞれが指す失敗経路を列挙して両方カバーする修正**を作る（本事例では同じ 1 文の修正で両方閉じた）。
