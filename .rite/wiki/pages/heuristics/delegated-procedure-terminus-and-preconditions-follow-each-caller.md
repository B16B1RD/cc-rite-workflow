# 既存手順を新しい入口から呼ぶときは、終端と前提分岐を呼び出し元ごとに書く

## 概要

委譲先の手順が自前の終端（ループの再実行など）を持つと、委譲元の戻り先と食い違って入れ子実行を招く。新しい入口から既存手順を呼ぶときは、終端を呼び出し元ごとに分け、既存手順の前提分岐（作業が既に進行中の状態など）も新しい経路に置く。

## 詳細

### 起きたこと

base と競合して CI を待てない cycle を閉じたあと、base を取り込む手順を reference に足した変更で、3 回のレビューに次の欠陥が順に見つかった。

- 足した手順の最終箇条は「`/rite:iterate` を行う」だった。iterate 自身から委譲されたときに字義どおり読むと iterate を入れ子で起動し、「同じ実行で 1 回まで」の counter が 0 から始まって停止条件が効かない。呼び出し元ごとに終端を分ける書き方（iterate から来たときは iterate のステップ 1 へ戻る、それ以外は再実行）で解消した
- commit ガードの案内が誘導する先の手順は、新たに `git merge` から始まっていた。ところが案内が出るのは merge が既に進行中（MERGE_HEAD がある）のときで、二重の merge が失敗する行き止まりだった。既存手順の手順 1 と同じ分岐（取り込み相手が同じなら競合の解消から始め、違えば abort してから取り込む）を新しい経路にも置いた
- 停止条件を「想定外の失敗に限る」と書き直したとき、列挙から最初のコマンド（fetch）が抜けた。逆に「非ゼロなら停止」と書くと、想定どおりの非ゼロ（競合で merge が rc=1）まで止まる読み方が残る

3 回目のレビューで新たな指摘は 0 件になった。

### 書き方

- 委譲先の手順は呼び出し元ごとに終端を分けるか、委譲元で「手順 N は行わない」と明記する
- 案内文の誘導先を変えるときは、その案内が出る状態で誘導先の手順が実行できるかを辿る
- 停止条件を絞るときは、対象手順の全コマンドを列挙し直す
- 新しい経路の手順は、既存手順の同じ分岐と同じ文型で書く。矛盾の検査が文字列の比較で済む
- fail-loud の分岐を OR で足したら、各側にテストを置く。fixture の値は既定値と変えて出所を区別する（PR の base と既定の `branch.base` が同じ値の fixture では、値の出所を取り違えても通る）
- 判定が発火する範囲（欠落だけでなく実行中の pending でも発火する等）と、コメントや文書の説明範囲を揃える
