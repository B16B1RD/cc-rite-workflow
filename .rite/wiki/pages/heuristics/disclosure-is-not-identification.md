# 残余の緩和策として値を開示するなら、その値が問題発生時と正常時で違う値になるかを確かめる

## 概要

既知の残余に対して「値を marker へ併記するので silent にはならない」と書くとき、その値が決定論的に組まれていると健全な状態と stale な状態でバイト単位に同一の文字列が出るため、開示は残余の識別に使えず緩和策として機能しない。

## 詳細

### 起点

中間ファイルの存在検査が stale なファイルを掴んで fail-open しうる、という既知の残余を明記したうえで、緩和策として「marker に解決先パスを併記するため silent にはならない（どのファイルで通ったかを人間が追える）」と書いた。

しかしそのパスは 3 つの構成要素すべてが健全 cycle と stale cycle で一致する:

| 構成要素 | 値 | 健全 / stale の差 |
|---|---|---|
| ディレクトリ | セッション内不変と明記済み | 同一 |
| PR 番号 | 同一 PR | 同一 |
| commit SHA | HEAD 不変が stale の発生条件 | 定義上同一 |

したがって marker は両状態で**バイト単位で同一の文字列**を出す。人間はパスを見ても本 cycle のファイルか前 cycle の残骸か判別できない。開示は「どこを見ればよいか」を示すだけで、「今それが正しいか」は何も語らない。

### 判定手順

緩和策として値を開示すると書いたら、次を確かめる:

**この値は、問題が起きているときと起きていないときで違う値になるか。**

ならないなら、それは緩和ではなく所在の表示にすぎない。書くべきは次のどちらか:

1. **主張を実態まで狭める** — 「本残余は緩和されない。marker は解決先を開示するのみで、stale 判定には使えない」
2. **値に識別力を持たせる** — 判定対象側に状態依存の値（cycle 識別子・生成時刻・世代カウンタ）を書き込み、消費側で照合して食い違いを出す

非ブロッキングな観測層として設計されている機構では 1 が整合的。fail-loud を優先する層なら 2。

### 前例との類比は層の数まで含めて確認する

同種の残余を持つ既存機構を引いて「あちらも同じ形だから許容範囲」と書くとき、**開示している層が同じ数あるか**を見る。

起点事例では、既存機構は独立した marker 層が skip を検出した**うえで**所在を開示していた（2 層）。新設側は存在検査 1 層しかなく、**その 1 層が fail-open する当の条件を開示だけで埋めようとしていた**（1 層）。前例は「開示があるから安全」ではなく「検出があり、加えて開示がある」構造だった。

### 一般形

過大な主張は、それ自体が次の改修の土台になる。「silent にはならない」と書かれていれば、次の変更者はそこを検証済みの前提として扱う。**緩和策の主張は、その緩和が効く条件を自分で一度反証してから書く。**
