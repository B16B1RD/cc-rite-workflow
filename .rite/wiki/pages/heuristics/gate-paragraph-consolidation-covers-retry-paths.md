# 検査を独立した段落ではなくゲート段落自体へ統合すると、再回収経路にも自動で効く

## 概要

ある検査を「別の段落」として書くと、その段落を名指しせず「ゲートを再実行する」とだけ書いた再回収経路（retry / reroll）では検査が抜ける。検査をゲート段落そのものへ統合すると、ゲートを再実行するすべての経路に自動で含まれる。ゲートを再実行しない経路だけ、検査を名指しで明記すればよい。

## 詳細

新しい検査を追加するとき、既存のゲート段落とは別に「### 追加検査」のような独立節を作りがちである。しかし失敗時の回復経路（部分 retry / reroll）が「ゲート段落を再実行する」とだけ書かれている場合、独立節として書いた検査は再実行対象に含まれない — 回復経路の記述者が独立節の存在を意識して個別に書き足さない限り、検査が silent に抜け落ちる。

対策は逆転の発想: 新しい検査をゲート段落**そのもの**の一部として記述する。そうすれば「ゲートを再実行する」という既存の記述だけで、新しい検査も自動的に再実行対象になる。例外的にゲートを経由しない回復経路（そもそもゲート自体を呼ばない特殊 case）だけ、検査を個別に名指しする必要がある。

関連する教訓として、同一レビューでは以下も指摘された:

- **文字列一致だけで固定するテストの脆さ**: 同じ文字列が複数の検査行に含まれると、片方の検査行を削除してもテストが通ってしまう。対策は shell ブロックを抽出して実際に実行し、失敗ケースを guard ごとに分けて（ファイル不在 / 見出し欠落 / 相対パス）、止めた guard の文言まで確認すること。相対パスのケースは実ファイルに解決できる cwd で実行しないと、後段の検査が先に止めて前段の削除を見逃す。
- **契約変更時のテンプレート本文の見落とし**: 契約を変えたときは、散文コメントだけでなく、子（サブエージェント等）へ実際に送られるテンプレート本文に残る旧契約の記述も探す。コメントだけ更新してテンプレート本文が古いままだと、実行時の挙動はテンプレート側に従う。
