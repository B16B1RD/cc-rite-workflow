# 意図的除外と失敗を同じカウンタに載せると、そのカウンタの存在理由が消える

## 概要

無音の欠損を可視化するために失敗カウンタを新設したら、そこに何を載せるかが設計判断になる。**規約どおりに除外した行**を同じカウンタへ載せると、本物の drift と routine な除外が区別できなくなり、健全な入力でも毎回警告が出る。警告が常時出る状態は、警告が無い状態と情報量が同じである。

## 詳細

起点事例では、欠損を surface するために作った signal に意図的除外を混ぜた結果、正常な run でも毎回発火する状態になった。修正は除外を **entries（分母）にだけ計上し、失敗カウンタには載せない**方針で、既に同様の扱いをしている他の除外（E1-E4）に揃えた。

同じ設計に付随する規則が 3 つある。

**診断メッセージは原因を絞る。** 1 つのカウンタに複数経路が合流している状態で「形式変更の可能性」と断定すると、存在しない調査へ運用者を誘導する。合流させるなら文言も全経路を包含させ、絞るなら合流そのものをやめる。

**「上の WARNING を参照」と誘導するときは、上の WARNING に上限があるかを確認する。** 件数を告げてから行番号を 3 件しか出さないと、運用者は残りが打ち切られたのか WARNING が壊れているのか判別できない。上限を設けるなら残件数を明示する。

**欠損ガードは「失敗を数える」だけでなく「対象を認識できたか」も数える。** 抽出失敗のカウンタは、抽出を試みる前段（エントリの認識）が空振りした場合を捕まえられない。認識件数そのものを 0 件チェックの対象にしないと、走査対象を読めているのに何も認識できない状態が無言の 0 件として通る。

なお、**append-only で増えるコーパスの実測値は厳密値を持たない**。桁で書けば陳腐化しないし、除外判断を支えているのは絶対数ではなく他カテゴリとの比である。実測値を表に並べるときは単位も揃える（hits とファイル数が同じ列に混ざると除外コストの比較が誤る）。

**適用条件**: 検出器に失敗カウンタ・欠損 signal を新設するとき。「このカウンタが 1 以上になったとき運用者は何を調べるべきか」を 1 文で書けるかを判定基準にする。書けないなら経路が合流しすぎている。
