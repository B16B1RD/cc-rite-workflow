# 機構を削除して解くと、pin 面積だけでなく失敗モードの重さ（blast radius）も縮む

## 概要

「規律を作って pin で守る」より「規律が要らない構造にする」ほうが安い、という判断は pin の本数だけでは測れない。**削除は、その機構が壊れたときの帰結の重さも同時に縮める**。

PR #2142 では、`print` する全規則が「出力済み」フラグを立てるという規律を pin で守る代わりに、本体規則を記録だけにして **print 点を END へ一本化**した。結果:

- 規律・説明コメント・腕ごとの pin という 3 つの問いが同時に消えた
- reviewer は「新規律は 3 本体規則すべてが構造的に pin 済み」「旧形が 2/3 しか pin できなかったのに対し構造的に解消」と評価した
- **同じ変異の帰結が軽くなった** — `exit` 削除変異は旧形では「二重 print → WARNING 消滅」だったが、新形では「報告行の選択が変わるだけ」になった

blocking はこの cycle で 2 → 0 になり mergeable へ到達した（推移 6 → 6 → 6 → 3 → 2 → 0）。

## 詳細

### 単純化は「削りすぎ」の向きにも失敗する

同 PR の cycle 3 → 4 では、交替腕を 1 本落としたことで空セクション（テンプレートを途中まで埋めた Issue）の WARNING が完全に消えた。落とした理由「見出しは解釈できているので是正先にならない」は、**値行が存在する場合にしか成り立たなかった**。値行が 1 行も無いときは見出しこそ唯一の是正先である。

**交替腕を 1 本落とすときは、その腕だけが救っていた入力クラスを列挙してから決める。**

### 単純化のたびに「この防御は今も到達可能か」を問う

print 点の一本化により awk の stdout が「空か 1 行の数値」だけになり、非数値を弾く `case` の腕が構造的に到達不能になった。到達不能なガードは、将来の regression を loud に落とさず**沈黙させる退路**として残り続ける。単純化の diff では、触っていないガードの到達可能性も再確認する。

### 「なぜ消したか」の考古学は消した機構と同じ速度で腐る

削除を正当化するために書いた注釈は、cycle 4 の指摘 9 件のうち 4 件の発生源になった。「4 段 idiom が要るがモードが無いので廃止した」という経緯説明は、廃止後の読み手には要らない一方で**主張の正しさを検証され続ける負債**になる（実際その主張は次 cycle で虚偽と判明した）。残すのは現在のコードを読むのに要る 1 文だけにする。主張を狭めて生き延びさせるより、経緯ごと削るほうが安い。

### 等価変異を「生存」と数えない

mutation の生存件数を報告するときは等価変異を分けて数える。本 PR では 2 件が等価変異だった（`if (n)` ガードの削除 = コマンド置換が末尾改行を剥がして同じ `case` 腕へ吸収される、規則順序の入れ替え = 述語が構造上排他）。あわせて、**投入した mutant の一覧を申し送りに残す** — 「12 種を全て kill した」という自己申告は一覧が無いと差分検証できず、3 reviewer が独立に等価性検証を重複実行した。

### 「複製の同期漏れ」を指摘されたら、同期ではなく複製の削除を先に検討する

同期で応えると複製構造がそのまま残り、**次の同期漏れを別の場所で再生産する**。別事例（PR #2229）では、cycle 1 が「4 箇所に複製された誤った根拠を直せ」という指摘に同期で応え、複製構造を残したまま新たに 3 サイトの複製を作り、1 箇所（宣言済み SoT）を掃き残して同じ欠陥クラスを再生産した。cycle 2 は定義を単一述語（「結果を回収できたか」）へ置き換えることで、経路ごとの除外規則（確認 UI での増減、spawn 失敗マーク）を書き足す必要自体を消した。

> **経路ごとに規則を足す形になっていたら、全経路の帰結を 1 つの述語で表せないかを問う。**

同じ判断がテスト側でも効く。実装が同じ述語を「強制用」と「診断用」に複製していると、ファイル全体 grep の pin は診断側で満たされ、強制側を削っても緑のまま通る（[Test pin protection theater](../anti-patterns/test-pin-protection-theater.md) の双子サイト成立）。この事例では pin を区間限定 grep へ賢くする案を **mutation で検出できないことを実測して棄却**し、実装側の複製を消すことで検出力を回復させた。

修正の妥当性は実測で示す。3 種の変異（強制条件の削除 / ラベル語の書き換え / SoT 片側の巻き戻し）を隔離 worktree で流し、修正前 0 件 fail・修正後 2/2/1 件 fail を確認してから commit した。**「テストを直した」は主張ではなく実測で示す。**

### 削除で応えるべきところに説明を足すと複製面積が増える

「誤った案内を消す」修正で、削除した対象の代わりに**その理由づけを長く書く**と、参照先の実文言と食い違う新しい不整合を作る。PR #2229 cycle 4 では、効かない設定キーを復旧レバーから外す際に、削除の根拠として参照先スキルの内部機構を英日 2 言語で再掲し、引用元の見出し・定義文と正面から矛盾した。**4 名のレビュアーが独立に検出**した cycle 唯一の指摘だった。

悪化の構造は 2 段ある。第一に、**SoT ポインタで委譲すると宣言している段落の直後に機構を再掲する**と、宣言と行為が同じ場所で矛盾する。第二に、2 コピーが**言語違い**だと literal 一致を要求する契約テストで pin できず、次の drift を機械的に検出できない形になる。

修正は SPEC 側をレバー名 + ポインタへ戻し、説明を SoT 側 1 箇所に閉じたうえで引用元の実文言に合わせて狭めることだった。前節「『なぜ消したか』の考古学は消した機構と同じ速度で腐る」と同じ帰結 — **削除に応えるときは、説明ではなく削除で応える。**
