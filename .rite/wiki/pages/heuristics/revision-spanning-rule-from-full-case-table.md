# 改訂をまたぐ判定規則は、改訂なしの既存ケースも含むケース表から 1 つの規則で決める

## 概要

仕様の改訂をまたいで進展や同一性を判定する規則を、指摘された改訂パターンごとの場合分けで直すと、別のパターンで逆向きの誤りが出続ける。改訂ありと改訂なしの全ケースを表にし、全行を満たす 1 つの規則を選んでから実装すると収束する。

## 詳細

レビューの途中で合意して受入条件を改訂しても、同じレビューを続けられるようにする変更で、「受入条件の進展」の定義を直すたびに別の改訂パターンで誤りが出た。改訂パターンには、未観測の経路、文言の書き換え、いったん外してから戻す、があった。場合分けの修正を重ねる代わりに、指摘されたケースを表にし、全行を満たす 1 つの規則を選んでから実装した。この切り替えで、場合分けのための記録や境界の計算を撤去できた。

選んだ規則は「受入条件の（ID・本文）の組が、未充足と観測されたあとで充足に移ったら進展とする」である。追加・書き換え・外して戻す・未観測経路のどれでも一貫する。ただしこの規則は、改訂の無い run で成り立っていた既存の保証を弱めた。見直しの時点ですでに満たしていた条件は進展に数えない、という保証である。ケース表には、改訂ありのケースだけでなく、改訂なしの既存ケースも行として入れる。

同一性の判定には、次の点も効いた。

- 受入条件の ID の集合差だけでは、同じ条件かどうかを判定できない。文言の書き換えや取り消しを区別できないので、ID と本文の組で扱う。
- 本文で同一性を決めるなら、抽出する範囲を契約として固定する（例: コードブロックの行を含めるか）。範囲が変わると、同じ条件かどうかの判定がずれる。
- 比較の前に正規化（空白の圧縮・行頭空白の削除）をすると、意味のある差を落とす。コードブロックの字下げのように空白が意味を持つ本文では、正規化そのものが判定のすり抜けになる。正規化の種類を 1 つずつ足さず、本文を逐語で比べて差を落とさない方向に倒す。
- 出力側と読む側で行の区切りが一致しないと、入力由来の問題が環境障害として現れる（awk は改行だけで区切り、Python の `splitlines()` は Unicode の行区切りも使う）。

既存の helper に出力モードを足すときは、既存モードの出力を変えず、同じ検査を共有した。テストは、変異で空振りしないことに加えて、落ちる地点（判定行か例外か）を確かめる。確かめないと、テストが何を固定しているかを過大に名乗りやすい。
