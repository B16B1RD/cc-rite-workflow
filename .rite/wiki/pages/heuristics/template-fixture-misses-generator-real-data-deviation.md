# テンプレート準拠の fixture では、生成器が実データで作る構造的逸脱を検出できない

## 概要

除外規則やパーサの fixture を「そのファイル種別のテンプレート」に合わせて作ると、テンプレートが持つ偶然の性質（当該見出しが最終節にある、など）によって**誤った実装と正しい実装が同じ結果を返す**。生成器が実データで作る構造は、テンプレートに書かれた形と一致しない。

## 詳細

PR #2066 では、`## ソース` 節を走査から除外する規則を検証する fixture をページテンプレートに合わせて作った。テンプレートでは当該見出しが最終節にあるため、「見出し以降 EOF まで打ち切る」実装と「節スコープで除外する」散文が同じ結果になり、ずれが露見しなかった。実データでは生成器（wiki-ingest の LLM）が見出しの後ろに別の節を追記しており、**13 ページ・81 hits の盲点**として初めて現れた。

さらに次の cycle で対になる失敗も起きている。**除外の範囲を狭める修正は、境界を決める識別子の実データ上の表記揺れを先に数える** — EOF 打ち切りは見出しの後ろを丸ごと落とすため、見出しの表記揺れ（`## ソース（追記分）`）を偶然カバーしていた。節スコープへ狭めた途端、揺れた見出しは「節の開始」として認識されないまま「次の見出し」としては認識され、直前の節の除外を打ち切って以降を走査対象に戻した。`（追記分）` はテンプレートにもコードにも定義がなく、生成器の LLM 出力で発生していた。

同 PR ではもう 2 つの構造的教訓が出ている。

- **同一の除外を 2 実装に持つと、判定順序の違いで片側だけが安全になる**。一方はフェンス判定を他の分岐より前に置いたため構造的に fence-safe だったが、もう一方はフェンス保護が無くコードフェンス内の見出しで走査が止まった。regex だけでなく**判定順序まで揃える**。
- **mutation テストは、mutant が到達しない除外を素通りさせる**。差分ガード（sed が no-op なら fail）は機能して vacuous pass を防いだが、mutant がフィルタ本体の一部を残す設計だったため、その除外だけ mutation からも fixture からも到達不能だった。mutation の設計時に「どの除外がその mutant で測れないか」を列挙し、測れないものは fixture 側で pin する。

**適用条件**: 生成器（LLM / スクリプト）が出力するファイルを読むパーサ・除外規則の fixture を設計するとき。テンプレートではなく実データのサンプルを先に見る。
