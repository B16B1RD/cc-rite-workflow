# テンプレート準拠の fixture では、生成器が実データで作る構造的逸脱を検出できない

## 概要

除外規則やパーサの fixture を「そのファイル種別のテンプレート」に合わせて作ると、テンプレートが持つ偶然の性質（当該見出しが最終節にある、など）によって**誤った実装と正しい実装が同じ結果を返す**。生成器が実データで作る構造は、テンプレートに書かれた形と一致しない。

## 詳細

起点事例では、`## ソース` 節を走査から除外する規則を検証する fixture をページテンプレートに合わせて作った。テンプレートでは当該見出しが最終節にあるため、「見出し以降 EOF まで打ち切る」実装と「節スコープで除外する」散文が同じ結果になり、ずれが露見しなかった。実データでは生成器（wiki-ingest の LLM）が見出しの後ろに別の節を追記しており、**13 ページ・81 hits の盲点**として初めて現れた。

次の cycle では対になる失敗も起きている。**除外の範囲を狭める修正は、境界を決める識別子の実データ上の表記揺れを先に数える** — EOF 打ち切りは見出しの後ろを丸ごと落とすため、見出しの表記揺れ（`## ソース（追記分）`）を偶然カバーしていた。節スコープへ狭めた途端、揺れた見出しは「節の開始」として認識されないまま「次の見出し」としては認識され、直前の節の除外を打ち切って以降を走査対象に戻した。`（追記分）` はテンプレートにもコードにも定義がなく、生成器の LLM 出力で発生していた。

同じ作業からもう 2 つの構造的教訓が出ている。

- **同一の除外を 2 実装に持つと、判定順序の違いで片側だけが安全になる**。一方はフェンス判定を他の分岐より前に置いたため構造的に fence-safe だったが、もう一方はフェンス保護が無くコードフェンス内の見出しで走査が止まった。regex だけでなく**判定順序まで揃える**。
- **mutation テストは、mutant が到達しない除外を素通りさせる**。差分ガード（sed が no-op なら fail）は機能して vacuous pass を防いだが、mutant がフィルタ本体の一部を残す設計だったため、その除外だけ mutation からも fixture からも到達不能だった。mutation の設計時に「どの除外がその mutant で測れないか」を列挙し、測れないものは fixture 側で pin する。

**適用条件**: 生成器（LLM / スクリプト）が出力するファイルを読むパーサ・除外規則の fixture を設計するとき。テンプレートではなく実データのサンプルを先に見る。

### 手書き fixture は「生成器側のドリフト」も見えなくする

fixture が実データから逸脱する向きは 2 つある。上記は「fixture が正しく、実データが逸脱する」向き。もう 1 つは**生成器が変わっても fixture は変わらない**向きで、こちらは実装が生成器の出力に依存した瞬間に死角になる。

実例: 所属判定 `_body_belongs_to_issue` が、コメント生成テンプレートの書く `- **Issue**: #N` の 1 行だけを入力にする実装を入れた。テストは全て手書き fixture（`- **Issue**: #42` をハードコード）を通すため、**テンプレート側のラベルを改名しても 31 passed / 0 failed のまま**だった。故障は fail-safe（スキャンへ縮退するだけ）なので、性能契約（gh 往復を増やさない）だけが無警告で死ぬ。

対策は fixture を増やすことではなく、**実際に生成される出力を捕まえて実 parser にかける**こと:

- 生成側を shim で走らせ、投稿・書き込みに渡された body をそのまま保存する
- parser 本体を `awk '/^_fn\(\) \{/,/^\}$/'` 等で抽出して `eval` し、保存した body に直接適用する
- 対象 ID で真、別 ID で偽、の両方を assert する（片方だけだと部分一致実装が通る）

これで fixture を介さずテンプレートと parser を同じテストで突き合わせられる。実際、部分一致実装へ mutate すると当該 assert だけが落ちる。

**「実装がテンプレートの特定の行に依存し始めた」ことが、この対策を入れる合図である**。依存が生まれた PR でテストを足さないと、依存を知らない後続の変更者がテンプレートを触った時点で無警告で劣化する。

### 状態ファイルの fixture は、書き込み元が同じ更新で書く全フィールドから組む

読み手の分岐に新しい値を足しても、その手前にある早期 exit のゲートが書き込み元の実際の state を通さなければ、足した分岐は本番で一度も実行されない。実例では、停止理由を書く経路が同じ更新で `active=false` も書くのに、案内は `active=true` のときだけ動く位置に置かれていた。テストは停止理由だけを置き `active=true` のままにした fixture を使ったため、到達不能な分岐でも green になった。

- fixture は書き込み元を grep し、同じ更新で入る他のフィールドまで含めた実形で組む
- 実形に直した fixture で先に red を確かめてから修正する
- 修正後は、新しい値を持たない同形の state では何も出ないことを対照として置く
- 受入条件の充足をテスト結果だけで判定しない。fixture 自体が架空の state を置いていれば green は充足を意味しない。書き込み元から実 state を再現したレビュアーだけが未充足を捉えた

### 状態ディレクトリを見る掃除処理の fixture には、掃除を走らせるセッション自身の state も置く

掃除処理が「所有セッションの state が無い残骸だけを回収する」ように状態ディレクトリを参照して分岐するとき、fixture に状態ディレクトリそのもの（例: セッション一覧のディレクトリ）が無いと、判定は手前で別の経路へ倒れ、残骸を回収する分岐へ一度も到達しない。その分岐を壊した mutant は生き残り、テストは green のままになる。本番では掃除を呼び出すセッション自身の state が必ず存在するので、fixture にもそれを置いて本番と同じ形にしてから分岐ごとに assert する。
