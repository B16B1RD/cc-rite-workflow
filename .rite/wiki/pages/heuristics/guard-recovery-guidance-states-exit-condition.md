# ガードの復旧案内は状態ごとのコマンド列ではなく、ガードの解除条件で示す

## 概要

処理を止めるガードの復旧案内を、原因の状態ごとのコマンド列で書くと、列挙していない状態がレビューのたびに見つかり続ける。ガードが見ている条件そのもの（例: git status に対象が表示されなくなったら再実行）を解除条件として示すと、案内とガードが同じ状態を見るので全状態で成り立つ。テストは原因の状態を列挙してループし、各状態で止まることと、解除条件を満たせば通ることを検査する。

## 詳細

**コマンド列の案内は状態の列挙になる**: 複数の原因を持つ ERROR に「この場合はこのコマンド」と手順を並べると、案内は原因の状態の列挙になる。列挙から漏れた状態では手順が効かないか、別の害を起こす。submodule の変更だけが残って作業の退避ができない状態を止めるガードで、案内を 4 回書き直した実例では、書き直すたびに次の漏れが見つかった。

- submodule の中で退避する案内は、参照先 commit だけが変わった状態に効かない。さらに、ブランチ切り替えで空になった submodule の中で取り出しを実行すると、親リポジトリの退避（別セッションのものを含む）を取り出す。
- submodule を記録済みの状態へ戻す更新コマンドは、submodule の HEAD が記録済み commit と一致していると作業ツリーの編集を捨てない。中身の変更を捨てるには強制の指定が要る。
- 強制を付けても、戻す先は親の index にある参照である。親で stage 済みの参照先変更は、先に stage を外さないと戻らない。

**解除条件で示す**: 案内を「変更を残すなら commit し、残さないなら記録済みの状態へ戻して、状態表示に対象が出なくなってから再実行する」という解除条件に置き換えると、案内はガードの判定と同じ状態を見る。状態ごとの具体的なコマンドを約束しないので、列挙の漏れが構造的に起きない。この書き方に変えた次のレビューでは、4 名の reviewer のだれも状態の漏れを見つけられず収束した。

**全原因で安全に効く手順だけを残す**: コマンドを案内に残す場合は、挙げた原因のすべてで安全に効くものに絞り、原因ごとに効くことを実測で確かめる。

**テストは状態を列挙してループする**: 原因の状態（中身の変更・未 stage の参照先変更・stage 済みの参照先変更・submodule 内の stage 済み変更）をテストのループで回し、各状態で「止まる」ことと「解除条件を満たせば通る」ことを検査する。原因と選択肢の組み合わせを個別に書くと、漏れた組み合わせが次のレビューで指摘される。

**テストコメントの主張はループの範囲に限る**: テストの意図を書くコメントが「すべての状態で止まる」と一般化すると、reviewer が列挙の外の状態を実測して反証する。コメントの主張は、ループで列挙した状態の範囲に限る。
