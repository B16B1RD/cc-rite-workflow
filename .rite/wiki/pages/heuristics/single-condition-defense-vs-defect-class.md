# 特定の 1 バイト・1 条件で書いた防御は、defect class 全体を覆うか修正直後に自問する

## 概要

レビュー指摘は具体的な 1 ケースで届く。その 1 ケースだけを塞ぐと、**同じ defect class の別インスタンスが次の cycle で返ってくる**。指摘を直した直後に「この防御は class 全体を覆っているか」を問う習慣が、サイクル数を実際に削る。

## 詳細

### 実測された 2 例

**例 1: 文字クラス。** 「区切り文字 `0x1f` が値側でエスケープされない」列ずれを、その 1 バイトの除去で塞いだ。次 cycle で **NUL による同じ迂回**が実測で出た。NUL は列をずらさない — bash の command substitution が NUL を*削除*するため断片が連結し、`12<NUL>34` が `1234` という実在しない数値に化けて、非数値降格も WARNING も発火しない。迂回の*形*は違うが「区切り 1 種類だけを潰す実装では捕捉できない」点で同一クラス。C0 制御文字全域へ広げると、副次的に LF による herestring 切断も構造的に閉じた。

**例 2: 遮断述語。** cross-Issue の値転写を止めるガードが「identity が食い違う」ときにしか発火せず、identity 判定キー自体を削除すれば迂回できた。「異常を検出したら止める」から「正常を確認できなければ止める」へ述語を広げると、材料の欠落そのものが停止条件になる（[fail-closed ガードの書き方](../patterns/fail-closed-confirms-normal-not-detects-abnormal.md)）。

### 判断の手順

1. 直した 1 件を抽象化する — 「`0x1f` が値に混ざる」→「区切り文字が値側でエスケープされない」→「制御文字が値に混ざる」
2. 抽象化した class の他のインスタンスを列挙する — NUL / LF / CR / ESC ...
3. 現在の実装がそれらを捕捉するか、実際に試す
4. 捕捉しないなら、**個別に足すのではなく述語を広げる**

3 を飛ばして 4 だけやると、広げた述語の射程をコメントに書いた時点で別の指摘を生む（射程の記述が実挙動より狭い / 広い）。実測してから書く。

### 広げないという判断も選べる — ただし根拠を残す

同型の join/split idiom はプラグイン内 11 箇所に存在したが、伝播適用は 0 件とした。理由は 2 つ。

- Issue の Non-Target / Out of Scope に該当する
- 他サイトの入力は rite 自身が書く flow-state JSON で、ユーザーが改竄しうる作業メモリとは脅威面が異なる

**確立イディオムの横展開是非は別 Issue の判断事項**として調査推奨へ回した。スコープを守りつつ指摘を握り潰さない形として機能する。

### 修正の副作用を織り込む

修正を入れる cycle では、**修正そのものが次 cycle のレビュー対象面になる**。実例では、前 cycle の修正が生んだ指摘が 5 件中 3 件を占めた（テスト変数の衝突 / 半角スペース欠落 / 文言の未検証）。うち 2 件は「修正の質」の問題で機構的な欠陥ではない。**修正の直後に「この修正は何を新たにレビュー対象にしたか」を自問する**とサイクル数を削れる。

具体的な副作用の型:

- **テストのトップレベル変数の衝突**: 番号順では空きに見える接尾辞が別ブロックで使用済みだった。宣言順と番号が乖離しているファイルでは目視の「次の番号」判断は信頼できない。追加前に `grep -c` で衝突を確認する。
- **「揃える」修正が byte 一致しない**: 2 箇所の literal を揃えたつもりが半角スペース 1 個が欠けていた（3 reviewer が独立に検出）。**揃えた後に `grep -c` で一致数が期待どおりかを機械確認する。** リテラル二重化を選んだ時点で目視 drift は不可避なので、検証を機械側へ寄せる。
