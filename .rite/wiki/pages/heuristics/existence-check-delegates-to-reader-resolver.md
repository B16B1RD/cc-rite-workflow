# 設定の存在確認は読み手の解決処理に委ね、自前の候補リストを持たない

## 概要

設定ファイルの有無を確かめる手順が、実際に設定を読む処理と別の候補リストを持つと、両者の差の分だけ「あると案内したのに読まれない」「無いと案内したのに読まれる」が起きる。存在確認は読み手が使う解決処理の結果で判定する。

## 詳細

設定を読む側の解決処理は作業ツリー自身と main checkout の設定ファイルだけを候補にしていたが、案内用の存在確認は別のディレクトリの設定も「あり」とみなしていた。その場所にだけ設定を置いた利用者は初期化済みと案内されたまま既定値で動く。余分な候補を存在確認から外すと、この方向の食い違いは消えた。

ただし存在確認が現在のディレクトリだけを見る自前の判定のままだと、逆方向の食い違いが残る。解決処理は作業ツリーに設定が無ければ main checkout を 2 番目の候補にするため、設定を commit していない利用者がセッション worktree で存在確認を実行すると、読み手は設定を読めるのに「未初期化」と案内される。

- 存在確認は、読み手が使う解決処理（その終了コードや解決先）で判定する。候補リストを手順側に書き写さない
- 候補を増減する修正では、読み手より広い側と狭い側の両方の差を列挙し、片方だけ直して終わりにしない
- 「特定の文字列が残らない」形の受入条件は、grep 0 件の観測だけでは再追加を止められない。固定するテストが要るかどうかを判断材料として残す
