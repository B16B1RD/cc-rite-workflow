# 機械的な述語を文書化するときは意図の語彙ではなく字句の語彙で書く

## 概要

判別子は字句的にしか判定できない。記述側がそれを意図の語彙（「何を意図した崩れか」）で言い換えると、意図の語彙は読みやすい代わりに、必ず「そう意図していないのに同じ帰結になる入力」を生む。判別子が意図を読めない以上、この乖離は原理的に閉じない。**述語を文書化するときは、どの文字がどこにあるかで書く**。

## 詳細

**実測された乖離**: 起点事例の判別子は「marker から `=>` までの間に改行 / `<br>` / 句点 (U+3002) があるか」という字句条件だったが、SoT 側は「折り返しアンカー」「散文中の言及」「書き損じ」という意味論の語彙で説明していた。security reviewer が実測で示した反例は、**折り返していない 1 行アンカーでも LHS に句点が 1 字あれば降格側に落ちる**というもの。日本語で散文を書くリポジトリでは句点は最も踏みやすい文字であり、この乖離は理論上の話ではない。実測済み CRITICAL が merge を止めなくなる経路が「安全」と読める形で残っていた。

**条件節の追加では止まらない**: 3 cycle かけて帰結記述を条件付きに直してもなお同型の指摘が出続けた。面ごとに条件節を足すたびに、その追加自体が次 cycle の指摘面として再生産されるため。有効だったのは**語彙の一本化** — 意味論の言い換えを削除して字句条件 1 本へ寄せると、面の数は変わらないが記述の自由度が消えるので drift の再生産が止まる。Simplification-First の Escalation trigger（同一 PR の前 cycle fix が導入した箇所への指摘）はこの判断を明示的に要求する。

**診断文言も述語の定義に合わせる**: 判定が選言（アンカー不一致 OR 未判定への boolean 先書き）へ広がったとき「アンカー有無と矛盾する」は狭すぎて、実際に発火した第 2 項が説明されない。「本ゲートが算出する判定と食い違う」のように**述語そのものを言い換える**と、母集団が増えても文言が陳腐化しない。

**同一文言を 2 箇所に持つ場合は機械的に一致検証する**: helper の WARNING 文言とその SoT が literal 一致を契約とするなら、編集後に `grep -o` で両者を抽出して文字列比較する。目視同期は必ずずれる。

**同期対象は grep で機械的に洗う**: 列挙面の粒度差（上位 SoT の 1 面だけが同期対象から漏れる）は、記憶で数えると必ず起きる。`grep -rn '装飾\|全角\|折り返し'` のように**旧語彙で掃く**のが確実。列挙が「reviewer が自分のケースの帰結を判定する手段」として機能している以上、面ごとの粒度差はそのまま判定不能を意味する。

**行き過ぎの方向にも注意する**: 字句条件へ寄せる際に述語の依存関係を落とすと、今度は強すぎる断定になる。母集団の束縛は必ず残す（[一般化した断定は、実装が特殊化されている限り必ず偽になる](./generalized-claim-false-while-implementation-specialized.md) を参照）。

**規則の外延は検出層の literal を実際に読んで合わせる**: 字句の語彙で書いても、**その外延が検出 regex より狭ければ規則は必ず破れる**。ある PR は「marker 文字列そのものを書かない」という authoring 規則を置いたが、検出側の regex は大文字小文字を無視し、装飾文字とコロンまで吸収する実装だった。規則に従って書いた記述が検出され、規則が守れない状態になる。散文で規則を書くときは、対応する機械側の literal を開いて読み、regex のフラグ・吸収する文字クラスまで含めて外延を一致させること。「意図としてはこの範囲」で書いた規則は、実装の吸収範囲を必ず取りこぼす。
