# 近似判定が parser の判定を包含することは境界の両側の差分検査で確かめ、正規化の選択肢ごとにテストで固定する

## 概要

処理量の上限を超えた入力を parser の代わりに文字列の近似で判定するとき、近似が parser より弱いと上限の外側だけ素通りが生まれる。上限の直下（parser が判定する側）と直上（近似が判定する側）に同じ入力群を流し、直下で拒否されて直上で許可される形が無いことを差分検査で確かめる。近似の正規化（引用・バックスラッシュ・行継続の除去など）は選択肢ごとに、それを外すと落ちるテストを置く。

## 詳細

**近似は parser を包含しなければならない**: 入れ子の深さのような上限を超えた部分を解析しない設計では、その部分に隠れうる危険な形を近似で拒否する。近似が「生の文字列に危険な語が含まれるか」を見るだけだと、引用で綴りを分けた語（`g''it`）やバックスラッシュ・行継続を挟んだ語は、parser なら同じ語として読むのに近似では見つからない。上限の直下では拒否され、1 段深くしただけで許可される形があれば、それが素通りの経路になる。近似の側で shell の語の読み方に合わせて正規化する（引用・バックスラッシュ・行継続を外してから探す）と包含に近づく。

**包含は差分検査で確かめる**: 包含の確認は、個別の例を並べるより、同じ入力群を上限の直下と直上に置いて判定を比べるほうが確実である。実測では reviewer が数千通りの入力で直下と直上を比べ、「直下で拒否・直上で許可」の組が 0 件であることを示した。近似が parser より強く拒否する（HEAD を動かさない形まで拒否する）側のずれは fail-closed なので許容し、仕様にその旨を書く。

**正規化の選択肢ごとにテストを置く**: 正規化の正規表現は複数の選択肢（単引用、二重引用、バックスラッシュ、行継続）の和になる。テストが一部の選択肢しか通らないと、残りの選択肢を削る変異をしてもスイートは green のままになる。選択肢ごとに、その選択肢でしか綴りを分けられない入力（二重引用で分けた語、行継続で分けた語）を拒否ケースに置き、選択肢を削る変異が 1 件ずつ検出されることを確かめる。テストのラベルには内側の入力を出し、どのケースが落ちたか判別できるようにする。

**テストの見出しコメントは例外の範囲まで書く**: 「上限を超えても HEAD を動かさないコマンドは拒否しない」のような見出しは、解析しない部分の中では近似が拒否する例外を落としている。仕様・実装コメント・テストの見出しで同じ主張を書くときは、例外の範囲（解析しない部分の外に限る）を揃える。
