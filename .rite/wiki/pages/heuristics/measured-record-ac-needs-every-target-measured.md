# 「実測を記録する」型の受入条件は対象全件の実測で満たす — 形の検査や類推で代わりにしない

## 概要

受入条件が各対象を実際に動かした記録を求めるとき、一部だけ動かして残りを「形が同じだから通る」で埋めると、別の条件（形の検査）の根拠を流用しただけになり未充足と判定される。通常経路で通らない分岐は、同じ実行の中で直接呼び出して記録を補う。

## 詳細

### この型の受入条件は記録の欠落として指摘される

受入条件の中には、コードの正しさではなく「実際に動かした結果が残っていること」を求めるものがある（例: 各サブコマンドを呼んで結果を PR 本文に記録する）。この型は実装が済んでいても、記録が全対象を網羅していなければ未充足のまま残る。修正もリポジトリを変えず、実際の run を回して記録を集め直し、PR 本文を更新する形になる。

- 呼び出しの形を検査する自動テストは、その呼び出しが実際に通ったことの記録にはならない。形の検査は別の受入条件の根拠であり、実測の代わりに数えると同じ根拠を 2 度使ったことになる
- 状態を書き換える操作も、実際の run の中で 1 行の呼び出しとして使えば実測として数えられる。「状態を変えるから試せない」は省く理由にならない

### 通常経路で通らない分岐は直接呼び出して補う

1 回の通常の run では呼ばれない操作がある。ファイルが無いときだけ使う fallback、矛盾したときだけ出す signal、ループの 2 周目以降でだけ進む記録などである。これらは同じ run の中で literal な引数を渡して直接呼び出し、結果を記録に加える。

### 同じレビューで見つかった付随の取りこぼし

- placeholder を廃止したら、同じ文書の見出しや説明文に残る旧 placeholder 名も直す
- helper に新しい exit 原因を足したら、helper ヘッダの exit 契約と手順書の対処表も更新する
- placeholder を sed で一括置換すると、`${var}` 形の変数参照まで書き換わり、別のファイルへ書き込む事故が起きる。置換対象は `"{var}"` の形に限定する
