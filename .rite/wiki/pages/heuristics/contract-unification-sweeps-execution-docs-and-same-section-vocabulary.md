# 契約を一意化する変更は、参照文書だけでなく実行手順書の placeholder と同節の旧語彙まで同時に揃える

## 概要

二義的だった契約文を一意に定める変更は、契約を書いた参照文書を直すだけでは足りない。実行者が実際に読む手順書側の placeholder 表やテンプレートが旧方式を無条件に命じたまま残ると曖昧さの発生源が解消せず、同一節に残った旧語彙は除去したはずの二義性を再生産する。主張は証跡が裏付ける範囲に限定する。

## 詳細

独立 reviewer への本文引き渡しを「絶対パス + 着手前の全文読取 + 先頭行の読取完了申告」に一意化した変更で、レビューは 3 種の取りこぼしを同時に指摘した。いずれも参照文書の変更としては正しく、テストの pin も通っていたが、読み手が辿る経路の側で二義性が残っていた。

- **実行手順書が旧方式を命じたまま**: 参照文書は「全文 inline せず絶対パスだけを契約とする」と宣言したが、pr-review スキルの placeholder 表と reviewer prompt テンプレートは host 条件なしに共通原則の全文を prompt へ渡すよう命じていた。独立子経路の入口は参照文書を指すだけで、テンプレートの該当 placeholder を絶対パス行へ差し替える規則を持たなかった。実行者は「テンプレートに従えば inline、参照文書に従えば絶対パス」という二択に再び直面する。契約の一意化は、その契約を消費する手順書・テンプレート・placeholder 表まで同じ変更で揃えてはじめて成立する
- **同節に残った旧語彙**: 表行と新設節を書き換えたあとも、同じ節の直後段落に「同じ本文を渡す」という旧語彙が残った。変更前は上の表行と整合していたため無害だったが、新設節と並んで読まれると inline とも読める。旧語彙の grep は書き換えた表行だけでなく、同じ節の段落・隣接文まで掃く
- **証跡の範囲を超えた主張**: 参照文書に「複数ホストで完走している」と書いたが、同じ変更に含まれる設計文書の検証記録は単一ホストの実績しか持たず、他ホストは未検証のままだった。配布先の読者が未検証のホストまで確認済みと誤読する。事実の主張は設計文書や Issue が記録する証跡の範囲どおりに限定し、広げるなら記録側を同時に更新する

3 件はいずれも実測アンカーを持たない字面整合クラスで non-blocking に降格され、blocking 0 で mergeable となった。実測必須ゲートの設計どおりだが、記録された指摘はマージ後に follow-up として拾い直す必要がある。

同じクラスは、契約参照側へ例外を足したあとも実行手順書の複製が未更新のまま残る形でも再発する。Target Files の実パス検査を足した変更では、マッピング参照が File 列のプレースホルダ例外を書いたのに、手順書 Step 2 項 4 は MUST 未収集へプレースホルダを無条件挿入する複製のままだった。同一 4.2 内で挿入せよと拒否せよが併存し、後段検査が作成を止めるので受入基準は守られるが、実行者は矛盾した命令を読む。拒否アクションを単一 helper 名に固定すると、適用範囲に書いた別経路（分解 helper）では字面どおり従っても止まらない。独立表を早期 exit の後に置くと、質問枠を満たした時点で表に到達しない。契約の例外・適用範囲・拒否アクション・評価順は、実行者が辿る手順書の複製まで同じ変更で揃える。

取りこぼしを埋める follow-up でも、同じクラスは 3 つの形で再び現れた。
- **規則の限定句を容器単位で書くと兄弟テンプレートを取りこぼす**: 差し替え規則を「4.5 テンプレートの placeholder は inline せず絶対パス行に置き換える」と書くと、検証モードで連結される 4.5.1 検証テンプレートが同名 placeholder を独自に持つため、そちらは規則の外に残る。差し替え規則は容器（テンプレート名）ではなく識別子（placeholder 名）を単位に書き、同名の出現箇所をすべて覆う。2 名の reviewer が独立に同じ取りこぼしを検出した
- **証跡限定では主語と観測対象を分ける**: 「絶対パス方式は Codex で計画/実装子の起動と完了回収を完走している」は範囲を子の種別に狭めたが、方式を主語に残したため、設計記録が観測していない「絶対パス方式による回収」の帰属を主張し続ける。設計記録が観測した対象（子の種別・回収の事実）と、その観測がどの方式によるものかは別の主張であり、記録に無い側を主語にしない
- **区間 pin は上限も切る**: 節スコープの pin を `split(見出し)[1]` の下限だけで作ると、後続節まで区間に含まれ、規則文が隣の節へ移動しても assert が通る。reference 側と skill 側で同じ切り方（下限と上限）に揃えないと「節スコープ pin」の主張をテストが保証しない

証跡限定の書き直しを適用した follow-up では、修正そのものは 3 reviewer が独立に裏付けを確認して blocking 0 で通ったが、書き直しの形が新しい取りこぼしを生んだ。提案文（1 文）を「観測した事実」「未検証の主張」「設計記録は裏付けていない」の 3 文へ分割すると、末尾文の目的語が暗黙化して直前文に係ることが文脈依存になり、単独で読むと第 1 文の観測まで打ち消すように読める。証跡限定の書き直しは主語と目的語を各文に明示するか、提案文の 1 文形を保つ。また配布物の散文に「設計記録」の語を置くと参照先（`docs/designs/`）が配布物外にあり、配布先の読者はその語を解決できない。証跡の所在を名指しするより「未検証である」で止める方が配布物として自己完結する。新規散文を追加したときは既存 pin の部分文字列に埋もれる細粒度の変異（限定句の削除・末尾文の削除）が残るため、追加した句ごとに pin を足す。

主張の範囲を実装に合わせて狭める方向でも同じクラスが出る。警告や除外の対象を文書で「〜を問わない」と広く書くと、helper が別の分岐で入力を捨てる経路と食い違う。範囲を書くときは helper の分岐を列挙して一致を確かめ、合わなければ実装を広げるより記述を限定する。限定の書き直しは、同じ文言を持つ疑似コード・散文・docstring を grep してまとめて直す。それでも同じ節にある別の二重定義（入力キーの列挙など）は取り残されやすく、複数の reviewer が同じ未同期を独立に再掲した。境界を文書で明記したら、その境界を固定するテストを同じ変更で足す。文書と実装の一致を将来にわたって守るのはテストである。

実装にある停止条件を文書の登録条件へ書き足す場合も同じ照合が要る。条件の境界（実装が `-ge` なら文書は「at or past」「未満のときだけ」）と、比較する値がいつ確定するか（カウンタを加算してから凍結するか）まで実装と突き合わせると、文言の境界ずれを防げる。書き足す位置にも注意する。表のセルに別の用途を追記すると、同じセルの後続文（無効値の扱いや発火時の挙動）が新しい用途にも掛かるように読めるため、追記はセル内の話題の切れ目に置く。

規定に例外を設ける場面でも、二義性は例外の判定基準に宿る。日本語文書の記号を全角にそろえる規定を新設したとき、既存テンプレートが半角で固定している生成ラベルと衝突し、例外を 3 cycle かけて詰めることになった。
- **例外は 1 か所の一覧に集める**: 例外が字形表・ラベル節・半角のまま残す場所のように複数の節へ散ると、同じ行が全角にも半角にも読める。制限文を足して調整するより、制限文を削って例外を 1 つの一覧へ集めるほうが、新しい規則を足さずに衝突が消える。テンプレートが字面を固定している行は、その一覧へ 1 項目足すだけで既存のテンプレートや検査に触れずに済む
- **判定基準は 1 つに絞る**: 「テンプレートが固定している」と「検査が固定している」のように 2 通りに読める基準を並べると、同じ欄にある別の行（検査の対象外の項目行）が例外に入るかを読み分けられず、表記揺れが再発する。基準を 1 つに決め、例は限定し、隣接する行の扱いは同じ項目に 1 句で書く
- **基準の語は指示対象を添えて書く**: 例外の根拠に「検査」と書くだけでは、検査が見ているのがテンプレートの字面か生成物かを読み手が決められない
- **一覧の名詞と参照する文の名詞をそろえる**: 例外を「行」と呼びながら一覧にコードスパンや URL のような「場所・構文」が混ざると、粒度の違いが読み違えの余地として残る
