# 段階分割 PR では「契約として宣言したこと」と「いま実装されていること」を時制で書き分ける

## 概要

Sub-Issue でデータ契約だけを先に切る PR では、SoT ドキュメントと LLM 向け指示が「write 側は常に N キーを出力する」「フィールドとして保存される」と現在形で書かれやすい。producer 側の配線が後続スコープに繰り延べられている場合、grep すると抽出側はゼロで、記述は事実ではない。同じ現在形で書かれた「契約」と「実装済みの事実」は読者に区別できず、後者と受け取られる。起点事例（5 cycle 収束）では cycle 1〜3 の HIGH 指摘の半分がこの型だった。

## 詳細

### 症状の 2 系統

**1. 未配線の機能を現在形で断定する**

データ契約 PR が「6.1.a は常に 3 キーを出力する」と書いたが、write 側の配線は後続 Sub-Issue のスコープで、その時点の実装は 1 キーも出力していなかった。読者（次の保守者・レビュアー・LLM）は「もう動いている」と読み、その前提で下流を設計する。

**処方**: 責務宣言と配線状況を分ける。

- 責務宣言: 「出力する場合は 3 キーすべてを埋める」（形式契約。いつでも真）
- 配線状況: 「producer 側の配線は Sub-B のスコープ。現時点の write 経路はこのフィールドを出力しない」

**2. 予防的配置の理由を現在形で書く**

型ガードを invariant 評価の前段に置いた理由を「後段が nested access で jq rc=5 になるから」と現在形で書いたが、その時点の後段 invariant はそのフィールドを参照しないため主張が再現しない。3 reviewer が独立に base 版へ fixture を通して受理されることを実測し、同じ結論に到達した。

守っている対象が「将来の consumer」なら、そう書かないと保守者が「主張が再現しない → 配置を動かしてよい」と誤結論する。

**処方**: prospective に書く。「現時点の後段はこのフィールドを参照しないため、この配置は将来 consumer が入ったときの保護である」。

### 併存する逆向きの基準に注意する

同じ PR 内に「その経路が参照しないからガード不要」という逆向きの除外理由（例: Priority 3 に guard を置かない理由）が併存していると、同じ基準を自分のガードに適用したとき「不要」という結論になる。除外理由は経路固有の根拠（入力が永続ファイルか否か、など）に置き換える。

### 一括処理が要る — 1 箇所直して他を放置する drift

起点事例では「この記述は形式契約であって現在の配線状況ではない」という限定句を、サブフィールド表と型ガード節には入れたが、cross-field invariant と reviewer 向け自問には入れなかった。結果、同一ファイル内・同一注入プロンプト内で「配線は後続」と「read 側が auto-correct する」が併存した。**未配線の機能について書くときは、その機能名を grep して現在形で語っている箇所を全部拾い、一括で処理する**。cycle 2 と cycle 3 で同じ取りこぼしを 2 度繰り返している。

### チェックリスト

段階分割 PR で SoT / 指示ドキュメントを書くときに通す:

1. この文が主張しているのは「契約」か「実装済みの事実」か
2. 「事実」側なら、その機能名を grep して実装が存在するか確認したか（enforcement 主体は grep で実装の存在を確認してから schema に書く）
3. 「契約」側なら、配線状況を明示する 1 文が同じ箇所にあるか
4. ガードや分岐を予防的に置いたなら、その理由は prospective に書かれているか
5. 同じ機能名を語る他の箇所も同じ扱いになっているか（grep 全数）
