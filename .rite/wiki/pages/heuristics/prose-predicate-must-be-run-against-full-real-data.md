# 散文で機械的述語を定義したら、字義どおりの実装を実データ全件へ当ててから書く

## 概要

散文が実行契約であるリポジトリでは、手順書に書く「対象行の同定述語」「値の抽出規則」はコードと同じ厳密さを要求される。正常系のデータを念頭に書くと、**まさに是正対象である外れ値だけ**を取りこぼす。しかも同じ述語が修復手順（重複削除など）にも使われていると、取りこぼした行は永久に修復されない。

対処は 2 つ。**述語の定義軸を一般化する**（分岐を足さない）。**提案する文言をそのまま実装したプローブを実データ全件に当てる**。

## 詳細

### 実測された取りこぼし

起点事例は index.md のカタログ形式を箇条書きから 5 列 GFM テーブルへ反転させる PR で、「登録行の同定述語」を新設した。初版はページ列を **「`|` で分割した最初のセル」** と定義していた。

実データ 342 行に当てると 333 行しか一致しなかった。取りこぼした 9 行は **title に未エスケープの生パイプを含む行** — つまりこの PR が是正しようとしていた破損行そのものである。

失敗の構造はこうなる。

1. 同定できない → 手順 1 が「既存行なし」と判断して行を追加する（重複発生）
2. 同定できない → 手順 2 の更新も掛からない
3. 同定できない → **手順 3 の重複削除も同じ述語なので回収できない**

3 レビュアーが独立に到達した。是正対象を掴めない述語は、自己修復の経路まで同時に塞ぐ。

### 是正は分岐の追加ではなく定義軸の一般化で行う

自然な反応は「破損行を検出する分岐を足す」だが、これは誤り。1 ケース専用の面が増え、次サイクルでその追加自体が指摘対象になる。

正しい是正は述語の**定義軸**を変えることだった。ページ列を「行頭の `|` から、行内で**最初に現れる** `](pages/...)` の閉じ括弧まで」と**位置で**定義する。

- 壊れた行も掴める（実測 342/342）
- 「他セルのリンクに一致させない」という禁止条項が「最初に現れる」に吸収されて不要になる

**分岐を足すと述語が増える。定義軸を変えると述語が減る。**

### パイプを含み得ない列を anchor にする

同様に、サマリー列の切り出しは「先頭から数える」設計だと最初の壊れたセルで破綻する。更新日（ISO 8601）と確信度（enum）が **構造的にパイプを含まない** 性質を使い、**末尾から数える**と、サマリーに生パイプが残る 29 行でも 342/342 で正しく分離できた。

抽出の起点は「値の性質上ずれ得ない列」に置く。

### 字義どおりの実装を先に走らせる

次のサイクルで、この位置ベース抽出が今度は**全 342 行で列を 1 つずらした**。原因は、`|` 分割の結果の**両端に区切り由来の空要素が生じる**ことを規定していなかったため。

「決定的に働く」と書いた規則ほど、字義どおり適用した結果を実測すべきである。修正時は **提案する文言をそのまま実装したプローブを実データへ当て**、期待するフィールドに着地することを確認してから書いた。

> 検証コードと散文の差こそが前サイクルの欠陥そのものだった。

散文をレビューするときも同じで、**実データ全件への機械的適用が最も強い検証**になる。起点事例では実 index.md の 342 データ行に対して前提の成立を全件確認した（ページリンク直後に非空白が来る行 0 件 / 行末パイプ欠落 0 件 / 区切り 6 個未満 0 件）。

### 到達不能な fallback は削除する

同時に見つかった型として、サマリー決定順の候補 (2) が「新規ページ作成時にのみ実行されるステップ」を参照しており、更新経路では構造的に到達しなかった。dangling 参照を残したまま次の候補の挙動だけ規定すると、読み手は到達しない分岐を前提に判断する。

早期 return / ガードの前倒しを追加したときも同じで、**それが無効化する下流分岐を同じコミットで畳む**。

### チェックリスト

散文に機械的述語を書くとき:

| 確認 | 方法 |
|---|---|
| 実データの外れ値に一致するか | 全件に当てて一致数を数える（サンプルではなく全件） |
| 分割・切り出しの両端はどうなるか | 字義どおりのプローブを走らせて着地を見る |
| 是正対象そのものを掴めるか | 掴めないなら定義軸が誤っている（分岐を足さない） |
| 修復手順が同じ述語を使っていないか | 使っているなら取りこぼしは永久に残る |
| 参照先のステップは実際に到達するか | 到達しないなら参照を削除する |
