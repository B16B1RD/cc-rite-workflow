# 読み直しによる検証は操作の不発しか捕まえない — 対象の取り違えには独立した照合元が要る

## 概要

操作と読み直しが同じ変数を対象にすると、検証が捕まえられるのは「効かなかった操作」だけになる。上流で渡された対象そのものが誤っていれば、誤った対象への成功を読み直しが確認してしまうため、取り違えを検出したいなら操作と独立した情報源との照合を入れる。

## 詳細

「close したあとに状態を読み直し、閉じていることを確かめる」型の検証は、API エラーや権限不足で操作が効かなかった場合には確かに失敗を検出できる。しかし close と読み直しがどちらも同じ ID 変数を使う限り、その ID が上流で取り違えられていた場合は「誤った対象を閉じ、誤った対象が閉じていることを確認する」だけで検証は成功してしまう。検証が見ているのは操作の効果であって、対象の正しさではない。

対象の取り違えまで検出範囲に含めるには、操作の入力とは別経路で得た情報源（例: PR が実際に持つ closing reference、ブランチ名から独立に導いた番号）と照合する段を加える。照合元が操作と同じ変数から派生しているなら、それは独立した検証にならない。

実務上の帰結は 2 つある。

- 散文で「この検証は取り違えも検出する」と主張する前に、照合元が操作から独立しているかを確かめる。独立していないなら、検出範囲の主張を「操作の不発」に限定する。
- 受入条件が失敗例を列挙している場合（API エラー・権限不足・対象の取り違え など）は、1 件ずつ検出経路を対応付ける。読み直し検証だけで全件を満たしたつもりになると、取り違えの 1 件が未対応のまま残り、受入確認で再現手順付きの未充足として差し戻される。
