# 外部からの取得は「存在しない」と「取得できない」を分け、件数上限で切れたことを印として残す

## 概要

取得の失敗を一律に error として扱うと「存在しない」という判定材料が「判定不能」に化け、上限で黙って切った一覧は否定の根拠に使われる。失敗の種類を分け、切り捨てを事実として記録し、判定側は印のある一覧を否定の根拠にしない。

## 詳細

PR の文書と本文で出典を挙げた行を全件確かめる helper を足した変更で、外部から取得した事実の扱いに次の欠陥がまとめて見つかった。

### 失敗の種類を分ける

- `gh api graphql` は存在しない番号でも exit 1 を返し、本文に NOT_FOUND の JSON を載せる（REST の 404 とは形が違う）。exit code だけで分けると「存在しない」が「取得失敗」に化ける
- mock は実際の API と同じ形で答える。既定の形だけの fixture では、実際の分岐がテストを通らない
- 外部コマンドが rc=0 で想定外の形式を返したときは、解析例外の文言をそのまま記録せず、「出力が JSON でない」と応答の先頭を error に残す

### 上限で切れたことを残す

- 件数上限のある取得（GraphQL の `first:N` など）は totalCount と比べて切り捨ての印を付け、判定側は印のある一覧を否定の根拠にしない
- 境界の判定は、印が付く側だけでなく付かない側もテストで固定する。片側だけでは `>` と `>=` の取り違えを検出できない
- 手順書が「全体を取り直す」手段として挙げたコマンド（`gh pr view --json files`）も同じ件数上限で切れていた。上限への対処を書くときは、その手段自体の上限も実測する

### 取得の前提を確かめる

- GitHub の closing keyword によるリンク（closedByPullRequestsReferences）は既定ブランチ向けの PR でしか作られない。develop をベースにする repo では、解決済み Issue のリンクが空になる
- `git show` の既定出力は、マージコミットで変更ファイルが 0 件になる。コミットの変更ファイルを根拠に使うときは `--first-parent` を付け、作業先に無いときの取得手段と、どちらも失敗したときの判定不能を明記する
- `str.lstrip("./")` は接頭辞ではなく文字集合を剥がす
- 受理側の正規表現は、生成側の自然な出力（コマンドに `=` を含む）と、同じアンカーを受理する既存のゲートの式に揃える。`[^=]` で切ると正しい出力を拒否する
