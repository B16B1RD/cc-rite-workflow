# コメントの「正確化」は主張を強めがち — 実態へ合わせるより強度を下げる方が安全

## 概要

コメントに誤りを指摘されたとき、自然な反応は「正しく書き直す」ことである。ところが書き直しは往々にして **より強い断定**になり、その分だけ外れやすくなる。PR #2120 cycle 4 では「将来の小修正に備えた冗長」という**正しい旧記述**を「`|| return 1` は rc 伝播の唯一の経路である」という**誤った断定**へ置き換えた。cycle 5 の mutation で `|| return 1` を削除しても全 assert が green のままだった（`set -e` が同じ rc を伝播する）。5 cycle を通じて最も再現性の高いパターンの最終形である。

## 詳細

### 正確化には 2 方向ある

| 方向 | 内容 | リスク |
|---|---|---|
| **(a) 主張を実態へ合わせる** | 記述を実装の現状に一致させる | 実態の把握が誤っていれば新しい誤りになる。実態が変われば再び陳腐化する |
| **(b) 主張の強度を下げる** | 断定を弱める・条件を付ける・そもそも書かない | 外れる余地が減る。検証対象面が狭くなる |

**(b) が安全である場合が多い。** 「唯一の経路である」より「この形を選んだ」の方が、実装が変わっても外れない。PR #2120 では application と tech-writer が独立に「訂正ではなく削除」を推奨した。

### なぜ強まるのか

指摘を受けた側は「曖昧だったから間違いと読まれた」と解釈しやすく、曖昧さを消す方向へ書き直す。曖昧さを消すとは断定を強めることであり、断定が強いほど反証可能な主張の数と射程が増える。

```
✗ 「将来の小修正に備えた冗長」 → 指摘されて曖昧と判断
   → 「rc 伝播の唯一の経路である」 → mutation で反証されて finding
✓ 「将来の小修正に備えた冗長」 → そのまま残す、または削除する
```

旧記述は弱いがゆえに正しかった。**弱い正しい記述を強い誤った記述へ置き換えるのが、正確化を意図した書き換えの典型的な失敗である。**

### 定量的な裏付け — 削減が効いた

PR #2120 の 5 cycle でコメント由来の finding は次のように推移した。

```
cycle 2 → 3: 4 件（cycle 2 で追加した約 20 行のコメント塊が供給源）
cycle 3 でコメントを約 20 行 → 約 8 行へ削減、恒真 assert を削除
cycle 4: 2 件 → cycle 5: 1 件
```

cycle 3 で採った「訂正ではなく削減」が転換点だった。**指摘の供給源が「コードの欠陥」から「自分が書いた説明」へ移ったら、説明を減らすのが最短経路である。**

### 削減の具体的な基準

- 実 assert が検証している範囲を超える claim を書かない
- errno 名・環境宣言・分岐総数のような**外部の事実に依存する主張**は、書かずに済むなら書かない
- 恒真 assert は「これは vacuity 検知だ」と説明するより消す

書くべきは「なぜこの形を選んだか」のうち**実装を読んでも分からない部分だけ**である。実装を読めば分かること、外部の事実、自分の assert が検証していないことは書かない。

### 「宣言」を根拠にしない

同 PR の cycle 3 では、locale 依存 assert の効力根拠を「このプロジェクトは ja_JP を宣言している」と書いたが、リポジトリにそのような宣言は無く、config の `language: ja` は**出力言語**のキーだった。効力の実体は実行ホストの `LANG` である。

同種の locale 依存を扱う既存テストは「実測: ja_JP.UTF-8 で indented=0 bare=0」と**実測ベースの表現**を採っていた。宣言ベースの根拠を書いたのは新しい行だけだった。

**「プロジェクトが X を宣言している」と書く前に grep する。** 宣言が無い場合、実測結果を根拠として書く方が正確で、しかも後から検証できる。

### 非存在の consumer を現在形で語らない

cycle 4 では「the only consumer of this log parses timestamps」というコメントが、同一 PR が「consumer は将来の集計 Issue」「読む subcommand は存在しない」と明記している consumer を現在形で主張していた。読み手が grep しても 0 件で、陳腐化なのか将来形なのか判別できない。

**write-only を謳う成果物について「consumer が〜する」と書くときは、その consumer が実在するかを確認する。将来形なら将来形と書く。**
