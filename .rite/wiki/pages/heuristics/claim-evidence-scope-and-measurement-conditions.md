# コメントや文書の根拠は、実装が名指す範囲と測定の条件まで確かめて書く

## 概要

コメントに「別ファイルのテストが書式を固定している」「実測の最大は 17.7 分」と書くとき、固定しているのが consumer の依存する範囲の一部だけだったり、数値が成功した run だけの最大で打ち切られた run を含まなかったりすると、次に読む保守者が誤った前提で判断する。根拠は、実装やテストが実際に名指す範囲と、測定の条件（どの run を数えたか）まで確かめて書く。定義を別の言い方に置き換えるときは、元の言い方が暗に含んでいた付随の規則を実装と突き合わせる。

## 詳細

**固定の範囲**: CI の step が別スクリプトの出力行を sed で解析するとき、そのコメントに「書式はテストが固定している」と書いた。実際のテストは一部のフィールドしか固定しておらず、step が依存するフィールドと順序は未固定だった。書式を変えてもテストは green のままなので、コメントを読んだ保守者は「テストが捕まえる」と誤解する。直し方は、固定を足して主張を真にするか、主張を削って実際の挙動（書式が変わると警告が出る）だけを書くか。後者は機構を増やさない。

**測定の条件**: 上限の根拠として「成功した run の最大」を書くと、同じ期間に上限で打ち切られた run（真の所要時間が分からない）が抜ける。数値を根拠に書くときは、何を数えたか（成功 run のみ、打ち切りあり）まで書く。

**引用先の意味も確かめる**: 書き換えたコメントが別の出力文言（警告メッセージ）を引用するようになると、その文言自体の正確さ（書式が一致しないだけなのに「行が無い」と言う）が新たに問われる。

**定義の置き換え**: 除外の対象を「書き手」ではなく「形」で定義し直すと、元の言い方が暗に含んでいた付随の規則（空になった節を見出しごと除く）が列挙から落ちやすい。定義を置き換えるときは、実装がしている処理を 1 つずつ列挙と突き合わせる。
