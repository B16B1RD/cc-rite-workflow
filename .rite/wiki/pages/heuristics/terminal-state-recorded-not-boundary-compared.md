# 終端状態は「到達した事実」で記録し、可変値との境界比較で代用しない

## 概要

サーキットブレーカーの「発火後か」を `cycle_count >= max_review_cycles` で判定していたが、この等式は**最終 cycle を実行している間ずっと成立する通常状態**でもあった。counter を書いてから review を invoke する順序のため、最終 cycle の途中で中断して復帰すると「発火後の再実行」と誤認され、ブレーカーが一度も発火しないまま上限が無通知で 2 巡分に緩む。

## 詳細

### 2 つの独立した欠陥が同じ形に潜む

この判定式には性質の異なる欠陥が 2 つ重なっていた。片方だけ直しても残る。

**(1) 境界値の一致は終端を表さない**

`X >= 上限` が真になるのは「上限に達して停止した後」だけではない。「まさに今その上限の cycle を実行中」でも真になる。カウンタが上限に**達している**ことと、上限に達して**停止した**ことは別の状態であり、前者は後者の必要条件でしかない。

述語を書くときは必ず「この述語は、その状態に**向かっている途中**でも真にならないか」を問う。真になるなら終端状態を表せていない。

**(2) 基準値が可変なら符号化が成立しない**

cycle 2 では境界を `-ge` から `-gt` へ直し、発火時に `max + 1` を書く形にした。これは境界の位置を直しただけで、「可変値との相対比較で終端状態を表す」という根の構造は残っていた。`max_review_cycles` は毎回 config から読み直される入力なので、

- 上限を下げれば、未発火の counter が「発火済み」と誤認される
- 上限を上げれば、発火済みが認識されなくなる

**符号化に使う基準値が実行間で変わりうるなら、その符号化は状態を表せていない。**

### 同じ失敗クラスが 2 cycle 連続で別の形で出た

cycle 2 の修正が「条件式の中の定数・演算子」に留まったとき、cycle 3 の指摘は同じ場所の**構造**を指していた。これは一般化できる読み方で、**1 度目の修正が境界の位置だけを動かしたなら、2 度目の指摘は表現方法そのものを疑うべき**という signal になる。境界を動かして直る問題と、表現を変えないと直らない問題を区別する。

### 解は「マーカーを足す」ではなく「マーカーを要らなくする」

最終的な収束案は、発火時点で counter を 0 にリセットして判定そのものを削除するものだった。発火時に継続 handoff が default-clear され自動再入場経路が無い、という**既存の不変条件**が、そのタイミングでのリセットを安全にしていた。

新しい状態変数を導入する前に、既存の不変条件から「その状態を覚えておく必要が本当にあるか」を問う。今回は覚える必要が無く、marker・override 分岐・デッド変数・設定値依存が一度に消えた（実測 -15 行）。

なお、リセットで終端を表す場合は [失敗状態のクリアは失敗の記録より後に置く](../patterns/clear-failure-state-after-recording-it.md) が同時に効く — リセットを記録より前に置くと、その隙間の中断が無記録の成功に化ける。
