# 汎用契約の表に経路固有の詳細を書かず下位節へ委譲する。ただし委譲は委譲先の網羅性を load-bearing にする

## 概要

複数の呼び出し元が参照する汎用契約（例: Non-blocking Contract の「契約の構成要素」表）へ、特定経路の reason 集合・exit code・ステップ番号を書き込むと、**同じファイルの数行下にある「適用箇所」節が明示的に否定する主張**を同時に複数導入する。行を sibling と同じ抽象度に戻し、詳細を下位節へ委譲すれば 1 編集で解ける。ただし「下記◯◯を参照」と書いた瞬間、**委譲先の網羅性の欠落が初めて load-bearing になる**ため、委譲を書いたら委譲先も同時に点検する。

## 詳細

### 事象 — 1 行の追記が 3 つの実装乖離を同時に導入した

汎用契約の定義表に carve-out 行を 1 行足したところ、レビュー 1 cycle で HIGH / MEDIUM / LOW-MEDIUM の 3 指摘が返った。3 件はいずれも**同一の 1 文**に含まれ、うち 2 件は**同じファイルの 4-5 行下の既存テキスト（未変更）が明示的に否定していた**。

| 書いた主張 | 実体 | 否定していた場所 |
|---|---|---|
| 差し戻しの実例に sub-phase A ⇄ gate A を含めた | A は失敗時に marker を残さない。残すと非ブロッキング契約が gate 経由で blocking 化するため意図的に非対称 | 同ファイルの適用箇所が「A はこの 2 点で非対称」と明示 |
| 「caller 契約違反に分類される失敗は exit 0」 | プロジェクト内で「caller 契約違反」は exit 1 を指す**定義済み用語**。marker を残す 11 reason のうち exit 0 は 4 つだけ | 同ファイルの適用箇所が「7 種は caller 契約違反として exit 1」と正反対を記述 |
| 「IO 起因の失敗は marker を残さない」（無条件） | marker 削除自体の `rm` 失敗は IO 起因でありながら marker が残る。しかも「再実行では収束しない」という同じ理由づけが正反対の帰結を導く | 同ファイルの適用箇所と helper の WARNING 文言 |

### なぜ 1 行に集中したか

3 件は別々の誤りではなく、**抽象度を 1 段下げたこと**の帰結だった。sibling 5 行はいずれも skill 非依存の汎用規約（60-120 字）だったのに対し、追加行は約 250 字で唯一具体ステップ番号を含んでいた。経路固有の情報を書こうとすれば、その経路の実装詳細（どの reason か / exit code は何か / どの gate が受けるか）を正確に把握し続ける義務が発生し、その義務は下位節が既に果たしている。

**個別に直すと同一文を N 回編集して悪化する。** 共通の原因（粒度）を先に特定し、1 編集で解くほうが速く安全だった。

### 判定の目安

- **汎用契約の表に具体ステップ番号が入り始めたら粒度崩れの兆候。** 既存 sibling 行の文字数と抽象度が事実上の基準線になる
- **定義済み用語を別の意味で使わない。** 用語を使う前に既存の定義箇所を grep する。同一ファイル内で正反対の主張が並ぶ形は、用語の再定義から生まれることが多い
- **無条件の否定形（「〜は残さない」「〜には影響しない」）は例外を 1 つ持つだけで偽になる。** 十分条件形（「〜なら残す」）に書き換えれば、条件節から漏れる経路があっても矛盾は生じない

### 委譲の副作用 — 委譲先の網羅性が load-bearing になる

抽象度を戻して「どの reason が marker を残すか・exit code・非対称は下記『適用箇所』を参照」と委譲したところ、次 cycle で**委譲先の網羅性の欠落**が指摘された。委譲先には sub-phase A の但し書きだけがあり、sub-phase B の同種経路には無かった。委譲する前は「A にだけ但し書きがある」で済んでいたが、委譲を書いた後は「委譲を辿った読み手が B に該当経路が無いと読む」という実害に変わる。

**委譲は責務の移動であって消滅ではない。** 「下記◯◯を参照」と書いたら、その参照先が委譲した 3 項目をすべて供給しているかを同じ編集で確認する。

### 副次 — 仕様文と repo 記述の両面修正では伝播漏れが起きる

仕様（Issue body）と repo 記述の両方を直す作業では、片方だけ直して伝播漏れが残った。cycle 1 の指摘を repo 側で直し、同一文言が Issue body 2 件に逐語で残っていたことに cycle 2 で気付いた。**同一文言の grep を両面で行う。**

### 同じ形は「修飾語を N 箇所へ展開する」作業でも出る

同一の修飾を複数箇所へ展開する docs 作業でも、機構の詳細をどこに置くかで同型の失敗が出た。2 サイクル連続で「修飾を足すたびに別種の不正確さが入る」形になり、収束したのは短い箇所では**上位概念**で述べ、機構の内訳を **SoT ポインタを持つ 1 箇所にだけ**書いた版だった。結果として文字数も減った。

- **同名概念が近傍に複数あるとき、「see below」型の相対参照は最も近い誤答へ誘導する。** 修飾の目的が「2 種類の同名概念を取り違えさせない」ことだったのに、追記した相対参照の直下に現れるのは**別機構**の同名概念で、参照が目的と逆方向に働いた。既存の解決可能なアンカー idiom が同一ファイルにあるなら必ずそれに揃える（この事例では同じテーブルの 2 行下が既に `see [X § Y](#anchor)` を使っていた）
- **「〜されたもの」という原因帰属は、経路が 1 つであることを暗黙に主張する。** 残留する非 blocking 指摘を「ゲートが降格したもの」と書いたが、実体は 2 経路（ゲートが降格して別配列へ移送する分と、ゲート対象外でそのまま残る分）で、正常終了時に実際に残るのは後者だった。存在主張としては偽ではないが、読者が誤った機構に帰属させる。経路が複数あるなら上位概念で述べるほうが短く、実装変更にも強い
- **N 箇所へ展開する作業では、機構の詳細を全箇所に書くと N 個の drift site ができる。** 詳細は SoT ポインタを持つ 1 箇所へ集約し、他は上位概念で済ませる

### 同一文書内に正典記述があるフィールドは、条件を書き直さず所有を委譲する

同じ文書の中に、あるフィールドの定義表（そのフィールドを誰が書き誰が消すかを列挙した行）が既にある状態で、新しい節がそのフィールドの条件を自前の言葉で断定すると、**同一文書内に同じ契約の記述が 2 つ生まれ、必ず一方が古くなる**。起点事例では新規追記が負キャッシュを「replica の作成成功だけが解除する」と断定したが、同じ文書のフィールド表は「Issue 切替でも落ちる」と明記しており、実装側の解除経路は 3 つあった。追記した側が最初から偽だった。

**先行する正典記述があるなら、条件を再記述せず所有をそこへ委譲する**（「フィールド表が `X` について列挙する経路でのみ解除される」）。インラインで 3 経路を列挙し直す修正は、経路が増えるたびに 2 箇所を同期する義務を新設するため採らない。委譲なら経路の増減が正典側 1 箇所で閉じる。

判定は「その概念の canonical な定義が同じ文書内に既にあるか」で行う。あるなら委譲、無いならその節が正典になるので書き切る。
