# 作業ツリーの内容 hash を証跡にするなら、削除されたパスを表す値を持たせる

## 概要

作業ツリーのファイルを hash して記録し、index と比べる型の証跡は、削除・改名で消えたパスに hash を取れず、その取り込みを表現できない。削除は「HEAD にあって作業ツリーに無い」ときだけ専用の値で記録し、どちらにも無いパスは誤りとして止めると fail-loud を保てる。

## 詳細

**表現できない値が回復経路を壊す**: 取り込みの前後でパス集合を使い回す手順では、commit 前に有効だったパスの集合が commit 後には削除されたパスを含み、hash を取れなくなる。回復分岐の行き先を付け替えるとき、行き先の手順が前提とする入力（パス集合）が回復時点でも成り立つかを確かめないと、回復経路だけが壊れる。

**回復文の側に入力条件を書く**: 回復分岐が別の手順のブロックを再利用するときは、そのブロックの入力定義が回復時点でも成り立つかを確かめ、成り立たない条件は回復文の側に書く。あわせて、テスト用の一時リポジトリには実リポジトリと同じ追跡除外（`.rite/` など）を入れる。入れないと、作業ツリーの変更一覧を使う経路が実運用と違う結果になる。

**削除の記録条件を絞る**: 削除を表す値を記録してよいのは、HEAD に存在して作業ツリーに無いパスに限る。HEAD にも作業ツリーにも無いパスに削除の値を付けると、入力の誤りを黙って受け入れてしまう。誤りは止めて出力する。

**受入条件の範囲は黙って狭めない**: helper の制約を理由に範囲外とするより、helper 側を直して満たす方が早く収束する。
