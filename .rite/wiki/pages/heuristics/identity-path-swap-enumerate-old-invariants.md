# 同定手段の取得経路を差し替えるときは、旧経路が構造的に保証していた述語を先に全部列挙する

## 概要

同定子・キー・参照を取りに行く経路（API エンドポイント・クエリ・検索式）を差し替えると、**旧経路がパスやクエリの形で暗黙に保証していた制約が落ちる**。旧経路のコードにその検証が書かれていないのは、検証が不要だったからではなく、経路の構造が保証していたからである。

落ちる述語は 1 つとは限らない。1 件ずつ後から見つかる形になると、cycle 数だけ消費する。差し替え前に旧経路が満たしていた述語を列挙し、新経路で 1 つずつ対応を確認する。

## 詳細

### 実測された症状（PR #2112）

記録コメントの同定手段を、本文照合（`repos/{o}/{r}/issues/{PR}/comments` の列挙）から durable id（`repos/{o}/{r}/issues/comments/{id}` の直接 GET）へ移した。

旧経路は PR 番号を URL パスに含むため、**「取得したコメントが当該 PR に属する」ことを検証する必要すらなかった**。新経路は repo スコープで issue 非依存のため、author が自分であることを確認しても別 PR / Issue のコメントを掴んで PATCH しうる。application と security が独立に検出し、security は「PR body は書き込み権限を持たない PR 作成者でも編集できる」ことから権限昇格として評価した。

**cycle 1 でスコープを補って終わりにしたのが誤りだった。** 旧経路は 3 述語（author ∧ 見出し前方一致 ∧ 末尾 sentinel）で対象を絞っていたのに、cycle 1 後の新経路は 2 述語（author ∧ 所属 PR）しか持たなかった。「対象が期待する種類のオブジェクトか（= 記録コメントであること）」という軸が丸ごと残っており、cycle 2 で 3 つ目として指摘された。

### 列挙すべき述語の軸

旧経路が構造的に保証していた制約は、少なくとも次の軸で洗い出す。

| 軸 | 旧経路での保証のされ方 | 差し替えで落ちる例 |
|---|---|---|
| **スコープ** | URL パス / クエリ条件に含まれる | repo スコープの直接 GET で別 PR の資源を掴む |
| **種別** | 列挙対象の集合が既に絞られている | 同一 PR の別種コメントが素通りする |
| **一意性** | 検索式が 1 件しか返さない | id が指す先が意図と別のオブジェクト |
| **順序** | 列挙 API の返却順が安定 | 直接 GET には順序の概念が無い |

### 新経路で旧述語を評価するのは「戻す」ことではない

PR #2112 では、id で 1 件へ絞り込んだ**後**に旧来の本文述語（記録コメントであること）を必要条件として評価する形にした。これは同定手段を本文照合へ戻すことではない — id が指す先は 1 件のままなので、raw markdown を複製した人間コメントが述語を満たしても誤認は起きない。

**同定は新手段で行い、旧手段の述語は事後の必要条件として残す**。この分離ができると、旧経路が持っていた保証を失わずに新経路の利点（本文の文字列に依存しない）を取れる。

### レビュー時の問い方

差し替えの diff に対しては次を機械的に問う。

1. 旧経路の URL / クエリに含まれていて、新経路に含まれない要素は何か
2. 旧経路のコードが**検証していなかった**制約のうち、経路の構造が保証していたものは何か
3. 補った制約は 1 つか、それとも「1 つ補ったから済んだ」と早期に打ち切っていないか
