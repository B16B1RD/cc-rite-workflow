# LLM が照合する候補集合は母集団全体にし、helper の抽出結果は手がかりに留める

## 概要

LLM に照合させる手順の候補を helper の抽出結果（正規表現が拾えた値・文字列一致のグループ）で絞ると、抽出が拾えない書き方の対象が黙って照合から外れる。候補は母集団全体にし、抽出結果は照合の手がかりとして渡す。同じ形の絞り込みを 1 行で直したら、同じ手順の他の行も横に確かめる。

## 詳細

### 何が起きたか

Issue 群を横断して監査するスキルで、LLM が「本文の受入条件と実装がずれた Issue」「同じ根因の Issue の組」を判定する手順を書いた。候補を毎回全件読むのは重く見えたので、helper が作った集計（系譜・ファイルパスの一致グループ・本文から正規表現で抽出したファイルパス）に現れた Issue だけを候補にした。

受入条件の Given は候補を限定していない。レビューでは次の順に取りこぼしが見つかり、受入条件が未充足のまま cycle が続いた。

1. 候補を系譜・集中グループの構成員に限ったため、どちらにも属さない Issue のずれが照合されない
2. 「抽出したファイルパスを持つ Issue」まで広げても、正規表現はディレクトリ付きのパスしか拾わないため、実装をファイル名だけで名指しする Issue が外れる
3. 方向修正の行を全件に直した後も、統合の行が「パス文字列が完全一致するグループ」に限られたままで、同じファイルを別のパス表記で書いた Issue の組が統合提案に出ない

どの段でも、抽出の網は「拾えた値がある」ことしか保証せず、「拾えなかった対象は存在しない」ことは保証しない。抽出を候補の条件に使うと、抽出の穴がそのまま照合の穴になる。

### 書き方

- 候補の入力は母集団全体（全 Open Issue 等）にする。helper の集計・抽出結果は「照合の手がかり」と明記して渡し、絞り込みの条件には使わない
- helper の docstring には抽出の事実（どの形を拾うか）だけを書き、方針（候補を絞らない等）はスキル側の 1 か所に置く。両方に方針を書くと片側だけが古くなる
- reviewer の推奨が「候補を限定する」方向のときは、採る前に受入条件の Given と突き合わせる。Given が限定していなければ、限定は受入条件の縮小になる

### 1 行を直したら同じ手順の他の行も見る

同じ形の欠陥が別の行で再発したのは、指摘された行だけを直し、同じスキルの同種の手順行を横に確かめなかったためだった。候補の決め方のように手順全体に共通する設計は、1 か所の指摘をきっかけに全行をまとめて直す。再発が続いて見直し（replan）を求められた時点で、行単位の修正をやめて同種の行を一括で直す判断に切り替えると収束した。

### 修正の記録

修正を記録するとき、指摘 ID と直した箇所を取り違えると、次の cycle で同じ指摘が「未修正」として再掲される。対応を記録する前に指摘の本文を読み直し、直した行と指摘の対象が一致していることを確かめる。
