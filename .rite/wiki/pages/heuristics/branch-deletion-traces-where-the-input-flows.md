# 到達不能に見える分岐の削除は、その分岐が受けていた入力の行き先を確認してから決める

## 概要

散文で「helper が返しうるのは 2 値」と宣言した後に 3 分岐の `case` が残っていると、指示とコードが矛盾する。矛盾の解消手段として分岐の削除は自然に見えるが、**削除してもその入力は消えない — catch-all（`failed|*)` 等）へ流れ込む**。結果、失敗ではない値に対して「更新に失敗しました」という誤診断と手動復旧コマンドが出る。これはデッドコード除去ではなく診断の劣化である。

## 詳細

### 判断手順

分岐の削除を検討するときは、次の順に確認する:

1. **その分岐が受けていた入力は本当に到達しないか**。散文の「到達不能」宣言は主張であって観測ではない。helper 側の契約（返しうる値の集合）を実装で確かめる
2. **到達しうるなら、削除後にその入力はどこへ流れるか**。`case` なら catch-all、`if/elif` なら末尾の `else`。流れ先の診断文が、その入力に対して正しいかを読む
3. **流れ先の診断が誤りになるなら、削除は診断の劣化**。分岐を残し、代わりに散文側を緩める（「helper 契約側の全 result を受ける保険」等）ほうが最小手になる

### 削除のコストがガードの改変なら、別の最小手を探す

同 PR での実測: 到達不能に見える `case` 分岐を削除すると、`skill-rail-diff-check` の subsequence 保存ガード（base の機械レール行は消せない）が落ちた。ガードに除外行を足せば削除は通るが、それは**機構の追加**であり、除外リストは累積する。指摘元が併記していた第 2 案（散文を緩めて分岐を保険と位置づける）は散文 1 文の書き換えで済み、ガードに触れない。

**削除が原則でも、削除のコストが既存ガードの改変なら、同じ矛盾を解く別の最小手を探す。**

### 除外リストの前例は性質まで確かめる

rail の subsequence 保存ガードには既存の除外前例があったが、それは 1 行が別の書き方へ**移設**されたケースだった。恒久的に pin から外す除外を「削除を通すため」に足すと、散文 88 バイトと引き換えに機械レール pin を 1 本失う取引になる。**除外の前例があっても、前例の性質と自分のケースの性質が同じかを確かめる。**

### 併走する観測: fix が足した分岐にも fixture を足す

同 PR の cycle 1 で入れた修正（marker 正規化行、新設 WARNING 2 本、引数エラー腕の既定値報告）はいずれも削除しても全テストが緑のまま通る状態で残り、cycle 2 で 3 件の指摘として戻ってきた。テストは正常系 fixture しか通しておらず、fix が足した経路には一度も入っていなかった。**「テストは通った」と「fix が守られている」は別**で、後者は mutation を 1 回かければ即座に分かる。
