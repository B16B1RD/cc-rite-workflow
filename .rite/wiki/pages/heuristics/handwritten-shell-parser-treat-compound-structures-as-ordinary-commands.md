# 手書きシェル解析器では複合構造を特別扱いせず通常コマンドとして返す

## 概要

手書きのシェルコマンド境界解析器で `( )` グループ・関数定義・case パターンなどの複合構造を「外側リストの特殊セグメント」として個別に扱うと、その特殊扱いが前後の語・演算子の通常処理と食い違い、境界追跡から漏れる。複合構造も前後の語・演算子を含めた通常の 1 コマンドとして返す方が、特別扱いの分岐を減らして食い違いの発生源を消せる。

## 詳細

worktree 隔離ガードのような、コマンド列から `cd` の宛先を追跡する手書きシェル解析器で、`( ... )` グループを「外側リストの空セグメント」という別形式で表現する簡略化を行ったところ、`)` の後ろの演算子・`(` の前の語（`!` / `time` 等）の扱いが通常のコマンドと食い違い、その差分の分だけ背景リストの境界判定が漏れた。具体的には、関数定義 `f() { … }` や `case` パターン `(a)` の丸括弧も同じ「グループ」として誤って扱われ、`)` の後ろの本体にある `cd` が外側コマンドの引数に吸い込まれて追跡対象から外れた。

見直し（replan）の結果、空セグメントに例外を積み増す方向を棄却し、**グループを `(` の前の語と `)` の後ろの語・演算子を含む通常の 1 コマンドとして返す**形へ単純化した。前後の演算子が通常のコマンドと同じルートを通るため、境界判定用の特別な分岐（事前走査の `before == &` 判定等）を削除できた。副次的に、プロセス置換 `<( … )` の後ろの語を新しいコマンドと誤認していた既存の誤判定も同じ単純化で解消した。

この修正は 3 cycle を要し、指摘件数は 3 → 1 → 2 と推移した。いずれも同じ「手書き解析器が語と演算子の区切りをどこで引くか」という境界の取り扱いに起因していた。手書きシェル解析器のレビュー・修正では、個々のケース（グループ・関数定義・case・プロセス置換）を都度パッチするのではなく、**複合構造をどう通常のコマンド境界へ写像するかという統一規則**を先に立ててから各ケースを検証する方が、同型の見落としを減らせる。
