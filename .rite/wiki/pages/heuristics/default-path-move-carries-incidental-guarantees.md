# 設定の既定パスを移すときは、旧パスが副次的に担っていた保証を新パスへ引き継ぐ

## 概要

既定のパスを別のディレクトリへ移す変更は、パス文字列の置換だけに見える。旧パスは親ディレクトリの規則（nested な `.gitignore` の全除外など）のおかげで、書いた覚えのない保証を満たしていることがある。移した先にその規則が及ばなければ、保証は黙って失われる。

## 詳細

- **退行は開発リポジトリで見えない**: 開発側のリポジトリでは移動先が別の規則で既に除外されていることがあり、PR 本文に書く検証も通る。配布先の標準構成（移動先を除外する規則が無い）でだけ、worktree が git の差分へ漏れる。同じ根因を 2 名のレビュアーが独立に指摘した。
- **確かめること**: 旧パスが満たしていた副次的な性質を列挙し、新パスの構成（親の規則・設定ファイル・検査）で同じ性質が成り立つかを、規則が無い構成で実測する。
- **引き継ぎ方**: 新しいパスのベースディレクトリ自身に `*` だけの `.gitignore` を冪等に書く自己完結の方式が、利用者の root の設定に触らず、既存の nested 規則と同じ形で済む。
- **既定値の置換は固定するテストとセットで入れる**: 既定値の文字列を複数箇所で置換する変更は、その既定値を使う分岐を通すテストが無いと旧パスへ戻しても suite が通る。fixture が既定値を明示しているテストは既定値の分岐を通らない。設定でキーを省略した場合と custom の場合を、drift と healthy の両面で固定する。
- **既存の機械レールのテスト**: 手順書の行を固定する既存テストは、意図した既定値の変更を superseded 行の**全行一致**の除外で許容する。前方一致の除外は置換後の新しい行まで隠してしまう。
- **旧パスの記述の取り残し**: README・docs・hook のコメントに旧パスの説明が残りやすい。旧パスの grep は差分の外まで広げる。
