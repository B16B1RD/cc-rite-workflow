# 不正入力は「落とす」より「無害化して残す」— 落とす設計は件数報告という第 2 の機構を要求する

## 概要

抽出した要素のうち不正なものを入力から落とす設計は、落とした件数を数える必要を生み、その件数用の
述語が本体の述語と分裂し、件数を運ぶ marker が下流の判定表と食い違う、という連鎖を起こす。
不正な部分だけを null へ写して要素自体は残す形にすると、件数カウント・その fallback・数値
サニタイザ・専用 marker・下流の加算規則がすべて同時に不要になる。

## 詳細

### 起点: 1 つの追加が次サイクルで 3 件の指摘になった

JSON から要素を抽出するとき、`id` が想定書式に合わない要素を `select()` で落とす形にした。
落とした要素は下流の報告から消えるため、「何件落としたか」を伝える必要が生じる。そこから:

1. 件数を数えるための第 2 の `jq` 呼び出し（本体とは別の述語）
2. その `jq` が失敗したときの fallback
3. 件数値が数値であることを保証するサニタイザ
4. 件数を運ぶ専用 marker
5. 下流の判定表で、その marker を既存の件数へ加算する規則

の 5 つが芋づるに要求された。次のレビューサイクルではこの一群から 3 件の指摘が出た。
述語が 2 か所に分裂したこと（本体の抽出条件と件数の条件が独立に drift する）、marker の値域が
下流の判定表と食い違ったこと、fallback が失敗を無言化したこと。

### 対処: 落とさず、不正な部分だけを null へ写す

```jq
# 弱い: 不正な要素を落とす → 落とした件数を伝える第 2 の機構が要る
.items[] | select((.id // "") | test("^F-[0-9]{2,}$"))

# 強い: 要素は残し、不正な id だけを null にする
.items[]
| { id: (if ((.id // "") | test("^F-[0-9]{2,}$")) then .id else null end),
    file, line, description }
```

安全性（不正な値が下流のリテラル置換へ届かない）は維持したまま、可視性（要素が黙って消えない）
も同時に満たせる。`id: null` は下流で「同定不能 → 安全側の扱いへ倒す」という既存の判定に
そのまま乗るので、新しい語彙も要らない。

### 判定基準

**不正入力への対処を設計するときは「落とす」と「無害化して残す」を先に比較する。**

落とす側は必ず「落ちたことをどう伝えるか」という第 2 の機構を要求し、**その機構が次サイクルの
欠陥面になる**。無害化して残す側は、既存の下流判定に不正値を合流させられるなら、機構を 1 つも
増やさずに済む。

| 設計 | 要求される付随機構 | 可視性 |
|---|---|---|
| 不正要素を落とす | 件数カウント + その fallback + サニタイザ + 専用 marker + 下流の加算規則 | 落ちた要素は下流から消える |
| 不正部分を null へ写す | なし（既存の「同定不能」判定に合流） | 要素は残り、不正値だけが無効化される |

### 同型: ガードを足すより失敗モード自体を消す

同じ PR の別サイクルで同型の判断が出た。`jq -R` の行単位処理が改行入力に対して複数 JSON の
連結を生み、非空判定を通過した後で `--argjson` が落ちて WARNING が無言で消える経路があった。
対処として型ガードを足すこともできたが、`jq -Rsc` で入力全体を 1 文字列として読む形に変えると、
**その経路そのものが消えて** WARNING が正しく成立した。

「失敗モードにガードを足す」より「失敗モード自体を消す」を先に検討する。前者は必ず
「ガードが発火したことをどう伝えるか」という次の問いを生む。
