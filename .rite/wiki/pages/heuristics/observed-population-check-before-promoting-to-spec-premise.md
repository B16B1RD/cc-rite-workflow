# 「実体に合わせる」是正では実体の観測母集団を確認し、1 リポジトリの観測を仕様の前提に昇格させない

## 概要

「指示が実体と食い違っているので実体に合わせる」という是正は自然に見えるが、**その実体がどの母集団で観測されたか**を確認しないと、観測範囲の外へ退行を拡張する。

実例では、Issue が「実ファイルは 5 列テーブル」を前提に書かれていたが、同一マシン上の他 2 リポジトリは箇条書き形式で計 139 行が生きており、読み手（query hook）で正しく引けていた。**前提はリポジトリローカルだった。** 書き手をテーブルへ一本化すると、欠陥のなかったリポジトリへ「古い知見は引けるが新しい知見は引けない」という気づきにくい形の退行を持ち込むことになる。

## 詳細

### 実体には複数世代がある

成熟したリポジトリの実ファイルだけを「実体」として指示を書き換えると、**テンプレート生成直後の初期状態**（対象セクション自体が無い）の分岐が消える。改修前の指示が偶然テンプレート実体と一致していた場合、是正 PR がその経路の退行を持ち込む。

同一 PR 内で片方の不在ケースだけを明示ハンドリングして他方を落とすと非対称が残る。**不在ケースの網羅は節ごとに確認する。**

### provenance は git history で裏を取る

Issue の Non-goal 文の主節と括弧が逆向きを指していた（「テーブルから箇条書きへ戻す（過去の決定を覆さない）」）。`git show <commit>^:<path>` で確認すると、その過去の決定**以前**が既にテーブルで、当該決定が箇条書きへ変えていた。つまりこの是正は過去の決定の**反転**だった。

- provenance を文書に書き足すときは必ず `git show <commit>^:<path>` で前後を確認する。
- 同一リポジトリ内に反対の記述（test fixture のコメント等）がないか grep する。
- 誤った provenance は次の編集者に「その形式は一度も正式だったことがない」と読ませ、**その形式の consumer の存在を見落とさせる**。

### 形式収束の帰結を指示に併記する

書き手の生成規約を新形式へ移すとき、その構造を機械 parse する consumer が新形式を受理するか `Grep` で確認する。読み手が旧形式専用のままなら、書き手側ドキュメントの「consumer がこれを使う」という断定は誤記述になる。断定は**実装状態へ限定する caveat に置き換える**。

初期状態を新形式へ収束させる分岐を足すと、それまで動いていた新規リポジトリでも読み手が使えなくなる。この帰結は silent にせず指示本文に明記する（意図した挙動であることと、読み手対応が別 Issue であることを添える）。

### deferred は番号を採る

「読み手の対応は別 Issue」と 3 箇所に書いたが番号がなく、レビュアー 2 名が「追跡不能な TODO」と指摘した。**deferred を文書に残すならその場で起票して番号を入れる。** 番号なしの deferred は、後から誰も同一の Issue を指していると確認できない。

### 形式変更は実行時に読まれる参照チェーンまで洗う

書き手の指示とテンプレートを直しても、skill が実行時に読み込む共通参照（構造契約表）が旧形式を宣言していると、実行 LLM は同一セッションで相反する 2 契約を受け取る。**SoT 列に自分が変更したファイルを名指ししている表は特に危険。** `grep` の対象に「skill の参照チェーン内のファイル」と「同一初期化 run で配られる他テンプレート」を含める。
