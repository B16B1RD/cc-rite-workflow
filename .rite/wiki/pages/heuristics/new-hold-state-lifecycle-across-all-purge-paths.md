# 保留（hold）を新設したら、寿命を state を消す全経路で揃え、解除の手段を保留の理由ごとに用意する

## 概要

処理を止めて後で再開させる保留状態は、state を消すどれか 1 経路が保留を知らないだけで破壊的な整理へ流れる。purge・孤児回収・決着時の後片付けのすべてで保留の寿命を揃え、再開の案内は保留の理由ごとに実行できる手段を示す。案内が 1 種類だと、正しい記録のままでは解けない保留が行き止まりになり、処分済みへ書き換える動機を生む。

## 詳細

**寿命を全経路で揃える**: 保留は「まだ決着していないので消さない」という不変条件を持つ。state を消す経路は 1 つではない（明示的な purge、孤児の回収、決着時の後片付け）。兄弟関係にある script の片方だけが不変条件を守り、もう片方が保留を通常の残骸として整理すると、保留は無言で失われる。保留を新設したら、state を消す全経路を列挙し、それぞれが保留を残すことをテストで固定する。

**解除の手段を理由ごとに示す**: 再開の案内が「記録を直して再実行」の 1 種類だけだと、記録が正しいまま解けない保留が行き止まりになる。例として、対象 commit が決まらない保留や、マージ後に PR 起因と判定された候補がある。行き止まりの実行者は、保留を処分済みへ書き換えて先へ進もうとする。これは保留が守るはずだった判断を消す。案内は保留の理由ごとに、その理由を実際に解消できる手段を持つ必要がある。

**再開経路で保留を明示的に合流させる**: 手順書を経由してレビューをやり直す再開経路では、保存した保留候補を次の候補集合へ明示的に合流させる。合流させないと、再レビューが再掲しなかった候補が無言で消える。

**守る側と解く側を組で直す**: 保留を消さない不変条件は、保留を作るゲートではなく state を消す側（purge）に置くと 1 か所で判定でき、放棄を明示した経路だけがフラグで消す。ただし守る側を強めると、保留を解く入口の穴がそのまま行き止まりとして表に出る。典型は候補 0 件の入口で、0 件を特別扱いしてゲートを飛ばすと、残っている保留は誰にも解かれない。0 件でもゲートを通し、ゲート側で「引き継ぐ保留が無ければ判定なしで決定」とする。

**寿命は保留の種類ごとに決める**: 候補がほかの経路に残るかどうかで寿命を分ける。ほかに残らない候補は commit を問わず持ち越して新しい commit で判定し直し（直っていれば解消済みとして処分する）、ほかの経路が作り直す候補は古い commit の保留をゲートで退役させる。一律の規則にすると、片方で候補を失うか、もう片方で二重起票を招く。退役を選ぶ前提の「ほかに残る」は、その経路が読む入力の集合と、退役させる候補の出典の集合が一致するときだけ成り立つ。出典の一部しか後段が読まないなら、残りは処分されずに消えるので、両側の出典を突き合わせてから選ぶ。一致しないと分かったら、退役ではなく次の実行の候補へ持ち越して判定し直す。持ち越した候補の処分を記録する台帳は候補ごとに元の出典を保つ。出典を今回の入力にそろえると、出典で照合する後段の除外に一致せず二重に起票される。

**判定は最新の commit で行う**: 保留を解くために古い入力のまま処理をやり直す案は、判定の検証がその入力の commit に縛られる（証拠をレビュー済みの commit で読む）と、直した後の状態を正しく書けず保留が解けない。持ち越した候補は最新の commit で判定し直す。

**保留した run は全候補を保存する**: 保留した run が何も書かないなら、同じ run で決まっていた候補も保存しないと処分の機会ごと失われる。保留した候補だけでなく、その run の全候補を保存する。

**完了直前の確認は 1 か所に置く**: 保留を解く経路が複数あるときは、完了の直前に「どの種類の保留も残っていない」を確かめる入口を 1 か所に置く。ある種類の保留だけを見る完了判定は、別の工程が skip される経路でその保留を素通りさせる。

**決め手の入力が失われたら保留ではなく失敗で止める**: 判定対象の commit のように決め手になる入力が失われた状態を保留にすると、どう記録を書いても解けない行き止まりになる。失敗として止める。再開の案内は理由ごとに実行できる手段を示す 1 つの関数に寄せ、手順書側はそれを読むだけにする（文面を複製すると理由の追加でずれる）。

**同じ変更で起きやすい周辺の抜け**:

- 契約を変えたとき、SPEC・利用者の Issue へ投稿される本文・設定テンプレートに旧契約の約束が残りやすい。revert すれば一致に戻る種類のずれなので、変更した契約の語で関連文書を grep する。
- 新しい fail-loud 分岐（保存失敗・呼び出し先の失敗）はテストで通られていないことが多く、変異させても既存スイートが green のままになる。分岐ごとに失敗を起こすテストを足す。


### 保留から次の実行へ持ち越す候補のキーと、保留を解く時点

- 次の実行へ持ち越す候補の id は、出典と元のキーを組にした安定したキー（元の記録名と元のキーの連結）にする。今回の候補とだけ照合して付け直す方式は、持ち越しが重なると衝突する。キーに使う欄が空になりうるなら空どうしも衝突するので、空のときはキーとして使わず再利用されない側に倒す。
- 保留は、外部への書き込み（起票・台帳・申し送り）がすべて済んだ後に呼び出し側が解く。判定を出した時点で解くと、書き込みの途中で止まった再実行が候補を失う。「すべて済んだら解く」は成功の信号を数える手段とセットにし、失敗を non-blocking で続ける手順の後に無条件の解放を置かない。
- 中断からの再開で「どの実行の途中成果物か」を判別するときは、成果物自身にその実行の識別子を 1 行持たせる。行ごとの属性で判別すると、属性が混在する正当な成果物を古いものと誤判定する。
- 同じ記録を読む処理を新しく足すときは、兄弟の読み手が空・欠落・失敗をどう分けているかをそろえる。記録がまだ無いことを正常とする扱いを落としやすい。
- 書き手の出力を読み手に渡す往復を 1 本のテストで通す。fixture が生産側の出力を自分で用意すると、生産側の指示が消えても green のままになる。
