# 保留（hold）を新設したら、寿命を state を消す全経路で揃え、解除の手段を保留の理由ごとに用意する

## 概要

処理を止めて後で再開させる保留状態は、state を消すどれか 1 経路が保留を知らないだけで破壊的な整理へ流れる。purge・孤児回収・決着時の後片付けのすべてで保留の寿命を揃え、再開の案内は保留の理由ごとに実行できる手段を示す。案内が 1 種類だと、正しい記録のままでは解けない保留が行き止まりになり、処分済みへ書き換える動機を生む。

## 詳細

**寿命を全経路で揃える**: 保留は「まだ決着していないので消さない」という不変条件を持つ。state を消す経路は 1 つではない（明示的な purge、孤児の回収、決着時の後片付け）。兄弟関係にある script の片方だけが不変条件を守り、もう片方が保留を通常の残骸として整理すると、保留は無言で失われる。保留を新設したら、state を消す全経路を列挙し、それぞれが保留を残すことをテストで固定する。

**解除の手段を理由ごとに示す**: 再開の案内が「記録を直して再実行」の 1 種類だけだと、記録が正しいまま解けない保留が行き止まりになる。例として、対象 commit が決まらない保留や、マージ後に PR 起因と判定された候補がある。行き止まりの実行者は、保留を処分済みへ書き換えて先へ進もうとする。これは保留が守るはずだった判断を消す。案内は保留の理由ごとに、その理由を実際に解消できる手段を持つ必要がある。

**再開経路で保留を明示的に合流させる**: 手順書を経由してレビューをやり直す再開経路では、保存した保留候補を次の候補集合へ明示的に合流させる。合流させないと、再レビューが再掲しなかった候補が無言で消える。

**同じ変更で起きやすい周辺の抜け**:

- 契約を変えたとき、SPEC・利用者の Issue へ投稿される本文・設定テンプレートに旧契約の約束が残りやすい。revert すれば一致に戻る種類のずれなので、変更した契約の語で関連文書を grep する。
- 新しい fail-loud 分岐（保存失敗・呼び出し先の失敗）はテストで通られていないことが多く、変異させても既存スイートが green のままになる。分岐ごとに失敗を起こすテストを足す。
