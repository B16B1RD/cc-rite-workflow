# 保護は「設定ファイルの内容」ではなく「保護対象と同じ場所」に置く

## 概要

「機密を含むファイルが公開リポジトリに入らないようにする」ような保護を、セットアップが生成する設定ファイル（`.gitignore` など）へ 1 行追記する形で実装すると、その保護は 3 つの状態に同時に依存する — セットアップをいつ実行したか、アップグレード経路が追記ブロックに到達するか、ユーザーが設定を手で編集していないか。**保護対象のディレクトリ自身に、そのディレクトリを作る瞬間に保護を同梱する**方式は、この 3 依存すべてから独立する。

## 詳細

### 設定ファイル依存が持つ 3 つの隠れた前提

PR #2114 では「cleanup が退避するレビュー結果 JSON（脆弱性の全文を含む）が公開リポジトリへ入らないよう、setup が生成する `.gitignore` にエントリを 1 行足す」修正を入れた。cycle 3 のレビューで次が判明した:

1. **到達不能な経路**: 追記を行う Phase は `--upgrade` 経路から構造的に到達できなかった
2. **既存利用者が通るのは到達不能な側だけ**: 既存インストールへの自動案内は `--upgrade` のみ。案内どおり実行したユーザーは保護を永久に受け取らない
3. **配布先の既定構成が開発元と違う**: 開発元リポジトリでは既に `.gitignore` が効いていたため、開発中は保護が効いているように見えていた

3 番目が特に危険で、**開発元では常に緑・配布先でだけ穴が開く**という検出しにくい形になる。

### 代替: ディレクトリ同梱方式

有効な修正は、保護対象のディレクトリを作成する箇所で、そのディレクトリ自身に `*` だけを書いた `.gitignore` を置くこと:

```bash
mkdir -p "$archive_dir"
[ -s "$archive_dir/.gitignore" ] || printf '*\n' > "$archive_dir/.gitignore"
```

同じリポジトリに既に先例（`.rite/logs/`）があり、コメントに「downstream consuming repos ではセットアップが生成する `.gitignore` は一部しかカバーしない」と理由まで書かれていた。**同種の保護を足すときは、まず「同じ問題を既に解いている場所」を grep する** — 設計判断だけでなく、その判断の根拠まで既に書かれていることがある。

### 判定基準

> 保護が「ある状態が成立していること」を仮定するなら、その状態が成立する経路を全部列挙できるか。列挙が 3 経路以上になるなら、状態に依存しない置き方（対象と同じ場所に置く）を探す。

### 同梱方式で新たに気をつける点

ディレクトリ同梱へ切り替えると、今度は同梱ブロック自身が次サイクルのレビュー面になる（実際 cycle 4 で 4 件の blocking を生んだ）。少なくとも次の 3 点を同じ commit で押さえる:

- **ガードの述語を不変量へ合わせる**: `[ ! -f ]`（存在）ではなく `[ ! -s ]`（内容）。`printf > F` は redirect が先に truncate するため ENOSPC で 0 バイトのファイルが残り、存在ガードはそれを「作成済み」と読んで以後の全サイクルが無音で skip する
- **全経路に置く**: 同じディレクトリを保存経路と退避経路の両方が作るなら、片方だけでは保存を挟まない既存インストールで一度も効かない
- **置き場所はループ内で 1 回だけ**: ループ前だと結果ファイル 0 件の PR で毎回失敗して無意味な marker が出る。ループ内無条件だと 1 つの状態に対して N 本の marker が出る

### pin は「守りたい不変量」に結合させる

同じサイクルで、追加した保護を守る静的 pin も「現在の整形」に結合させないこと。行継続バックスラッシュ（`grep -cF '... .sh \'`）に結合させると、呼び出しを 1 行へ畳む無害な整形で偽陽性になる。行頭パイプ除外（`grep -v '^[[:space:]]*|'`）で表を絞ると、2 つ目の表を足す形を 1 assert も捕捉しない。**pin の pattern に「対象の意味」ではなく「対象の書かれ方」（改行位置・インデント・行頭文字）が入っていたら整形結合**であり、無害な整形で偽陽性/偽陰性が出ないか試す。
