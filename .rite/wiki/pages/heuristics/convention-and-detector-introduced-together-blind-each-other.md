# 「規約」と「その規約を検査する検出器」を同一 PR で入れると、規約に従った書き方が検出器の盲点に入る

## 概要

同じ PR が (a)「新規コードはこう書け」という規約と (b)「こう書いたら警告する」という検出器を同時に導入すると、検出器の正規表現は **PR より前から存在する書き方**に対して書かれる。同じ PR が導入した新しい書き方は自然には視野に入らない。結果として「規約に従って書いたコードほど検出器の入力ドメインから外れる」という反転が起き、規約の遵守者だけが無検査になる。

## 詳細

### 実測された反転（cycle 1）

同一 PR が次の 2 つを導入した。

- 規約: 「新規 bash helper の tempfile は `hooks/scripts/lib/tempfile.sh` 経由で作る」
- 検出器: lib で消せない残余パターン（mktemp 由来パスの派生、pipefail 下の `grep -q`）を非ブロッキング warning で拾う

検出器のハンドル追跡は `x=$(mktemp ...)` という **raw mktemp 由来の綴りしか見ていなかった**。規約どおり `rite_tempfile_new f` と書いた helper の派生パスは、そもそも検出器の入力に入らない。規約を守るほど検査されなくなる。

### 「綴りの網羅」は 1 度では終わらない（cycle 2 → cycle 5）

同じ穴が形を変えて 3 回出た。

| cycle | 見落としていた入力 | 塞いだ範囲 |
|---|---|---|
| 1 | lib 経由で作られたハンドル | 規約が推奨する書き方そのもの |
| 2 | 1 論理行の 2 個目以降のハンドル（`a=$(mktemp) && b=$(mktemp)`） | 登録側が最初の 1 個で return していた |
| 5 | 第 3 の綴り（`_mktemp-stderr-guard.sh` 経由、走査対象内に 11 site） | 綴りの種類そのものの網羅 |

cycle 2 で「1 行の 2 個目以降」を塞いでも、**綴りの種類の網羅は別問題**として残った。「もう塞いだ」と宣言する前に、走査対象ツリーで実際に何種類の綴りが使われているかを数える。

### 対処

1. **規約が推奨する書き方が検出器の入力ドメインに含まれるかを明示的に確認する。** 規約側の推奨形をそのまま fixture にして、欠陥を仕込んだ版が検出されることを見る（negative control）。
2. **走査対象ツリーで綴りを実測してから「網羅した」と書く。** 検出器の正規表現を書く前に `grep` で実在する書き方を数える。cycle 5 の第 3 の綴りは、走査対象内に 11 site 実在していた。
3. **「規約に従って書いたコードで欠陥があれば検出される」ことをテストに置く。** これがないと、規約と検出器がそれぞれ単体では正しいのに、組み合わせたときだけ盲点になる状態がテストで表面化しない。

### なぜ気付きにくいか

検出器の作者と規約の作者が同一人物（同一 PR）なので、「新しい書き方」は作者にとって自明すぎて検査対象として意識に上らない。レビューでは 3 reviewer が独立に同クラスを検出しており、**同一 PR 内の 2 つの成果物の間の整合性は、作者よりも第三者のほうが見つけやすい**。
