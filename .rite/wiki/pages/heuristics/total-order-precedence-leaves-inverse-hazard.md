# 全順序で優先順位を決める設計は逆向きの残存ハザードが必ず残る — 選ばなかった側を文書に残す

## 概要

複数の記法・入力形式・候補を全順序で優先する設計では、順序をどちらに倒しても「先に読む側が後ろの側の宣言を隠す」ハザードが必ず残り、順序変更はハザードを消さず露出面を移すだけである。

## 詳細

新しい選択肢を既存の選択肢群へ足すとき、**優先順位を決める規律を先に言語化しないと、既に片方で論じた危険を新しい境界で再生産する**。

観測例（`issue-complexity-lane.sh` の Complexity 記法）: 既存の記法 1（コロン形式 Meta）と記法 2（`## 複雑度` 節）に、記法 3（表形式 Meta）を追加した。記法 1 については「helper は code fence を剥がさないので、表記法そのものを説明している Issue が本文中の例から値を解決する」という危険を明示的に論じて TC で pin していたのに、新設した記法 3 と記法 2 の間の順位には同じ検討をしなかった。結果、`## 複雑度` で M を宣言した Issue が本文中の表の例から XS を採り、**M+ が silent に軽量レーンへ落ちる**経路が生まれた。

### 順序変更はハザードを移すだけで消さない

上記を「探索順を 1 → 2 → 3 に変える」で直したところ、逆向きのハザードが実測された:

| body の形 | 旧順（1 → 3 → 2） | 新順（1 → 2 → 3） |
|---|---|---|
| 記法 2 で M 宣言 + 別節に表の例 | `light; XS`（危険側） | `full; M`（正しい） |
| 記法 3 で M 宣言 + fence 内に `## 複雑度` の例 | `full; M`（正しい） | `light; XS`（危険側） |

**全順序で決める限り、どちらへ倒しても「先に読む側の例が後ろの側の宣言を隠す」経路は残る**。順序の選択は正しさの問題ではなく、**露出の非対称性**（どちらの形が実運用で多いか）で決める工学的判断になる。上記の例では、記法 2 を宣言に使う Issue は直近 200 件の走査で 0 件、記法 3 は定常的に存在したため、記法 3 を守る側へ倒すのが正しい。

### 選ばなかった側を文書に残す

順序を決める根拠を文書へ残す際、**片側の誤判定だけを書くと、次のサイクルが逆向きの是正で順序を戻す動機を持つ**。順序の SoT には次の 3 点を揃えて書く:

1. 順序を決めた**規律**（例: 「明示宣言を先に読み、表行を最後に読む」）— 個別の誤判定ではなく判断基準として書く
2. 選んだ側で消した誤判定の**実測**
3. **選ばなかった側に残るハザードの実測** — これが無いと SoT が「たまたまそう書いてある」ものに見える

### 順序非依存にする解は実トリガーが出るまで作らない

候補をすべて評価して値の衝突を fail-loud にすれば順序依存は消えるが、新しい code path・新 reason 語彙・複数箇所の文書同期・テストを伴う。トリガー母集団が実測 0 件の段階でこれを入れるのは `no_speculative_structure` に反する。**実際に衝突を踏む入力が観測されてから**着手する候補として記録しておく。
