# 診断メッセージの主語と射程は、その文が発火する条件が保証している対象に限る

## 概要

縮退時の診断が誤情報になると、既に degraded な状況でのトリアージを誤らせる。WARNING を書くときは (1) その文を書く位置で値が確定しているか (2) 発火条件が覆う範囲と主張の範囲が一致するか (3) 主語が発火条件によって保証されているか、の 3 点を確認する。

## 詳細

### 失敗の 4 類型

**1. 値の確定前に書いた断定。** WARNING が「A / B / C を既定値へ倒します」と書いたが、実際に倒れるのは C だけで A / B は後段の env override が最終値だった。しかもその WARNING が届く唯一の caller が A / B を渡す経路だったため、**誤報が最も届く場所で起きていた**。メッセージを書く位置が値の確定前なら、確定しない対象は条件付きで書く。

**2. 主語が発火条件に保証されていない。** 「値を carry-forward しました」と書いたが、発火条件は「parse が corrupt かつ `.data` が非空」だけで carry-forward が起きたことは保証していない。env override が渡る経路では実際に carry-forward された値が 0 件でも発火する。

**3. 主張の射程が発火条件より広い。** 「WARNING で観測性を確保する」と書いたが、発火条件が `.data` 全体の空判定だったため、**個別 key だけが欠落する系統は無警告のまま**値が巻き戻った。主張の範囲は発火条件の範囲で書く。

**4. 診断値を捕捉しながら意味を持たない分岐で出した。** parse の corrupt verdict を変数に捕捉しながら、印字しているのは parse が成功している側の分岐だけだった。結果として「rc=0」と書かれた縮退 WARNING が出る一方、本当に corrupt なファイルからの値伝播は無警告になっていた。**捕捉した診断値は「どの分岐で出すか」まで設計する。**

### 観測性を足す修正は、それ自体が 3 種類の新規指摘面を作る

「縮退が沈黙する」という指摘に WARNING を 1 本足したところ、次 cycle で以下 3 件が出た。

- 発火条件が広すぎて成功時にも出る false positive
- その WARNING を pin するテストが無い
- call site の `2>/dev/null` で破棄され届かない

**WARNING を足すときは「発火条件が縮退のケースだけに一致するか」「テストで pin するか」「その stderr が実際に届く経路か」を同時に決める。** 特に 1 点目は既存 TC の fixture と突き合わせて確認する — 同一 PR 内でテストが「正常」と宣言する経路に対して「縮退しました」と警告していた実例がある。

### 分岐を足すと既存コメントの射程も変わる

`if`/`else` 全体を統べる位置にある解説ブロックに「rc は条件に使わない」と書いてあると、`else` 側に rc を条件とする新分岐を足した瞬間、その解説が新分岐を「誤報」と宣言する形になる。**コメントの適用範囲は物理的な配置で決まるので、分岐追加は既存コメントの意味も変える。**

同様に、コメントの例示は**一般命題が真になる側から選ぶ**。「個別 key の欠落は無警告」は非必須 key では真だが必須 key では偽。例示に必須 key を挙げると、例だけが命題の反例になる。

### 兄弟 WARNING の片肺 hedge

同一 diff で追加した 2 つの WARNING が同じ前提を語るのに、片方だけが条件を明記し他方は無条件に断定している状態は、3 reviewer が独立に検出するほど目につく。**同じ前提を語る WARNING を複数追加したら、条件節の有無を突き合わせる。** ただし「揃えた」だけでは複製構造が残り再び割れるため、変数へ束縛して複製を消すところまで行く（[コメントの複製構造](./comment-rationale-widens-review-surface.md) 参照）。

### 診断文言は「リテラル」ではなく「振る舞い」で pin する

WARNING の文言を条件付き表現へ直しても、その文言が宣言する挙動を通る走行が存在しなければ、文言を旧断定形へ戻す変異でも全アサーションが生存する。**文言リテラルを assert するのではなく、その文言が主張する挙動を走行させて assert する。** リテラル pin は他コンポーネントのメッセージ形式への結合を増やすだけで、drift には弱く保守コストだけが増える。

逆に言えば、**WARNING が断定した挙動はそのまま assertion にできる**。「sync_revision を 1 から採番し直します」と書いた分岐では、その値を assert すればよい。診断文は仕様の宣言でもある。ただし検証用 fixture の元値が偶然 1 だと mutation を入れても Green のままなので、値が偶然一致しない fixture を選ぶ。

### ファイル由来の文字列を診断へ載せるときは 3 点セット

corrupt なファイル内容を診断へ補間する場合、**中和・clamp・アサーションの 3 点セット**が要る。実例では `.errors` の添付が (a) 丸ごと外す変異が全 PASS を素通りし、(b) ファイル内容を補間するため 20 万バイトが 1 行で stderr へ流出した。リポジトリに先例（`neutralize_ctrl` + `head -c 200` 等）があるなら踏襲する。
