# 規範文を新設したら、その規範文が支配する範囲すべてに適用し直すか、適用範囲を明示的に狭める

## 概要

「この表は SoT と同期すること」「各行は全 script を名指しすること」のような規範文を文書へ新設すると、その文が支配する既存行のうち条件を満たさないものが即座に契約違反になる。新設の直後に、支配範囲の全行へ適用し直すか、規範文自体の適用範囲を狭めるかを選ばないと、契約を導入した変更そのものが次サイクルの指摘源になる。

## 詳細

### 観測

hook 登録表と `hooks.json` の乖離を直す変更で、表の直前の SoT 注記へ「各行の Purpose は当該 event に登録された全 script を名指しすること」という要求文を新設した。同じ変更で更新したのは表 7 行のうち 2 行（複数 script を束ねる `PreToolUse` / `PostToolUse`）だけで、残る 5 行の Purpose は script 名を 1 つも含まなかった。要求文は表全体を主語に取るため、新設した瞬間に自分の表の 5/7 行が違反する状態になった。

レビューは要求文の新設と違反を同一 PR 由来と判定した（revert すると要求文ごと消え、違反も消える）。つまり **契約を導入する変更が、その契約に対する違反を同時に導入した**。

### なぜ起きるか

規範文を書く動機は、たいてい「いま直している箇所を将来も同期させたい」である。書き手の視野は修正対象の行に絞られており、その規範文が **修正対象以外の行も支配する** ことは意識に上らない。文の主語（「各行」「この表」「すべての caller」）が修正範囲より広いことが、書いた本人には見えない。

同型の失敗は次の形でも起きる:

- **数え上げの追記が主語の集合とずれる**: 「per-session state を読み書きする hook は hooks.json に登録されている — 現在 7 event / 9 エントリ」と書くと、9 エントリのうち state に触れない 2 件が主語の外に出る。主語を狭く保ったまま数だけ足すと、文が自分の主語と矛盾する。直す方向は「数を主語に合わせて減らす」ではなく「主語を数え上げた集合に合わせて広げる」ほうが実態に近いことが多い（登録先は関与に依らず 1 つだから）。
- **非網羅マーカーの位置が足りない**: 呼び出し元を `several skills (A, B)` と書くと 2 件が全集合に読める。`e.g.` を足しても、括弧の後半を `C / D / E call it too` と閉じた形で書くと、その後半だけが再び全集合に読める。開いた表現は括弧の全体に及ばせる必要がある。

### 対処

規範文（MUST / 契約 / 同期要求）を文書へ新設したら、コミット前に次のどちらかを選ぶ:

1. **支配範囲の全要素へ適用し直す** — 表なら全行、caller 一覧なら全 caller。適用後、規範文が機械検証可能な形になっているかも確認する（例: 「Purpose セルは必ず `.sh` を含む」なら grep で検査できる）。
2. **規範文の適用範囲を狭める** — 本当に必要な部分集合だけを主語にする。上の例では「複数 script を束ねる event の行は全 script を名指しする。単一 script の行は script 名を繰り返さない」に限定した。単一 script の event は event 名から script が一意に決まるため名指しは冗長で、要求の本来の目的（1 event に複数 script が束ねられているとき、どれが何をするかを読者が判別できること）は限定後も満たされる。

**2 を既定にする**。1 は規範文の適用面を広げ、次サイクル以降のレビュー対象面をその分だけ増やす。2 は虚偽の要求を消す方向なので、機構を足さずに矛盾が根から消える（実際に cycle 2 のレビューは「機構を足さないため次 cycle の審査面も増えていない」と評価した）。1 を選ぶのは、適用し直した結果が機械検証可能になり、その検証を実際に配線する場合に限る。

### 判定の手がかり

新設した文の主語が、その変更で触れた範囲より広いかを読み直す。「各行」「すべての」「この表は」で始まる文を書いたら、その主語が指す集合を実際に数え、そのうち何件を今回更新したかを突き合わせる。全件でないなら 2 を選ぶ。
