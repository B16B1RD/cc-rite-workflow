# スキルのシェル処理を helper へ移すときは値の入力経路を対の処理と揃え、ファイル入力には存在と形式の検査を同時に入れる

## 概要

fenced bash を helper へ移すついでに値の受け取り方（placeholder の文字どおり置換 → ファイルや引数の生値読み）を片側だけ変えると、同じ値を置換経由で扱う対の処理と入力が食い違い、ファイル入力は読み取り失敗という新しい無言の経路を生む。

## 詳細

スキル本文の fenced bash は、LLM が placeholder を二重引用符の中へ書き込んでから実行する。helper スクリプトへ移すと、値はファイルや引数から生のまま読むのが自然になる。ところが同じ値を別の場所でまだ置換経由で扱っている処理があると、両者の入力が一致しなくなる。置換では引用符やエスケープの扱いが入るため、生値と同じ文字列になる保証がない。hash の比較のように両側の一致を前提にする処理は、この差で常に不一致になるか、偶然一致して検査が素通りする。移設では片側だけ入力経路を変えない。変えるなら対の側も同じ経路へ移す。

自由文を「LLM が Write したファイル」で渡す形に変えると、ファイルが無い・途中で切れている・形式が崩れているという失敗経路が新しく生まれる。置換方式ではこの経路は存在しなかったので、移設前の検査には含まれていない。読み取りの失敗を見ないまま進めると、空の内容で既存の節を上書きしたり、空の値から hash を計算したりして無言で進む。ファイル入力に変えたら、存在と形式の検査を同じ変更で入れる。

移設にはほかにも置き場所に依存する記述が付いてくる。コメントの相対パス（rationale ポインタ等）と「Claude が literal substitute する」のような入力経路の説明は、移設先の実態に合わせて書き直す。関数本体の終わりを列 0 の `}` で判定して抜き出すテストは、関数内で列 0 に閉じ括弧を置く書き方（`|| {` のブロック等）で途中で切れるため、移設後の関数の形で抽出が成り立つかも確かめる。
