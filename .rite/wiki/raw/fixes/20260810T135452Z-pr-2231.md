### Fix Patterns

**「観測できなかったこと」を「観測して問題なかったこと」に畳む 2 つの型**が、同一 helper 内で別々の構文から生まれていた。どちらも silent failure を検出する道具自身が silent failure を持つ形で、fail-loud 原則の破れ方として再発しやすい。

型 1: **`cmd 2>/dev/null | awk` の左辺 rc 消失**。jq をパイプの左に置くと element 単位の parse 失敗が rc ごと捨てられ、右辺は切り詰められた stream をそのまま処理する。しかも件数を右辺で数えていると total も一緒に縮むため、「実在数と件数が合わない」型の防御ガードが構造的に発火できない。修正時、`set -o pipefail` の追加 + 件数の独立再取得（2 つの追加）よりも、**パイプを外して左辺の出力を変数へ受け rc を直接検査する**（1 つの単純化）方が短く、かつ切り詰めの経路自体が消える。件数の独立取得も不要になる。追加より削除を先に検討する原則が、そのまま最短の修正になった実例。

型 2: **`if / elif` が仕様の「併記」要求を落とす**。仕様が「A のとき報告」「B のとき併記」を別々に定めているとき、実装で `elif` を使うと A ∧ B の cycle で B が消える。2 つの述語が独立に成立しうるなら実装も独立した `if` にする。レビューで見つけるには A ∧ B の fixture を明示的に作る必要があり、A のみ・B のみのテストが両方 green でも検出できない。

**テスト設計上の含意**: 上記 2 型はいずれも「単独ケースは全て green だが組合せで壊れる」形。3 帰結（serialized / parallel / undetermined）の各単独ケースを固めただけでは不足で、**帰結を跨ぐ組合せ（直列化かつ欠落）と、入力の構造破壊（配列要素が object でない）を明示 fixture で固定する**必要がある。
