### Fix Patterns

**規約の drift guard は「正しい形の複製」を検査していても「規約を無視した新規呼び出し」は捕まえない**。リポジトリは portable shim (`_timeout`) の byte 同一性を専用 test で機械検査していたが、その discovery は「shim を**定義する**ファイル」を grep する設計だった。新しい TC が shim を定義せず bare binary を直接呼んだため、guard を素通りして macOS で hard FAIL する状態が入った。定義の複製を検査する guard を作るときは、**「定義せずに素の依存を使う」経路も同時に禁止**しないと片肺になる。

**閾値を持つ安全装置は「存在の TC」と「境界値の TC」の 2 本が要る**。cycle termination を assert する TC は cap を削除すると kill されるが、cap の値を下げても green のまま通った。修正では cap ちょうどのチェーン（40 ホップ）が deny されることだけを assert し、上限側（41 ホップで allow）は assert しない — より大きい cap も同等に安全なので、上限を固定すると実装詳細の over-pin になる。**下限だけを pin する**のが正しい粒度。

**バイト保全の修正は、その値が流れ込む先の 1 行契約も壊す**。コマンド置換を排して生の LF を保全した結果、その値を埋め込んでいた 1 行ログ（`edit-guard: BLOCKED ... path="..."`）がレコード分割・偽装されうる新経路が開いた。**「値の表現を厳密化する」修正は、その値の全消費先で表現の前提が変わっていないかを確認する**必要がある。同ファイル内に既存の無害化パターン（`neutralize_ctrl --c0-only`）があったので、それに揃えた。

**人工的な PATH farm で回帰検証するときは、変更前の HEAD でも同じ farm を回して差分を取る**。farm には他のバイナリも欠けるため failure が複数出るが、「変更前にも出る failure」と「変更が消した failure」を分離しないと、自分の修正が原因の regression を見落とす。本 cycle では farm 上で変更前 3 failed → 変更後 2 failed となり、消えた 1 件がまさに修正対象（cycle TC の rc=127）であることを確認できた。
