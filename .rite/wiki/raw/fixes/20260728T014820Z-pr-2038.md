### Fix Patterns

- **pin の「強度」と「適用範囲」は独立の軸 — 強度を上げても範囲が欠ければ守れない**: canonical 完全一致 pin は当てた行について言い換え・極性反転・削除・並べ替えのすべてを捕捉するが、4 データ行のうち 2 行にしか当てていなければ残り 2 行は無防備のまま。実例: 未 pin だった「sentinel NOT found → ERROR」行（その gate が存在する唯一の理由を担う行）を pass へ反転しても suite は完全緑だった。pin を設計するときは「どこまで強いか」と「どこまで覆うか」を別々に確認すること。

- **allowlist のトークンが escape hatch になる**: 層 2 の allowlist に `legitimately skipped` を許容トークンとして含めていたため、ERROR 行を「Gate は legitimately skipped」へ反転する変異が allowlist を満たして通った。allowlist は「規約に沿っているか」を見るが「その行が正しい判定をしているか」は見ない。判定の向きを守る層では、allowlist ではなく **row role（pass / ERROR / legitimate-skip）ごとの本数を厳密等値で固定**する方が確実 — 役割をまたぐ書き換えは必ず本数の変化として現れる。

- **個別行に pin を足すのではなく層で当てる**: 同型の表が複数あるとき、指摘された 1 つの表に canonical pin を足しても他の表は露出したまま。ループが全表に適用される層（`_g_spec` のような表ごとの期待値リスト）に 1 項目足す方が、抜けが構造的に生じない。実例: ERROR 行数を `_g_spec` に足した 1 編集で、指摘された 8.0.3 だけでなく未指摘だった 8.0.1 / 8.0.2 の同型の穴も同時に閉じた。

- **「全廃した」という表明は、書き換えた箇所ではなく主張する性質に対して grep で裏を取る**: 「区間 anchor のハードコードを全廃（残存 0 件）」と commit message に書いたが、別 helper（`assert_grep_in_section`）経由で同じ range 形が 4 件残っていた。検証は「自分が触った行」ではなく「その性質を持つ行がファイル全体に 0 件か」に対して行う。

- **SoT の設計規則と実装が乖離したら、規則側に例外条項を書く判断もある**: 「denylist ではなく allowlist で書く（現行表記への係留を避ける）」という規則を持つリポジトリで、canonical 完全一致 pin（＝最大限の係留）を導入した。実装が正しいなら規則に「判定の向きを担う少数のセルは意図的に係留する」の例外を追記すべきで、規則をそのままにすると次の保守者が「規則違反だから」と塞いだ穴を開け直す。例外条項には**なぜ例外なのか**（4 世代の substring 系 pin が実際に通した穴の実績）まで書く。

- **SoT の「残存ギャップ」記述は実測してから書く**: 層 2 の近似誤差を「規約文言を持たない行を通す」と書いていたが、実測すると逆で、規約文言を持たない行は確実に検出され、通るのは「規約文言を含みつつ終端直行を追認する行」だった。誤った残存ギャップ記述は、保守者に実在しない穴を塞がせ、実在する抜け道を無防備に残させる。
