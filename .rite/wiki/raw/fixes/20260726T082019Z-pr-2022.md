### Fix Patterns

- 「存在確認する ref 集合」と「破壊的操作の対象 ref 集合」を別々の解決規則で決めると、両者が一致しない窓が生まれる。git では `ls-remote <pattern>` が slash 境界の tail 一致、`push --delete <dst>` が全 namespace 解決で、どちらも完全一致ではない。破壊的操作は検証と同じ ref 修飾で行い、検証側は rc だけでなく出力の ref 名まで完全一致で確かめる。
- 散文コメントに「この形なら完全一致になる」と書くだけでは契約にならない。前 cycle はコメントで完全一致を主張しながら実装は tail 一致のままで、テストも通っていた。技術主張は実測（サンドボックスで実際に ref を仕込んで rc と副作用を観測）で裏を取る。
- marker 契約に外部由来の値（ブランチ名）を無エスケープで載せる設計では、値がデリミタ文字を含むと右端境界を騙って別エンティティの判定へ誤帰属する。エンコード規約を emitter/consumer の両側へ増やすより、契約を満たせない入力を fail-fast で弾く方が単純。
- 片側（リモート）だけに「既に不在 = 正常系」を実装すると、もう一方（ローカル）で同じ症状（必ず失敗する処方の提示）が再生産される。対称性は fallback 行だけでなく emitter の経路まで揃える。
- SKILL.md の bash block をテストへ literal 抽出する方式では、抽出アンカーがブロックの**構造**に依存する。`^esac$` のような閉じトークン単体をアンカーにすると、内部に case が入れ子で増えた瞬間に途中で切れて構文エラーになる。fence 終端をアンカーにし、抽出結果へ `bash -n` を掛けて構文完結性を検査するのが頑健。
- 新しいガードを追加すると、既存の mutation 対象が非 load-bearing に後退することがある（完全一致検証を入れた結果 `--exit-code` の除去が挙動を変えなくなった）。mutation testing は「今どの検証が結論を支えているか」に合わせて対象を retarget しないと、vacuous な緑を出す。
- テスト自身の検証コマンドも同じ落とし穴を踏む。fixture に入れ子衝突 ref を仕込むと、テスト側の `ls-remote --exit-code` による存在確認まで tail 一致で誤判定する。
