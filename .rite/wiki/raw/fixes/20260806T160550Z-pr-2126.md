cycle 1 の 8 件を修正した直後の cycle 2 で新たに 5 件の blocking を検出（trend 8 → 5、下降）。**指摘の大半が cycle 1 の修正そのものに対するもの**で、これは「1 つの欠陥を直すと、直した機構が次サイクルの新しいレビュー対象面になる」構造を示している。

1. **ゲートが要素を *移送* する設計では、片方の配列だけを読む consumer が回帰を持ち込む**（最重要）。実測必須ゲートは非実測の gated 指摘を `findings[]` から `non_blocking_findings[]` へ移動させる。cycle 1 で「`findings[]` は blocking 集合ではない（nit-noted が混じる）」という**余分が入る方向**の欠陥を直したが、同じ移送の**足りなくなる方向**は見落としていた。その cycle の gated 指摘が全件非実測だった reviewer は `findings[]` に 1 件も残らず、次サイクルの再起動対象から構造的に脱落する。教訓: **配列間で要素を動かすゲートを挟む場合、consumer は「入ってくる余分」と「出ていく不足」の両方向を同時に検討する**。片方だけ直すと、直した側の対称位置に同型の欠陥が残る。

2. **`jq` の `select` は条件に合わない要素を無音で捨てる**。フィルタを足して「余分を除く」修正をすると、入力が壊れているときの出力が正常系（0 件）と区別できなくなる。特に危険なのは**部分欠落** — 出力が非空なので異常に見えない。教訓: **`select` でデータを絞る前に、絞る対象そのものの健全性を `jq -e all(...)` で確認して fail-loud にする**。「フィルタを足す」修正は「無音 drop 経路を足す」修正でもある。

3. **同一ファイル内の非対称は、後から読む人に「捨ててよい経路」と誤読させる**。cycle 1 で 4 経路の診断 surface を直したが、`commit_sha` 抽出の 1 経路だけ `probe_err` へリダイレクトしておきながら読まないまま残った。しかも rc を見ていなかったため、トップレベルが object でない破損が「旧形式＝良性」の reason で報告されていた。教訓: **診断の統一は「全経路」で数えて確認する**。「主要な経路を直した」で止めると残余が次サイクルの指摘になる。

4. **スキル冒頭の identity 宣言と、他スキルの handoff 実行時文字列が、新機能を実行時に打ち消す**。前文の「一切関係なく常にフルレビュー・スコープ縮退禁止」は手順より先に読まれる上書き不可の語調で、後段に足した分岐と正面衝突する。さらに強いのは別スキル（fix）の `flow-state --next` に載る文字列で、これは**新機能が発動すべきまさにその瞬間に** orchestrator の context へ反対の指示を注入する。教訓: **「例外なし」の語調で書かれた前文がある skill に例外を作る変更は、(a) 前文、(b) 他 skill の handoff 実行時文字列、まで含めて同時に更新しないと機能が実行時に無効化される**。文書の整合性の問題ではなく、機能が動くかどうかの問題。

5. **契約条項の pin は「肯定句の存在」ではなく「文の続き」までアンカーする**。行頭アンカー化しても、同一行に撤回節（「… という規則は cycle 2+ では適用しません:」）を追記する変異は素通りする。教訓: MUST / MUST NOT に文として現れる条項は、**肯定句の直後に続く具体語まで含めて** pin する。

6. **helper 側で挙動テストが守る規則を、consumer 側の散文でも同じ強さで pin する**。同じ規則（gated scope の絞り込み）を helper と SKILL.md の両方に書いたが、helper 側だけに挙動 pin を置いて consumer 側を無防備にしていた。教訓: 同一規則が実装と散文の 2 箇所にあるなら、pin も 2 箇所に置く。

7. **fail-safe の検証は「安全側へ倒れること」ではなく「安全側 *だけ* になること」**。`emit_full` の exit を局所的に落とす変異は、fallback marker の存在だけを見る TC では素通りし、full と incremental の両方が出力される。教訓: fail-safe TC には**負の assertion**（危険側の marker が出ないこと）を必ず 1 本添える。
