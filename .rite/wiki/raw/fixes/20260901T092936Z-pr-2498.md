### Fix Patterns

blocking 3 件はいずれも「抽出の忠実性」ではなく「抽出に付随して入った変更が、それを支える
契約・検出網と同期していない」クラスだった。修正戦略として有効だったのは次の 3 つ。

1. **rc 捕捉 idiom の統一を「追加」ではなく「削除」で解いた**: `if ! var=$(cmd); then rc=$?` は
   bash が `!` で終了ステータスを反転するため then 節の rc が常に 0 になる。ここに rc 保存用の
   新変数や分岐を足すのではなく、`!` を外して sibling helper が既に使っている
   `var=0; cmd || var=$?` の形へ寄せた。修正 diff は 4 行で、新しい機構は増えていない。
   同型の欠陥を repo 全体から探すときは `if ! var=$(cmd)` の grep だけでは過検出になる —
   **then 節で `$?` を読んでいるか**が判別子で、読んでいない site（エラー出力して exit するだけ）
   は欠陥ではない。この絞り込みで候補 30 件超が 1 件に落ちた。

2. **テストの pin は prefix ではなく値で置く**: `rc=` までの prefix 一致は、実 rc を取り落として
   常に 0 を出す実装を素通しする。値 pin（`rc=127`）へ強めたうえで、修正前の実装へ戻す変異を
   当てて FAIL することを確認した。pin を強めた直後に変異を 1 回当てるだけで「pin が
   load-bearing か」が判定でき、次サイクルで同じ指摘が再発行されるのを止められる。

3. **契約と実装が衝突する経路は、実装を戻さず契約側を更新する**: 純粋抽出 Issue の
   「振る舞い不変」MUST と、プロジェクト原則の fail-loud が正面衝突した（silent fallback を
   直すことが MUST 違反になる）。振る舞いを機械的に復元すると同じ reviewer が同じ指摘を
   再発行する往復になるため、Decision Log へ例外エントリを足し、AC の Then に例外を明記し、
   テスト名から契約を辿れるようにした。4 レビュアーのうち 3 者が独立に同じ結論
   （revert せず記録）へ到達しており、複数レビュアーの一致は契約更新の妥当性の指標になる。

配布物への開発リポジトリ固有 Issue 番号は、helper 本体から除去した修正がテスト側へ伝播せずに
残っていた。同種の除去を行ったら、同じ PR で追加した**兄弟ファイル全体**を検出器で走査して
0 件を実測してから閉じる（本体だけ直して満足しない）。契約アンカー（`T-xx` / `AC-x`）は
番号ではないので維持し、開発リポジトリでしか解決できない番号だけを落とす切り分けが要る。
