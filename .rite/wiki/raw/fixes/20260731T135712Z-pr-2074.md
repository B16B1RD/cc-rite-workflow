「実測必須ゲートを LLM から helper へ機械化する」PR を 5 cycle 回した経験則:

1. **機構の追加で塞いだ穴は、次 cycle でその機構自体が穴になる**。cycle 1 の fail-open 修正 →
   その修正のサブシェル exit → cycle 2 の routing 行が正常系で誤発火 → cycle 3 の集約 hard fail が
   両方向に壊れる、と 3 巡続いた。cycle 3 で「削除」に舵を切ってから収束が始まり、cycle 4 で
   HIGH/CRITICAL がゼロになった。**同一 PR 内で前 cycle の fix が指摘された場合、追加パッチを
   既定選択にしない**という Simplification-First の escalation trigger は実効性がある。
2. **緩い検出述語の出力を停止条件へ昇格させてはならない**。`anchor_unparseable` は
   「false-positive WARNING が増えることを許容して silent false-negative を潰す」設計判断で
   選ばれた緩い述語だった。その件数を hard fail の入力に使った瞬間、判断の前提が崩れ、
   誤発火と見逃しを同時に持つ形になった。検出層と停止層は入力を共有しない。
3. **削除が正解のときの見分け方**: 提案された修正案が「一方の失敗モードを他方と交換する」形に
   割れたら、その機構は測るべき量を測っていない。cycle 3 ではレビュアーの推奨が 3 案に割れ、
   それが撤去の決め手になった。
4. **ドキュメントの後追いは毎 cycle 1 箇所ずつ漏れる**。cycle 2-5 で件数表記・記載先・粒度が
   順に漏れた。機構を削除するときは、その機構を **参照する側** を grep で列挙してから消す。
5. **転記が新しい依存先になる**。LLM 分類を regex full match へ置き換えると、依存先が

   non-blocking 化した。機械化は依存を消さず移す。
