### Fix Patterns

「silent failure を塞ぐ修正」に対するレビューで、**修正コード自身が同じ defect class を再現している**ことを 6 reviewer が独立に検出した。塞ぐ側と塞がれる側の構造が同型になるのは偶然ではなく、以下のパターンで繰り返す。

1. **検出器の rc 契約に「検出できなかった」状態が無い**: 新設した静的チェックは fence 不整合 / awk fatal / target 不在をすべて「findings 0 件 + rc=0」に畳んでいた。呼び出し元 (`/rite:lint` Phase 3.5) は rc=0 を success と扱い、その場合スクリプト出力を表示しない契約なので、stderr の WARNING は構造的に誰にも届かない。**「stderr に WARNING を出しているから silent ではない」は、呼び出し元が WARNING を表示する経路を持つ場合にのみ成り立つ**。走査できなかった件数を数えて rc=2 に分けることで初めて observable になる。

2. **sentinel exit code が外部ツールの予約値と衝突する**: unbalanced fence の自前 sentinel に rc=2 を選んだが、gawk / mawk は fatal error でも 2 を返す。結果、awk が開けなかったファイルが「意図的に捨てた」扱いになり、用意した awk 失敗分岐が到達不能になっていた。**自前 sentinel は呼び出す外部コマンドの予約 exit code を避けて選ぶ** (3 以降が安全)。

3. **空集合の差分が成功と同義になる**: DoD 検証は `comm -23 <(emit) <(表)` の出力が空なら合格としていたが、emit 側の抽出が 0 件でも空になる。emit 側は prose markdown への正規表現マッチなので、記法が変われば検証は無言で no-op 化する。**集合演算で検証するときは、入力集合が空である可能性を成功と区別する**。

4. **恒真アサーション**: 除外契約 (「実スクリプトは走査しない」) のテストで、fixture の検出対象を fence の**外**に置いていた。fence 外は元々検出されないため、走査範囲がどう広がっても finding が出ず、実装が壊れても pass する。**除外のテストは「除外されなければ必ず検出される内容」を境界の両側に置いた対で書く**。除外条件を外す変異で rc が変わることを実測して初めて非恒真と言える。

5. **mktemp 名からの派生パスは atomic-creation 保証を失う**: `$(mktemp).part` のような派生は予測可能で mktemp が作ったものでもないため、symlink を置かれると追随して truncate する。隔離環境で実測再現した。**一時ファイルが 2 本要るなら 2 回 mktemp する**。

6. **シンボルを消しても、それを列挙する側は同期されない**: inline 実装を helper へ委譲した際、削除したシンボル名を参照する「同期リスト」「caller 列挙」「構造ツリー」「相互参照」「設計判断の根拠文」「reason 表の説明」が 6 箇所取り残された。うち 1 つは自ら「唯一の同期一覧。全 site を漏れなく同期更新する義務がある」と宣言しているファイルで、箇条書きは更新されたが直下の設計差異ブロックが取り残されていた。**削除したシンボル名で全文 grep する**のが唯一の確実な検出手段で、「grep で 0 件確認した」という主張自体が 1 件の残存で反証された。
