### Fix Patterns

1. **GNU 拡張の除去は「境界指定を足す」ではなく「トークン全体を切り出して既存の妥当性判定へ委ねる」で解く**: `sed` の抽出式が `\b`（単語境界）で値の切り詰めを防いでいたが、POSIX BRE に `\b` は無く BSD/macOS では無警告で不一致になる。ここで「BSD 用の分岐を足す」「`sed -E` へ切り替える」ではなく、**貪欲な `[A-Za-z][A-Za-z]*` でトークン全体を取り、妥当性判定は既に存在する `case` に一本化する**ことで、GNU 依存と「レーン値の集合が 2 箇所にある」重複を同時に消せた。**境界指定が必要に見えたのは、値の長さ制限（1-2 文字）という別の制約を正規表現側に持たせていたため**で、その制約自体が不要だった。移植性の指摘に対しては「環境分岐の追加」より先に「その正規表現機能が本当に要るのか」を疑うと、単純化で解ける場合がある。

2. **fail-safe の向きが安全側でも「無警告で常に発動する」なら機能は死んでいる**: 本件は full（フル装備）へ倒れる安全側の縮退だったため、CI も緑（macOS leg は `continue-on-error`）、実行時エラーも出ず、reason 表示は `complexity_absent`（= 起票者の不備）で、**「機能が一度も動いていない」ことを示す信号がどこにも無かった**。fail-safe を設計するときは「倒れた事実そのものが観測値として記録されるか」「reason が原因を正しく帰属するか」を併せて設計しないと、安全側の縮退が恒久的な不作動を隠す。

3. **契約 pin の needle は「守りたい行の形」まで書き切る — 語彙だけの pin は同一ファイル内の別行に代替で満たされる**: 散文契約を grep で pin する際、reason 名や section 名のような**語彙**を needle にすると、同じ語彙を持つ Reference 行・要約表のセル・複製テンプレートが pin を満たしてしまい、**守りたい行を反転・削除しても suite が green のまま通る**。実測では 3 種の mutation（条件値の反転 / 別方向の反転 / 節の全削除）を旧 pin が全て素通しした。対策は (a) 行頭 anchor（`^`）、(b) 条件だけでなく**帰結節**まで needle に含める、(c) `assert_grep_in_section` で節にスコープを切る、のいずれか。**兄弟 reason の片方だけが完全 literal でもう片方が裸単語、という非対称は defect の強い予兆**。

4. **「pin が効いているか」は mutation を実際に走らせて示す — 一致行数の計測が軽量な代理指標になる**: pin の検出力は目視では判断できない。安価な機械検査として **`grep -c` で pin の一致行数を数え、1 でないものを列挙する**だけでも、over-matching な pin をファイル横断で洗い出せる（本 fix では 7 件が判明）。ただし**「一致 1 が常に正しい」ではない** — full mode / verification mode のように意図的に複製された 2 コピーでは「各 section に 1 ずつ」が正しい要求であり、一律の uniqueness assert を入れると誤った assert になる。同じ欠陥クラスでも**正しい修正が同一でない場合、機械的な伝播適用はしてはならない**。

5. **散文の前提は「必ず〜である」と書く前に母集団を実測する**: 全 reason を WARNING で loud にする根拠として「この値は rite が作る全 Issue に必ずある」と書いていたが、実測すると 60 件中 23 件（38%）が持たなかった。前提が偽だと WARNING が定常出力になり、同じ reason に潰れている actionable なケースが noise に埋もれる。**loud を維持する場合でも根拠は実測可能な別の理由に置き換える**（本件では「倒れた事実が効果計測の分母になる」）。さらに、定常出力と真の異常を切り分けるために **「情報が本当に無い」と「あるが解釈できない」を別の診断行で分ける**（後者だけ対象行を名指しする）。

6. **Markdown table の途中に非表行（blockquote / HTML コメント）を挟むと AND 条件が黙って消える**: 既知の anti-pattern（HTML コメント）と同型で、**blockquote でも同じ boundary 破壊が起きる**。「all of the following」を要求する条件表の 2 行目と 3 行目の間に注記を挟んだ結果、3 行目が引用ブロックの lazy continuation として吸収され、レンダを読む実行者にはゲートが 2 条件に見えた。raw markdown を読む LLM には 3 条件に見えるため、**LLM 実行者と人間で解釈が割れる**のが厄介。注記は表の直後（空行を挟んだ独立ブロック）に置く。検証は `gh api /markdown -f mode=gfm` の `<tr>` 数で機械的に取れる。
