## PR #2052 fix (cycle 5) の知見

### 有効だった修正戦略

**1. pin literal は「ラベルの主張と 1 対 1」で選び、変異注入で必ず kill を確認する**
素の識別子（`n_stats_abort` = 5 hits、`WIKI_INGEST_STATS=ok` = 3 hits）を pin にすると、
対象行を消しても別箇所に一致して変異が生存する。手順: (a) 編集を**すべて適用してから**
`grep -cE` で hit 数 1 を確認、(b) その literal を置換する変異を注入し自分の assert が
ちょうど 1 件 FAIL することを実測。編集前に計測すると、同じ commit 内の別修正が
literal 自体を消す/増やすため stale な数値になる（本 cycle では F-08 が F-02 の pin 対象
`最後の Raw Source を処理したときにのみ実行` を消した）。

**2. marker 契約は producer と consumer を対で pin する**
consumer（展開表）だけ pin しても、producer（emit 契約）が消えれば正常サイクルで
「marker なし → ⚠️ 未確認」が毎回誤発火し、pin が守るものが無くなる。

**3. 成功 marker の emit 点は「attest したい状態が確定した後」へ置く**
計算完了時ではなく副作用（Edit / push）の完了後に出す。移設するときは**副作用が no-op に
なる経路**も同時に規定する — 「値が既に一致していて Edit が空振り」は移設で初めて可視化
される 4 つ目の経路で、規定しないと健全なサイクルが「未確認」に落ちる。

**4. gate を外すときは skip 経路の適用範囲も同時に明示する**
「重複削除を集計比較から切り離す」だけでは不十分で、統計節なし / 統計中止の skip が
「3 行同期だけをスキップし、重複削除は実行する」と書かれていないと、指摘された失敗モードが
そのまま生き残る。分割したら**分割の両側それぞれに skip の scope を書く**。

**5. 数え上げ不能な述語は既存カウンタとの照合へ置換する**
「最後の N を処理したとき」→「処理済み件数が `n_raw_sources` に達したとき」。
新しいカウンタを作らず既存の確定値を使うと、機構が増えない。あわせてループ本体側にも
同一条件を 1 行置き、ループを読んでいる時点で分岐が確定するようにする。

### 過剰反応を避けた点（Simplification-First）
前 cycle の fix が導入した箇所への指摘 6 件はすべて、分岐・条項の**追加**ではなく
emit 点の移設 / gate の削除 / 述語の置換 / 到達不能分岐の畳み込みで解いた。追加パッチを
重ねると、その追加自体が次 cycle の新たなレビュー対象面になり指摘を再生産する。

### 手順として効いたこと
- 散文を書き換える前に `grep -rn '<string>' hooks/tests/` で pin 依存を全走査する
  （本 cycle は 14 文字列を事前走査し、2 件が test に依存していることを検出した）
- ファイル単位の編集ごとに関連スイートを回す（最後にまとめて回すと原因の切り分けが効かない）
- GFM の code span 入れ子は `gh api -X POST /markdown -f mode=gfm` で実際にレンダリングして確認する
