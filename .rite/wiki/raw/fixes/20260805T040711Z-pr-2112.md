### Fix Patterns

blocking 6 件のうち **4 件が cycle 1 の修正自身の回帰**だった。修正が新しい欠陥面を作る形に 3 つの型がある。

**1. 述語を厳格化するときは「一致しない」の内訳を 2 つに割る**

「散文中の同形文字列を誤検出しない」ために抽出 regex へ行アンカーを足したところ、正規の入力でも行末 CR・字下げ・末尾空白があると不一致になり、抽出結果の空が「対象が存在しない (正常系)」と同一経路へ落ちた。機能の中核保証が WARNING 1 行も出さずに失われる。同じコードのコメントが「厳格化すると壊れた入力が入力なしと区別できなくなる」と自ら禁じていたのに、その禁止を厳格化そのものが破った。

再発防止: **抽出述語を厳しくする diff には、必ず同じコミットで「対象らしきものはあるが述語を満たさない」を検出する緩い probe を足す**。厳格化した式と probe の 2 本立てにして、後者に当たったら fail-loud に落とす。「一致しない」を 1 本の経路に畳んだ時点で fail-loud は構造的に成立しなくなる。probe 自体も厳格化前の式ほど緩くしてはいけない (誤検出が新しいノイズになる) — 元の式から「値の抽出」だけを外した形が過不足ない。

**2. 連言の述語を pin するには、項の数だけ fixture が要る**

`^` と `$` を pin したはずの fixture は decoy の**両側**に非空白を置いていたため、両方を同時に外す mutation しか落とせず、片方だけを外した 4 mutant がすべて生存した。`A ∧ B` に対し 1 つの fixture では `¬A ∧ ¬B` しか検出できない。

再発防止: **連言を pin するときは、各項を独立に殺す fixture を項の数だけ用意する**。行アンカーなら「行頭に対象 + 後ろに散文」(`$` を殺す) と「前に散文 + 行末に対象」(`^` を殺す) の 2 形状。mutation も項ごとに当てる。

さらに本 cycle では、**pin の観測経路が片方しか通っていない**という別軸の穴も出た。read 側 (抽出) の TC は書いたが、write 側 (除去) は別経路 (fallback) を通らないと発火しないため、除去式だけを狭める mutation が生存した。**同一の形状定義を read/write で共有している場合、pin も両方の経路で張る**。

**3. read 経路を差し替えたとき落ちる不変条件は 1 つとは限らない**

cycle 1 で「旧経路が URL パスの形で暗黙に保証していたスコープ」を補ったが、旧経路が持っていた述語は 3 つで、新経路は 2 つしか持っていなかった。1 件ずつ後から見つかる形になると cycle 数だけ消費する。

再発防止: **差し替え前の経路が満たしていた述語を先に列挙し、新経路で 1 つずつ対応を確認する**。「1 つ補ったから済んだ」と早期に打ち切らない。旧経路が「検証していない」ことは「検証が不要」ではなく「構造的に保証されていた」を意味しうる。

**4. 同一規律の適用漏れは「2 本直して 3 本目を忘れる」形で出る**

### 手法として効いたもの

- **修正後に mutation matrix を取り直す**: 修正でアンカーの形が変わった時点で、前 cycle の mutant 定義は無効になる。同じラベルの mutation でも中身が変わるため、`^` の除去と `[[:space:]]*` の除去を別軸として測り直して初めて生存が見つかった。**修正した箇所の mutation は、修正前の軸ではなく修正後の軸で取り直す**。
- **到達可能性の実測でガードを削除する**: 防御コードが現行のデータ形状では到達不能であることを、出力を `od -c` で直接確認して確定した。「テストで固定できない条件を実装に残さない」判断の根拠になる。

- **ドキュメント修正が別種の lint 違反を増やしていないか確認する**: 「番号で指し示す」修正案をそのまま適用したら Issue/PR 番号参照が 1 件増えていた。番号に依存しない書き方へ言い換えることで、指摘の意図 (事実誤りの解消) を満たしたまま増加を避けられる。
