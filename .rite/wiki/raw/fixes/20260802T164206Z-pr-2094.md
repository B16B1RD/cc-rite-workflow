### Fix Patterns

- **散文の断定は Grep で全 call site を列挙してから書く**: 「〜だけが X を持つ」「どの経路でも Y されない」という全称・唯一性の主張は、同一 PR 内の別ファイル (SPEC / 設計ドキュメント) や Issue の Assumptions と矛盾しやすい。skill markdown は LLM が実行時に読む仕様なので、誤った系統図は後続セッションの判断を直接歪める。修正は「削除」ではなく「実態に合わせた書き換え」を第一候補にした (rationale を references/ へ退避する選択肢は、当該 skill に references/ が無い場合 1 行のためにディレクトリを新設することになり simplicity と衝突する)。
- **load-bearing なコメントは mutation テストで固定する**: 「A ではなく B と書く理由」を長いコメントで説明している箇所は、A へ書き換えても全テストが通る状態になりやすい。隔離コピー (worktree ではなく plugin ツリーの cp -a でも足りる) に mutation を当ててスイートを走らせ、Red になる assertion が実在することを実測してから完了とする。
- **corrupt-but-parseable な fixture が要るケース**: parse が「エラーだが .data は埋める」設計のとき、ヘッダ不在型の corrupt fixture では「stdout を捨てる実装」と「捨てない実装」を判別できない。判別には .data が埋まる種類の corrupt (識別子の不一致など) を作る必要がある。
- **対称な 2 ガードには対称な assertion を置く**: pr_number / loop_count のように独立した条件式で守る 2 フィールドは、片方だけ検証すると他方のガード除去が無検知で通る。
- **fail-loud と best-effort 契約は両立する**: 「失敗しても処理を止めない」契約がある経路でも、rc を捨てずに WARNING を出せば観測性は確保できる。空文字判定で代替しようとすると、失敗時にも非空の出力を返す parse 実装では検出できない。隣接コードが既に rc 付き WARNING を出しているなら、その規範に揃える。
