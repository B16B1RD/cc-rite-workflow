### Fix Patterns

cycle 7 の 8 件は「**検証機構を導入した PR が、その機構の周辺（診断文・コメント・規約文・テスト）に同型の穴を残す**」という単一の型に収まった。cycle 6 の「直したパターンを再生産するテンプレートを放置」と連続しており、移植性/検証機構を入れる PR で反復して出る構造なので経験則として残す。

1. **parser を書いたら、同じ PR 内で「その parser の入力になりうる文字列を出力する箇所」を grep する**（F-02、実測再現済み）
   `run-tests.sh` の skip 会計は「診断文が `SKIP: N` に見えるのを防ぐためサマリ行に anchor する」とコメントで明言していた。ところが同じ PR が新設した `_test-helpers.test.sh` TC-15.1 の**失敗診断**が `print_summary` の生出力を改行込みで echo するため、`SKIP: 2` が行頭に着地して自分の parser に食われた。結果、テストが 1 件落ちただけなのに「summary format drift」という誤原因が表示され、skip 総数も 0 件が 2 件と表示される。
   → **規則: 変数の生出力を診断に埋める箇所は改行を潰す**（`tr '\n' '|'`）。parser 側を緩めて解決しない（会計を FAIL 扱いにした判断自体は正しく、壊すべきは診断側の漏出）。

2. **「A を却下して B を採用した」と書くときは、却下理由が B に当てはまらないことを実測する**（F-03、3 レビュアーが独立検出）
   `| tee` を却下した理由「背景プロセスが残るとパイプが EOF を待ち続ける」は、採用した `$(...)` にもそのまま当てはまる。実測すると direct（変更前、fd 直接継承）= 0 秒、`$( )` = 6 秒、`tee` = 6 秒で、**変更前が唯一ハングしない形だった**。コメントは逆の安心を与え、将来ランナーが停止したときの調査を誤誘導する。
   → **規則: 却下理由が採用案にも当てはまるなら、それは differentiator ではないので理由から外す。** 代わりに採用案が犠牲にしたもの（ここでは hang 耐性と、CI job timeout 時の出力消失）を明記する。

3. **機械的制裁を伴う規約は「何をすると」「何が」落ちるかまで書く**（F-01、HIGH）
   規則は「skip を使え、bare echo は禁止」とだけ書いたが、実装した契約は「⏭️ 数とサマリ件数が一致しないと**スイート全体が exit 1**」で、件数抽出は厳密に 2 形のみ。`print_summary` 非使用テスト 48 本中 25 本が該当形状で、そこへ規則どおり `skip` を足すと blocking gate が落ちる。さらに実際のアンチパターンは bare `echo` ではなく `pass "... skipped"`（PASS を水増しした上で突き合わせも素通り）で、こちらが規則の対象外だった。
   → **規則: 禁止事項を列挙する前に、実際にリポジトリで見つかるアンチパターンを grep する。** 制裁の範囲（ファイル局所かスイート全体か）を必ず書く。

4. **「SoT を参照するので将来も有効」と書いたら、同じ文書内の他の記述がその抽象を破っていないか grep する**（F-04、2 レビュアーが独立検出）
   「blocking gate がどちらの leg かは ci.yml が宣言するので、この規則は入れ替わっても生き残る」と書いた段落と、「a shadowed or missing tool **on Linux** must not silently drop coverage」と Linux を名指しした規則が、同一ブロック内で共存していた。実装は後者（floor 6 箇所すべて `[ -d /proc ]`）。
   → **規則: 抽象化の宣言と具体の記述は同時に grep で突き合わせる。** 実装が具体に倒れているなら宣言を弱める側に直す。

5. **「壊れると緑が嘘になる」でテストを新設したら、同じ論拠が当てはまる他のコンポーネントを列挙する**（F-05）
   この PR は `_timeout` に専用テスト、`skip()` の計数に TC-15 を新設した。その論拠はまさに「壊れると緑が嘘になる」。ランナーの終端ロジック（skip パーサ 2 形式・marker 突合・bail 順序・exit code、約 90 行）は同じ性質を持つのにテストが 0 件だった。
   → **規則: ランナーは fixture ディレクトリへコピーして駆動できる**（コピー先を SCRIPT_DIR にすると sibling glob が未マッチになり再帰しない）。両ランナー × 4 象限で pin した。

6. **新テストは必ずミューテーションで load-bearing を確認する**（本 cycle の自己適用）
   新設した会計テストの初版は 42 assertions が緑だったが、ミューテーション（成功行から gated group サフィックスを削除）を**検出できなかった**。原因は `assert_contains` が出力全体を見ており、集計行にも同じ文字列があったため。行を特定する `assert_line_matches` を足して塞いだ。
   → **規則: 「N 件 pass」はテストが効いている証拠にならない。** 守りたい退行を実際に注入して赤くなることを確認する。3 種のミューテーション（順序 revert / サフィックス削除 / パーサ破壊）で確認した。
