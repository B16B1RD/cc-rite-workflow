### Fix Patterns
永続データを in-place で書き換える機構を足すときは、そのデータを読む consumer を全部列挙してから
実装する。書き手側のテストがいくら緑でも、consumer 側の前提は壊れる。今回は「per-cycle の
レビュー結果 JSON」を書き戻す設計で、それを読む consumer が 3 つ（収束トレンド判定・nb-sweep・
schema の派生フィールド）あり、いずれも 7 cycle の差分レビューで一度も検査されなかった。

差分レビューは「直前の変更が壊したもの」しか見ない。設計の穴は最初のコミットから存在するため、
差分に現れず永久に検出されない。cycle 数が増えても収束しないときは、指摘の粒度が下がり続けて
いないかを疑う。今回は 7 cycle かけて「どの散文をどう pin するか」に収束していた。

自分が書いた安全網が自分の変更で壊れることがある。本 PR は収束トレンド判定に「consumer 式を
ここで適用してはならない」というコメントを追加しながら、helper の書き戻しで同じ効果を別経路から
発生させていた。コメントを足すときは、その主張が自分の他の変更で偽にならないかを確認する。

「捨てない」という契約の終端は、記録先ではなく消化される場所である。配列に残っていても、
消化する側の集合から外れれば失われたのと同じ。しかも記録先には残るため、完了報告は「記録済み」と
表示して損失を隠す。

外部入力を診断行へ出すときは、その診断行より前に機械可読な marker があるかを確認する。改行を
含む値は行境界を作り、後勝ちで marker を塗り替えられる。id だけを allowlist して file / line を
素通しにしていた非対称が実際の注入面になった。
