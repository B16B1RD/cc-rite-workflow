### Fix Patterns

本 cycle の中心的な学びは 1 つ: **同型の欠陥は 1 箇所直しても同じ節に残る**。

cycle 1 で「置換マニフェストに載っていないプレースホルダ」(`{ROOT}` / `{SID}`) を修正したが、
同じ注意行ブロックの数行下にある実在確認コマンドの `$root` / `<UUID>` は手つかずだった。
`$root` は「値が解決できなかった場合」の案内文でだけ代入される shell 変数で、値が得られた
支配的経路では人間の端末に存在しない。結果、正しい値を持つ人間が実行しても guard が常に偽を
返し、「root か UUID が誤っている」と誤診されて唯一の復旧手順から遠ざけられていた。

**教訓: 修正時に grep 対象を「直したトークン名」に限定すると取りこぼす。** 「同じ節にある
同種のトークンを全部数える」ことが必要。今回は `$root` / `<UUID>` という**別記法**だったため
`{ROOT}` の grep では引っかからなかった。プレースホルダ体系を直すときは、記法をまたいだ
「人間が実行するテキストに埋まっている未解決トークン」全般を対象にする。

同じ構造がドキュメント側の**列挙の非対称**にも現れた。同一ファイルに並行する一般記述が複数
あるとき (CONFIGURATION.md の exit path テーブル・yaml コメント、別ファイルの同型テーブル)、
変更のトリガーになった 1 箇所だけに carve-out を入れると、同じ文書が自分の invariant を
否定したまま残る。**列挙は grep で数えてから直す** — 今回は 3 箇所あり、指摘されたのは 1 箇所
だけだったが 3 箇所とも同時に直した。

なお **CHANGELOG の同型記述は遡及編集しない**。過去リリースの履歴エントリはその時点の仕様を
記録するものであり、現在の仕様に合わせて書き換えると履歴としての価値が失われる。

### 「名前を出す」と「検証可能にする」は別

cycle 1 で「either が指す 2 項が未導入」と指摘され 2 項を名指しする修正を入れたが、cycle 2 で
**同一クラスの再発**として再指摘された — 2 項は名指しできたが、それを結論に繋ぐ前提
(`--handoff` を省いた set は handoff キーを削除する) が文書内で未定義のままだった。

**参照の解決可能性は「名前が出ているか」ではなく「読者がその文書だけで結論まで辿れるか」で
判定する。** 条件節を書いたら、その条件が成り立つ根拠まで同じ文書内に置けているかを確認する。

### 自己矛盾は「同じファイルの別の場所」に現れる

SPEC.md の schema 表セルが「human command が唯一の再入場経路」と無条件断定する一方、同ファイルの
別セクションは「human re-run なしで再開しうる 1 ケースがある」と例外を明言していた。どちらも
同じ PR の追加行。**長い散文セルに rationale を書き込むと、他の場所の記述との整合を追いにくく
なる** — schema 表は「セマンティクス」に絞り、設計理由は SoT へ 1 行ポインタで委譲する方が
drift も自己矛盾も減る。
