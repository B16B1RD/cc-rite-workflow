### Fix Patterns

前 cycle で 1 つのブロックに 3 種の対処（reason 語彙の分離・入力の書式絞り・エラーの
surface）を独立した追加として重ねた結果、互いに噛み合わないデッドパスと重複が残った。
「未解決なら即座に抜ける」分岐を後段に置いたまま前段の代入とループを残すと、結果が
読まれない計算が残る。エラー検出条件を rc ではなく stderr 非空にすると、同一フィルタを
2 回書く必要が生じ、実際に出力を生む側が無検査になる。対処を足すときは、既存の制御構造の
どこに入るかまで含めて設計しないと、対処そのものが次 cycle の指摘対象面になる。

テストの pin では 2 つの空振り形を実測した。(1) ファイル全体を見る `assert_grep` は、
同一文字列が他ブロックにも在ると対象行だけ消しても既存行に一致して PASS する。
(2) `grep -c` は行数しか数えないため、同一行に重複させる変異を見逃す。前者は
`assert_grep_in_section` でブロックへスコープし、後者は `grep -o ¦ wc -l` で出現回数を
数えることで両方向に機能する pin になる。
なお `assert_grep_in_section` の end アンカーに `^#### ` のような見出しパターンを使うと、
start 行自身が end にも一致して awk flip-flop レンジが 1 行で閉じる。end は直後の
散文行やコード行にアンカーする。
