### Fix Patterns

**規範文を新設したら、その規範文を自分自身に適用して確かめる**。本 PR は「hook 表の各行の Purpose は当該 event に登録された全 script を名指しすること」という契約文を新設したが、その表の 7 行中 5 行が新設した契約を満たしていなかった。同期を要求する側が同期されているかを確かめる視点が抜けると、契約文の追加そのものが新しい違反を生む。

**修正方針は「機構の追加」より「要求範囲の縮小」を先に検討する**。上記の違反に対し、5 行に script 名を足す（追加）ではなく、要求文を複数 script を束ねる event に限定する（縮小）を選んだ。単一 script の event は event 名から script が一意に決まるため名指しは冗長で、要求の本来の目的は限定後も満たされる。追加で直すと、その追加自体が次 cycle の新しいレビュー対象面になる。

**同期対象の列挙が複数ある機構では、片側追加が「検出されない状態」を作らないか毎回確認する**。setup の LEGACY 経路は「走査対象 event の列挙」と「必須 hook 集合」の 2 つの列挙を持ち、後者にだけ Stop を足した結果、旧パスの Stop hook が残っていても走査対象外で検出されず、必須側は script 名の存在だけを見るため missing にもならず、Decision logic が「up to date」と判定して修復経路に入らない経路ができていた。列挙を足すときは「この列挙に無いと何が検出されなくなるか」を列挙の直後に書き残すと再発を防げる。

**例示列挙には非網羅マーカーを付ける**。helper の呼び出し元を「several skills (A, B)」と書くと、実際には 7 スキルから呼ばれていても読者は 2 件が全部だと読む。`e.g.` を付けるか全列挙するかを選ぶ。

**実測アンカーの種別ラベルは正規形を使う**。`Verification: static_analysis => ...` は種別ラベルが `repro` / `failing_test` 以外のため実測必須ゲートが「未判定」として blocking のまま残す。静的検証でも `repro` を使う。降格されないので判定結果は変わらないが、実測の記録としては不正確になる。
