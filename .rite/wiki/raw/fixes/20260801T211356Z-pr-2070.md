### Fix Patterns

**「要検証」は調査コストが高いときの逃げ道であって、断定を避ける万能の安全策ではない。**

前 cycle で「下流ツールが逸脱形式を受理するかは断定しない」という方針を採り、ドキュメントに「要検証」注記を置いたうえで「閲覧できない場合は形式を変換してください」という是正手順まで添えた。しかし上流実装を読むと、そのツールは当該ファイルを走査対象から**明示的に除外**しており、形式は結果に一切影響しない。つまり「未確認の争点」として提示した命題は、確認すれば偽と分かるものだった。指示に従った利用者は空振りし、真因は別のまま残る。

- **教訓 1**: 上流がオープンソースで API 1 回・数十行で読める場合、「要検証」のコストは高くない。断定を避ける判断の前に、まず読めるかどうかを確かめる。
- **教訓 2**: しかも同じファイルの別節が既に正しいモデルを書いていた。**断定を避ける前に、自リポジトリ内の隣接記述と矛盾していないかを grep する。** 矛盾していれば、少なくとも片方は既に検証されている。
- **教訓 3 (副次)**: 是正手順を添える注記は、前提が偽のとき「無害な保留」ではなく「積極的な誤誘導」になる。前提が不確かなら手順は書かない。

**段落内で列挙集合を再掲するときは、冒頭の集合と機械的に照合する。**

手順書の同一段落が、冒頭で「契約は A / B / C と同一」と D を除外しながら、末尾の括弧で「A / B / C / D も同じく〜」と D を含めて断定していた。D は構造が違うため断定は偽。LLM 向け手順書では、この種の**括弧内の再掲**が最も矛盾を生みやすい — 本文を書いた後に補足を足すとき、冒頭のスコープ限定を読み直さずに書くため。

**新設した出力フィールドは producer と consumer の両側を pin する。**

新しい stdout フィールドについて producer 側の emit だけを assert し、その値を読む唯一の消費者 (完了レポートの note 展開表) は無防備だった。展開表から条件が消えても全 assertion が緑を通る = フィールドが誰にも読まれなくなる変更を検出できない。同ファイルは別の箇所で consumer を静的 pin する慣行を確立していたのに、新フィールドにだけ適用されていなかった。**producer の assert は「値が出ること」しか保証せず、「値が使われること」は保証しない。**

**「宣言」と「検査」の片側だけが存在する状態を、宣言の側から探す。**

cycle 3 の 5 件中 3 件は、コメントや手順書が「こう振る舞う」と宣言しているのに、それを固定する assertion が無い形だった (マスクは削除ではなく置換 / 除外の判定単位は行ではなくサマリー / 新フィールドに消費者がいる)。いずれも既存の別経路には対称の pin が存在した。**レビューでも修正でも、コード中の「〜すること」「〜と同一にする」という宣言を grep して、その宣言を破る変異が kill されるかを確かめる方向が効率的。**
