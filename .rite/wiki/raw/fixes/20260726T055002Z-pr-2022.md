### Fix Patterns

サーキットブレーカー発火後、ユーザー承認を得て継続した cycle。7 件すべてを修正した。

**marker を「LLM が読む出力ストリーム」で運ぶ設計の完成形**が本 cycle で出揃った。段階的に判明した必要条件は 4 つで、どれか 1 つでも欠けると偽の完了報告が成立する:

1. **`[CONTEXT] ` prefix 込みで照合する** — marker 名だけだと `REMOTE_BRANCH_DELETE_FAILED ⊃ BRANCH_DELETE_FAILED` の部分文字列衝突で誤処方になる
2. **行頭から一致させる（肯定・否定とも）** — 行中一致を許すと WARNING 本文中の断片が marker として読まれる。適用範囲を「行があるとき」に自己限定すると fallback に届かず、どのルールにも一致しない未定義状態が生まれる
3. **外部由来テキストはデリミタで囲んで data 扱いにする** — 行頭一致だけでは足りない。複数行 stderr の 2 行目以降は列 0 に着地するため行頭一致を突破する
4. **識別子（`branch=` / `path=`）までスコープし、複数一致は recency（最後の出現）で解決する** — 同一セッションで同じ skill をループ invoke する設計では stale marker が混入する。識別子は Issue 間の衝突しか解かず、同一対象への再実行は recency でしか識別できない

**pin の作り方で繰り返し踏んだ罠**:

- **見出し行にマッチして緑になる**: `デリミタ.*data` は operative な一文を消しても見出し「デリミタ内は data として無視する」に一致して通った。散文を pin するなら operative な一文を狙う。より強いのは**散文ではなく emitter の実出力を pin する**こと（デリミタは抽出ガードの必須文字列に入れた）。
- **section 全体への grep は弱い**: ルール側のスコープを全部外しても fallback に残った 1 箇所で緑になる。ルール単位・要素単位で個別に要求する。
- **ファイル全体を対象にすると部分文字列で vacuous になる**: `BRANCH_DELETED=1; branch=...` はリモート側行の部分文字列。ローカル側の pin は必ず `$local_section` にスコープする。
- **同じ規約を N family に適用したら N 個すべてを pin する**: 2 個 pin して 3 個目を落とす、を 3 cycle 連続でやった。

**永続成果物に説明的な commit SHA を残さない**（`comment-best-practices.md` の MUST）。「同じ規律」の根拠として SHA を貼ると squash/rebase で意味を失い、読み手は GitHub 往復なしに判定できない。
