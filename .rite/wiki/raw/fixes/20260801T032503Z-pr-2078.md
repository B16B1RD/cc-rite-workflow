### Fix Patterns
cycle 4 の fix。3 サイクル連続で「指摘への対応が新しい退行を生む」パターンが続いた後、
方針を「追加ではなく削除」へ切り替えた cycle。

効果的だった修正戦略:
- **成果物の存在を完了の証拠に使わない**: 中断された cross-device mv (copy+unlink) は宛先に断片を
  残すため `[ -e "$dest" ]` は「始まった」ことしか示さない。「完了した mv だけが source を消す」
  という不可逆な副作用 (`[ ! -e "$src" ]`) を述語に使うと、rename でも copy+unlink でも正しく判定できる。
- **observability フィールドは consumer を決めてから足す**: sentinel に足した `consumed=` は consumer が
  ゼロで、4 状態すべてが既存 WARNING から導出可能だった。撤去でドキュメント 3 箇所の同期義務と
  4 状態の pin がまとめて消えた。
- **防御を足したら同じ turn で mutation 実測する**: 追加した AND 項ごとに「その項だけを外すと red に
  なるテスト」を用意する。実測せずに「3 条件どれを欠いても誤判定する」と書いたコメントは、実際には
  1 項が無検査で、次サイクルの指摘面になる。
- **閉じた列挙は実装が経路を増やすたびに嘘になる**: 診断メッセージの「原因は N つです」を開いた列挙
  (「既知の経路。網羅ではありません」) に変え、各項へ観測可能な切り分け条件を付ける。

過剰反応の傾向 (cycle 1-3 で観測):

  「保存成功なのに gate が恒久的に落ちる」非収束を生んだ。**guard を足すより、危険な値を受け取らない
  インタフェース (path ではなく id token) に変える**方が失敗クラスごと消える。
- 実装を変えたら診断メッセージ・テストの pin・rationale ドキュメントが同時に dangling reference 化する。
