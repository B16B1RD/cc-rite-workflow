### Fix Patterns

前 cycle が足した 2 つの追加（節境界規則と見出し退避）が、それぞれ新しい負債を生んでいた cycle。
どちらも**追加パッチではなく削除**で解いた。

1. **早期終了と END フォールバックを併用したら、print 点を END へ一本化する**: 本体規則でも
   print する形にすると、awk の `exit` が END を実行する性質に対して「print する全規則がフラグを
   立てる」という**規律**で二重出力を防ぐことになる。規律は (a) 説明コメントを要求し、
   (b) 腕ごとの pin を要求し、(c) 腕が増えるたびに両方が増える。**本体規則を「行番号を変数へ
   記録するだけ」にして print を END の 1 箇所に集約すると、二重出力が構造的に起こりえなくなり、
   規律・コメント・腕ごとの pin という 3 つの問いが同時に消える。** 前 cycle の指摘「3 腕中 1 腕が
   未 pin」は、pin を足すのではなく規律そのものを不要にして解いた。

2. **診断メッセージの原因列挙は、退避先が増えるたびに実態とずれる**: 「節に値行が無い」という
   新しい原因クラスを、その原因を列挙していない既存の WARNING 文へ合流させた結果、
   **崩れていない正しい見出しを名指しながら存在しない記法崩れを探させる**診断になった。
   列挙に 1 項目足す道もあったが、同じ列挙を持つ散文 site との同期義務が増えるだけで、
   次の退避先が増えれば同じ指摘が再発する。**runtime 診断は「どこを見ればいいか」を示せば足り、
   原因の分類は SoT（docstring と reason 表）が持てばよい** — runtime 側の列挙を撤去した。

3. **fixture は実運用の body 形状にする**: 記法 2 のテスト fixture が全て「対象節が 1 行目か
   直前が散文行のみ」で、**先行見出しを持つ body を 1 本も持たなかった**。そのため節境界述語から
   連言の片腕（`f &&`）を落とす崩れが素通りし、Section 見出しを持つ Issue のほぼ全域で機能が
   死ぬ欠陥を検出できなかった。**新しい述語の pin は「規則を消す」変異だけでなく「連言の片腕を
   消す」変異でも検証する** — そのためには fixture が実運用の構造を持っている必要がある。

4. **行番号を pin する fixture は、対象行を 1 行目に置かない**: 期待値 1 は「定数化した実装」とも
   一致するため、算出をどう壊しても落ちない空振り assert になる。2 行目以降に置き、かつ
   「最終行の NR」とも異なる値になるよう配置する（本件では見出しの後ろに空白のみの行を足した）。
   同じファイルが既に別の fixture 群へ課していた規律を、新設分だけが満たしていなかった。

5. **指示語（前者 / 後者）で対比を圧縮した説明文は、実測せずに書くと帰属が逆になる**: 同クラス
   （コメントが実測を騙る）は 4 cycle 連続で再発し、しかも**同種を潰した commit の中で新しい
   個体が生まれている**。対比構造は指示語で圧縮せず、両方のサブケースを明示的に書き分ける。

6. **不変条件を守る機構が 2 つになったら、SoT の因果節を両方に更新する**: 「同じ記入漏れが記法で
   reason 分裂しない」という不変条件は、当初「値の開始文字クラス」だけで成り立っていたが、
   節境界の追加で 2 機構の連言になった。SoT が 1 機構しか書いていないと、読み手が節境界を
   「冗長」と判断して外し、分裂が再発する。

7. **reviewer が作る mutation worktree は orchestrator が回収する**: reviewer は READ-ONLY 制約で
   `git worktree remove` を実行できないため、隔離ツリーが `$TMPDIR` に蓄積する。本 run では
   8 個が残留し、`pr-cycle-cleanup.sh` は `mutation_worktrees=0` と報告した（同 helper の走査条件に
   `/tmp` 配下の detached worktree が含まれない）。fix 側の後処理で `git worktree list` を確認して
   明示回収する必要がある。
