### Fix Patterns

1. **「レコードを丸ごと再生成する」方式は、対象行の同定述語を一意性まで検証しないと破壊的になる**（CRITICAL、2 レビュアーが独立検出）
   部分更新（特定セルだけ書き換え）を「行全体の再生成」へ単純化したとき、対象行を決める述語が「キーを**含む**行」のままだった。実データにはサマリー列に他レコードへの相互参照リンクを持つ行があり、1 キーが最大 3 行に一致した。全行再生成は一意性を前提にしているため、別レコードを丸ごと上書きして消す経路が開いた。しかも同じ手順が「列位置を数えるな」と書いていたため、唯一の識別シグナルを契約側が禁じていた。
   教訓: 部分更新を全行再生成へ単純化するときは、**同定述語をキーの出現位置（第 1 セル等）まで anchor する**。「キーを含む」で書くと、そのキーが本文中に相互参照として現れるデータで必ず誤爆する。複数一致は fallback（1 件目を採る）ではなく **fail-loud で中止**する — silent に誤った行を書き換える経路を残さない。

2. **述語をレンダラの解釈に委ねると、実データで対象集合が縮む**（MEDIUM、1 レビュアーが単独検出）
   「テーブル行」を対象と書いたが、これは GFM のブロック意味論に依存する。実 index の節内には空行が 2 本あり、GFM は先頭ブロックだけをテーブルと解釈するため、登録行 298 のうち 135 行が段落として描画されていた。厳格に読むとその 135 行は重複ガードと重複削除の両方から漏れ、更新のたびに行が増える。
   教訓: 構造化テキストの対象範囲は**位置ベース（見出しから次の見出しまで + 行頭文字）で定義**する。「レンダラがテーブルとみなす行」は実データの些細な瑕疵（空行 1 本）で集合が変わる。あわせて瑕疵そのものを次サイクルで直す healing 手順を入れると、漸次是正されて対象集合が収束する。

3. **optional フィールドを唯一の値ソースにすると、持たないレコードで既存値が消える**（HIGH、2 レビュアーが独立検出）
   「値はすべて frontmatter から取る」と SoT を一本化したが、当該フィールドは schema 上 optional で実データの 55%（164/298）が持っていなかった。全行再生成と組み合わせると、それらのレコードでカタログ側の蓄積値が空で上書きされる。
   教訓: SoT を宣言する前に**そのフィールドが schema 上必須か / 実データの充足率**を確認する。optional なら値ソースを順序付き（SoT → 当サイクル生成値 → 既存値保持）にし、**空文字での上書きを明示的に禁止**する。あわせて SoT 側を補完する手順（frontmatter への書き込み）を上流ステップに追加しないと、「SoT を更新してから実行せよ」という指示が不在フィールドに空振りする。

4. **同じ欠陥を 3 レビュアーが別々の切り口で見つけることがある。切り口の違いが修正範囲を決める**
   同定述語の欠陥を、2 名は「ページ列 anchor の欠落」として、1 名は「GFM 解釈依存」として報告した。前者だけ直すと 135 行漏れが残り、後者だけ直すと相互参照リンクの誤爆が残る。両方が同じ 1 文の修正で閉じた。
   教訓: 複数レビュアーが同一箇所を別の言葉で指摘したら、**それぞれが指す失敗経路を列挙して両方カバーする修正**を作る。片方の言葉に寄せると、もう片方の経路が残る。
