### Fix Patterns

1. **代理値を役割から外すときは、その値が偶然満たしていた invariant を列挙してから捨てる**:
   cycle 1 で run 境界を counter から実データ pin へ移した際、旧実装の配列スライスが counter=0 で
   構造的に空集合を返す（＝発火不能）副次的保護を見落とし、pin 不在経路で誤発火する退行を入れた。
   「この式が偶然守っていた性質」を洗い出さないリファクタは、安全機構では退行に直結する。

2. **同じ代理値を「方向を分けて」再導入すると、捨てた保護と避けたい失敗を両立できる**:
   実在数が counter を**超える**＝他 run 混入（判定を降ろす）、**下回る**＝run 内の欠落
   （降ろさず続行）。cycle 1 は両方向をまとめて「降ろす／降ろさない」に倒したため、片方で
   誤発火、もう片方で恒久無効化を起こしていた。非対称な失敗には非対称な扱いを与える。

3. **fix-introduced 欠陥は「同じ cycle で追加した兄弟コード」の粒度差として現れる**:
   cycle 2 の指摘 9 件のうち 5 件が cycle 1 の fix 由来で、内訳は WARNING 文面の断定、
   assert の粒度非対称、marker の消費者ゼロ、reason の値域漏れ — いずれも「同時に足した
   別の箇所では正しくやっている」形だった。fix の自己レビューでは、追加した要素同士を
   横に並べて粒度が揃っているかを見るのが最も歩留まりが良い。
