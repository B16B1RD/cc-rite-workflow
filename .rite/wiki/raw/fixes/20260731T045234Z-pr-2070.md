### Fix Patterns

指摘 3 件はいずれも「前 cycle の修正が新規に導入した欠陥」で、修正作業に固有の失敗形が 3 つ揃って現れた。

1. **ガードの precondition に、守りたい対象ではなく手近な代理値を使う**（最重要）。前 cycle で「index.md のエントリを 1 件も認識できない = 検出失敗」ガードを足したとき、発火条件を index.md 自身の内容ではなく stdin (`pages_list`) の非空性に置いた。ところが手順書側は「`pages_list` が空でもこのステップは skip するな」と明示的に定めており、その理由が「初期化直後や list 構築失敗時に指摘が無言で 0 件になるのを防ぐ」ことだった。**ガードが無効化される経路とガードを必要とする経路が完全に一致していた**。修正は判定材料を「リンク形状の行はあるがリンク先が想定と認識できない」へ移し、終端アクションの戻り値を 3 値から 4 値へ拡張した。教訓: **precondition は守りたい対象と同じものを測る。代理値は相関が切れる場所——すなわち守るべき場所——で沈黙する**。

2. **1 箇所を実装へ揃えると、同じ文書内の別定義と新たに矛盾する**。前 cycle で SPEC の helper 説明に「テーブル / 箇条書きを行単位で判別」と書いたが、同じ SPEC 内の対象ファイル定義行は「箇条書き」のままだった。develop 版には矛盾が無く、修正の `+` 行が新規に作った。教訓: **記述を実装へ揃えるときは、その記述が依拠している別の定義も同時に見る**。grep で対象ファイル名を引くと定義行が出る。

3. **指摘へ答えようとして手順書本体に説明を足すと、rationale 退避規約を破る**。前 cycle で追加した設計根拠が references 側とほぼ逐語で二重化していた。修正は本体を 3 文へ削り 1 行ポインタへ置換、同時に参照先へアンカーを整備してポインタ形式（`#anchor` 付き）へ統一した。**規約違反は「指摘に丁寧に答えようとした結果」として入り込む**ため、修正時こそ規約を確認する。

### Verification Practice

修正が本当に効いているかを、3 種の変異（precondition を元へ戻す / 新しい条件だけ削除する / arity 検査を無効化する）で実測し、いずれも新 TC が kill することを確認した。特に「元へ戻す変異」は、その修正が回帰テストで守られているかを直接測る唯一の方法で、修正と同時に必ず実行する価値がある。sed による変異はクォート起因で silent に失敗しうるため、**変異後の該当行を表示して適用を確認してからテストを回す**（今回 1 回目の変異適用が失敗し、未変異のまま「全 pass」を得ていた）。
