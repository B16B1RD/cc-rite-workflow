### Fix Patterns

**「塞いだつもり」の assert は、削除するか塞げない範囲を明記する**。片側から抽出した期待値で等値を取る symmetry pin に「両側が同じ壊れ方をした場合も固定する」という assert を足しても、期待値自体が片側から来ている以上、同時 drift では等値が保たれて通る。実測（両側に同一の `tail -1` → `tail -n 1` を当てる）で 4 assert すべてが緑になり、その assert が先行 assert から論理的に含意される dead code だと確認できた。検出力が同じなら削除が正しい — テストコード中の偽りの能力主張は冗長性より有害で、次に読む人へ誤った安心を渡す。value pin が本当に要るなら期待式をハードコードするしかなく、それは「期待値をテスト内にハードコードしない」という設計方針との衝突として明示的に判断すべき論点になる。

**正規化で 2 つの値を同一視したら、同一視の前提そのものを別 assert で固定する**。producer と validator で被演算子の変数名だけが違う（`$body` / `$CONTENT_FILE`）とき、共通プレースホルダへ正規化して式を比較するのは妥当だが、その正規化は「両者が同じファイルを指す」という前提を暗黙に置く。式の比較ではその前提を確かめられない。実測: 呼び出し側の `--content-file "$body"` を別変数へ変えても全 62 assert が緑のまま通った。正規化を導入した変更が、同時にその前提を検証する 1 行を持つべきだった。

**レビューの実測主張も再現を取る**。同一 reviewer から内容の異なる 2 通のレビューが届き、片方の「被演算子改名が素通りする」という repro 付き主張は、こちらで同じ変異を当てると 2 assert が fail して再現しなかった。`Verification: repro` アンカーが付いていても、判断を変える指摘は自分で再現してから採否を決める。再現した指摘（同時 drift の素通り）は 2 名の reviewer が独立に同じ結論へ到達しており、そちらは信頼度が高い。

**テストケースの識別子はファイル内の既存慣習に合わせる**。同ファイルの T-01〜T-07 が `(AC-N)` で別 Issue の AC に 1:1 対応しているところへ `(#2480)` を混ぜると、どの仕様文を検証しているか読み取れなくなる。ヘッダと本文コメントで別表記になっていた点も含め、`(#2480 AC-1..AC-3)` へ統一した。
