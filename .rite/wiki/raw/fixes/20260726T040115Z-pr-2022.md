### Fix Patterns

**「規約を新設する修正」は自分がその規約を守れているかの検査を同時に要求する**。本 cycle の 6 件のうち 3 件は前 cycle の修正が作った自己矛盾だった:

- リモート側 fallback を「marker 不在 = 未確認」へ反転し禁止文まで書きながら、7 行上のローカル側 fallback を `x` のまま残した（同一 bash fence 内なので同じ条件で同時に不在になる = 同一到達条件に正反対の意味）
- 「負の assertion は非アンカーにする」規約をファイル冒頭に新設した同一コミットで、追加した TC-5 の負 assertion にアンカーを付けた
- consumer 契約の静的 pin として TC-6 に足した grep が判定値でなく**言い回し**まで拘束し、AC を満たしたままの言い換え 7 種すべてで赤くなった

対処として得た経験則:

1. **散文を pin するテストは「判定値・識別子・処方コマンド」に限定する**。語尾・助詞・行末アンカーを含めると、補足の追記だけで偽陽性になる。正規表現を緩めて対処すると pin が摩耗するので、最初から契約部分だけを拘束する。修正後は「手動削除→手動で削除」「止められない→抑止できない」等の言い換え mutation で**緑のまま**であることを実測して確認した。
2. **非対称を解消する修正は、対称化の相手側も同じコミットで直す**。片側だけ直すと「直し忘れ」ではなく「意図的な非対称」として読まれ、次 cycle で矛盾として再指摘される。
3. **fallback の意味は emitter の設計に依存する**。「4 経路すべてが marker を出す」ステップ 5 では marker 不在 = 未確認だが、「成功時は marker を出さない」ステップ 4-W では marker 不在 = 成功でよい。同じファイル内で規約が分かれるときは、その前提の違いを fallback 自身に明記しないと後続の保守者が「直し忘れ」として揃えてしまう。
4. **`git ls-remote <pattern>` は slash 境界の tail 一致**。`refs/heads/{branch}` を渡さないと入れ子 ref に誤ヒットして rc=0 になる。一方 `git push --delete` は tail 解決しないため、その rc=0 は「削除試行 → 失敗」に落ちて偽の残作業を生む。**3 cycle・4 reviewer が独立に到達してようやく finding に昇格した** — 複数 cycle で同じ調査推奨が繰り返されたら finding へ昇格させるシグナルとして扱う。
5. **abort する事前検査は、原因クラスごとに診断文面を分ける**。「抽出アンカーの破損」と「artifact 側の契約消失」を同じ文面で報じると、検出すべき退行を「テスト側の問題」に誤帰属させる。
6. **回帰 pin は本番と同じ前提条件をテストに仕込む**。full refname 要求は、衝突 ref (`wip/{branch}`) を origin に置いた状態で TC を走らせて初めて pin になる。
