### Fix Patterns

cycle 2 の 17 件は、cycle 1 の修正が「守りたい性質」ではなく「その時点の形」に係留していたことに集約できた。修正の型も 1 つに収束する — **検査したい性質そのものを述語にする**。

**(1) pin は denylist ではなく allowlist で書く**。「特定の文言が出現しない」は、同じファイルが既に使っている別表記（英語 → 和文）で自然に回避できた。「pass 行はすべて規約文言を含む」に変えると、言い換えでも検出できる。同様に、インデント幅・出現回数・区間内の総数といった「偶発的な形」への係留は、無害な整形で false positive を出しつつ契約破壊は見逃す最悪の組み合わせになる。

**(2) 誤検出を避けるために pin の対象を絞ると、守るべき側が外れる**。誤検出対策で 6 gate を 1 gate に縮退させた結果、invariant が本当に守りたい「最後の gate」が対象外になった。**anchor を強くする（行頭 anchor）ことで、対象を絞らずに誤検出だけを消せる**。

**(3) 区間スコープの pin は終端 anchor の存在を先に固定する**。start 不一致は loud に落ちるが end 不一致は無音で EOF まで区間を伸ばし、隣の節の同名行を拾って通ってしまう。

**(4) 同種の防御は grep で全適用箇所を列挙してから当てる**。制御文字の無害化を 9 箇所中 6 箇所にしか当てなかったため、残り 3 箇所（うち 1 つは trap 設置前で最悪の位置）が同じ入力に無防備なまま残った。

**(5) enumeration を増やしたら基数を書いた散文を探す**。reason を 8 → 10 に増やして 3 箇所の数詞が取り残された。**数詞と列挙の二重管理をやめる**（「上記 N 種」→「上記の表の全 reason」）と drift が構造的に起きない。

**(6) 新設 gate の Always execute は上流の hard fail 経路と衝突しうる**。上流が「この場合は gate に進まない」と規定する一方、gate 側に legitimate skip 行が無いと、LLM はどちらの指示に従っても仕様どおりにならない（上流指示違反 か livelock）。兄弟 gate が持つ skip 行を必ず対称に用意する。

**(7)「同一の述語」を主張するなら選択規則まで同一にする**。gate が読む sentinel が会話に複数存在する設計では「どれを本 cycle とするか」が述語の本体。片側だけがそれを書いていれば対称性は成立しない。

**(8) fail-fast の ERROR text は、その状態に至る全経路を想定して書く**。「未実行」と断定すると、契約違反で早期 exit した経路が同じ ERROR に落ちたとき、ACTION（同じ手順の再実行）が収束しない指示になる。retained flag の reason を先に確認させる診断分岐を ACTION の先頭に置く。
