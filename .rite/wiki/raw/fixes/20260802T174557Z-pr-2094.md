### Fix Patterns

- **同じ失敗様式が 3 サイクル続いたら、内容ではなく「記述の形」を疑う**: cycle 1 は skill 側の散文、cycle 2 も同じ散文、cycle 3 は hook 側のコメントと診断文 — 場所は毎回違うのに、指摘はすべて「列挙・断定を持つ記述が、対象が 1 つ増えただけで偽になる」という同一の形だった。実態へ列挙し直す修正は次の cycle で再び偽になる。**列挙を持たない記述へ縮める**と、その指摘面ごと消える。
- **コメントで call site を数え上げない**: 「env で渡す caller は X のみ」は、同じ PR が call site を 1 つ足しただけで偽になった。代わりに「env override も flow-state 読み取りも伴わない更新経路では〜」のように、条件で書けば call site が何個あっても正しい。
- **観測性の限界は call site の形式ではなく helper 自身の性質で説明する**: 「call site が `2>/dev/null` で捨てるから届かない」は (a) 数え間違える (b) 退避形の call site を見落とす (c) follow-up Issue のスコープを no-op にする、を同時に招いた。「helper が rc=0 を返すため、捨てるか rc ゲートで握るかに関わらず届かない」なら call site を数えずに済み、remedy も正しく導ける。
- **診断文が断定してよいのは、その文を書く位置で確定している値だけ**: WARNING を値の確定前に置くと、後段の override で決まる field まで「既定値へ倒します」と断定してしまう。位置を動かせないなら、確定しない対象は条件付きで書く。
- **肯定と否定の assertion が同じリテラルを別々に持つと、否定側が静かに死ぬ**: 文言変更で肯定側だけ追随すると、否定側の grep は何にも一致せず「出ていない」と誤って PASS する。照合文字列は 1 変数に集約して両方から参照する。
- **否定 assertion は「その否定が最も破られやすい入力」で書く**: 「誤報しない」を非既定値 fixture だけで検証すると、production 最頻の既定値状態での誤発火 mutant が生存する。
- **mutation は適用前に一致件数を assert する**: コメント中に同じ文字列があると置換対象が 2 件になり、意図しない箇所を壊す。適用前に「ちょうど 1 回一致」を確認し、適用後に `bash -n` を通す。
