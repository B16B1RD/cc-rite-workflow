### Fix Patterns

**「step が走ったか」を後段で機械判定するとき、cycle 識別子の供給元がその step 自身だと、検出したい唯一の状態でだけ判定が成立しない。** 本 cycle の blocking はこれ 1 件で、3 レビュアー全員が独立に同じ欠陥へ収束した。

具体的には、timings ファイルのパスに cycle 一意の epoch を付けたところまでは正しかったが、その epoch を鋳造するのが検出対象の step 自身だった。step を飛ばした cycle には本 cycle のパスが存在せず、解決規則「末尾 epoch が最大のもの」は前 cycle の値を返す。TMPDIR がセッション内不変で cleanup 経路も無いのでそのファイルは実在し、存在検査は真になる。**判定が成立するのは「step が走った cycle」だけで、走らなかった cycle では必ず誤る。**

**同じ idiom でも極性で安全性が反転する**: 既存の pending marker 群（8.0.3 / 8.0.4）は同じ「末尾 epoch が最大」規則を使うが、あちらは**不在が pass 条件**なので stale ヒットは loud に落ちる。本ガードは**存在が pass 条件**のため stale ヒットが fail-open する。idiom を借りるときは pass 条件の極性を確認する。

**対処は機構を増やさず減らす方向で取れた**: 識別子を step の外（既に確定している commit SHA）から取ると、marker 1 本と解決規則 1 つを削除できて、かつ検出が全 cycle で成立する。「ガードを足す」ではなく「ガードの前提を外から与える」。

**副次的な教訓**: 挙動を変える fix は、その挙動を**根拠として引用している設計記録**も stale にする。本 cycle では「この block の出力は X だけ・値はセッション不変・skip しても下流に齟齬なし」という anchor 不採用理由の 3 文のうち 2 文が偽になっていた。設計記録は「なぜそう決めたか」を書くので、前提が崩れると次の改修が誤った土台に載る。grep で自分の変更対象を引用している箇所を洗う。
