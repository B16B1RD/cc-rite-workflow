### Fix Patterns

本 cycle の 3 件はすべて `documentation_consistency` で、コード修正はゼロだった。パターンは 2 つ。

1. **優先順位表を散文化すると、表が扱わない失敗経路が落ちる**。docs 2 ファイルの記述は Issue §4.3「値の優先順位」表（値が存在する 3 経路）を散文にしたもので、同表が扱わない第 4 の経路（既存 frontmatter が parse 不能 → 既定値へ倒れる）が転記されていなかった。**設計文書の「優先順位表」は正常系の列挙であって全経路の列挙ではない**。散文化する際は実装の失敗経路を別途 grep して補うこと。本 PR は自身でその経路に WARNING とテストを実装していたため、実装と文面の断定範囲だけがずれる形になった。

2. **修正対象がリポジトリ内に無い finding のアンカー**。「PR 本文の検証記録が stale」という finding は、`file:line` を書く先がリポジトリに存在しない。レビュアーはテストファイルをアンカーに使ったが、そのまま fix へ流すとテストファイルを編集しに行く。**アンカーと修正対象が一致しない finding は `suggestion` の冒頭で「このファイルを変更するな」と修正手段（`gh pr edit`）を明示する**ことで誤修正を防いだ。

**レビューサイクルが進むと PR 本文が実体から乖離する**: cycle 2-5 で追加されたテスト 37 アサーションが PR 本文に反映されず、「31 PASS / T-01〜T-07」のまま実体は「68 PASS / T-01〜T-12」になっていた。数値の向きは保守側だが、後続が再実行すると記録との食い違いを実装退行と誤認する。fix サイクルが複数回走る PR では、本文のテスト結果セクションも成果物として同期対象に含める。
