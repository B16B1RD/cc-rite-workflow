### Fix Patterns

rite 自身のワークフロー定義 PR で観測された、修正側の有効パターン:

1. **「新設した規約を自分自身に適用する」を修正方針の軸にする**: 12 件の指摘のうち 8 件は
   「新規経路 6.1.d が既存 6.1.a/b/c の machine-enforced gate 規約と reason 表登録規約から
   外れて追加された」という単一の根本原因に還元できた。個別に潰すのではなく規約側から
   逆算すると、修正漏れ (reason 表への新規 reason 登録漏れ等) が構造的に減る。

2. **SoT 同期は双方向に書く**: detection 側 (assessment-rules.md) に制約を書いても、
   reviewer が実際に読む authoring 側 (_reviewer-base.md / reviewer-prompt-generator.md) に
   無ければ機構は空振りする。修正時は両側に相互参照を張り、「この制約の反対側 SoT は X」と
   明記して次回の drift を検出可能にする。

3. **静的 parity テストの追加では semantics は守れない — mutation で検証する**: 述語文字列を
   anchor にした parity テストは、3 site を一貫改修する mutation では素通りする (実測: 112 pass
   のまま正準形状が fallback に落ちた)。修正後は実際に mutation を当てて「新しい assertion が
   落ちること」を確認する。今回は 3-site 一貫 mutation で 4 件、P0 all→any で 2 件の追加失敗を確認。

4. **fallback ではなく「中止 + WARNING + reason」を選ぶ**: 空 body での PATCH は marker を消して
   検索を恒久破綻させるため、既定値で続行する fallback ではなく投稿中止が正しい。
   Fail-Fast Response Principle のチェックリストを通すと、防御コード追加ではなく
   「処理を止めて理由を出す」が選ばれるケースが多い。

5. **スコープ外の類似パターンは伝播修正しない**: 伝播スキャンで見つかった
   `-gt 0 ] 2>/dev/null` の他 2 箇所は pre-existing かつ 1 件は Issue の Non-Target File
   だったため修正せず調査推奨に落とした。revert test (「この PR を revert したら消えるか」) が
   伝播適用の可否を機械的に決める。
