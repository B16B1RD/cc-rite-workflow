### Fix Patterns

cycle 2 の 2 件はどちらも **cycle 1 の修正自体が生んだ欠陥**で、根本原因は 1 つに収束した。

1. **失敗状態のクリアを、失敗の記録より前に置いた（HIGH）**: 「再実行でループを再開できる」ために cycle counter を発火分岐でリセットしたが、その分岐は発火を記録する sentinel より手前にある。両者の隙間で turn が終わると、**発火が無記録のまま counter だけ 0 になる**。同じ set が継続 handoff も消しているため Stop hook は停止を許可し、次の recover は満額の予算でループを再開する。修正前は counter が上限のまま残ることでこの窓が自己修復しており、リセットの導入が意図せず安全網の自己修復性を外していた。**教訓: 「失敗を記録する」処理と「失敗状態をクリアする」処理が別ステップにあるなら、クリアは記録の後に置く。前に置くと、その隙間での中断がすべて無記録の成功に化ける。** 縮退の向きで設計を選ぶ判断基準としても使える — クリアを後に置けば、途中で落ちたとき「まだ失敗状態」に留まる（停止側）。

2. **Asymmetric Fix Transcription（同型分岐への invariant 未転記）**: cycle 1 で「marker に載せる counter は実効（永続）counter と一致させる」を reset の成功・失敗の両分岐に入れたが、構造的に同型の increment 分岐には転記しなかった。**教訓: invariant を分岐に足したら、同じ変数を同じ目的で書く他の分岐を grep して全部に適用する。** 本 repo はこの型に parity test という名前まで付けているのに、markdown 埋め込み bash 側は sweep 対象外だったため機械検出も効かなかった。

### Design Constraint Encountered

より構造的な解（発火時に FINALIZE handoff を置いて Stop hook にステップ 6 到達を強制させる）は、Stop hook の `FINALIZE:*` arm が block は行うものの reason 文面が別ステップ（完了通知）を指すため流用できず、文面の是正は hook 本体の改修を要した。その hook は Issue の Non-Target（MUST NOT modify）だったため断念し、「クリアを記録の直前へ移す」という窓の縮小＋縮退方向の是正に留めた。**教訓: 汎用 handoff 機構を後から別用途へ流用するときは、block 判定（prefix 非依存）と reason 文面（prefix 依存）が別軸であることを確認する。前者だけ見て「使える」と判断すると、誤った指示を出す経路を作る。**

### Verification Approach

散文 PR の修正でも **A/B 対比の実測**が有効だった。修正後の埋め込み bash と、修正前相当（sed で 1 行戻した版）を同じ stub 環境で走らせ、「fire → ステップ 6 未到達で中断 → resume」の 1 シナリオで `REFIRE=1 → ITERATE_CB=fire`（修正後）と `REFIRE=0 → ITERATE_CB=ok; cycle=1`（修正前）を並べて観測した。**「直った」ことの証拠は、修正後の正しい出力ではなく、修正前との差分で示すほうが強い。**
