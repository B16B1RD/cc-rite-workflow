### Fix Patterns

散文が実行契約であるリポジトリで「分岐を 1 つ廃止する」PR の指摘を直したときに効いた修正戦略。

1. **marker 値は消費側の分岐数と 1:1 に対応させる**: 新設した `RESET` marker を「reset が失敗した」という**発生側の事実**で 1 値に定義したことが欠陥の根本だった。消費側 (停止通知) は「即時再発火したか」で排他分岐する必要があり、1 値では両立できず、片方の状況で事実と逆の説明が出る。marker を `failed-refire` / `failed-stale` に分割し、発生側ではなく**消費側の分岐**で値を切ったことで解消した。新しい enum 値を足すときは「これを読む側はいくつに分岐するか」を先に数える。

2. **stderr を捨てた出力の下流で原因を推測してはならない**: `>/dev/null 2>&1` で helper の診断を捨てたうえで、その失敗の復旧手順に「書き込み権限を確認」と単一原因を書いていた。捨てた情報を推測で埋めると誤誘導になる。既存の canonical パターン (mktemp で stderr 退避 → 失敗時 `head -5` 表示) が同一リポジトリ内の sibling skill にあり、それに揃えるのが最小コストだった。**原因を断定する文言を書く前に、その原因を判別する情報が実際に届いているかを確認する**。

3. **波及調査は「廃止した語彙」と「フィールド名」で走査する**: 本 PR の波及漏れ 3 件はすべて「新語彙 (機械的に停止) で grep したため旧語彙の記述が残った」型。新語彙は自分が書いた側にしかヒットしない。廃止語彙 (「ユーザー委譲」「AskUserQuestion」「3 択」) と、挙動を記述するフィールド名 (`cycle_count`) の両方で再走査すると拾える。とくに**同一ファイル内の別段落**と**スキーマ表/フィールド定義**が漏れやすい (散文とスキーマ表は読者が違うため語彙が揃わない)。

4. **総論と各論の矛盾は「削除」ではなく「適用範囲の限定」で直す**: 節冒頭の総論 (複数の設定キーを束ねる) が 1 キーの挙動変更で偽になるケース。総論を消すと他キーの説明が失われるため、限定句を足す。ただし**限定句を足す前に、他キーで総論が今も真であることを実際に確認する** (今回は `max_implementation_rounds` が到達時に AskUserQuestion を出すことを実装で確認してから限定した)。

5. **伝播スキャンは「同じ事実を述べる第 3 の箇所」を探す**: 指摘された 2 箇所を直した後、同一ファイルの Placeholder Legend に同型の drift が残っていた。指摘は網羅ではなくサンプルとして扱い、修正パターンで再 grep する。
