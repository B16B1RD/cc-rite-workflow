### Fix Patterns

SKILL.md のインライン bash を helper へ抽出する refactor のレビュー指摘 12 件を 1 cycle で解消した。指摘は 1 つの根本原因から派生していた（抽出がプロセス境界を新設した一方、消費側の「marker 不在 = 成功」契約と検出網をその境界に合わせて設計しなかった）ため、修正も境界の両側を揃える形に収束した。

1. **新設したプロセス境界には rc → marker の変換を置く**: インライン bash を helper へ移すと「helper が起動しない」経路（usage error / rc=127）が新規に生まれる。呼び出し側が rc を捨て、消費側が「marker 不在 = 成功」と読む設計なら、未実行が完了として報告される。抽出元の中に同じガード（内側の helper に対する rc → marker 変換）が既にある場合、それを外側の新境界へ持ち上げるのが最小修正になる。
2. **fail-loud の追加は呼び出し側の正規経路と衝突しうる**: 抽出時に「必須引数の検証」を足すと、抽出前は正常に処理していた入力（スキルが公式にサポートする状態、例: Issue 番号未識別）が marker なしで落ちる。fail-loud は消費側の規則とセットで設計しないと挙動退行になる。
3. **引数パーサの空文字列トークンは値として shift する**: `case "${1:---}" in --*) ;;` のような「次がフラグなら値なし」判定は、明示的な空文字列 `""` を消費せずに残し、次の周回で "unknown option" に落とす。トークンの形を変えただけで同じ欠陥が再発する。`if [ "$#" -gt 0 ]` で引数の有無を先に見てから、`--*` だけを値なしとして扱う。
4. **消費側が glob で marker family を scope するなら、新 marker は prefix ごと外へ出す**: `PREFIX_*` の glob で family を絞る消費側に対し、同 prefix の新 marker（`--dry-run` 用など）を足すと、判定表のどの行にも一致せず fallback にも落ちない未定義状態を作る。コメントで「family を分離している」と書いても分離は成立しない。`DRY_RUN_` のように prefix 自体を変える。
5. **静的検査の regex に行頭アンカーを使うと実行行を見落とす**: `^[[:space:]]*git branch -d` は `if cmd; then` / `|| cmd` / `elif x=$(cmd)` の位置にある実行行に一致しない。抽出前のコードに当てて一致数を確認すると、ゲートが検査したつもりの対象を最初から見ていないことが分かる。コマンド境界 `(^|[;&|[:space:]])` で照合し、対象は bash フェンス内に限定する（散文には手動復旧コマンドが引用として現れる）。
6. **assert のチャネルを実装の出力先と一致させる**: `assert_not_contains` を stdout だけに当てても、対象の文字列が stderr にしか出ないなら構造的に常時 pass する false positive になる。「この assert はどの実装で落ちるか」を問うと検出できる。
7. **テスト fixture は suite の環境前提に合わせる**: `run-tests.sh` が session id env を unset して各 sandbox の `.rite-session-id` へフォールバックさせる設計の場合、fixture にそのファイルを置かないと単体では env 由来で通り suite でだけ落ちる。単体 PASS / suite FAIL は fixture の hermeticity 不足を疑う。
8. **部分文字列の assert は識別子の包含関係を確認する**: `BRANCH_DELETED=1; branch=X` は `...; branch=X; via=squash-merged` の部分文字列でもあるため、通常削除と強制削除を区別できない。`via=` が続かないことを併せて assert する。
