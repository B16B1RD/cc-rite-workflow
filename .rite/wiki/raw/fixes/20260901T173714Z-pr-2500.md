### Fix Patterns

cycle 3 は blocking 1 件のみで、その 1 件も「機構を畳んだときに取り残した入力の行き先」だった。
blocking 推移は 6 → 3 → 1。

1. **機構を畳むときは「消したものが受けていた入力の行き先」を数える**。判定を bash から prose へ
移す際、旧 bash が持っていた `rc≠0 → failed → Phase 7 に列挙` という写像だけが落ちた。新しい prose の
判定は母集団を marker 接頭辞行に限定したため、helper が起動せず接頭辞行を 1 本も出さない経路が
規則の外へ抜けた。Wiki 経験則「機構を畳んだら付随物も同時に畳む」の裏返しで、**畳む側でも入力の
全ケースを列挙し直す**必要がある。畳む前の bash が持っていた分岐（rc / marker / 正常）を表に書き出し、
畳んだ後の prose がその全行に行き先を与えているかを突き合わせるのが確実。

2. **同一コミット内の sibling 節との非対称は、設計判断か取り残しかを判別する強い証拠になる**。
本件では 4.4 が「または上記 WARNING が出た」という選言を持ち 4.6 が持たなかった。同じ cycle で同じ
著者が書いた 2 節が食い違っているなら、まず取り残しを疑ってよい。逆に非対称が意図的なら、その理由を
1 句添えておくと次 cycle のレビュアーが再導出しなくて済む。

3. **negative control の行スコープ盲点は positive pin で塞ぐ**。`grep` は行単位なので
`<helper>.*2>"$` の形は helper 名とリダイレクトが同一物理行にある場合しか赤くしない。長い helper
呼び出しを `\` で折るのが家風のリポジトリでは、退行が取る自然な形がちょうど死角に入る。
negative control を積み増すより、**呼び出し行そのものを固定する positive pin**（`^bash <helper> ... 2>&1`）
を置くほうが確実で、行継続・別名のどちらにも耐える。cycle 2 で同じ欠陥クラスを潰した修正が、
その修正で導入した control に同じ盲点を持っていた（欠陥クラスの自己再生産）。

4. **pin は「規則本体」へアンカーし、戒めの一文や散文の言及に張らない**。「除外形で書く」ことを
pin したつもりで、規則の隣に置いた戒めの一文（`**失敗語彙を列挙して判定しない**`）を照合していた。
規則本体を列挙形へ書き換えて戒めだけ残す変異は緑のまま通る。同様に、marker 名は helper 契約を説明する
散文にも出るため、名前の presence を pin すると判定表の左辺を rc 単独へ差し戻しても検出できない。
**ラベルが名乗る挙動を担っている行そのもの**（判定表の行、規則の帰結節）へアンカーする。
