### Fix Patterns

前サイクルの fix が**自分で回帰を作り**、それをレビューが実測で捕まえた。学びは 3 点。

1. **「包含するから置換できる」は範囲を限定して初めて正しい**。総尺ガードを最短シーン尺ガードへ置換したとき、`x < min(d) ⟹ total > 0` は成り立つが、**それは n>=2 のときだけ**だった。判定ごと `n>=2` の分岐内へ移した結果、単一シーン経路のガードが丸ごと消えた。包含の証明を書いたら、**その証明が成立する範囲と、実装で判定が走る範囲が一致しているか**を別途確認する。今回は前者が n>=2、後者も n>=2 になってしまい、n==1 が両方から漏れた。

2. **ガードを増やす前に「必要量が位置で変わる」構造を疑う**。最短シーン尺では中間シーンを守れなかった（クロスフェードは繋ぎ目ごとに食うため、端は 1 回・中間は 2 回食われる）。ここで「中間シーン用のガードを追加」すると 3 本目のガードになり、次のサイクルで 4 本目を呼ぶ。**位置ごとの必要マージンを回す 1 ループ**にすると 3 種が 1 つに畳まれ、しかも n==1 が必要マージン 0 として自然に含まれた。ガードが増える兆候は、多くの場合パラメータ化できる次元を見落としている合図。

3. **子プロセスの終了検査は close の `code` ではなく ChildProcess の `exitCode`/`signalCode` を見る**。signal で殺されると `code` は `null` のままなので、`code !== null` の検査は素通りする（実測: SIGKILL で `close: code=null signal=SIGKILL`、`exitCode=null signalCode=SIGKILL`）。自前の追跡変数を捨てて Node 自身の状態を読むと、変数が 1 本減り、かつ signal 経路が同じ述語で捕まる。

補助: コメントを直したのに**運用者が実際に読むエラーメッセージだけ**が古い主張のまま残った。同じ事実を述べる箇所は「コメント・ドキュメント・エラー出力」の 3 面あり、人間の目に触れるのは 3 番目。1 面だけ直すと、直した側が矛盾の証拠になる。
