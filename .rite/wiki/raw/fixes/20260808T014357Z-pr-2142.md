前 cycle で「番人を立てる」ために書いたコメントと assert 自身が、次 cycle の blocking 6 件のうち
4 件の発生源になった事例への対応。得られた経験則。

1. **「診断へ外部入力を埋め込む」と決めた瞬間に、長さ上限・CR 除去・改行畳み・制御文字中和の 4 段と「そのどれが pin されているか」という問いが同時に発生する**: 本件では 3 cycle かけてこの 4 段を積み上げ、最後に中和モードが C1 (CSI U+009B) を素通しすることが判明した。閉じるには共有 helper (30 caller) への新モード追加が要る。**そこで埋め込みをやめ「行番号だけ報告する」形へ単純化したところ、4 段と 4 件の指摘がまとめて消えた**。診断の目的が「切り分け」であって「内容の提示」でないなら、外部入力を診断チャネルへ通す経路自体を持たないほうが安い。**足すコストは 4 段だけでなく、その各段の番人と、番人の正しさの証明まで含む。**

2. **assert のラベルは契約の宣言である — 述語がそれを満たさなければ「虚偽主張」クラスの欠陥**: 「all three AND-conditions contiguous」と名乗りながら 3 条件のうち 1 対しか見ない assert は、読み手に「3 条件すべてが守られている」と誤認させる。**新しい assert を書いたら、ラベルが約束する全ての壊れ方に mutant を当てる。1 つでも生存したら、ラベルを狭めるか述語を広げるかの二択で、放置は選べない。**

3. **隣接性を「対」で検査すると検査していない対が必ず残る — ブロックごと 1 回で照合する**: `grep -A1 <2 行目>` で 2→3 の隣接だけを見る形にしたため 1→2 が無防備だった。表ヘッダ直後の N 行を 1 回の抽出で取り出して期待値とまとめて照合すれば、対の数だけ assert を足す必要がなく、条件が増えても期待値を 1 箇所直せば済む。

4. **`assert_not_contains` の counterweight は「可変部分」を needle にする**: 「制御文字が出ない」の裏返しとして「可読部分は残る」を置いたが、needle が script 側の**固定接頭辞**だったため、出力から payload を丸ごと削除しても両方 green になった。counterweight は payload そのもの（行番号・抽出値など、実装が壊れれば変わる部分）を needle にしなければ counterweight にならない。

5. **共有ヘルパーの欠陥を主張するときは、影響範囲を grep で数えてから書く**: 「常に PASS する」「全 caller に同じ縮退がある」と書いたが、実測では start 不一致で empty section を検出して FAIL し、縮退するのは終端に意味を変える escape を含む caller だけで既存 28 caller 中 0 件だった。**誤った一般化は「28 箇所の一斉修正」か「正常な assert 全体への不信」のどちらかを誘発する。** 主張の範囲は数え、数えた結果を主張に書く。手段の判断（この helper を使わない）が正しくても、理由が誤っていれば別の欠陥として残る。

6. **同一 diff 内の行番号参照は、自分自身の挿入で必ずずれる**: `:157 / :170 の house pattern と揃える` と書いた時点で、同じ diff が上流に 8 行を挿入していたため参照先は `:160 / :177` だった。意味的アンカー（「記法 1 / 記法 2 の抽出式」等）で書けば腐らない。
