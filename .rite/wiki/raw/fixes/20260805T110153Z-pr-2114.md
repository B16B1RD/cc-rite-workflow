### Fix Patterns

cycle 2 の blocking 10 件のうち **8 件が cycle 1 の修正自体が持ち込んだもの**だった。「修正が次のレビュー対象面を作る」形が 4 系統あり、いずれも**修正時に数え忘れた対象**が原因。

**(1) 指摘された 1 箇所だけを塞ぐと、同じ性質の兄弟が無検査で残る**

cycle 1 で「TC-4a の stderr assert が vacuous」と指摘され `^  mkdir` へ anchor し直したが、同じ helper が持つ stderr 転送は 3 本 (jq / mkdir / mv) あり、mv は無検査のまま残った。さらに cycle 2 で rm 側にも捕捉を足したことで 4 本目が生まれた。**修正の対象が「同じ性質の兄弟を持つか」を数えてから直す** — 指摘は 1 本しか名指ししないが、守るべき invariant は通常その族全体に及ぶ。有効な問いは「この pin が守る対象は、このファイルに何本あるか」。

**(2) helper を厚く pin しても、その呼び出し元は別の面**

helper 本体を 60 assert まで固めた一方、唯一の呼び出し元 (skill の bash block) を固定する層はゼロだった。呼び出しを旧形へ revert しても全 suite が green。**「機構を足した」commit では、機構本体だけでなく「機構が呼ばれていること」も pin する**。skill ⇄ helper の coupling は静的 pin (該当 skill 区間を grep して呼び出し 1 本 + 旧形 0 本を assert) で足りる。

**(3) 新しい reason / marker を足したら、同じ commit で consumer の分岐表も更新する**

`_undecidable` を「失敗ではない (failed に数えない)」と helper が宣言しながら、既存の失敗 marker family に載せた。consumer が reason 非依存の flat 判定だったため、何も失敗していない cycle が完了報告で「残作業」として描画される。**reason 非依存の consumer に対して reason を増やすこと自体が意味論の衝突を生む**。同じリポジトリに per-reason 表を持つ先例があるなら、それを新 reason にも適用する。

**(4) 保存期間を延ばす変更は、保存先の到達可能性を配布先の既定構成で確認する**

「削除」を「退避」に変えた結果、脆弱性の全文が merge 後も残るようになった。開発元リポジトリでは `.gitignore` が効いていたが、**配布先のセットアップが生成する `.gitignore` には当該エントリが無かった**。PR コメントから外した全文が、より恒久的な公開面 (git repo) へ移る経路ができていた。**retention を延ばす変更では「その保存先は誰から見えるか」を、開発元ではなく配布先の既定構成で確認する。**

**(5) pin を広げたら、広げた後の allowlist 内要素だけで同じ違反を組めないか試す**

cycle 1 で placeholder 抽出の文字クラスを広げて空白入り placeholder を捕捉できるようにしたが、今度は「allowlist 済みの placeholder だけで組んだ表外の再掲載」が捕捉できなかった。**mutation matrix に「pin が拾える形」だけを並べると穴は露見しない** — pin を広げた直後に「広げた後の許可要素だけで違反を作れるか」を必ず試す。負の対照 (旧 pin + 同一 mutation で全 green) を取ると、pin が blind だったことを実測で示せる。

**(6) guard を足す前に同名・同目的の既存 helper を grep する**
