### Fix Patterns

本 cycle の指摘はすべて「前 cycle の削減が実測済み silent failure を再導入した」型だった。
削減の可否判定を「Issue のエラー表に載っているか」の 1 段だけで行ったことが根本原因で、
**同じ PR の過去 cycle が実測を根拠に追加したガード**を落とした。削除判定は 2 段必要:
(a) 契約表に対応するか、(b) 削除で実測済み silent failure が復活しないか。(b) の確認を
省くと、自分で宣言した維持基準を自分で破る。

有効だった修正戦略:

- **入口検査は class predicate で書く**: `case "$x" in ''|*[!0-9.]*|*.*.*)` のような文字クラスの
  否定は defect class を表現できず、`.` 単体や `0` が抜ける。「正の数値であること」を
  正規表現 + 数値比較で直接述語化すると、one-off の穴が構造的に閉じる
- **照合層を新設せず、測って報告する**: 「解析値を報告する + 別に照合層を足す」ではなく
  「1 回実測して報告と検査の両方に使う」と、機構が増えずに誤情報の発生源が消える
- **契約 MUST には自動 pin を置く**: fixture を置くだけでは、ガードを変異させても検証コマンドが
  green のまま通る（実測で確認）。非ゼロ終了・診断メッセージ・出力物の不在の 3 点を assert する

  いずれも実測で fail-loud の成立を確認済み
