### Fix Patterns

cycle 5 (最終サイクル)。前 cycle で「防御を足す修正が次の指摘面になる」型を自覚して削除方向へ
振った結果、今 cycle は別の型が 3 件出た。共通するのは **「直した」の範囲を実装の 1 点に限定し、
その判定を読む側・測る側まで辿っていない** こと。

効果的だった修正戦略:
- **判定を直したら、その判定を読む下流を全部辿る**: signal handler は 3 条件 AND で正しく
  「保存済み」を判定していたが、その結論を `json_saved` へ書き戻していなかったため、同じ trap が
  `saved=false` を emit していた。**述語の正しさと sentinel の正しさは別の性質**で、後者は
  「その値を読む consumer が何を案内するか」まで確認しないと検証できない。
- **防御を足したら、その項だけを外す mutant で red になるまでが完了**: `--pending-id` の
  allowlist と `neutralize_ctrl` は、どちらを削除しても全 assertion が green のままだった。
  既存 arm が case の brace 節で先に捕捉されるため、allowlist 本体に assertion が 1 本も
  届いていなかった。**「N pass / 0 fail」は防御が測られている証拠にならない** — case 分岐の
  ように「先に別の節で捕まる」構造では、テストが到達していない節が無検査のまま残る。
- **塞いだ範囲を実測より広く書かない**: `set -C` (noclobber) が拒否するのは既存**通常
  ファイル**だけで、FIFO には効かない。「TOCTOU を塞ぐのは set -C」と書いたコメントは、
  先置きケースしか塞いでいない実装に対して過大な保証だった。実測 (300 回並走で 18/300 が
  rc=124) が範囲を確定させた。**保証を書くなら、その範囲を実測で確定してから書く**。
- **選択規則は「主語」まで含めて 1 つの規則**: 「本 cycle のもの = 末尾 epoch が最大のもの。
  空文字なら空文字を渡す」の後半は、空文字が epoch を持たないため前半の規則で順序付けできず、
  主語 (どの cycle の空文字か) を書かないと過去 cycle の値を受理しうる。同じ規則を検査側は
  主語付きで書いていたため、**規則の写し間違いが片側だけに残った**。

観測: 実装側の 1 行を直す指摘でも、レビュアーに mutation 実測を明示的に依頼すると、静的 pin の
抜け (assertion が届いていない防御) が定量的に出る。
