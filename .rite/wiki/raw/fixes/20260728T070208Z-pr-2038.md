### Fix Patterns

本 cycle の 9 件はすべて「gate と、それを検証する pin の設計」に集中しており、修正も 2 つの
設計原則の適用に収束した。

1. **分類の境界は「原因」で引く。「検出位置」で引くと同種の違反が漏れる**

   「caller 契約違反は機械強制で差し戻す / 外部要因は非ブロッキング」という設計判断を、実装が
   exit code (trap 設置の前後) で近似していた。結果、trap 設置後に検出される決定論的な caller
   契約違反 (本文検査 3 段) が gh outage と同じ扱いになり、gate を素通りした。修正は明示フラグ
   (`retain_pending_marker`) を導入して境界を原因側へ移すこと。

   一般化: 「差し戻せば収束するか」で分類する。収束する class (caller が入力を作り直せば直る)
   は差し戻し、収束しない class (network / rate-limit / 権限) は非ブロッキングで通す。実装上の
   検出位置は分類の根拠にしてはならない。

2. **不変条件が「配置」なら pin も「配置」で書く。件数 pin は移動を検出しない**

   `grep -cF '<literal>' <file> == 1` は、対象の文を別スコープへ移動しても件数が保たれるため
   緑のまま通る。守りたいのが「関数 X の内側にこの文が 1 本ある」なら、区間を awk で解決して
   **区間内 1 本 / 区間外 0 本**を等値 assert する。区間外の件数は「全体 − 区間内」で求めると、
   「移動しても総数は変わらない」という変異の性質を素直に写せる。

3. **同型の coupling は網羅を確認する。2 本 pin していて 3 本目が抜ける**

   3 者 (生成側 / 削除側 / 検査側) で結合するパス導出式のうち 2 本には「片側から抽出して他方に
   照合する」pin があり、3 本目だけ無かった。同種の coupling を列挙して網羅を確かめる工程が要る。

4. **prose gate に実行可能コードを入れた時点で「実行テスト不能」の前提は失効する**

   markdown 埋め込み bash を静的 pin だけで守り続けると、AC の検証欄が別テストを誤って対応付けた
   まま「検証済み」の外観ができる。fence を awk で抽出して実行するテストは容易に書けるので、
   実行可能になった時点で分岐を実際に走らせる。

5. **write 側と read 側の条件は同時に更新する**

   lookup 述語に条件を 1 つ足すときは、write 側の本文検査にも同じ条件を足す。片方だけだと、
   条件を満たさない本文を投稿し続けて次 cycle の lookup が自分の投稿を miss し、記録が増殖する。

6. **人間可視の文字列は同定に使えない。機械専用 sentinel を使う**

   前方一致 + author 一致でも、同一 author が marker で始まる見出しの人間コメントを書けば
   PATCH 先を奪われる。rendered view に現れない HTML コメントを needle にすると、人間が
   書き写す経路が構造的に存在しなくなる。「本文全体への contains は引用に弱い」という否定理由は
   人間可視文字列に対するもので、機械専用トークンには当たらない。

7. **上位仕様書で単一経路を断定しない**

   「この値は X から来る」と書いた経路が、同じ PR の別契約により当該値を構造的に一度も供給しない、
   という自己矛盾が起きた。read-route が複数あるなら列挙し、現行契約でどの経路が実際に値を
   供給するかまで書く。

### 手法上の知見

- **mutation は隔離コピーで当て、negative control を必ず併置する**: `cp -r plugins "$W/plugins"` で
  作業ツリーを汚さずに 7 件の positive control と 2 件の negative control を実測した。positive だけだと
  「何を変えても落ちる過敏な pin」を作り込んでも気付けない。
- **mutation matrix は pin を変更した PR の本文にその場で書く**: 後追い更新の運用にすると、本 PR で
  実際に起きたように「最終 commit 分だけ matrix に無い」状態が生まれ、AC の裏付けが欠ける。
