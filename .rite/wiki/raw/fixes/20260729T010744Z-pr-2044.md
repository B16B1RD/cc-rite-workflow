### Fix Patterns

「機構を削除した後の掃除」に固有の型が 4 件すべてを説明する。

1. **削除時は旧語彙で grep する（追加時は新語彙で足りる）**: 機構を消したのに、その機構を名指しする散文が 3 箇所残った。同一ファイル内で「override を持たない」と「override が counter をリセットする」が共存する自己矛盾になり、4 レビュアー全員が独立に検出した。追加のときは「自分が書いた新語彙」で grep すれば波及先が見つかるが、削除のときは新語彙が存在しないので、**削除した識別子・機構名そのもの**で grep して 0 件になるまで掃く必要がある。今回は `override` / `発火後再実行` / `which resets the cycle counter` の 3 パターンで網羅した。

2. **削除は下流の条件式を孤児にする**: override を消したことで、それに依存していた通知の付加条件が主経路を外した。判定に使っていた marker が「特定の分岐でしか値を持たない」性質だったため、その分岐を通らなくなった経路で条件が成立しなくなった。**削除した分岐に依存する条件を、条件側から逆に辿る**。今回は「全経路で無条件に計算される変数」を marker に載せ替えて解決した。

3. **`2>&1` capture + 「rc≠0 のときだけ表示」は観測性を下げうる**: helper が rc=0 のまま WARNING を出す経路があると、リダイレクトが無かった頃には届いていた診断が消える。capture の導入は観測性の向上とは限らない — **表示条件を rc に紐付けた瞬間、rc=0 の診断は捨てられる**。診断の emit は if/else の外に置き、rc とは独立に surface する（成功時の capture は通常空なので `-n` guard でノイズは出ない）。

4. **手順書に書く運用コマンドは、同じ手順書の他の約束を壊さないか確認する**: 手動リセット手順に書いた `--phase pr` が、3 行下で約束していた「`/rite:recover` でも再開できる」を壊していた（recover は phase で routing するため別コマンドへ飛ぶ）。文書に書くコマンドも副作用を持つ。
