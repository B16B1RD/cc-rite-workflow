**同一セッションで同じ skill をループ invoke する設計では、marker を識別子までスコープしないと stale marker が後続の判定に混入する**。`/rite:batch-run --merge` は Issue ごとに `/rite:cleanup` を同一会話で呼ぶため、先行 Issue の失敗 marker が後続 Issue の完了報告を汚す。marker が `; branch=X` を持っているのに照合側が marker 名までしか見ていなければ、スコープは実質存在しない。**評価順序の入れ替えは解にならない** — 失敗先頭なら stale な失敗が実成功を潰し、成功先頭なら stale な成功が実失敗を潰す。どちらも嘘の報告になるので、識別子でスコープするしかない。

**pin は「section 内のどこかに文字列がある」形にすると弱い**。本 cycle で `branch=` スコープの pin を追加したとき、最初は section 全体への grep 1 本にしたため、ルール側のスコープを全部外しても fallback に残った 1 箇所で緑になった。mutation を投入して初めて気づいた。**ルール単位・要素単位で個別に要求する**こと。

**「必須文字列」の pin はコード行だけに現れる形に狭める**。`push origin --delete` は同じ抽出範囲のコメント（「一方 `git push origin --delete` は tail 解決せず…」）だけで充足されるため、コマンド本体を消しても pre-check を素通りしていた。説明文に登場する語をそのまま必須文字列にすると、その説明文が pin を無効化する。

**AC が「A と B を区別して記述」を要求するとき、片側だけの pin では半分が無防備**。否定表現（できない側）だけを検査していたため、「できる側」を丸ごと削る整理で緑のまま通った。両側を独立に pin する。

**診断文面の分離は、分離した先に契約文字列を残すと意味がない**。前 cycle で群を 2 つに分けたのに契約文字列を群 1 に残したままにしたため、誤帰属が解消していなかった。分離したら「その群に属さないものが混ざっていないか」を確認する。
