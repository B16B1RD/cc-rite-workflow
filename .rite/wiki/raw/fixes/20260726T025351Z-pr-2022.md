### Fix Patterns

marker contract を持つ実装（emitter が `[CONTEXT] X=1` を出し、consumer が `[CONTEXT] X` でアンカー照合する）に対するテストは、**marker 名ではなく emitter が実際に出力する literal 全体を pin する**。marker 名だけを pin すると prefix / 区切り / アンカーの退行が丸ごと素通りする。本 cycle の指摘はまさにこれで、emitter から `[CONTEXT] ` を落とす mutation がスイートを 8 passed / 0 failed で通過し、consumer 側では全ルール不一致 → fallback（marker 不在 = 成功）発火で「削除失敗が完了として報告される」false-success が復活していた。

派生する経験則:

1. **正の assertion はアンカーし、負の assertion はアンカーしない**。「marker が出ていること」の検査は consumer と同形まで厳密化する。「marker が出ていないこと」の検査は非アンカーの方が捕捉範囲が広く、アンカーすると弱くなる。両者を機械的に揃えてはいけない。
2. **`grep` のパターン内で `[CONTEXT]` を literal 扱いするには `\[` `\]` エスケープが必須**。BRE ではブラケット式に解釈され「C/O/N/T/E/X のいずれか 1 文字 + `] ...`」を探す別物になる。pin を追加したつもりで無効化される典型。
3. **静的検査（抽出必須文字列）と runtime assertion の二重化**は、それぞれ独立に mutation で赤くなることを実測して初めて二重化と言える。本 cycle では片方ずつ無効化した mutant で個別に検証した（静的のみ: rc=1 / runtime のみ: 3 failed）。
4. mutation は隔離 worktree（`git worktree add --detach`）で行い、親ツリーの working tree を一切触らない。検証後に `git worktree remove --force` で回収する。

本 PR は 6 cycle を要したが、cycle 2〜6 の指摘はすべて同型（「テストの assertion が検証対象を実際には pin できていない」）だった。テスト追加時は「この assertion が守っている invariant を壊す最小の mutation は何か」を先に決め、それで赤くなることを確認してから緑にする順序が有効。
