### Fix Patterns

「機構を削って解く」単純化の直後の cycle。指摘 9 件のうち 4 件は、前 cycle が**削除を正当化する
ために書いた注釈**が発生源だった。得られた経験則。

1. **「なぜ消したか」の考古学は、消した機構と同じ速度で腐る**: 機構が消えれば、その機構への
   言及も消すのが正しい。「4 段 idiom が要るがモードが無いので廃止した」という経緯説明は、
   廃止後の読み手には要らない一方で**主張の正しさを検証され続ける負債**になる (実際、その
   主張が虚偽であることが次 cycle で指摘された)。残すのは「現在のコードを読むのに要る 1 文」だけ。
   **主張を狭めて生き延びさせるより、経緯ごと削るほうが安い。**

2. **交替腕を 1 本落とすときは、その腕だけが救っていた入力クラスを列挙してから決める**:
   「見出しを名指ししても是正先にならない」は**値行が存在する場合にしか成り立たない**。
   値行が 1 行も無い空セクションでは見出しこそ唯一の是正先で、そこまで一括で落としたのが
   過剰修正だった。単純化は「削りすぎ」の向きにも失敗しうる。

3. **awk の `exit` は END 規則を実行する — early-exit と END フォールバックの併用は二重出力になる**:
   `f && /^#/ { print h; exit }` と `END { if (f) print h }` を併用すると正常系で `3\n1` を出し、
   呼び出し側の数値 guard が改行込みの値を非数値として飲み込んで**診断が丸ごと消える**。
   併用するなら **print する全規則が「出力済み」フラグを立てる**。

4. **レビュアーの提案パッチは指摘と同じ強度で検証する**: 本 cycle では 2 つの独立した提案が
   どちらも欠陥を持ち (片方は誤帰属を残す、片方は正常系を壊す)、7 ケースの実測比較で初めて
   合成形が確定した。**指摘の実測アンカーは「欠陥が実在すること」を示すが、suggestion 欄の
   実測は誰もしていない。** 統合側が提案を走らせる工程を省くと、次 cycle の fix が壊れた
   パッチを適用して新しい blocking を生む。

5. **`grep -qE` に渡すパターンの裸の `|` は交替演算子 — `^` 単独腕が全行に一致して常に PASS する**:
   Markdown の表行を pin する assert を書いた際にこれを踏み、mutation で初めて生存が判明した。
   ERE を取る assert helper に表行を渡すときは `\|` を必ずエスケープする。**同じ欠陥クラス
   (「番人が番をしていない」) を修正した cycle の中で、別の形で再生産した** — 新しい assert は
   書いた直後に mutant を当てる以外に検証手段がない。

6. **awk のデフォルト FS は `\r` を含まない — CRLF 入力で「空行」判定が壊れる**: `f && NF` は
   CR だけの行を `NF=1` = 非空と数える。是正は述語側ではなく**入力捕捉時に CR を 1 度落とす** —
   述語ごとに直すと同型欠陥の非対称が残る。1 行で両側が閉じるなら、pre-existing の側を副作用で
   閉じるのはスコープ超過ではない (その旨を commit message に明記する)。

7. **コメントに件数を焼き込むと、その数はコミットの瞬間から腐る**: 「hooks/ 側 30 ファイルと同形」は
   どの数え方 (37 / 34 / 33) とも一致しなかった。正しい数へ直しても同じ問題が再発するので、
   件数ではなく SoT (helper の header) を指す。

8. **片方の site に節境界を入れたら、同じ述語を持つ対称サイトを必ず見る**: 診断側にだけ節境界を
   入れた結果、抽出側は空セクションを越えて次節見出しを値として捕捉し続けていた。しかも
   読み飛ばしクラスの都合で**英字見出しのときだけ**捕捉が成立し、reason が「見出し語の言語」で
   分裂していた (日本語見出しでは absent、英字見出しでは invalid)。伝播スキャンで検出。
