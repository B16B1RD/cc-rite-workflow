### Fix Patterns

本 cycle の 6 件は「ガードが書かれているのに構造的に発火しない」という 1 つの欠陥クラスに 4 件、
「テストのラベルが名乗る挙動を pattern が検証していない」に 3 件（重複あり）が集中した。

1. **rc を pipeline 末尾で取ると fail-loud が dead code 化する**。`var=$(cmd | sort) || rc=$?` の rc は
最終段のもので、`sort` は空入力でも 0 を返す。埋め込み bash block は Bash tool 呼び出しごとに
`pipefail` OFF の fresh shell で起動するため、この経路は既定で開いている。修正は rc を持つコマンドを
パイプから外す capture-first（`raw=$(cmd)` → `rc=$?` → 整形は後段）。`set -o pipefail` を block 冒頭へ
置く形でも rc は伝播するが、capture-first なら pipefail の有無に依存しない。同 block の 1 行下に
「取得失敗と 0 件を畳まない」と自己宣言していても、bash 側がそうなっていなければ意味を持たない。

2. **プラグイン自身の PreToolUse hook が自プラグインの skill 定義をブロックする**。`select(.x != null)` は
`pre-tool-bash-guard.sh` の `jq-not-equal-null` が実行前に deny するため、記述どおりには一度も走らない。
truthiness（`select(.x)`）が canonical。契約テストが「行の形」だけを grep していたため 68 PASS のまま
素通りしていた点が本質で、**実行可能性を pin しない静的テストは実行不能な記述を緑にする**。

3. **非ブロッキング helper を rc だけで判定すると残置が完了として報告される**。「全運用経路で rc=0、
部分失敗は marker のみ」契約の helper（`cleanup-pr-state-purge.sh` / `flow-state.sh reap-issue`）は
`REVIEW_CLEANUP_PARTIAL_FAILURE=1` や `WARNING: reap-issue:` 行でしか失敗を通知しない。新しい呼び出し側を
書くときは、同じ helper を呼ぶ hardened sibling（本件では `skills/cleanup/SKILL.md` の
`{review_cleanup_check}`）の判定表を必ず突き合わせる。marker 判定を持たない caller が増えると、
sibling が持つ検出がその caller でだけ失われる。

4. **契約テストの assertion は「ラベルが名乗る挙動」を pattern が実際に照合しているかで検算する**。
素の語（`停止する` / 設定キー名 / コメント冒頭リテラル）を pattern にすると、同セクション内の無関係な
文や第 1 文だけで充足し、AC の `Then` を反転させても緑のまま通る。判定表の行そのもの（行頭のテーブル
区切り + 帰結）へアンカーし直すのが有効。検算は隔離コピーへの mutation が確実で、本 cycle では 8 変異
すべてが赤くなることを確認してから commit した。

5. **禁止構文の anti-pattern pin は、その禁止を説明する散文まで赤くしない粒度で書く**。`!= null` 一般を
`assert_not_grep` にすると、禁止事実を記述した行自身が anti-pattern 判定される。禁止したい構文
（`select(... != null)`）へ絞る。
