### Fix Patterns

**signal の挙動を主張する散文は、条件を揃えた実測で裏を取ってから書く**。今回直した 1 文
（「EXIT のみの trap では中断された run が成功として報告される」）は 3 signal を一括で
述べていたが、実測で成立するのは SIGINT だけだった。しかもこの 1 文は 2 人の reviewer を
往復させている — cycle 3 で error-handling が「実測と矛盾する」と指摘し、cycle 4 で自ら
撤回（`kill -INT $$` を自プロセスへ直接送る形では bash の default disposition が即座に
殺すため rc=130 になり、主張が偽に見えていた）、同 cycle で security が TERM 側の実測から
同じ箇所を指摘した。

**bash の signal 検証で条件を分ける軸**: (a) 誰が signal を送るか（自プロセスへ `kill -SIG $$`
か、外部から親プロセスへか）、(b) 受けたときプロセスが何をしているか（自身がコマンドを
実行中か、foreground child でブロック中か）。この 2 軸で結果が反転するため、片方だけの
計測は正しい記述を誤りと判定させる。今回の検証は「victim を background で起動し、sleep に
入ったことを marker ファイルで確認してから外部で kill、`wait` で rc を取り、後続命令が
実行されたかを marker で見る」形にした。TERM=143 / HUP=129 / INT=0 かつ INT のみ後続実行、
と修正後の記述どおりに再現した。

**修正範囲の確定**: 同一主張の複製を grep で 3 箇所と報告されたが、実際に誤った因果を
含むのは 2 箇所だった（3 箇所目は「cleanup registered for EXIT only」とだけ述べており
帰結を主張していない）。テストコメント側は TERM/HUP について正確だったので変更しない。
「N 箇所同期」と言われたときも、各箇所が実際に何を主張しているかを読んで範囲を絞る。
