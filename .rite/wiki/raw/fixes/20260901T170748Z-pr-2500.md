### Fix Patterns

cycle 1 の fix が持ち込んだ 3 件を cycle 2 で解消した。3 件とも「機構の追加で直した箇所」に生じており、
cycle 2 では**追加パッチではなく機構の除去**で直した。fix cycle 特有の再発パターンとして重要。

1. **marker 判定を 2 つ目の helper へ複製するときは、その helper の出力語彙を先に確認する**。
ある helper で成立した「失敗専用 marker で判定する」形を語彙未確認のまま別 helper へ写すと、
その helper が同じ prefix を成功通知にも使っていた場合、主経路で常時誤報告する機構になる。
本件では `flow-state.sh reap-issue` の `WARNING: reap-issue:` が「stale を見つけて非 active 化する」
という成功側の告知にも使われており、5 レビュアーが独立に同じ結論へ到達した。
**判別子として使えるかの検算**: helper 実装で当該文字列を grep し、成功経路の分岐にも現れないかを見る。
現れるなら bash 述語にはできない。hardened sibling が同じ helper に対して出力判定を採っていない場合、
それは手抜きではなく同じ非対称を踏まえた選択である可能性を先に疑う。

2. **失敗の観測手段を確保する層が、観測できないまま「成功」を宣言する経路を作りうる**。
`err=$(mktemp) || err=""` → `2>"${err:-/dev/null}"` → `[ -n "$err" ] && grep -q ...` の形は、mktemp 失敗時に
(a) helper stderr を marker ごと捨て (b) 判定を短絡し (c) `else` の「成功」へ落ちる。塞ごうとした当の欠陥を
観測層自身が再生産する。**捕捉層を持たなければこの縮退は存在しない** — sibling が stderr を素通しして
判定を読み手に委ねているのは、この理由で正しい。捕捉を書いたら「この経路で何が観測できなくなるか」を
1 行で言えるかを検算する。

3. **判定は列挙形ではなく除外形で書く**。失敗語彙を列挙して一致させる形は、helper に新しい失敗
メッセージが増えた時点で一致しなくなり静かに「失敗なし」へ倒れる。既知の成功通知だけを除外し、
残りをすべて失敗として扱えば、未知の語彙で fail-loud 側に倒れる。

4. **negative control (`assert_not_grep`) は identifier ではなく構造でキーする**。tempfile 名を pin すると
別名の同一構造を素通しし、しかも「二重防御に見えて実体は 1 本」になる。禁止したいのは
「helper の stderr を変数保持のファイルへ退避する」構造そのものなので、リダイレクト形
(`<helper>.*2>"$`) でキーする。**検算方法**: 禁止したい退行を**別名で**隔離コピーへ再投入し、
それでも赤くなることを確認する。名前を変えただけで緑になるなら、その assertion は名前に束縛されている。

5. **推奨事項由来の削除は commit body でそう明示する**。指摘 (finding) と推奨事項 (recommendation) は
fix の scope 上で扱いが違う。推奨事項に基づく変更を混ぜるときは由来を書いておかないと、次 cycle の
レビュアーが「名指し範囲外の変更」として再導出する手間を負う。
