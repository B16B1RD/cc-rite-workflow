### Fix Patterns

**新しい選択肢を既存の選択肢群に足すときは、優先順位を決める規律を先に言語化する**。本 cycle の中心指摘がこれだった。記法 3（表形式 Meta）を追加する際、記法 1 について「helper は code fence を剥がさないので、表記法を説明している Issue が本文中の例から値を解決する」という危険を明示的に論じて TC で pin していたのに、新設した記法 3 と記法 2 の間の順位には同じ検討をしていなかった。結果、`## 複雑度` で M を宣言した Issue が本文中の表の例から XS を採る経路（M+ の silent light 降格）が生まれた。規律を「明示宣言を先に読み、表行を最後に読む」と言語化したことで順序が一意に決まり、両 reviewer が別々に見つけた 2 つの誤判定が同時に解消した。**片方の記法で回避した hazard は、優先順位を変えた先の記法でも再評価する**。

**load-bearing な制限を追加したら、その制限を外す mutant で必ず落ちる TC を同時に足す**。本 PR は行頭 anchor（キーが先頭セル）と `head -1` という 2 つの制限を追加し、コード上はどちらもコメントで「これが load-bearing である」と明記していたが、どちらも外す mutant が全テスト green のまま生存していた。コメントは規律を記録するが、規律を強制するのはテストだけ。既存のテストが「正しい入力で PASS する」ことしか見ていない状態では、制限の追加は無検証の追加と同じ。

**片側だけ更新した散文 drift は、列挙をやめて SoT を指す 1 行に畳むと再発しない**。`SKILL.md` の記法列挙を 3 記法へ更新したが、その pointer 先である `references/rationale.md` の同じ列挙が 2 記法のまま残った。列挙を消して SoT（complexity-lane.md）へのポインタに置き換えることで、次に記法が増えても同期義務が生まれない。
