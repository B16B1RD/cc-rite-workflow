### 修正パターン

anti-pattern pin（禁止語の再導入検出）に文脈語を足して「誤発火を防ぐ」と、**実際に除去された表記形を取りこぼす**ことがある。今回は禁止語と文脈語の間に markdown 強調記号が挟まる形が抜け、5 名のレビュアーが「実証済みの検出力を未観測の誤発火リスクと交換している」と指摘した。**pin を狭めるときは、狭めた pattern が「実際に除去した全表記形」を今も捕らえるかを履歴（`git log -S`）で確認する**。誤発火の実例が 0 件なら裸の語のままにし、実際に入った時点で fail-loud に顕在化させる方が安全（no speculative structure）。

同一 pattern を N サイトへコピーすると、片方を締めて他を忘れる drift がそのまま再生産される。既存の idiom（`for f in ...; do assert_not_grep ...; done`）に合わせて **pattern は 1 度だけ書く**。

canonical snippet / 共有 reference が「新規箇所追加時は usage site として登録すること」と自ら指示している場合、その指示は**自分の PR にも掛かる**。今回は save helper へ必須キーを 2 つ足しながら canonical 節へ登録しておらず、snippet に忠実な JSON が save 段で拒否される乖離を作っていた。**共有 reference を参照する実装を変えたら、その reference の登録リスト・限定句も同じ commit で更新する**。ただし snippet 本体を広げるのではなく「write 側だけの追加検証」として書く — read 側は書込済みデータを信頼する設計なので、広げると read 側が誤って厳格化される。
