### Fix Patterns

- **「列挙をやめる」の次に来るのは「基準語が実コードの集合を選べるか」の検証**: 列挙を撤去して判別基準に置き換えても、その基準で grep した結果とコメントの主張が食い違えば同じ指摘が返る。基準を書いたら実際にその基準で grep し、件数と集合が一致することを確認してから commit する。
- **規則をコメントに書いたら、その規則をファイル全体へ適用しきってから commit する**: 「caller を列挙して説明しない」と書きながら同じ diff の 2 箇所で列挙していた。規則と反例が同時に入ると、保守者は「規則に従って直す」か「規則を無効と見なす」の二択を迫られ、どちらもコストになる。適用しきれないなら規則の scope を明示する。
- **撤去は grep で残存 0 を確認して終わる**: 指摘された行だけを直すと、同じクラスが別の行に残って次の cycle で返ってくる。指摘のクラスを言語化し (今回は「caller 名・件数・呼び出し形への言及」)、そのクラスを機械的に検索して一掃する。
- **診断値を捕捉したなら、それが最も意味を持つ分岐で出す**: parse の corrupt verdict を変数に持ちながら、印字していたのは parse 成功側の分岐だけだった。結果として corrupt と判定されたファイルからの値伝播が無警告になり、これは元の実装には無かった新規挙動だった。捕捉した診断値は「どの分岐で出すか」まで設計する。
- **観測性の主張は発火条件の射程と一致させる**: 「WARNING で観測性を確保する」と書くなら、発火条件が覆う範囲だけを主張する。今回は `.data` 全体の空判定だったため、個別 key だけの欠落は無警告で通っていた。
- **新機能が「片方だけ渡す」構成を作ったら、その構成を直接テストする**: 独立した 2 ガードに対し「両方渡す」「両方渡さない」しか通っていないと、ガードの取り違えが無検知で通る。本 PR 自身が追加した seed 行がその未検証構成だった。
