### Fix Patterns

「fail-loud を網羅した」と主張する変更で、blocking 2 件がどちらも**契約表と実装のズレ**だった。修正時に効いた判断は次の 3 つ。

1. **契約表の各行から実装の分岐へ 1 対 1 で辿り直す**。DESIGN.md に「クロスフェードがシーン尺より長い → エラー終了」と書いてあっても、実装のガードは総尺 `Σd − (n−1)x` しか見ておらず、`d0 < x < d0+d1` の窓を素通りしていた。表を書いた時点では「書いたから実装した」と錯覚しやすい。**網羅を主張する変更ほど、主張そのものが検査対象になる**。

2. **追加ではなく置換で直せないか先に確認する**（simplification-first）。今回は `x < min(d)` が `total > 0` を含意するため、最短シーン尺ガードは総尺ガードを**包含**する。ガードを 2 本並べる代わりに 1 本へ置換でき、分岐が増えなかった。「指摘された 1 ケース専用の分岐を足す」と、その分岐自体が次 cycle のレビュー対象面になる。

3. **「エラーメッセージが出る」と「エラー終了する」を同一視しない**。ループ内 `fail()` で catch は動きメッセージも出るのに、`finally` が子プロセス（ffmpeg）を解放しないため event loop が生き残り、exit code が呼び出し元へ届かなかった。`set -e` で待つ側は無限に待つ。**fail-loud の検証は exit code が呼び出し元に届くかで行う**（プローブで `timeout` → exit 124 が exit 1 に変わることを実測した）。

補助: 修正の副作用がないことは、決定論チェックの md5 が**修正前と同一**であることで裏を取れた。出力ハッシュが不変であるパイプラインでは、これが「挙動を変えていない」の最も安いエビデンスになる。
