### Fix Patterns

blocking 3 件を修正。3 件とも「劣化した局面でだけ効かない安全網」型で、通常経路では観測されない。

1. **1 つの軸を明示的に必須化したら、同じ resolver が持つ他の軸も同時に塞ぐ**: 人間へ渡す復旧コマンドで `--session` により sid 軸の誤対象化を塞ぎながら、同じ解決経路が持つ state root 軸を放置していた。`resolve_state_root` は cwd へフォールバックするため、repo 外 cwd での実行は rc=0 のまま別ファイルを作り、本来直すべき state は手つかずで残る。marketplace install ではコマンド文字列にプロジェクト参照が無く新規端末の既定 cwd が `$HOME` (非 git) になるため、空振りが例外でなく既定経路になる点が重要。修正は既に算出済みの値を marker に載せて `RITE_STATE_ROOT={state_root}` として提示すること。「片方の軸を塞いだ」時点で対称性を確認する。

2. **「失敗」と「未到達」を別軸に分けた場合分けは 2x2 になる**: 「A も B も失敗」「A の前に終了」の 2 件で網羅を宣言すると「A が走って失敗 × B に未到達」の象限が漏れる。しかもこの漏れた象限が「通知が一切出ない唯一の経路」であることが多い (B に到達しないと B が emit する marker が無く、その marker を条件とする通知も出ない)。対策は総論を「A も B も消せていない (失敗したか、到達しなかったか)」と 1 条件に畳むこと。畳めば象限の数え落としが構造的に起きない。内訳を残す場合も、到達しない象限では通知自体が出ないことを併記する。

3. **canonical spec の保証文に部分的な留保を書くと無留保より誤解を生む**: 実装が best-effort (2 つの write のいずれか成功に依存) なのに spec が「〜が必要」と書き、片方の caveat だけを添えると、読者は「留保は列挙し尽くされている」と合理的に推論する。留保が 2 つあるなら両方書くか、委譲先へ導線を張る。
