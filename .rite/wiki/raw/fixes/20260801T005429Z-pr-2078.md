### Fix Patterns

marker ライフサイクル系の指摘 13 件を修正して見えた、修正側の反復パターン:

1. **同一ブロック由来の複数指摘は、パッチを 3 枚重ねるより「受理判定を 1 箇所に集約」した方が小さい** — sentinel 偽造 / traversal / errno 握り潰しの 3 指摘はいずれも「caller 由来の値が検証なしで複数用途へ流れる」1 つの原因の別方向の顕在化だった。個別に guard を足すと分岐が 3 本増えるが、判定を引数確定時の単一ゲートへ出すと分岐は 1 本で済み、trap 内の責務も「消して emit する」に戻る。**Simplification-First は「追加を我慢する」ではなく「原因の粒度で束ねる」と読むのが実用的**
2. **文字列の中和だけでは機械可読チャネルの偽造を塞げない** — 改行を `?` に潰しても `[CONTEXT] ... KEY=1 ...` という**文字列**は残り、行頭 anchor を持たない consumer が拾う。そのチャネルで構造を作る文字 (`[ ] ; =`) まで潰して初めて閉じる。中和関数は「端末制御の無害化」用であって「構造の無害化」用ではない
3. **診断を capture する新規箇所は `LC_ALL=C` とセットで書く** — 中和関数が 0x80-0x9f をバイト単位で潰すため、ロケール依存の多バイト診断は原因語ごと判読不能になる。errno を読ませるのが目的の capture でこれをやると修正の目的自体が失われる
4. **テストの期待値に置いた `.*` は「そのフィールドは未検証」と同義** — sentinel が出ることは pin されるが正しい値を載せることは pin されない。値が gate の判定入力そのものなら、ワイルドカードは検査層の穴と等価。同型の弱化が過去に全 assertion green で生き延びた記録が同ファイルにあっても、新設 gate へは自動では引き継がれない
5. **assert に使われない診断変数は「pin 済み」の誤った安心を生む** — 未使用変数は shellcheck の warning 帯で error-only の CI gate を通過するため機械検出されない。直後に pass/fail を伴う if/else があると読み手には検査が成立して見える。削除するか実効化するかの二択で、コメントだけ残すのが最悪
6. **改番は本体・rationale 退避先・テストのコメント引用の 3 箇所を同時に見る** — 本体だけ繰り上げると `rationale:` ポインタの先が「既に追加済みのものを未来形で語る」状態になり、次の追加で同じ番号を再採番する誤りを誘発する
7. **canonical 契約ファイルは双方向に drift する** — 「X のみ」と書いた同じ変更が X 以外の経路を増やすことも、隣接する別 helper の語彙が混線して過剰包含を招くこともある。片方向だけ確認して閉じない
