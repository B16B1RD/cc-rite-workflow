### Fix Patterns

原則を立てたあとの「部分適用」が繰り返し新しい盲点を作った事例:

1. **原則は立てた箇所ではなく当てはまる全箇所に適用する**: cycle 2 で「capability probe は platform check ではないので blocking gate では成功を要求する」という床を 1 箇所に入れたが、同じ形の probe が他に 2 つあった。「非 ASCII 隣接の未ブレース変数を禁じる」も、宣言文は全体規則として書きながら走査は 1 ファイルに限っていた。原則を部分適用すると、残りの箇所は「対処済みのクラス」に見えて逆に発見されにくくなる。レビューで原則を立てたら、その場で `grep` して全適用箇所を列挙すること。

2. **fixture は検証したい対象と同じプラットフォーム差異を踏む**: canonicalization を pin する TC を「$TMPDIR を symlink に向ける」方式で書いたが、その誘導は bare `mktemp -d` が $TMPDIR を尊重することを前提にしており、BSD/macOS では成立しない — つまり検証したい差異と同じ差異を fixture 自身が踏んでいた。プラットフォーム差異の修正をテストするときは、fixture がその差異に依存していないかを先に確認する。単一のアサーションで両方を load-bearing にできないなら、プラットフォームごとに別の観測点を持つ 2 系統に分ける（一方は「戻り値が自身の canonical 形と一致する」、他方は「symlink 化した TMPDIR 経由」）。

3. **床の判定手段が、床が守ろうとしている脅威に汚染されないか確認する**: 「realpath が PATH 上で shadow されている」ことを検出する床を `$(uname -s)` で書くと、`uname` も同じ PATH を引くため脅威に汚染されうる。`[ -d /proc ]` のようなファイルシステム事実に基づく判定の方が強い。

4. **カウンタは per-file で止めず集約点まで通す**: skip を数える機構を各テストファイルに入れても、runner の headline が変わらなければ「31 アサーション未実行」は誰も見ない。可観測性の改善は、実際に人間が読む出力まで到達して初めて完了する。

5. **新しく追加した機構自体にもテストを書く**: `skip()` と SKIP カウンタを導入したが、`SKIP=$((SKIP + 1))` を外しても検知するテストが無かった（⏭️ 行は出続けるので緑のまま）。機構を足したら、その機構が壊れたら落ちるテストを同じ変更に含める。

6. **degrade する対象をテストするときは判別子を probe と連動させる**: 「degrade 出力と正常出力が同一なので判別子を要求する」修正を GNU 側の値で固定すると、degrade する環境そのものが赤になる。判別子は probe で切り替え、degrade 側は degrade 契約を明示的に要求する形にすると両環境で fail-closed になる。

7. **perl の alarm は整数に切り捨てる**: 小数秒を渡すと `alarm 0` = タイムアウト無効になり、waitpid が CI の job 上限までブロックする。GNU timeout の代替 shim を書くときは非整数を明示的に拒否する。
