### Fix Patterns

cycle 3 の 10 指摘は「pin の設計」と「rationale の事実性」に集約された。cycle 1→2→3 で指摘の性質が実装バグ → 記述の不整合 → pin の精度へと移った点自体が記録に値する。

1. **対称な実装には対称な pin を置く**: P0/P2 が別変数を使う以上、片方の経路しか実行しない pin はもう片方の退行を構造的に検出できない。cleanup 登録から片側ずつ外す mutation を当てると、実行していない側だけが SURVIVE する。実装の対称性を主張するなら、pin も同じ対称性を持たせる必要がある。glob を `-p0-` / `-p2-` に分けると、失敗時にどちら側が漏れたかも判別できる。

2. **「不在の確認」には必ず到達の確認を添える**: 「tempfile が残っていない」は「cleanup が働いた」でも「そもそもガードに到達していない」でも等しく成立する。ターゲットを `exit 0` するだけのスタブに差し替えても PASS することで露見した。rc と marker を positive に固定してから不在を判定すれば、この 2 状態が分離できる。

3. **rationale を書く前に集約前の実態を確認する**: 「N 箇所に複製されており差分がない」と書いたが、実際は 2 箇所でありその 2 箇所は既に drift していた（片方に診断行が欠けていた）。結果、集約で stderr が増えた事実を comment 自身が否定する状態になった。「差分がないから畳める」は監査時に前例として機能してしまうため、事実でない場合の害が大きい。

4. **リファクタでラベル体系が消えたらテストのラベルも追随する**: ソースから「Instance」という概念が消えたのに、テストだけが `Instance 3/3` を参照し続けると、失敗時に grep しても該当ロジックに辿り着けない。番号体系ではなく呼び出し元の性質（`schema-invalid path` 等）で名指しすると陳腐化しない。

5. **few-shot に「実行していない実測」を書かない**: 調査手順に現れないコマンド結果をアンカーに書くと、few-shot はその形をそのまま模倣される。実測アンカーを載せる例では、調査手順側にも実行ステップを明示する（あるいはアンカーを外して「実測できないから付けない」例にする）。
