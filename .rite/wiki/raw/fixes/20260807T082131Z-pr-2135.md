**「指摘を迂回で覆う」と root cause が残り、次 cycle で同じ穴の別サイトが指摘される**。cycle 1 の F-06 は「(a) 半角スペース必須で `（既定5）` を素通し」「(b) ERE の `?` が多バイト文字に掛かり LC_ALL=C で失効」の 2 つの root cause を挙げていたが、fix は (b) を直し (a) は positive count pin で迂回した。結果 `（既定 15、` のように閉じ括弧を伴わない 4 サイトが無防備のまま残り、cycle 2 で F-08 として再指摘された。**指摘が複数の root cause を列挙しているとき、片方を迂回策で覆っても他方は残る**。

**`grep -c` は行数であって出現数ではない**。長い段落を 1 行で書く markdown（CONFIGURATION.md の safety 表・backstop 節はいずれも 1 行 1000 字超）では、同一行に同じ文字列が 2 つ同居すると count pin が黙って過小評価する。cycle 2 の fix でまさにこれが起き、期待値 3 を設定したのに実測 2 が返った。`grep -o ... | wc -l` へ変えると 4 が返り、そこで初めて「下限制約の記述も同じ網に入る」ことが分かった。**count pin を長い段落に掛けるときは出現数で数える**。

**注記が pin 対象の文字列を含むと、pin の数え方が自己参照的になる**。「T-04n counts the four `the default of 15` phrasings」と書いた瞬間、その注記自身が 5 つ目の出現になり count pin が落ちた。**pin の説明文には pin 対象の literal を書かない**（「the four spelled-out mentions of the default value」のように言い換える）。

**根拠を書き足すときは helper を実際に走らせて範囲を確かめる**。cycle 1 の fix は「全 head で converging_or_descending」と書いたが、helper は結果 3 件未満で `need_3_cycles` を返すため実際は head 4 以降だけだった。同じスキルの別セクションと同 PR の英語 docs の両方が正しく書いていたにもかかわらず、新しい 1 文だけが矛盾した。**引用する挙動は grep ではなく実行で確かめる**。
