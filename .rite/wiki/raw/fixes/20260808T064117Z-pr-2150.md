### Fix Patterns

**委譲・遅延・後回しの設計では「委譲を受け取る側が機械可読な担体で受け取れるか」を必ず確認する**: 発火条件と回復条件が同一の状態変数に依存していると、回復経路が構造的に成立しない。本 PR では「flow-state に worktree 記録が無い」を委譲モードの発火条件にし、回復手段として「main checkout での再実行」を案内したが、再実行時も同じ状態変数が空のままなので検出 helper が同じ結論を返し、委譲した項目に到達しなかった。修正では既存の reap manifest record API を呼んで担体を人間宛ての散文から機械可読な台帳へ移した。「案内文を実態に合わせる」だけの修正は人間の手作業を定常化させるため採らなかった（人間の役割は 2 点のみ原則）。

**prose-driven skill のテストは marker 名の在処ではなく指示語を pin する**: `assert_grep` で marker 名の存在だけを見るテストは、ガードの削除は検出するが「実行しない」→「通常どおり実行する」の指示反転を検出しない。prose が実装本体である skill では指示語そのものが pin 対象。修正では grep パターンを `CLEANUP_DELEGATED=1` を emit している場合、本ステップの bash を**実行しない**` まで伸ばした。

**新設した marker には排他性の negative control を置く**: 「この marker を emit してよいのは 1 箇所だけ」「このガードを持つのは 3 ステップだけ」という排他性は `grep -c` による件数固定でしか pin できない。存在 assert だけでは marker の漏出（別 arm からの emit）やガードの混入（state 系ステップへの誤挿入）を検出できず、いずれも受入基準を丸ごと無効化しうる。

**「構造的に不可能」という前提は形態を特定して書く**: harness の worktree 隔離ガードは「Bash 呼び出しのコマンド文字列に直接 `cd` / `git -C` が現れる形」を拒否するが、helper スクリプト内部の `cd` は拒否しない。一般化して書くと自動化可能な操作を恒久的に人手へ委ねる設計判断が固定される。

**同一問題を 3 名の役割の異なる reviewer が独立に検出した**: 設計レベルの欠陥（発火条件と回復条件の同一性）は prompt-engineer / tech-writer / test のいずれの視点からも到達する。cross-validation で severity を boost する判断はこの性質に基づく。
