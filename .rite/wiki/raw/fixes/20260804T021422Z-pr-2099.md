### Fix Patterns

1. **条件式を広げたら「その条件を散文で再掲している箇所」を grep で洗う**: コードの参照は
   識別子で追えるが、「pin 不在のときだけ判定を降ろす」のような言葉での再掲は同じ grep に
   掛からない。cycle 4 の 1 行の OR 追加が 5 箇所（header 結論行 / usage / SPEC 2 / CONFIGURATION）
   を同時に偽にし、次 cycle の blocking の半分を占めた。条件の**言い換え表現**を列挙してから
   commit する。

2. **同一コメントブロック内の「前提 → よって結論」は前提だけ直すと自己矛盾する**: header に
   新条件を追記しながら結論行を旧条件のまま残した。ブロック内に導出構造があるときは、
   前提の更新が結論の更新を要求するかを必ず見る。SoT 文書ではこれが下流へ伝播する。

3. **guard の「限界」をテストで明示すると、次の担当者が残余を誤解しない**: `cycle_count == 0` は
   stale pin の部分集合しか捕まえない。「塞いだ」と書くのではなく「ここまで塞いだ（残余は別機構が担う）」
   を assert として書く。限界の assert は退行検出だけでなく設計意図の伝達装置になる。

4. **本番の 100% が通る経路にカバレッジ 0 がありうる**: 既定 `results_dir` 解決ブロックは、
   テストが常に `--results-dir` を渡すため一度も実行されていなかった。「テストが通る」と
   「本番経路が検証されている」は別。呼び出し側が渡す引数の**既定値側**を踏むケースを 1 本置く。

5. **`jq empty` を通過した妥当な JSON でも filter はエラーを返しうる**: `findings[]` に object でない
   要素が混ざる等。診断を `2>/dev/null` で捨てると、reason にファイル名しか出ず原因の特定に
   filter の再構成が要る。sibling が持つ診断退避パターンへ揃えた。
