blocking 18 → 9 → 1 と収束した最終サイクル。cycle 3 の唯一の blocking が示したのは、**修正が効いていることと、その効果がテストで固定されていることは別**という点だった。

1. **効果が stdout/stderr にしか現れない修正は、rc の assertion では固定できない**: cycle 2 で「走査不能の集約 ERROR を findings 判定より前へ移す」修正を入れたが、rc は移動の前後とも 1 で同値だった。テストが rc しか見ていなかったため、hunk を revert してもスイートは全緑のまま。修正の観測可能な効果がどこに現れるか（rc / stdout / stderr / 副作用）を特定し、そこを assert しないとリグレッションは検出されない。**mutation（該当 hunk の revert）でテストが赤くなるかを確かめるのが唯一確実な検証**。

2. **委譲は失敗モードの分布を変える**: inline awk を helper 呼び出しへ置換すると、最も起こりやすい失敗が「awk の IO エラー」から「helper 解決不能 = rc=127」へ移る。診断メッセージが旧い分布のままだと、運用者は起きていない原因へ誘導される。同じ委譲を複数サイトで行うと、片方だけ更新して非対称が残りやすい（本 PR では 3 サイクルにわたって同じ非対称が指摘され続けた）。

3. **陳腐化した相互参照には「ただ古い」ものと「逆方向に誘導する」ものがある**: 「ステップ 8.1 はステップ 1.1 と同じパーサ」という記述は、1.1 を helper 委譲へ変えた時点で偽になっただけでなく、**それを読んだ次の編集者が 1.1 の旧形を 8.1 へ持ち込む**経路を作る——つまり修正した欠陥へ戻す誘導になる。この種の記述は「古い」と判定して放置せず、なぜ現状がこうなっているかの理由まで書き足す必要がある。
