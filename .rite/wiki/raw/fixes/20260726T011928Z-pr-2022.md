### Fix Patterns

- **ローカルのフルスイート green を「テスト green」と報告してはいけない（マトリクス CI がある場合）**: Linux で 105/105 を確認して green と報告したが、実 CI の macOS leg は failure だった。`gh run list` の run 結論は `continue-on-error` のレグを隠すため success に見える。**教訓: `gh run view <id> --json jobs` で job 単位の結論まで見る。修正後の検証も同じ粒度で行う（今回は develop success → 修正前 failure → 修正後 success の 3 点比較で確証した）。**
- **glibc で再現しない欠陥は behavioral TC ではなく static guard で pin する**: `$var。` の多バイト取り込みは glibc ではどのロケールでも再現せず、Linux leg では behavioral TC が vacuous になる。リポジトリの既存 invariant テスト（TC-8b-h）も同じ理由で静的検査を選んでいた。**教訓: プラットフォーム固有の欠陥は「壊れることを示すテスト」ではなく「その形を書けなくするテスト」で守る。既存に同型の guard があればその除外規約（行頭 # のコメント行は exempt 等）まで踏襲する。**
- **既存の invariant テストがあっても走査範囲の外なら守られない**: TC-8b-h は `*.sh` のみを走査し SKILL.md の bash fence を対象外にしていた（テスト自身が scope limit として明記）。**教訓: 「この invariant はテスト済み」を根拠にするときは、自分の変更箇所が走査対象に入っているかを確認する。入っていなければ自分の側で guard を足す。**
- **`grep -P` はロケール依存でバイト範囲マッチを取りこぼす**: `[\x80-\xFF]` は UTF-8 モードでは期待通りに動かず、`LC_ALL=C` を付けても検出できなかった。perl / python では 1 件正しく検出。**教訓: バイトレベルの検査は grep でなく perl か python で書く。「検出ゼロ」を安全の根拠にする前に、既知の陽性例で検出器自身を検証する（positive control）。**
- **前 cycle で書いた rationale コメントも mutation で検証する**: 「救済文言を要求すれば `x` 判定には存在し得ないので堅い」と書いたが、文言を残したまま判定値だけ反転する mutation で反証された。**教訓: コメントに書いた「なぜこれで十分か」の主張自体が検証対象。誤った rationale は次サイクルの reviewer の探索をそこで止める。**
- **「握り潰しをやめる」修正が診断品質を下げることがある**: `|| true` を撤去して FATAL 化した結果、同じ状態を正しい帰属で検出する後段 TC と役割が重複し、誤った原因を指し、後続 4 TC のカスケード中断を招いた。**教訓: 二重防御より正しい帰属を優先する。既に別の場所で正しく検出されているなら、そちらに任せて手前は警告に留める。**
