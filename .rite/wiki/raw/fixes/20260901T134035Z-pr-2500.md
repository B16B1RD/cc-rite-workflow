### Fix Patterns

9 件の blocking 指摘は、根を辿ると 1 つの誤りに収束した: **`/rite:cleanup` を参照実装として写したが、cleanup が依存している前提（対象 Issue == 現在のセッション）は写した先で成り立たない**。issue-cancel は Issue 番号を引数で受ける最初の入口で、そこでは「対象の同定」を明示的にやり直さなければならない。写された 3 箇所（PR 検索・flow-state の branch 読み出し・worktree detect）がいずれも Issue 番号でスコープされておらず、同定できていないまま破壊的操作へ進む構造になっていた。

横断的に効く教訓:

1. **`gh` のフィルタオプションは「絞り込めていないのに成功して見える」形で失敗する**。`--search "linked:issue:{N}"` は `linked:issue` が boolean qualifier なので `:{N}` を捨て、存在しない Issue 番号でも同じ集合を返す。`--head` は exact-match でワイルドカードを解釈しないので glob は常に空。どちらも exit 0 + 非空/空の JSON を返すため、返り値をそのまま判定表に載せる設計では検知できない。**実ブランチ名を先に確定させて exact `--head` を引く**か、`--state all` で取ってから client-side で絞るのが確実な経路。
2. **helper が「判定できずに削除を試行しなかった」marker を、呼び出し側が消費しないと helper の fail-fast が無効化される**。marker family の一部（`BRANCH_DELETE_UNMERGED`）だけを見て残り（`BRANCH_CHECK_FAILED` / `BRANCH_DELETE_FAILED`）を無視すると、helper が弾いた入力クラスに対して呼び出し側が直接 `git branch -D` へ進む。marker 判定表は family 全体を列挙し、**marker 不在を「成功」と読まない**ことを明記する。
3. **参照実装から写した bash は「安全形」も一緒に写す**。`git branch -D -- "$branch"` の `--` と quote は 1 トークンのコストしかないのに、落とすと refname 中の `;` 以降がシェルへ渡る。リポジトリが invariant として明文化している形は、写す側でも維持する。
4. **一時ファイルの置き場所は「その間に何が消えるか」で決める**。中止経路は途中で session worktree を削除するため、worktree 配下に書いたファイルは Phase をまたいで生き残らない。読み出し側で rc と空値の**両方**を fail-loud にしないと、「読めなかった」が「空だった」に化けて成功経路を通る。
5. **テストの pin は実行行にアンカーする**。散文が同じコマンド名を引用していると、コマンド名だけの grep は散文に一致して契約挙動の除去を見逃す。この PR では 3 件が同じ形で、いずれも mutation で「契約を消しても全 assert green」を実証できた。セクション限定（`assert_grep_in_section`）と実行行アンカー（`^if gh ...`）が対処。
