### Fix Patterns

cycle 2 の blocking 8 件のうち 6 件が cycle 1 の fix 自体に起因していた。原因は 1 つに収束する
——**対称位置を列挙せずに 1 サイトだけ直した**。cycle 2 ではその順序を反転し、編集**前**に
`git grep` で同型サイトを数えてから当てることで、同じ型の再生産を止めた。

**cycle 1 → cycle 2 で実測した「fix が drift を生む」4 つの型**（次回の予防チェックリスト）:

1. **canonical を「形」だけ写して「順序」を落とす**: canonical doc を anchor で名指ししながら、
   その Instantiation Checklist の項目（trap は mktemp の前）を満たさない。
   **canonical を引用するときは checklist を項目ごとに照合する**。copy-paste 同形性は契約一致を
   保証しない。

2. **fix の rationale に書いた挙動が未 pin**: 「なぜ直したか」を長いコメントで書きながら、
   その挙動を守る assertion を書かない。1 行形へ戻す変異がスイートを緑のまま通る。
   **fix と同じ commit でテストに落とす**（[CONTEXT] flag の 3 点セット emit / consume / **test**
   の test を欠いた形）。時間依存の signal テストは flaky になるので、shim + pidfile で
   決定論的に届かせるのが実用解（background job は非対話シェルが SIGINT を SIG_IGN で継承させ、
   trap で上書きできないため foreground で走らせる）。

3. **片側だけ pin した diff が対称位置の穴を転写する**: 同形の site が n 箇所あるとき、
   1 箇所だけ pin すると残りは無検証のまま。**テストを書く前に `grep -c` で同形 site を数える**。

4. **fix が新規 ID / 番号を既存と衝突させる**: 追加テストのラベルと fixture 番号が既存と重複
   （3 reviewer が独立検出）。**新規 ID を採る前に既存連番の空きを grep で確認する**。

**「1 サイトだけ是正」が最悪な理由（実測）**: 同一 invariant を述べる 8 サイトのうち 1 つだけを
直すと、同一ファイル内で正反対の断定が 28 行離れて並ぶ——**修正前より悪い状態**になる。
Placeholder Legend のような「実行者が最初に読む定義位置」に旧断定が残ると実害が出る。
`git grep` で全出現を列挙し atomic に当て、`grep` で残存ゼロを確認するまでが 1 つの fix。

**非 blocking 指摘の扱いの実務**: 実測必須ゲートは non-blocking を fix 対象外とするが、
**自分の編集が段落を内部矛盾させた場合、その段落を整合させるのは scope creep ではなく
自分の変更を正しくすること**。blocking fix が触る段落に同根の non-blocking 指摘があるなら
一体で直し、完了報告で「付随解消したもの / 意図的に残したもの」を明示する。

**fix 後の standing step**: 変更行に対して repo 自身の lint（comment-journal / comment-line-ref /
hardcoded-line-number / tmp-hardcode / dollar-zero / bang-backtick / sh-cross-ref）を回し、
baseline との差分ゼロを確認する。cycle 1 では偶然気付いた自己混入を、cycle 2 では定常手順にした。
