### Fix Patterns

「検証手順を新設する変更」に対するレビューで、**手順が処方するコマンドの判別能力そのものを実測する**ことが最大の歩留まりを生んだ。手順の文面は正しく読めても、処方コマンドを実際に走らせると意図した判別ができないことがある。

- **`gh issue view {N}` は PR 番号でも成功して PR を返す**（`gh pr view {N}` は逆に Issue 番号を `Could not resolve to a PullRequest` で正しく弾く）。この非対称性のため、Issue/PR 番号の混同を検出する手順で `gh issue view` の **title 照合を判別手段にしてはならない** — squash merge 運用では PR title が Issue title から派生してほぼ一致し、誤った対象のまま VERIFIED に倒れる。
- **判別に使えるのは `url` のパスセグメント**（`/issues/` と `/pull/`）。`state` は使えない — open な PR は Issue と同じ `OPEN` を返す（`MERGED` だけを見る実装は closed PR しか捕まえられない）。実測で両方を確認した。
- **判定は同じ 1 回のコマンド出力から取る**。`-R {owner_repo}` を落とした二度目の呼び出しは SSH host alias 環境で別リポジトリを引くため、「値を見に行く」形の指示は `-R` 落ちを誘発する。
- **「SoT から転用する」宣言は、意味の表を自前で持った時点で偽になる**。ラベルだけ借りて判定根拠が異なるなら、その旨を宣言側に書かないと、誘導に従って SoT を読みに行った保守者が対応しない定義を受け取る。ラベル一致と定義一致は別物として書き分ける。
- **プロジェクト規約の数値上限は lint 対象外のファイルにも適用される**。番号引用の上限のような規約は、静的チェックの走査対象（本リポジトリでは CHANGELOG 2 種 + lint/SKILL.md）外でも守る必要がある。機械検出されないことは適用除外ではない。
- **具体番号を消しても再現性は保てる**。「実例が必要だから番号を残す」の代替として、読者にコマンド（`git log -1 --format='%s%n%b' {sha}`）を実行させる形にすれば、罠の再現性を保ったまま番号リテラルを 0 件にできる。
- **伝播スキャンは「本 PR の diff が導入した行」に絞る**。同じ defect パターンを持つ既存コードは revert test で pre-existing と判定されるため対象外。本 PR では追加した reviewer prompt の 1 行が同一欠陥を持っており、そこだけが伝播対象だった。
