### Fix Patterns

本 cycle の 4 件はすべて「**直前の cycle で新設した仕組みが、その仕組み自身の目的を局所的に打ち消していた**」という単一の型に収まった。移植性修正 PR の終盤で繰り返し出る構造なので経験則として残す。

1. **fail-closed ガードは既存の診断出力より後ろに置く**（F-02、MEDIUM）
   skip 会計の drift 検出という新しい `exit 1` を、既存の「失敗ファイル一覧」出力より前に置いたため、drift と実失敗が同時成立すると失敗ファイル名が一切出なくなっていた。同時成立は偶発ではなく構造的（`set -e` のテストが `skip()` 呼び出し後・summary 到達前に abort すると必ず両立する）。
   → **規則: ガードを追加するときは (a) 既存の診断より後ろに置き、(b) 両方を出してから exit する。** exit code は変えずに診断だけを足す形にする。

2. **新しい診断行は CI のログ抽出パターンにも同時に登録する**（F-02、MEDIUM）
   ランナー側に新設した 2 種の診断行が `.github/workflows/ci.yml` の job-summary 用 grep にマッチせず、drift だけでジョブが落ちた場合にサマリーが `Results: N/N passed, 0 failed` **だけ**を「Test failures」見出しの下に表示していた。赤いジョブが「全件 pass」と主張する状態。合成ログで再現・確認済み。
   → **規則: ランナーの出力を増やしたら、そのログを消費する側（CI summary の grep 等）を同じ PR で更新する。** 消費側は grep 1 行なので忘れやすい。

3. **可視化を入れたら成功メッセージまで一貫させる**（F-04、LOW-MEDIUM）
   SKIP カウンタを導入して集計行には gated group 数を出したのに、最終行は無条件 `All tests passed!` のままだった。しかも同 PR 内のもう一方のランナー（run-all.sh）は注記付きに直しており、**gated group を持つ側だけが未対応**という非対称になっていた。
   → **規則: 「緑を正直にする」目的の可視化は、集計行だけでなく成功メッセージにも通す。** 2 つの類似コンポーネントがあるなら両方を同時に直す。

4. **バグを直したら、そのバグを再生産するテンプレートも直す**（F-01、HIGH）
   macOS の `$TMPDIR`（`/var/folders` = `/private` への symlink）問題を実テストで 2 段階 canonical 化に直したが、CONTRIBUTING の「新規テストひな形」は 1 段のまま残り、コメントだけが「Two steps」を説明する矛盾状態になっていた。ひな形は複製起点なので、直したばかりのバグを次の contributor が再導入する経路が開いたまま。3 レビュアーが独立に同一箇所へ収束した。
   → **規則: 移植性・規約バグを直す PR では「そのパターンを再生産する SoT（ひな形・スニペット・生成器）」を必ず同時に grep して更新する。**

5. **新しい規約を書くときは、その規約が依拠する前提を同じ文書内で確立する**（F-03、MEDIUM）
   「blocking gate では fail させよ」「on Linux」という規約を CONTRIBUTING に追加したが、同文書はクロスプラットフォーム CI マトリクスの存在を一度も説明していなかった。読者はどの leg が blocking か判断できず規約を実行できない。
   → **規則: 前提はハードコードせず SoT へのポインタで書く**（「どの leg が blocking かは ci.yml が宣言する」）。将来 blocking が入れ替わっても文書が陳腐化しない。

### 検証手法の記録

修正が load-bearing であることを、合成ログによる**失敗経路の再現**で確認した（テストを足せない箇所の代替）。具体的には $TMPDIR にランナーを複製し、(a) 失敗 + drift 同時成立、(b) drift のみ、の 2 経路を人工テストで発生させ、修正前後の grep 出力差を実測した。「修正前は Results 行だけが出る」ことを見せられたので、指摘が仮説でなく観測であることを担保できた。
