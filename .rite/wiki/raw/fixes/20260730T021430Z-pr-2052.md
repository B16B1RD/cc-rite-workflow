### Fix Patterns

1. **「実体に合わせる」是正では、実体が 1 つだと思い込まない**（前提崩壊。cycle 4 で判明）
   Issue は「実 index.md は 5 列テーブル」を前提に書かれていたが、同一マシン上の他 2 リポジトリは箇条書き形式で計 139 行が生きており、読み手（query hook）で正しく引けていた。前提はリポジトリローカルだった。結果、書き手をテーブルへ一本化すると**欠陥のなかったリポジトリへ退行を拡張**することになった（古い知見は引けるが新しい知見は引けない、という気づきにくい形）。
   教訓: 「実体」を根拠に指示を書き換えるときは、**その実体が観測された母集団を確認する**。同じスキルを使う他リポジトリ／他環境を列挙して形式を実測する。1 リポジトリの観測を仕様の前提に昇格させない。

2. **Issue の Non-goal 文が史実と逆になっていることがある。git history で裏を取る**
   「テーブルから箇条書きへ戻す（#1519 を覆さない）」という Non-goal 文の主節と括弧が逆向きを指していた。`git show <commit>^:<file>` で確認すると #1519 以前が既にテーブルで、#1519 が箇条書きへ変えていた。つまりこの PR は #1519 の決定の反転だった。
   教訓: provenance を文書に書き足すときは**必ず `git show <commit>^:<path>` で前後を確認**する。同一リポジトリ内に反対の記述（今回は test fixture のコメント）がないか grep する。誤った provenance は次の編集者に「その形式は一度も正式だったことがない」と読ませ、その形式の consumer の存在を見落とさせる。

3. **スキル内に「全パスはこの基点で書く」という規約があるなら、追加する bash も従う**
   統計の件数算出を素の相対パス `ls .rite/wiki/pages/*/*.md` で書いたが、同ファイルは全 Wiki パスに絶対基点の埋め込みを要求しており、他 14 箇所は遵守していた。branch strategy が separate_branch のとき実体は別 worktree にあるため 0 が返り、正しい統計を silent に 0 で上書きする経路になっていた。
   教訓: 既存ファイルに bash 断片を足すときは**同ファイル内の他の断片が使っている基点解決 idiom を grep して踏襲**する。「3 つの cwd で同じ値を返すか」を実測すれば cwd 依存は即座に露出する。数値 0 が構造的にありえない箇所では 0 を書かずに WARNING で止める。

4. **判定述語は全手順で同一の対象集合に揃える**
   「重複ガードはテーブル行を見る」「行同定はリンク一致で見る」と述語が分かれていたため、節の外に残す旧形式行に対する扱いが未定義になった。片方の読みでは二重登録、もう片方では箇条書きリスト内へテーブル行を置いて literal text 化する。
   教訓: 同じデータを扱う複数手順の述語は**対象集合まで含めて一致させる**（「節内のテーブル行」のように範囲を明示する）。「残す」と決めたデータがある場合、各手順がそれを対象に含むか除くかを 1 箇所で宣言する。

5. **「写し」と宣言したデータの更新元を 1 つに固定する**
   テンプレートに「index は frontmatter の写し」と書きながら、更新手順の値の出所を「frontmatter + 今回のサマリー」と 2 系統にしたため、写しが原本より新しくなる読みが成立した。
   教訓: SoT を宣言したら、**その SoT 以外から値を取る経路を手順に残さない**。派生値を変えたい場合は「先に SoT を更新してから写しを再生成する」と順序で書く。

6. **削減した箇所に紐づく対称物も一緒に戻すか確認する**
   機構を削る際にテンプレートからテーブルだけ復元し統計節を戻さなかったため、新規リポジトリでは統計同期手順が永久 no-op になっていた（受け皿が生成されない）。
   教訓: 「Aを戻す」判断をしたら、**元の状態で A と対になっていた B** も確認する。片方だけ戻すと、その機能に到達する経路が構造的に消える。

7. **deferred を「別 Issue」と書くだけでは追跡できない。番号を採る**
   3 箇所に「読み手のテーブル対応は別 Issue」と書いたが番号がなく、レビュアー 2 名が「追跡不能な TODO」と指摘した。
   教訓: deferred を文書に残すなら**その場で起票して番号を入れる**。番号なしの deferred は、後から誰も同一の Issue を指していると確認できない。

8. **上限に達する前でも、前提が崩れたらループを止めて人間に返す**
   サーキットブレーカー（上限 5）は未発火だったが、cycle 4 で仕様の前提崩壊が判明した時点で cycle 5 に入らず停止した。前提が変わったまま自律ループを続けても、レビュアーが同じ矛盾を「仕様への疑問」として再指摘するだけで収束しない。
   教訓: **機械的な停止条件（cycle 上限）と、判断による停止（前提崩壊・スコープ判断・承認待ち）は別物**。後者は上限とは独立に発火させる。停止時は state と作業メモリに理由と再開手順を残す。
