### Fix Patterns

「値を出す側」を直して「読む側」の条件を直さない修正は、機構だけ作って効果がゼロになる。欠損を stdout に出す新フィールドを足したが、それを読む note 展開表の行が上位行に包含されて到達不能で、部分欠損は依然として注記なしの「実測済み」として通っていた。条件表に行を足すときは、既存行との包含関係を確かめて排他にする（優先順位規約に依存しない）。

「当てずっぽうの既定値」は無言の縮退を作る。ヘッダーを検出できないときに既定列を仮定すると、見出し語が drift しただけで別列を黙って走査し検出が 0 に倒れる。位置決めを外部データから取る設計では、取れなかった場合は「推測して続行」ではなく「スキップして surface」が整合的。

同じファイルを読む複数の検出器は判定 regex を共有する。片方だけが狭いと、その形式のデータで片方だけ無言で 0 件になり、もう片方が正常に動き続けるため他カテゴリからも異常が見えない。

`git cat-file -e` は「ref が無い」と「ref 内に path が無い」をどちらも rc=128 で返す。存在プローブでこれを畳むと、壊れた ref が「ファイル不在」と同じ静かな縮退になる。ref 自体の存在は `git rev-parse --verify` で先に確かめる。

ドキュメントの是正導線は、参照先の実装にその経路が存在するかを確かめてから書く。書いた手順が早期 return する / 入力に取らないフィールドを指している場合、読み手は効果のない作業へ誘導され、実際に効く手段を禁じられる。

「この構成では 0 件」という断定は、一時ファイルが実在する窓を見落とす。ingest 待ちの生成物が走査対象ディレクトリに置かれる期間があると、断定が偽になり正当な検出が「範囲外のはず」と却下される。

テストは「変異させて落ちるか」でしか識別力を測れない。ヘッダー不検出・相対パス形式・壊れた ref・マスク削除のいずれも、fixture が単一パターンに偏っていたため全件緑のまま通っていた。
