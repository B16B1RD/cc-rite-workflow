### Fix Patterns

本 cycle の 12 指摘は「コードは正しいが、それを説明する散文が実態とずれている」型が過半だった。修正して分かった再発防止の型を 3 つ記録する。

1. **段階分割 PR では時制で書き分ける**: データ契約だけを先に切る PR で、SoT ドキュメントが「write 側は常に 3 キーを出力する」、reviewer 指示が「フィールドとして保存される」と現在形で書いてしまった。producer 側の配線は後続スコープで、grep すると抽出側はゼロ。「契約として宣言したこと」と「いま実装されていること」を同じ現在形で書くと、読者は後者と受け取る。責務宣言（「出力する場合は 3 キーを埋める」）+ 配線状況の明示（「配線は後続」）に分けると誤読が消える。

2. **予防的配置の理由は prospective に書く**: 型ガードを invariant の前段に置いた理由を「後段が nested access で rc=5 になるから」と現在形で書いたが、現時点の後段はそのフィールドを参照せず主張が再現しない。3 reviewer が独立に base 版へ fixture を通して受理を実測し、同じ結論に到達した。守っている対象が「将来の consumer」なら、そう書かないと保守者が「主張が再現しない → 配置を動かしてよい」と誤結論する。あわせて、同じ PR 内に「その経路が参照しないからガード不要」という逆向きの基準（P3 除外理由）が併存していると、同じ基準を適用したとき自分のガードが不要という結論になる。除外理由は経路固有の根拠（入力が永続ファイルか）に置き換えるべきだった。

3. **安全側 fixture が観測窓を塞ぐ**: 受理テストの fixture を「先行 invariant が短絡する形状」に倒したのは正しい判断（そうしないと受理判定が観測できず vacuous pass になる）。しかし同じ判断を reject fixture にも適用したため、両分岐が発火しうる形状が 1 つも無くなり、順序契約（ガードは invariant の前段）を pin できなくなった。順序退行の mutation で全テストが通過することを 2 reviewer が実測。accept 側と reject 側では fixture の設計目的が逆になる — accept は先行分岐を黙らせ、reject は両方を鳴らして precedence を見る。

4. **jq の rc=1 と rc>=2 を融合しない**: `jq -e ... >/dev/null 2>&1` は「述語 false」と「jq 自体の失敗」を同じ非ゼロに潰す。型ガードでこれをやると、対象フィールドを一切持たない入力にも `type_invalid` という事実と異なる reason が付き、しかも P2 では rename 後にファイルが glob から外れてその誤 reason が唯一の痕跡になる。rc を明示捕捉して別 reason に分け、rc>=2 では破壊的操作（rename）をしないのが正しい（破損が未証明のため）。

5. **手書き同期契約は関数に置き換える**: 「3 箇所を同時に更新すること」というコメントは、差分がラベル語だけなら関数抽出のサインだった。rc 変数名が 3 つに分かれていた理由も top-level scope でのコピペのみで、local 化で消えた。
