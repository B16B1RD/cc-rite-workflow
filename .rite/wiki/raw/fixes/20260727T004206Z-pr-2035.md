### Fix Patterns

cycle 2 の 10 指摘は全て「cycle 1 の修正が対になる側を取りこぼした」型だった。修正パターンとして 3 つ記録する。

1. **新しいリソースを導入したら、そのファイルが既に持っている lifecycle 契約に合わせる**: 型ガード用の tempfile を `elif` の条件部で mktemp し `then` ブロックでのみ rm する形にしたところ、ガードが通る成功経路（最頻）で毎回リークした。TMPDIR に 780 件蓄積していたのを実測で確認。同ファイルの既存 tempfile は例外なく「先頭で空文字列に先行宣言 → cleanup 関数に登録 → trap で回収」というパターンを取っており、新規分だけがそこから外れていた。3 reviewer が独立に検出。教訓は「新規 mktemp を足すときは、そのファイルの cleanup 関数の引数リストを見て、そこに載っていなければ設計が違う」。テスト側にも hygiene pin（成功経路実行後に tempfile が残らないこと）を置けば mutation で守れる。

2. **限定句は、同じ主張をしている全箇所に同時に入れる**: 「この記述は形式契約であって現在の配線状況ではない」という限定句を、サブフィールド表と型ガード節には入れたが、invariant #6 と reviewer 向け自問 5 には入れなかった。結果、同一ファイル内・同一注入プロンプト内で「配線は後続」と「6.1.a が auto-correct する」が併存した。段階分割 PR で未配線を明示するときは、その機能について現在形で語っている箇所を grep して一括で処理する必要がある。

3. **順序契約は両端を pin する**: 「A と B の間に挿入」という要求に対し、下側（B より前）だけを pin して上側（A より後）を pin しなかった。上側を移す mutation が SURVIVE することで露見。上側の退行は「required-fields で弾かれるはずのファイルが型ガードで弾かれ、rename されなくなる」という副作用の消失として観測できたが、既存 fixture では両者の差が出ない形状（`findings` キー自体が無い）だったため検出できなかった。区間制約は「下限を破る fixture」と「上限を破る fixture」を別々に用意する。

4. **否定 assertion は終端値を固定しない**: reject 経路で `assert_err_lacks "REVIEW_SOURCE=local_file"` としても、routing 先が fallback に変わったケースを通す。schema が「この失敗はすべて Priority 3 へ」と定めているなら、その終端値を positive に assert する。P0 側には cycle 1 でこの補強を入れたのに P2 側に入れず、mutation が片側だけ SURVIVE した。
