### Fix Patterns

**正確さを条件の列挙で担保する方向は、条件が増えるほど In Scope から離れて破綻する**: 「X されます」の主張を正確にするため条件節を cycle ごとに足した結果、利用者向けの案内が 3.6 倍に膨張し、Issue が置き換える対象として名指しした「診断の羅列」を再生した。しかも列挙は必ず漏れる（3 経路のうち 2 つしか書けていなかった）。**案内先が条件に依らず有限個に閉じるなら、条件ではなく案内先を書く** — 全経路をカバーしつつ列挙より短くなる。正確さと簡潔さはトレードオフではなく、参照する軸を変えれば両立する。

**レビュー指摘への対応が 4 cycle 連続で同じ箇所を加筆しているとき、加筆そのものが誤った方向である可能性を疑う**: cycle 2〜5 の指摘はすべて正当だったが、対応が毎回「条件を足す」だったため文面が単調に膨張した。Simplification-First の Escalation trigger（前 cycle の fix が導入した箇所への指摘）が発火したら、加筆ではなく「その機構ごと削除して根から消せないか」を先に検討する。

**「警告が出ます」型の案内は surface（どこに出るか）まで辿ってから書く**: 案内した WARNING は hook が stderr ごとログファイルへリダイレクトするため利用者に届かなかった。無警告を「正常」と読ませる誤誘導になる。

**粒度合わせは述語の対象まで揃える**: 「recovery=auto になるのは X かつ Y のとき」を別箇所へ「記録は X かつ Y のときのみ」と写すと、「記録は記録が verify できたときのみ」という循環になる。実装では記録は X のみで gate され Y は別の値を決めていた。
