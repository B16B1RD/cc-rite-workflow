### Fix Patterns

**テンプレート準拠の fixture だけでは、実データの構造的逸脱を検出できない**: `## ソース` 除外の範囲を検証する fixture をページテンプレートに合わせて作ったが、テンプレートでは当該見出しが最終節のため「見出し以降 EOF まで打ち切る」実装と「節スコープ」の散文が同じ結果になった。実データでは生成器 (wiki-ingest) が見出しの後ろに別の節を追記しており、13 ページ・81 hits の盲点として初めて現れた。**生成器がどんな構造を作りうるかを、テンプレートではなく実データで確認してから fixture を設計する。**

**同一の除外を 2 実装に持つと、判定順序の違いで片側だけが安全になる**: 一方はフェンス判定を他の分岐より前に置いたため構造的に fence-safe だったが、もう一方はフェンス保護が無くコードフェンス内の見出しで走査が止まった。同じ除外を 2 箇所に書くときは、regex だけでなく**判定順序まで揃える**。

**mutation テストは、mutant が到達しない除外を素通りさせる**: 差分ガード (sed が no-op なら fail) は機能して vacuous pass を防いだが、mutant がフィルタ本体の一部 (frontmatter 除去) を残す設計だったため、その除外だけ mutation からも fixture からも到達不能で無防備のまま残った。**mutation の設計時に「どの除外がその mutant で測れないか」を列挙し、測れないものは fixture 側で pin する。**

**テスト内に被テスト対象の regex を複製すると、実装が変わっても落ちない**: 語境界のテストが helper を実行せず、テストファイル内に手書きした regex リテラルを検証していた。実装から語境界を削除しても全 assertion が緑のまま通った。

**貪欲な量指定子の下では、語境界は件数メトリクスに対して挙動不変**: `[0-9]+` が数字列の末尾まで到達するため、語境界の有無で件数は変わらない。件数ベースの assertion では原理的に検出できず、静的 pin か行内容ベースの検証に切り替える必要がある。

**「実測した」ことと「assertion がある」ことは別**: 非回帰の 2 項目は実測で確認済みだったが、対応する assertion がスイート全体に存在しなかった。チェックリストを実測だけで埋めると、次の変更で静かに壊れる。

**parity を宣言したコメントが実装より先に書かれる**: sibling helper との整合を冒頭コメントで宣言しながら、rc 判定もエラーフィールドも未実装だった。`set -e` を設定しない根拠として「`$?` を明示チェックする」と書いたが、ファイル内に `$?` は 1 箇所も無く、そのコメント自身が唯一の出現だった。**「なぜこの安全機構が不要か」を書くコメントは、その前提が実装に存在することを確認してから書く。**

**空文字判定は「空」と「読めなかった」を畳んでしまう**: コマンド出力の空文字で失敗を判定すると、正当な空入力が失敗として数えられ、逆に部分的な失敗が成功として集計から抜ける。rc で切り分け、失敗件数を出力契約に載せる。

**検出範囲を狭める用語変更は、同一概念の説明箇所すべてに及ばないと半端に終わる**: 用語の正規化を 2 箇所で行い 3 箇所に旧表記が残った。同一概念の説明が 5 箇所に分散していたことが原因。

**実測値は下流 Issue のスコープ入力になる**: 過少な値のまま下流へ渡すと、漏れた分がどの Issue にも属さなくなる。検出ロジックを直したら、記録済みの数値 (コミットメッセージ / PR 本文 / 作業メモリ / 下流 Issue のタイトルと本文) を列挙して同時に更新する。
