### Fix Patterns

1. **前提が overclaim だと分かったら、その上の機構は直すのではなく削る**
   「2 形式混在で構造が崩壊する」を根拠に分岐 3 系統 + 移行手順 + 退避規則を足したが、実測すると崩壊するのは「テーブルの内側に挿入した場合」だけで、別ブロックなら共存する。限定を落とした主張だけが機構の拠り所だったため、前提を正確な限定に書き換えると機構そのものが不要になった。結果 44 行 → 34 行の純減で、blocking 2 件と non-blocking 2 件が同時に消滅した。
   教訓: 機構の欠陥を 1 つずつ潰す前に、**機構を正当化している前提文を実測で検証**する。前提が過大なら修正コストは機構の削除で回収でき、以後の cycle も軽くなる。

2. **仕様が「A か B」と択一で書いている選択肢を両方実装していないか確認する**
   Issue のエッジケースは「実形式を検出して従う **か** テンプレートと形式を揃える」の択一だった。後者を実施した後に前者（移行機構）も足したため、仕様非要求のスコープを自分で抱え込んでいた。
   教訓: 仕様のエッジケース記述に `か` / `or` があるときは**どちらを採ったかを明示**し、もう一方を実装しない。両方やると相互作用の検証責任も両方分だけ増える。

3. **構造化データの部分更新より行全体の再生成のほうが単純で安全**
   「リンク一致で行を同定する」で誤爆を防いだつもりでも、同定後に列位置でセルを特定すれば、既に列がずれているデータ（実測 298 行中 16 行）では別のセルを破壊する。行全体を規定形式で再生成すれば列を数える必要がなく、既存の壊れた行も更新のたびに漸次是正される。
   教訓: 部分更新の指示は「どの列か」の解決を必ず要求する。**再生成に置き換えると解決自体が消える**。改修前の実装が位置非依存（セパレータキー）だった場合、位置依存への変更は退行なので diff で気付ける。

4. **形式変更は「実行時に読まれる参照ファイル」まで洗う**
   書き手の指示とテンプレートを直しても、skill が実行時に読み込む共通参照（構造契約表）が旧形式を宣言していると、実行 LLM は同一セッションで相反する 2 契約を受け取る。SoT 列に自分が変更したファイルを名指ししている表は特に危険。
   教訓: 形式を変えたら `grep` の対象に**skill の参照チェーン内のファイル**と**同一初期化 run で配られる他テンプレート**を含める。

5. **false positive の除去で検出器の欠陥が露出したら、phantom を復活させず別 Issue に切り出す**
   テンプレートからサンプルリンク入りコメントを消したところ検出器の enum が変わった。原因は検出器が全文 grep でコメント内 placeholder を実登録と誤認していたこと。緑を維持するためにコメントを戻すのは「走査不能」と「真に 0 件」の混同を覆い隠す行為で anti-pattern。
   教訓: **どちらの挙動が正しいかを先に決める**。正しい側を採り、露出した欠陥は別 Issue にする。挙動変更は commit message と PR 説明に明記する。

6. **accept は撤回可能な暫定判断として使い、範囲が狭まったら実行する**
   follow-up scope として accept した指摘が次 cycle で 2 名から current-pr として再指摘され、かつ対象ファイルがすべて Non-Target 外だったため、accept を撤回して全て修正した。fingerprint state file の削除が documented な撤回経路。
   教訓: accept は「今は触らない」の記録であって恒久免除ではない。**再指摘で範囲や根拠が変わったら再評価**する。撤回したら state file を消して記録を実態に合わせる。

7. **停止条件を事前に宣言しておくと、削減の判断が感覚論にならない**

   教訓: fix-introduced 指摘の**比率と集中箇所を cycle ごとに数える**。停止条件は結果を見る前に宣言する。
