### Fix Patterns

trend 8 → 5 → 4 → 6。**cycle 3 で「実測アンカーの無い散文指摘」を 11 件修正したことが、cycle 4 の HIGH 4 件を直接生んだ**（reviewer の言葉で「cycle 3 が追加した mandate 5 が…」「F-07 の修正で追加された例外が…」「Execution condition を拡張した一方で…」）。本サイクル最大の学びはここにある。

1. **非実測（字面整合クラス）の散文指摘は、修正の複製率が 1 を超えることがある**（最重要）。散文の矛盾を直すと、直した記述が新しい矛盾面になる — 手順書は相互参照の網なので、1 箇所の条件を変えると参照している側の条件・retry 手順・表示条件・テンプレート選択がすべて追随対象になり、そのどれかを漏らすと次サイクルの指摘になる。実測アンカーのある指摘は「壊れた成果物が観測できる」ので直せば終わるが、散文指摘は「2 つの記述が食い違う」ので直すと 3 つ目が食い違う。教訓: **非実測の散文指摘は、実行時に主機能を打ち消すものだけを例外的に直し、残りは Decision Log で明示的に後続 Issue へ切り出す**。「安いから直しておく」は収束を遠ざける。

2. **どのレーンが blocking を生むかを測ってから労力を配る**。cycle 2〜4 を通じて prompt-engineer / tech-writer レーンは実測 blocking をゼロ件しか生んでいない（両者自身が「決定論的に観測不能」と申告している）。一方 blocking はすべて helper 実装とテストスイートから出た。教訓: **収束させたいなら、実測アンカーを出せるレーンの指摘を優先する**。散文レーンの指摘は品質に寄与しないという意味ではなく、「mergeable への到達」という目的関数に対しては寄与しないということ。

3. **同居する複数世代のファイルを読む helper は run 境界を持たなければならない**。`.rite/review-results/` は cleanup まで同一 PR の複数 run を同居させるため、`find | sort -r` の先頭は「前サイクル」ではなく「前 run の最終」になりうる。同じディレクトリを読む sibling は既に run 開始点 pin でこれを解決していた。教訓: **同じデータソースを読む兄弟実装を先に読む**。解決済みの問題を独立に踏み直すことになるし、pin を共有すれば新しい状態も新しい書き手も増やさずに済む。

4. **`rc == 0` は「成功」であって「結果が非空」ではない**。`git diff` は差分ゼロ行でも rc=0 を返す。「前回起点から新規 commit が無い」状態（accept-only cycle で必ず成立する）が成功として通り、審査対象も解消検証の材料も空の prompt が生成された。教訓: **外部コマンドの rc と出力の有無は独立した判定材料として両方見る**。特に「その出力を下流が消費する」場合、空は成功ではない。

5. **単一行の区切り文字付き marker channel へ値を出すなら、値の「形」を検査する**。型（string）と非空だけでは足りない。改行が入れば 2 本目の整形式 marker が出て後勝ちで別フィールドが解決され、区切り文字（`; `）が入れば同一行に重複フィールドが付き、接尾辞除去で空になる値は phantom 要素を生む。教訓: **改行だけを潰す対症では足りない。消費側の文法で意味を持つ全文字を含む allowlist（形の正規表現）で一括して閉じる**。型検査を足した時点で「形も見ている」と錯覚しやすい。

6. **その修正が実行時に効くかを、テストが 1 本も見ていないことがある**。別スキルの handoff 実行時文字列を書き換えたが、どのテストもそのファイルを参照しておらず、旧文言へ戻しても全スイートが同一結果だった。教訓: **スコープ外のファイルへ意図的に手を伸ばしたら、その変更を pin するテストも同時に足す**。Decision Log に理由を書くのは人間向けで、回帰は止められない。

7. **新しい fail-safe を足すと、既存テストの fixture がその条件に該当することがある**。`empty_diff` を足したら、別スイートの fixture が「commit_sha == HEAD」だったため正しく発火して落ちた。教訓: **fail-safe の追加は「テストが壊れた」ではなく「テストの前提が実は退化していた」の signal** として読む。fixture を新条件に合わせるのが正しく、fail-safe を緩めるのは誤り。
