### Fix Patterns

cycle 4 の 7 指摘のうち 2 件は「既存構造の前提を確認せずに要素を足した」型で、これが 4 cycle を通じて最も再発した失敗パターンだった。

1. **Markdown の入れ子 fence は外側を 4-backtick にする**: テンプレート全体が 1 本の 3-backtick fence で囲われている文書に、記入例の fence を 3-backtick で 4 本追加したところ、fence が閉じ位置で分割され code と prose が反転した。追加の主目的だった記入例が prose になり、後半の推奨事項・READ-ONLY 節が code に閉じ込められた。同じリポジトリ内に「外側 4-backtick で内側 3-backtick を透過的に含む」という先例が既にあり、それを参照していれば防げた。この破損は 4 cycle 気付かれなかった — レンダリング結果を見ないと分からない類の欠陥は、レビューでも発見が遅れる。

2. **few-shot の「実測した」は実際に実測してから書く**: 実測手順として書いた `curl -X POST ... -d '{json}'` に `-H 'Content-Type: application/json'` がなく、主張した観測結果 (JSON として parse され生値が db に到達) が出ないコマンドだった。few-shot は形をそのまま模倣されるため、「もっともらしいコマンドを書く」挙動を学習させてしまう。実測手順とアンカーの文字列は一致させ、「手順で走らせたものをそのまま貼る」形を示す。

3. **対称性の取りこぼしは同じ cycle 内で繰り返す**: cycle 3 で hygiene pin の片側性 (P0 のみ) を直したが、同じ cycle で追加した上側境界 pin は P2 のみで、P0 側が欠けていた。「片側だけ直す」を指摘された直後に別の pin で同じことをしている。対称な実装に pin を足すときは、その場で両側に置いたか確認する。

4. **短絡形式の `rm` は失敗を silent 化する**: `[ -n "$v" ] && rm -f "$v"` は同ファイルが既に是正済みの形式だった (WARNING を出す if 形式に直されていた)。新規コードがその是正前の形に戻していた。tempfile が trap に登録済みなら inline rm 自体を削除するのが最も簡潔で、失敗の握り潰しも起きない。

5. **no-rename 分岐には脱出手順を書く**: rename しない設計判断は妥当でも、同一ファイルが毎回選ばれて同じ WARNING を出し続ける。sibling の no-rename 分岐はいずれも「/rite:pr-review を再実行すれば新しいファイルが選ばれる」等の脱出路を提示しており、新設分岐だけが「なぜ rename しないか」しか書いていなかった。
