**教訓を一般化すると**: fix cycle でコメントを厚く書くと、次 cycle の finding 供給源を自分で作る。書くべきは「なぜこの形を選んだか」のうち**実装を読んでも分からない部分だけ**で、実装を読めば分かること・外部の事実・自分の assert が検証していないことは書かない。

### 「前提条件の確認」を assert にすると恒真になりやすい

cycle 2 で追加した「分岐が実際に走ったことの確認」assert は、その前提（占有ファイルの存在）を作るのがテスト自身であるため、**いかなる実装変異でも FAIL しない**恒真式だった。しかもコメントが「これがないと上の assert が vacuous になる」と主張していたため、読み手には vacuity guard に見えた。実際の vacuity リスク（state root が別ディレクトリへ解決する）ではこの assert は PASS のままで、検知していたのは隣の assert だけだった。

**判定手順**: 「前提が成立していること」を assert に書く前に、**その前提を壊す実装変異が存在するか**を問う。存在しないなら恒真であり、assert ではなくコメントで足りる。存在するなら、その変異を実際に当てて FAIL することを確認する。

### skip ガードの背後に全カバレッジを置かない

AC-2 を検証する 2 つの TC が両方 `chmod` プローブの else 側にあり、root / WSL2 DrvFs / overlay マウントでは**両方 skip して AC-2 のカバレッジが皆無**になっていた。しかも skip は FAIL ではないので結果表示から判別できない。cycle 2 で 1 本を permission 非依存（パスを regular file で塞ぐ）に移したが、もう 1 本は残っていた。cycle 3 で 2 本目も permission 非依存（パスをディレクトリで塞いで EISDIR）に移し、**プローブが skip するホストでも AC-2 の床が 2 本残る**状態にした。

検証方法が有効: **skip ガードを skip 側に固定した状態で mutation を当てる**。修正前は `PASS 191 / FAIL 0`（素通り）、修正後は `FAIL 2`。skip ガードを持つ TC を書いたら、この「skip 固定 + mutation」を必ず一度実行する。
