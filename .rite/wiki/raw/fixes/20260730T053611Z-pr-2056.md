### Fix Patterns

散文手順（LLM が runtime で読むワークフロー定義）を新設・修正するときの最大の欠陥源は、**手順が実行されるフローの実際の制御構造と突き合わせていないこと**だった。文面は単体では正しく読めるのに、フロー上に置くと成立しない形が 3 種類ある:

- **分岐で迂回されるステップの値を要求する**: 「ステップ 4.1 で確定した値を使う」と書いた手順が、4.1 を通らない分岐パスからも参照されていた。手順を書いたら、それを参照する全 consumer が本当にその前提ステップを通るかを分岐表まで遡って確認する。分岐が排他なら片方だけが通る前提を全体に書いてはいけない。
- **承認ゲートを跨いで書き換える**: 「差分表示 → ユーザー承認 → 適用」の順序を持つフローで、表示後・承認前に本文を自動付記すると、承認した内容と適用される内容が乖離する。自ら「付記も書き換えだから承認下に置く」と明記した文書が、別経路でその原則を迂回していた。付記候補を確認に載せ、承認後にのみ適用する形へ倒す。
- **対象がまだ存在しない地点に指示を置く**: 「後続ステップ X で生成するものに検査を適用せよ」を X より前に書くと、線形実行する LLM は X の地点でそれを思い出さない。実行地点側に導線が無ければ、その指示は書かれているのに一度も実行されない。**移設できないならスコープから外して削除する** — 実行されない指示を残すより、範囲を狭めて明示するほうが良い。

そのほかの経験則:

- **結論が正しくても前提が偽なら直す**: 「分解パスは見込み Complexity が L/XL のため全検査」は、結論（全検査）が無条件なので挙動は正しいが根拠が偽（分解推奨は 4 条件の OR）。誤った根拠は後続の編集者が範囲を狭める余地を残すため、挙動不変でも修正対象になる。正しい根拠は helper 契約が定める固定値だった。
- **宣言と処理表が矛盾したら、仕様と逐語一致する側を正とする**: 「外部仕様へ広げない」という宣言と「外部仕様には要検証を付記する」という処理表が同一文書内で衝突していた。仕様の 3 値表が後者と逐語一致していたため、宣言側が広すぎたと判断して禁止対象を「検査・実測」に限定した。処理表を削ると仕様違反になる。
- **前 cycle の自分の修正が次 cycle の指摘を生む**: 追加した 1 行が、同 PR 内の SoT が明記する規約（`-R <owner>/<repo>` 必須）に違反していた。修正を入れる際は、同 PR 内で自分が書いた規約・警告文と矛盾しないかを確認する。
- **placeholder を新しいテンプレートへ持ち込む前に置換表を確認する**: 置換表に無い placeholder を書くと未置換のブレースが下流のプロンプトへ漏れる。表を増やしたくないなら placeholder を使わず自己完結した指示文に落とす。
- **番号引用は修正時にも増やさない**: 指摘に応じた説明を書き足すとき、つい `Issue #N` を引きたくなるが、それ自体が別の規約違反になる。書いた直後に `grep -oE '(Issue|PR) #[0-9]+'` で 0 件を確認する。
