### Fix Patterns

- **外部 API の enum を散文で言い換える前に introspection で値域を実測する**: `IssueStateReason` を 2 値と思い込んで書いた SoT 散文と、2 値しか捕まえない `case` と、残りを黙って畳む catch-all の 3 者が同時に成り立たなくなっていた。5 reviewer が独立に同じ根因へ到達した。修正は「値域の誤りを認めて散文を正す」+「catch-all を沈黙させない」で、dispatch そのものは契約どおりに保った。
- **catch-all は「既知で正しい値」と「未知の値」を分けてから使う**: 期待値を明示アームに narrow し、残りを WARNING 付き catch-all に降格すると、未対応値が沈黙で誤配される経路が消える。隣の分岐が WARNING を出しているのに catch-all だけ無言、という非対称が検出の手がかりになった。
- **negative control のないガードは緑のまま壊れる**: catch-all に WARNING を足したら「正常値がその枝に落ちていないこと」も同時に pin する。これが無いと全行で警告が出る退行が全テスト緑のまま通る。
- **contract literalism と仕様の前提崩壊の切り分け**: 契約が誤った前提の上に書かれていたとき、dispatch は契約どおりに保ち、誤った前提そのものは Decision Log に訂正として記録し、未決の設計判断は WARNING で可視化して判断待ちにした。実装を勝手に「正しい方」へ寄せるのでも、黙って契約に従うのでもない 第三の出口。
- **SoT に universal を書くと既存の非準拠経路が反例になる**: 「どの自動経路もここから読む」と書いた瞬間、現在値を読まずに固定値を書く既存 reconciler が主張を偽にする。主語を実際の consumer へ狭め、非準拠経路を「既知」として表に載せるのが、嘘を書かずに済む書き方。
- **派生文書は SoT の限定句ごと写す**: SoT 側が「option が無い board では lookup が失敗する」と限定していたのに、rationale 側の言い換えが無条件化していた。限定句の脱落は、派生側だけを読む人間に到達不能な保証を約束する。
