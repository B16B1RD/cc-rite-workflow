### Fix Patterns

**fail-loud 化の増分価値は、その出力が通る全段を実測して初めて確定する**。cycle 1 で無音の失敗経路を「WARNING + 原因の併記」へ格上げしたが、原因を通す中和フィルタがバイト単位で 0x80-0x9f を潰すため、ロケール依存の errno（日本語）が `?` の羅列に化けていた。primary WARNING は純 ASCII だったため無傷で、**静的レビューでも「原因を出している」ようにしか見えなかった**。cycle 2 で実機のロケールで走らせて初めて surface した。教訓は 2 つ: (a) fail-loud の価値は「何が起きたか」の情報量にあるので、その情報が出力経路の全段（中和・整形・字下げ・端末）を通過できるかを実測する、(b) 同じ経路に ASCII と非 ASCII が混在すると、ASCII 側だけを見て「動いている」と誤認する。

**修正は「上流を制約する」方が「下流を緩める」より安全**。errno のモジバケに対して中和フィルタを弱める（`--c0-only` 等）選択肢もあったが、それは中和の目的そのものを削る。採ったのは失敗するコマンドに `LC_ALL=C` を前置して**上流メッセージを ASCII 化する**方法で、中和フィルタは何も変わらず、その行に対して no-op になるだけ。**「安全機構が邪魔をする」と感じたときは、安全機構を緩める前に、その機構に渡る入力を安全機構が問題視しない形へ変えられないかを探す**。なお `LC_ALL=C` prefix が bash 自身の redirect-setup エラーのロケールに効くことは POSIX の simple command 処理順（redirection が assignment より先という読み方もある）から自明ではないため、必ず実測すること — 本 cycle では実測して効くことを確認した。

### 列挙に項目を足すときの検査項目

cycle 1 の drift のもう 1 件は、仕様書の「A / B / C はいずれも述語 P を満たす」という列挙へ新経路 D を差し込んだが、**D は P を満たさなかった**というもの。しかも同一コミットが追加したコード内コメントが D について P の否定を明記しており、doc とコードが 1 コミット内で自己矛盾した。

**列挙は「関連する項目の集合」ではなく「同じ述語を共有する集合」である**。項目を足すときは、共有述語が新項目にも成立するかを個別に検証する。成立しないなら列挙から外して別文にする。この検査は grep では出ず、列挙の述語を読んで新項目の実装と突き合わせる以外にない。レビュー側から見ると、これは「列挙 + 新規追加行」という diff 形状で検出できる — 該当したら述語の適合を必ず問う。
