### Fix Patterns

**prose gate に機械強制を併置するときは「消す主体を 1 つに絞る」**。post-condition gate を LLM の会話 grep で守る設計は、gate の発火は保証できても gate の評価そのものは保証できない。ファイル 1 個の存在検査に置き換えると LLM の認識から独立するが、その際は (a) 消す主体を実際の動作主 (helper の EXIT trap) だけに限る、(b) gate 側では消さない (消すと動作させずに再評価だけで通せる)、(c) 動作の成否ではなく完走だけを伝える (非ブロッキング契約を gate に持ち込まない)、の 3 点が要。引数検証で trap 設置前に落ちる経路では marker が残るため、「動作の失敗 (非ブロッキング)」と「呼び出し側のバグ (loud)」が marker の有無にそのまま写る。

**前方一致退行の pin は両方向の fixture が要る**。`[ "$a" != "$b" ]` を `[ "${b#$a}" = "$b" ]` へ退行させる変異は非対称で、片方向 (短い値が長い値の接頭辞でない向き) では不一致判定が保たれて緑のまま通る。「この軸の唯一の pin」とコメントに書いた箇所ほど、実際に両方向を覆っているか mutation で確かめる。

**`awk -v` に正規表現を渡さない**。`-v` はバックスラッシュエスケープを代入時に解釈するため `'^### 8\.0 '` が `^### 8.0 ` になり、警告が出るうえアンカーが弱まる。区間解決のような多数の pin が土台にする helper では影響が広い。`ENVIRON["name"]` 経由なら書いたとおりの ERE が届く。

**同じ節に 2 つ目の表を置かない**。gate 節の Routing 表を per-row canonical で pin している場合、同節に別表を足すと行数・allowlist 系の pin が壊れ「gate 表」の同定も曖昧になる。分岐は箇条書きで書くか、表は別節へ置く。
