- **経験則 1: 無音の縮退を塞ぐ機構をラッチ形式（開始トークンで立て、終了トークンで倒す）で実装したら、EOF 時点でラッチが立ったままかを必ず終端検査する。**
  記法例コメントを落とすために HTML コメントのラッチを入れたところ、閉じタグが来ないまま EOF に達する経路で以降の全行が落ち、カウンタにも WARNING にも現れない状態が生まれた。**塞ごうとしていた silent-0 を、塞ぐための機構が反対側から再導入した**形。fence / frontmatter / コメントなど「開始と終了の対で囲む」除外はすべて同じ構造を持つため、終端検査は除外規則の追加とセットで書く。
- **経験則 2: 全滅形だけを想定したガード条件は、部分欠損形を必ず取り逃す。**
  検出失敗ガードは `entries == 0` を条件にしていたため、「エントリを 1 件数えた後にラッチが立つ」形では entries>=1 となり構造的に発火できなかった。**ガードの条件を選ぶときは部分失敗の形を先に作ってから決める**。今回は判定をラッチ変数自身に置くことで両方を覆った。回帰テストでも部分欠損形が「もっともらしい誤った修正（`entries == 0` 併用）」と正しい修正を分ける唯一の assertion になっている。
- **経験則 3: 語彙統一・前提訂正は着手前に「何箇所あるか」を数え、完了後に訂正後の表現で全文検索して残存 0 件を確認する。**
  6 指摘中 5 件が「N 箇所のうち M 箇所しか直していない」型だった（enum 説明 / docstring / 部分失敗 WARNING / 同一セル内の隣接主張）。この型は機械的に潰せるのに、修正手順に検索が組み込まれていないと毎 cycle 再生産される。
- **経験則 4: 同格の主張が並ぶ場所で片方だけに「これは未検証」と修飾を付けると、残りが検証済みだと読まれる。**
  隣接する 2 つの conformance 主張の一方だけを「指示であって観測ではない」と名指した結果、無修飾で残った他方（実際には事実に反する）が観測事実として読める状態になった。修飾は主張単位ではなく**同格の主張の集合単位**でかける。
- **経験則 5: 修正が前 cycle の自分の変更に対する指摘のときは、クラス全体を 1 つの述語で閉じられないかを先に検討する。**
