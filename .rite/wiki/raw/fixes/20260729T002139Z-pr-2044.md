### Fix Patterns

「終端状態の表し方」に関する 1 つの原則が、この cycle の 4 件のうち 3 件を説明する。

1. **終端状態は「到達した事実」で記録し、境界値の一致で代用しない (最重要)**: サーキットブレーカーの「発火後」判定に `cycle_count >= max_review_cycles` を使っていたが、この等式は**最終 cycle を実行中ずっと成立する通常状態**でもあった (counter を書いてから review を invoke する順序のため)。結果、最終 cycle 中の中断→復帰が「発火後の再実行」と誤認され、ブレーカーが一度も発火しないまま上限が無通知で 2 巡分に緩んだ。修正は発火時に `max + 1` を書いて発火済みを状態として記録し `-gt` で判定する形。**カウンタが上限に「達している」ことと上限に達して「停止した」ことは別の状態であり、前者は後者の必要条件でしかない**。同種の判定を書くときは「この述語は、その状態に向かっている途中でも真にならないか」を必ず問う。

2. **1 つの述語に 2 つの用途を持たせない**: 上記の修正過程で、「発火済みか (fresh/resume の判定)」と「reset 失敗時に即再発火するか (通知文面の判定)」が別の述語 (`-gt` と `-ge`) を必要とすることが判明した。変数を `cb_fired` / `cb_will_refire` に分けた。1 つの boolean を 2 箇所で使い回すと、片方の要件が変わったとき他方が静かに壊れる。

3. **条件付き出力の存在を、後段の指示文が無条件に断定しない**: stderr 退避を足したが mktemp 失敗という縮退経路が残り、その場合診断は 1 行も出ない。にもかかわらず停止通知は「診断を確認してから再実行」と断定し、トークンも診断あり/なしで同一だった。**縮退の有無をトークンに載せて後段が分岐できるようにする** (`failed-refire` / `failed-refire-nodiag`)。「捕捉できた場合のみ出力される」ものを「出力済み」と書かない。

4. **不変条件を宣言したら、同じ PR の diff 全体を宣言に照らして読み直す**: 「両分岐は同構造で差は sentinel の消費者だけ」と宣言した同じ PR が、片方の分岐にだけ注意行を足して宣言を偽にしていた。宣言文は diff の他の部分に対する assertion であり、書いた時点で検証義務が発生する。

5. **相互排他な 2 規則を隣接段落に並置しない**: 「resume では継続」と「上限到達でリセット」が並び、実行主体 (LLM) がどちらを適用するか決定できない状態になっていた。分岐条件を状態語で一意に書く。
