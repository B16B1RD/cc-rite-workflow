### Fix Patterns

cycle 8 の 7 件は「**前 cycle で塞いだ穴と同じ型が、同じファイルの別の場所に残っていた**」が中心。移植性/検証機構の PR が終盤で踏む反復構造として、最重要の教訓を記録する。

1. **ミューテーションは「直した箇所」ではなく「そのテストが守ると主張する全アサート」に当てる**（F-01 CRITICAL、本 cycle 最大の教訓）
   前 cycle で「成功行のアサートが集計行にもマッチする」穴を見つけ `assert_line_matches` で塞ぎ、3 種のミューテーションで確認した。しかし**同じファイルの失敗ファイル名のアサート**が、runner の `=== Running: X ===` 進捗行にマッチしたまま残っていた。この行は結果に関係なく全ファイルについて出るため、失敗リストが名前を出さなくなっても 4 assertions が永久に green。しかも TC-4 のコメント自身が「ファイル名を出す行が消えるのを防ぐ」と書いており、**守ると宣言した軸そのもの**が未 pin だった。
   → **規則: アサートごとに「これが守る挙動を壊したら赤くなるか」を 1 つずつミューテーションで確認する。** 直した箇所だけを検証するのは「修正の確認」であって「テストの検証」ではない。
   → **規則: 文字列マッチを書いたら、被テスト対象がその文字列を別の目的で出していないか grep する。** 進捗行・ヘッダ・診断文は同じ識別子を含みやすい。

2. **`set -o pipefail` 下の `$(cmd | grep ...)` は、no-match でスクリプトごと落とす**（F-02）
   `line=$(printf ... | grep -F "$needle" | tail -1)` は grep の rc 1 が代入の失敗になり errexit を起こす。直後に書いた `[ -z "$line" ] && fail "..."` は**到達不能**で、needle が消えたとき（= そのテストが守る regression が起きたとき）だけ診断が消え、以降の assertions も走らない。
   → **規則: 「マッチしないこと」が正常系にありうる grep は `{ grep ... || true; }` で局所的に無害化する。** `|| var=""` で代入全体を握るのは `tail` / `printf` の失敗まで飲むので不可。

3. **「N 象限を pin した」と言うときは、軸が直交しているか確認する**（F-03）
   「4 象限（失敗 × drift）」に `失敗 × 正しく計上された skip` のセルが無く、各 TC のサンドボックスが 1 ファイルだったため**集計の積み上げ**が一度も実行されていなかった。パーサ 2 種のうち 2 つ目に至っては、1 つ目が先にマッチして到達すらしていなかった（`SKIP: N` を出すと `Results:` パーサに届かない）。
   → **規則: 象限を主張するなら各軸の値が独立に変化するケースを列挙して埋める。** 集計を pin するなら入力を複数に、フォールバック経路を pin するなら先行経路が空振りする入力を作る。

4. **仕様を「契約」と呼ぶなら、契約違反時に何がどこまで壊れるかを実測する**（F-07）
   `_timeout` の docstring は「reproduces timeout(1)'s full exit-code contract」と宣言していたが、保証されるのは exit code だけで**期限（deadline）は保証されていなかった**。GNU timeout は子を独自プロセスグループに置いてグループへシグナルを送るが、perl シムは直接の子にしか送らないため、孤児が捕捉パイプを保持すると 1s 期限に対し 30s ブロックする。runner が `$( )` 捕捉に変わったことで、この差が CI job timeout に直結する構造になっていた。
   → **規則: `setpgrp(0,0)` + `kill "TERM", -$pid` で GNU と同じ範囲にする。** 契約を謳う docstring は、保証する軸（exit code / 期限 / stdin 継承）を個別に列挙する。

5. **複製を強制する機械的検査を入れたら、その契約を文書化する**（F-04）
   `_timeout` は 6 ファイルに inline 複製され、TC-7 が byte-identity を、TC-8 が guard 存在を強制する。CONTRIBUTING は「`_test-helpers.sh` が提供し source 時に abort する」としか書いておらず、6 分の 1 の経路しか説明していなかった。文書だけ読んで本体を直すと TC-7 で落ちる。
   → **規則: 「複数箇所の同時変更」を機械的に要求するなら、その要求と floor 値の位置（統合時に触る場所）まで書く。**

6. **予約グリフ / 予約文字列の制約は導入と同時に文書化する**（F-06）
   `⏭️` はマーカーとして導入したが、実装は各テストの stdout+stderr **全体**を数えるため、被テストスクリプトが出しただけでスイート全体が落ちる。しかも失敗メッセージは無関係な自分のサマリ行を疑わせる。

7. **自分が課した規則は、同じ PR が触った全箇所に grep で確認する**（F-05）
   規則 6 に「capability probe には blocking gate の floor を張れ」と書いた同じ PR が、触った 3 つの `command -v jq` gate に floor を付けていなかった。なお他 7 ファイルの jq probe は `ERROR + exit 1` の hard fail で silent skip しないため対象外、と grep で全数確認してから修正範囲を決めた。
   → **規則: 規約を新設したら適用対象を機械的に列挙し、「対象外」の判断も根拠付きで記録する。**

### 検証手法の記録

本 cycle は **9 種のミューテーション**（失敗名 suppress ×2 / 集計行の gated group 削除 ×2 / 積み上げ→代入 / `[^❌]` ガード緩和 ×2 / 行アンカー除去 / bail 順序 revert / 成功行サフィックス削除）を全て KILLED まで持っていった。うち 1 種（`[^❌]` ガード緩和）は初回 SURVIVED し、原因を調べたところ「TC-8 が `SKIP: N` を出すため 2 つ目のパーサに到達していない」ことが判明、`Results:` 形式を使う TC-9 を分離して塞いだ。**ミューテーションが生き残ったら、テストを足す前に「なぜ届かないか」を実測で特定する。**
