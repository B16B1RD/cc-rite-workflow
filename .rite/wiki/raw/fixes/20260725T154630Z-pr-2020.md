### Fix Patterns

positive control を追加したとき、コメントに書く「control が無いと何が起きるか」の例が実際には到達不能なことがある。この PR では「不正な入力 JSON が正しい permit と読める」と書いたが、その入力ファイルは直前の jq が生成しており、失敗すれば `set -e` で control 到達前に落ちる。到達不能な例で存在理由を説明すると、次に読む人が control の役割を誤解し、削除しても安全だと判断しかねない。control が実際に捕捉する劣化（fixture の padding 不足でサイズ閾値を下回る / 入力フィールドの破損 / 対象が全入力を早期に通す退行）を mutation test で確定させてからコメントに書くべき。

control を「本体アサーションが実際に読む入力ファイルから派生させている」ことは、コメントに明記しないと失われる設計情報。同じ素材から独立に組み直した別ケースが既にあると「重複だから削除」と判断されるが、独立に組んだケースは本体側の入力生成が壊れても緑のまま通るため代替にならない。

「X を避けるために Y を使わない」と書いた直後に X と同じ構造のコードが置かれていると矛盾して読める。リスク階級が違う（片方は被テスト対象の出力、もう片方はテスト自作の入力で runner が loud に拾う）なら、その差を 1 行の但し書きで示す。

コメントのみの修正では「ロジック行の変更が 0 である」ことを diff で機械確認してからコミットすると、レビュー側の検証コストが下がる。
