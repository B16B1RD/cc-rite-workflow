### Fix Patterns

**テストの検証は「そのテストが実際に使う経路を変異下で走らせる」形でしか成立しない。**

cycle 1 で「実在しない見出しへの参照を作らない」ことを pin するアサーションを追加し、commit message に「修正前の状態でマッチする (= fail) ことを確認済み」と書いた。**これは誤りだった。** 検証に使ったのは素の `grep` (BRE) で、そこでは `\|` が選択子として機能するため「マッチする」と観測できてしまう。一方アサーション本体 (`assert_not_grep`) が使うのは `grep -qE` (ERE) で、`\|` は **literal のパイプ文字**になる。結果として「2 語をパイプで連結した 1 本の文字列」を探す、対象ファイルには決して現れないパターン = **常時緑の dead assertion** が「検証済み」として commit された。

- **教訓 1**: `grep` と `grep -E` はメタ文字の意味が反転する。選択子は BRE で `\|`、ERE で `|`。`assert_*` ヘルパーへパターンを渡すときは、ヘルパーがどちらを使うかを実装で確認する。
- **教訓 2 (より一般)**: 「このパターンならマッチするはず」という**推論**や、**別コマンドでの手元確認**は検証ではない。追加したアサーションは、**スイート本体を、そのアサーションが捕らえるはずの変異の下で走らせ、当該 assertion が FAIL することを目視する**まで検証されていない。cycle 2 では 3 件すべてをこの形で確認した (変異注入 → `FAIL: 1` / `FAIL: 2` を観測 → 変異を戻す)。

**同じ処理を 2 経路で実装したら、fixture の「意地悪さ」も 2 経路で揃える。**

新設した OKF 箇条書き経路の fixture は、リンク・区切り・サマリーがマスク処理と一切干渉しない素朴な形しか持たなかった。テーブル経路は生パイプ入りタイトルとコードスパン入りサマリーで相互作用を pin しているのに、箇条書き側だけ空白。結果、形式 dispatch の行頭 anchor を外す変異も、summary 抽出の match をマスク前の行へ向ける変異も、全 assertion 緑のまま生き残っていた。**素朴な fixture は経路の存在は測るが、経路の正しさは測らない。** 対応では 1 行足すごとに「どの変異を kill するために置くのか」をコメントで明示し、hits だけでなく `skipped_rows` も assert して件数の両側から捕らえた。

**準拠性の carve-out は、追加より同期漏れを生みやすい。**

SPEC 側に「index のカタログ形式は既知の逸脱」を足しながら、同じ話題を扱う reference の「**完全準拠した** bundle は visualizer で閲覧できます」を更新しなかった。しかも SPEC の carve-out が起動手順の参照先としてその節を名指ししており、読者は carve-out を読んだ直後に未更新の節へ送られる構図になっていた。**教訓: carve-out を 1 箇所に足したら「完全準拠」「フル対応」等の無条件肯定を同一トピックの全参照先で grep する。** 対応では前提を落とすだけに留め、**逸脱した形式を下流ツールが受理するかは断定せず「要検証」と明記した** — 断定すれば次 cycle の指摘になるだけで、未検証の事実は未検証と書くのが最も安い。
