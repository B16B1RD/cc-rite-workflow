### Fix Patterns

1. **分岐条件のキーは 1 つの観測量に統一する**（CRITICAL、cycle 1 の修正が生んだ欠陥）
   同一ステップに複数の分岐があるとき、一方を「節見出しの有無」、他方を「中身の形式」で条件付けると、**見出しは無いが旧形式で登録済み**のような実在形状がどちらにも一意に落ちない。字義実行すると新旧形式が混在し、それは他方の分岐が禁じている状態になる。検証 helper が形式非依存だと混在は lint で検出されない。
   教訓: 分岐条件を書いたら**全分岐の判定キーを 1 つの観測量へ揃える**（今回は「登録行の有無と形式」に統一し 3 分岐表にした）。加えて「その条件が偽になる実在形状」をプロジェクト自身の test fixture から探す — 今回は既存テストが該当形状を検証していた。散文や HTML コメント内の形式例を判定根拠から明示的に除外することも必要（成果物側に旧宣言が残っている場合があるため）。

2. **旧形式の仕様を削除しつつ旧形式へのフォールバックを残さない**（HIGH、3 レビュアーが独立検出）
   「実形式を検出して従え」というフォールバックは、従うべき形式の書式定義が同一変更で削除されていると実行不能になる。冒頭に無条件禁止文があると、フォールバックに従う行為そのものが禁止違反になる。
   教訓: フォールバックは**一方向の移行規定**（「旧形式は新形式へ移行する」）に置き換えるのが最も収束する。旧形式へ従う経路が消えれば旧形式の書式定義も不要になり、禁止文との precedence 衝突も同時に消える。禁止文は「本ステップの分岐で選択した形式以外を混ぜてはならない」のように分岐と紐付けて書く。移行時に必要な値が読めないレコードは推測値で埋めず退避して人間に委ねる。

3. **共通規約は全経路の親に置く。「共通」の係り先を明示する**（HIGH）
   セル破壊防止の規約を「新規追加」bullet 配下の sub-bullet に書くと、兄弟トップレベルの「既存更新」bullet には textual に適用されない。見出しに「全セル共通」と書いても、それは列の範囲を指す語で書き込み経路の範囲を指さない。
   教訓: 複数の書き込み経路に共通する規約は**全経路の親（手順リスト直下等）へ引き上げる**。「共通」という語は係り先（列 / 経路 / ファイル）が曖昧なので、係り先を列挙して書く（今回は「新規追加・既存更新・移行のすべての経路に適用」）。対象外の要素とその根拠（enum / タイムスタンプなので区切り文字を含み得ない）も併記すると読み手の推論余地が消える。

4. **カウント規則は母集団を拡張子・除外条件込みで書く**（HIGH）
   「配下の実ファイル数」と書くと初期化時に置かれる `.gitkeep` 等が混入し、現に正しい値を毎回ずれた値へ上書きする。読む consumer が存在しない数値は乖離を検出する主体がいないため silent に固定化する。
   教訓: 数値同期の指示は**母集団を `*.md` 等の形で限定**する。さらに「別の場所にある同じ量（テーブルのデータ行数）と一致すること」を不変条件として書くと、乖離が次の実行で気付ける形になる。0 件サイクルでの挙動も明記する。

5. **書き手の規約を変えたら生成物テンプレートの散文も同時に変える**（HIGH）
   テンプレートから展開される成果物の散文が旧形式を宣言したまま書き手の指示だけを新形式へ変えると、初回実行時の LLM は成果物自身の指示と skill の指示という相反する 2 契約を受け取る。別ステップでその成果物を Read する経路があると、単なる docs 陳腐化ではなく形式判定の競合入力として作用する。
   教訓: テンプレート側で**新形式の骨組み（見出し + ヘッダ行）まで生成**してしまうと、書き手側の新設分岐が防御的 fallback に退き混在経路も閉じられる。ただし骨組みの追加は別スキルの生成物の挙動変更なので、散文の是正（挙動に影響しない）と区別して commit message に明記する。

6. **表記変換規則を導入したら「等値」と説明している全箇所を洗う**（LOW-MEDIUM）
   「A は B と literal 一致させる」という括弧書きの等値関係は、B 側にエスケープ等の変換を義務付けた瞬間に偽になる。突合する lint が無ければ検出されない。
   教訓: 変換規則の導入時は該当語を grep して**どちらが SoT かを明示**する（「基準は変換適用前の生値」）。

7. **follow-up scope の指摘は accept (認知のみ) で終端させる**
   別 Issue 化が妥当な指摘は、fix loop の別 Issue 経路が廃止済みなら `accept` が設計上の終端。fingerprint を永続化すると次 cycle で自動 suppression され、commit trailer に `Acknowledged-finding:` が残って監査可能になる。別 Issue の起票は review 側の triage phase が担う。docs スコープの PR から無関係なファイル群へ手を伸ばすより、accept して SoT 収束を単一 Issue に切り出すほうがスコープ規律に合う。
