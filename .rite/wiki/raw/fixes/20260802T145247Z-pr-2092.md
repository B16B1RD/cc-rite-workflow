### Fix Patterns

**新しい抑止経路を追加するとき、補償制御の受け皿が実在するかを先に grep する**。
「filter するが記録は残す」という設計は、記録先に consumer がいて初めて成立する。
本 PR では既存の `監査ログ` セクションを補償制御に選んだが、それを読む統合ステップ・
schema フィールド・出力テンプレートのいずれも存在せず（grep 0 hit）、義務を課しても
記録は破棄されるだけだった。3 cycle かけて「全カテゴリ MUST 化 → 1 ケースへ縮小 →
義務ごと撤回」と辿ったが、最初に受け皿の実在を確認していれば 1 cycle で
「撤回 + follow-up Issue」に到達できた。

**AC が実体を持てないと判明したら、握り潰さず未達として明示し別 Issue で追跡する**。
本 PR の AC-2 後半（監査ログには残す）は、受け皿の新設が Issue の MUST NOT（新機構の追加）
に抵触するため本 PR では満たせない。fix 側で「満たしたことにする」誘惑が強い場面だが、
未達を明示して follow-up Issue を立てる方が、次に読む人間が状況を正しく把握できる。

**規約 PR は自分の新設原則を自分の diff に適用して検算する**。consumer のない記録先を
MUST 化するのは、同じ PR が新設した `no_speculative_structure` Rule 3 の違反だった。
新しい原則を導入する PR では、その原則で自分の変更を 1 度レビューする。
