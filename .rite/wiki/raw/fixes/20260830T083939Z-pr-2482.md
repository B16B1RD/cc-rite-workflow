### Fix Patterns

**正規化で 2 値を同一視したら、同一視の前提そのものを別 assert で固定する**。producer と validator で被演算子の変数名だけが違うとき、共通プレースホルダへ正規化して式を比較するのは妥当だが、その正規化は「両者が同じファイルを指す」という前提を暗黙に置く。式の比較ではその前提を確かめられない。実測: 呼び出し側の引数を別変数へ変えても全 assert が緑のまま通った。正規化を導入した変更は、同時にその前提を検証する 1 行を持つべきだった。

**「塞いだつもり」の assert は削除するか、塞げない範囲を明記する**。片側から抽出した期待値で等値を取る symmetry pin に「両側が同じ壊れ方をした場合も固定する」assert を足しても、期待値自体が片側から来ている以上、同時 drift では等値が保たれて通る。実測で 4 assert すべてが緑になり、その assert が先行 assert から論理的に含意される dead code だと確認できた。検出力が同じなら削除が正しい — テストコード中の偽りの能力主張は冗長性より有害で、次に読む人へ誤った安心を渡す。

**レビューの実測主張も自分で再現を取る**。同一 reviewer から内容の異なる 2 通のレビューが届き、片方の repro 付き主張はこちらで同じ変異を当てると再現しなかった。`Verification: repro` アンカーが付いていても、判断を変える指摘は自分で再現してから採否を決める。2 名の reviewer が独立に同じ結論へ到達した指摘は信頼度が高い。

**停止しない assert helper の前提は、後続コードのコメントに書く**。`fail()` が FAIL カウントを加算するだけで停止しない設計だと、先行 assert が落ちた実行でも後続の抽出処理まで到達する。そのため「先行 assert が保証しているから不要」に見える防御（`head -1` 等）が、実際には診断値を壊さないための保険として必要になる。この前提はコード上に現れないため、読み手が「冗長」と判断して消す余地が残る。
