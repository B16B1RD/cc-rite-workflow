### 修正パターン

1. **テストの同期は「到達可能な観測点」で行う**: stub の hang を親 stderr で待つ設計は、helper が
   gh の stderr を tempfile へ退避する rite の共通 idiom (`_mktemp-stderr-guard.sh`) と衝突して
   述語が一度も成立しない。stub が書く PID ファイルなど、退避の影響を受けないチャネルで待つ。
   加えて bash は foreground コマンド完了まで signal trap を遅延させるため、helper に TERM を
   送るだけでは trap が走らない。stub を `exec sleep` にして PID を kill 可能にする
   (子プロセスのままだとパイプの書き込み端を握り続け、コマンド置換が満了まで戻らない)。

2. **rc 単独は trap 経路の証拠にならない**: `rc=143` は trap 由来の `exit 143` と trap 設置前の
   既定 signal death (128+15) を区別しない。sentinel の存在 assertion と対で評価する。

3. **案内文は結末が確定してから出す**: 判定分岐より前で「投稿されます」と言うと、skip 経路で
   誤報する。degraded の案内は「update-in-place を諦める」ことだけを述べ、結末は sentinel の
   `outcome=` に委ねる。

4. **診断出力の行接頭辞は sentinel と衝突しない形にする**: 外部コマンドの stderr を字下げだけで
   再出力すると、そこに sentinel 同形の行が混じったとき gate の部分一致述語をすり抜ける。
   テストの negative control は行頭 anchor 付きで書かれるため、この非対称は検出されない。

5. **パイプの各セグメントで stderr を capture する**: `cmd 2>err | jq` では jq の stderr だけが
   素通りする。診断文言が「(gh/jq)」と両方を名乗るなら実装も両方を捕まえる。

6. **reason 語彙 × test 参照数の集計でカバレッジ穴が機械的に出る**: 文書化した reason のうち
   test 参照ゼロのものが 1 件残っていた。同じ集計で `rc >= 128` 分岐の無検査も判明。

7. **断定を実装より強く書かない**: 「必ず残る」「silent ではない」「1 件」といった表明は、
   縮退経路が 1 本でもあれば偽になる。可視性が経路ごとに非対称なら、その非対称を明記して受容する。
