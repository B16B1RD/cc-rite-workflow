### Fix Patterns

1. **エラーを 1 つの値へ畳むときは「原因の類型」が同じかを確かめる**

   `2>/dev/null` + `|| var=""` は「失敗したら空にする」慣用句だが、**呼び出し先の失敗**と
   **呼び出しは成功したが結果が期待と違う**を同じ値へ畳む。両者の復旧手順が違うなら畳んではいけない。
   今回は前者が環境起因 (作り直しても収束しない)、後者が caller 契約違反 (作り直せば収束する) で、
   帰結が正反対だった。**rc を捨てる前に「この 2 つは同じ対処でよいか」を 1 度問う。**

2. **リファクタで stderr を握り潰していないか差分で確認する**

   `tr | grep | tail` から `jq` へ寄せる際に `2>/dev/null` が新規に付いた。旧実装に stderr 抑止は
   無かったので、これは**リファクタが持ち込んだ観測性の後退**。同じファイルの別経路 (lookup 側 jq) は
   stderr を退避して開示する規律を持っており、非対称に気づける材料は差分の中にあった。

3. **commit 前にリポジトリ自身の checker を回す**

   cycle 4 で「tautology な pin」を直した同じコミットが、`hardcoded-line-number-check.sh` と
   `comment-journal-check.sh` の違反を 3 件持ち込んでいた。**自動検出できる違反を人間 (reviewer) に
   探させるのは無駄**で、しかも 1 cycle 遅れる。checker が存在する規約は commit 前に機械で潰す。

4. **閾値には境界値の fixture を置く**

   `-gt 0` の pin が「0 件」と「3 件」の fixture しか持たず、`-gt 1` への退行を検出できなかった。
   しかも境界値 1 は migration の支配的ケース (旧記録が 1 本残る) だった。
   **閾値を書いたら、その閾値ちょうどの入力を fixture にする。**

5. **pin を足す「前」に mutation を当てると、pin の要否が判定できる**

   診断の文字化け修正 (M-ED) は、修正だけ入れた時点で mutation が 400/0 = **検出されなかった**。
   pin を後から足して再実測することで有効性を確認できた。逆順 (pin を足してから mutation) だと
   「元から検出できていたのか、pin が効いたのか」が分からない。

6. **文字コード無害化のモード選択は call site ごとに決める**

   制御文字の無害化に「既定モード」と「C0 のみ」があるとき、既定モードが C1 帯をバイト単位で
   潰すなら **UTF-8 の多バイト文字を巻き込む**。ASCII しか通らない call site では既定でよいが、
   自由文が通る call site では診断が読めなくなる。**同じ関数でも call site の入力域で使い分ける。**
