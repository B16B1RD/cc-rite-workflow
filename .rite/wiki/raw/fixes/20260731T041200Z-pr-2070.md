### Fix Patterns

検出器の走査範囲を広げる PR に対するレビュー指摘 5 件をすべて修正した。修正側から見えた実務的な教訓は 3 点。

1. **「範囲を述べる散文」は実装より遅れて追随する**: スコープ拡張の指摘 (F-01) は、同一ファイル内の 5 箇所のうち 1 箇所 (冒頭タスク列) だけが旧スコープのまま残った形で現れた。修正時に `grep -n '説明的番号参照検出'` で同一ファイル内の全記述を列挙してから直すと、1 行修正で完結し他への波及がないことを構成で示せる。スコープを変えたら「その範囲を述べている散文」を grep で洗い出すのが定石。

2. **fail-loud を主張するコメントは、その機構の実在を実測で確かめてから信じる**: helper の戻り値 arity を巡る指摘 (F-02) は、コメントが「フィールド数がずれたら下の数値検証が拾う」と述べているのに、直下の case サニタイザが未束縛を既定値へ潰していた。修正は arity 検査を個別値の読み出しより **先** に置き、既存の失敗経路 (hits_rc → read_errors 計上 + continue) へ合流させる形にした。新しい失敗分岐を作らず既存経路へ倒すと、下流のカウンタ契約と完了レポートの note 展開に手を入れずに済む。

3. **「無言の 0 件を塞ぐ」ガードは、ガード自身を mutation で kill できるか確かめる**: 検出失敗ガードと契約 pin の TC 欠落 (F-03 / F-04) に対し、TC を足したうえで 4 種の変異 (arity 検査無効化 / ガード無効化 / ガードの前提条件だけ削除 / SKILL.md の分岐契約を旧版へ戻す) を実際に適用し、それぞれが新 TC で落ちることを実測した。特に「ガード本体の削除」と「ガードの前提条件だけの削除」は別の変異であり、肯定側 TC だけでは後者が生き残る。ガードに条件が付いているなら、肯定側と否定側を対で pin する。

補助的に、新規 TC が既存 TC と同じ T-ID を再利用していた問題 (F-05) は Issue 番号を接頭辞に付けて解消した。同一ファイル内で 1 つの T-ID が 2 つの仕様を指すと AC トレーサビリティが破れる。

### Verification Practice

mutation testing (実装を壊してテストが緑のままか確認する) が、テストカバレッジ指摘の修正が本当に効いているかを示す決定打になった。bash helper は sed で 1 行変えるだけで変異を作れるため、backup → mutate → run → restore のサイクルが安く回る。レビュー側 (指摘の Verification アンカー) と修正側 (修正の有効性確認) の両方で同じ手法が使える。
