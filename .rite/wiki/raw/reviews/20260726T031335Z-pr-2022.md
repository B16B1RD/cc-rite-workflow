### Finding Patterns

cycle 7（本セッション 2 回目）。前 cycle の HIGH（marker assertion の prefix 欠落）は 3 reviewer が独立に mutation で修正の有効性を実証し解消。代わりに MEDIUM 4 件が出た。4 件はすべて「marker 契約の非対称」という 1 つの根に収束している:

- emitter は rc=0 の削除成功時だけ marker を出さない（失敗系 3 経路は出す）
- consumer はその marker 不在を「削除成功」と**断定**する。同ファイル内の `{base_update_check}` は逆に marker 不在を「実行結果が確認できませんでした」として扱っており、規約が checkpoint 間で正反対
- consumer のルールは「行があるとき」という位置非依存の表現で、同ファイル :511 が確立した「marker は行頭 `[CONTEXT]` の行のみ」という位置規約を継承していない。外部由来の複数行テキスト（git stderr）を同じストリームに載せる設計が入ったことで、行頭かどうかが初めて意味を持つようになった
- テストの mutation TC が検証対象 artifact を読んでおらず、ガードが load-bearing であることの実証が名目化していた

経験則:

1. **「marker 不在」を成功の符号化に使うな**。成功も positive marker で表現する。marker 不在は「未実行」「出力喪失」「成功」を区別できず、consumer が断定すると false-success が復活する。同一ファイル内に反対の規約（marker 不在 = 未確認）が既にあるなら、そちらに揃える。
2. **marker を照合する規約には位置（行頭）も含める**。prefix だけアンカーしても、同じストリームに外部由来テキストを流す設計では行中の偽 marker を排除できない。data と marker を同居させるならデリミタで囲むか、行頭一致を明文化する。
3. **mutation テストは検証対象の artifact から mutant を導出する**。ハードコードした「修正前の式」を実行しても、それは git の挙動を確認しているだけで、現在の実装が load-bearing であることの証明にはならない。artifact を `sed` で変異させて初めて mutation test になる。
4. reviewer 6 名中 3 名が独立に同じ設計確認（success marker の追加）に到達した。**複数 reviewer の design_confirmation が収束したら、それは設計上の実欠陥のシグナル**として扱う価値がある。
