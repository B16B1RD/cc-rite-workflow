### Finding Patterns

cycle 1 の blocking 6 件は 5 件が FIXED、1 件が PARTIAL。一方で **fix cycle が新規に 3 件の欠陥を持ち込み**、
うち 2 件は「前 cycle の修正で追加した機構そのもの」に起因した。fix-introduced regression の類型として重要。

1. **helper の出力 prefix を失敗の判別子に使う前に、その prefix が成功経路でも出ないかを確認する**。
`flow-state.sh reap-issue` の `WARNING: reap-issue:` は「stale を見つけて非 active 化する」という
**成功側の告知**にも使われており、失敗専用ではない。ある helper（`cleanup-pr-state-purge.sh` の
`REVIEW_CLEANUP_PARTIAL_FAILURE=1`）で成立した「marker で判定する」形を、出力語彙を確認せずに別 helper へ
複製した結果、主経路で常時 `partial` を誤報告する機構になった。5 レビュアーが独立に同じ結論へ到達した。
**教訓**: caller 側で marker 判定を新設するときは、その marker / prefix が helper の成功経路に現れないことを
helper の実装と既存テストの両方で確認する。確認できない場合は判定を bash に持たせず、hardened sibling が
そうしているように stderr を素通しして人間 / LLM の読解に委ねるほうが正しい。

2. **失敗の観測手段を確保する fallback が、観測できないまま「成功」を宣言する経路を作る**。
`_err=$(mktemp) || _err=""` → `2>"${_err:-/dev/null}"` → `elif [ -n "$_err" ] && grep -q ...` の形は、
mktemp 失敗時に (a) helper stderr を破棄し (b) 判定を短絡し (c) `else` の `ok` へ落ちる。修正前は stderr が
端末へ素通ししていたため**観測性の後退**でもある。同じ diff 内の別ブロックが同一の mktemp 失敗を
`exit 1` で fail-loud にしていたため、PR 内で判断が非対称になっていた。
**教訓**: 「marker 不在＝成功」と読ませない規約を自ら書いたブロックが、縮退経路でその規約を破っていないか。
fallback を書いたら「この経路で何が観測できなくなるか」を 1 行で言えるかを検算する。

3. **negative control（`assert_not_grep`）は、禁止したい形が実ファイルで実際に取る行構造に一致するかを
実測で確かめる**。3 物理行に折り返された pipeline を 1 行前提の pattern で禁じても一致は 0 件で、
「二重防御に見えて実体は 1 本」になる。しかも fix で変数名が変わると、その名前を含む pattern は
恒久的に空振りする。**検算方法**: 禁止したい退行形を隔離コピーへ実際に再投入し、当該 assertion が
赤くなることを確認する。赤くならなければその assertion は削除するのが正しい（Over-fix Check）。

4. **fix cycle の diff にも over-fix が混入する**。`if [ -n "$_tl_raw" ] ... else pr_candidates="" fi` は
空入力でも `sort -un` の command substitution が空文字を返すため挙動中立で、3 レビュアーが独立に
「1 行へ畳める純増 surface」と指摘した。cycle 1 の指摘は rc 捕捉の是正のみを求めており、空入力の分岐追加は
名指し範囲外。**fix の diff は finding の名指し範囲に留める**という原則は、fix cycle でこそ破られやすい。
