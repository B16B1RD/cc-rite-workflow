### Finding Patterns

blocking 指摘 0 件で 1 cycle 収束。3 名が独立に到達した観察は次のとおり。

1. **否定条件の文書転記は、正側 assert 1 本で narrowing を検出できる**: 実装が `[ "$_os" != "Darwin" ]` で分岐するとき、文書側に「Darwin 以外は〜」という正しい文の存在を強制する `assert_grep` を置けば、「Linux は〜」への revert はその正側 assert が単独で落とす。対になる `assert_not_grep`（旧文面の不在）が独立に効くのは、新旧両方の文が同時に存在する編集に限られ、かつ literal 一致のため「Linux では」等の言い換えは捕まえない。2 本目は防御の重ねであって検出範囲の拡張ではない。

2. **字面 pin は「文書が実装より狭くなる」方向だけを守り、「広くなる」方向は守らない**: test reviewer が helper の分岐を `[ "$_os" != "Darwin" ] && [ "$_os" != "FreeBSD" ]` へ狭める変異を加えたところ、helper 側テスト（uname 不在 = WARNING / Darwin = 無言）も文書側 pin も全通過した。文書と実装の「同じ広さ」を名乗るテストヘッダは、実際には文書側の字面しか見ていない。ヘッダ文は実際に pin している側だけを名乗る形へ狭めるのが最小コスト。

3. **同一箇所への逐語 pin が 3 PR 連続したら、記述の分割を検討する合図**: 同じ Step 4-W の 1 文に対する drift 修正が 3 回続いた。1 文が約 400〜470 字で、marker・マスク 2 形状・判定順序・判定不能時の挙動・OS 例外の 5 事項を詰め込んでいる。どの限定句がどれに掛かるかの読み違いが再発しやすい構造そのものが原因。

4. **SoT スクリプト自身のコメントにも同型の狭い表現が残りうる**: 文書側を 2 度修正した後も、helper 内の別コメント行に「呼び出し側が Linux でのみ WARNING を出す」という無補正の狭い記述が残存していた。文書側だけを grep 対象にすると同じ欠陥クラスを取りこぼす。sweep は実装コメントまで含める。

5. **軽量レーンでも mutation を許可すべきクラスがある**: XS/S レーンは mutation 実験を M+ の装備として除外するが、「契約対応の未 pin」判定だけは例外として実施される。本 PR では 3 名中 2 名がこの例外条項を使って assert の空振りを実測し、いずれも「網羅的 pin 強化クラス（non-blocking）」と正しく分類した。例外条項が採否基準の緩和に転がらず機能した実例。
