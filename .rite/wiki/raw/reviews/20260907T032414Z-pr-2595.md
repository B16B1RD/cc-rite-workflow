### Finding Patterns

本 cycle で最も再現性の高いパターンは **「実装から機構を削除したとき、同じ契約を述べる散文だけが取り残される」**。6 reviewer 中 4 名が独立に同一箇所（skill 定義の冒頭にある規範散文）を検出した。実装・実装コメント・helper の 3 者は更新されたが、その 15 行上にある「集合の作り方」を宣言する 1 文だけが旧仕様のまま残り、削除した機構の再導入を指示する形になっていた。静的テストは jq リテラルを pin していたため散文の drift を素通しした — **リテラル pin は「コードが消えたこと」しか保証せず、「その挙動を指示する散文が消えたこと」は保証しない**。

第 2 のパターンは **「新設した診断・観測出力に回帰 gate が付かない」**。本 cycle が追加した stderr 原因行・非ブロッキング marker・射影失敗の WARNING はいずれも変異注入で消しても全テストが green のままだった（実測: 該当行を削除して 220 PASS / 27 PASS）。主経路（転記集合そのもの）には厚いテストがある一方、診断側は observability の宣言だけがあり強制層がない非対称。

第 3 は **「双子サイトの片方にだけ修正が伝播する」**。同一の和集合ロジックを helper (`.sh`) と skill 定義 (`.md` の fenced bash) の 2 実装で持つため、stderr 捕捉の修正が helper 側にのみ入り、skill 側は `2>/dev/null` のまま残った。同型の drift は前 cycle でも観測されており、2 実装を持つ限り再発する。

その他: 既存の reason 語彙を新分岐へ流用して完了報告に誤った原因を転記する、行動が必要な WARNING に `[CONTEXT]` marker がなく完了報告へ届かない、正規表現の `$` が末尾改行を許すため gate が意図した「発生源で止める」が末尾改行付き値で成立しない。
