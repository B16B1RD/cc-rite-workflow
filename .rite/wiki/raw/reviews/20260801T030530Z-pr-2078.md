### Finding Patterns

「防御を足す修正」が 3 サイクル連続で新しい退行を生んだ回。共通の型が見えた:

1. **成果物の「存在」を「完了」の証拠に使うと、中断された処理が残す断片で誤判定する** — `[ -e "$dst" ]` は copy 途中で殺された cross-device mv が残した壊れた断片にも真を返す。完了の証拠には **完了した処理だけが持つ性質**（rename も copy+unlink も source を消す → `[ ! -e "$src" ]`）を使う。存在検査は「始まった」ことしか示さない
2. **observability フィールドは consumer を決めてから足す** — 状態を 4 値で出すフィールドを新設したが、読む層が 1 つも無く、しかも 4 値すべてが既存の WARNING から導出できた。SoT 側の原則が明示的に「consumer ゼロ marker を作らない」と禁じていたのに、指摘への対応として反射的に足してしまった
3. **「原因は N つです」と閉じた列挙を診断に書くと、実装が経路を増やすたびに嘘になる** — 列挙は開いた形（「会話の WARNING / sentinel の値で切り分ける」）にし、分岐の網羅性は実装側の出力に委ねる
4. **タイミング窓の test は前提チェックの `if` を閉じ忘れると後続ケースを丸ごと飲み込む** — flush-left で書かれていると見た目では気づけない。前提が崩れた run で「報告される失敗 1 件」の陰に 5 assertion の不実行が隠れた
5. **AND の項を 1 つ落とす変異が全 assertion を素通りするなら、その項は pin されていない** — 「代入の位置」を pin しても「項の存在」は pin されない。load-bearing な conjunct はそれ専用のケースで固定する
6. **経緯コメント（この PR で何をやった / やらなかった）は実行時に毎回読まれる位置に置かない** — 現在形の制約文に畳めば、時間が経っても意味を失わない
7. **見出しは節が実際に扱う主題の集合を名乗る** — 複数の inbound ポインタが別々の主題で同一 anchor を指すとき、見出しが 1 主題しか名乗っていないと残りのポインタは「約束した論証」に着地しない
