### Finding Patterns

本 PR (bash helper 新設 + 散文契約の複数 site 配線) のレビューで、以下の指摘パターンが繰り返し現れた。

1. **GNU-only 正規表現拡張の混入 (portability)**: 新規 bash helper の `sed` 抽出式が GNU 拡張の BRE (`\b` 単語境界 / `\|` 交替) に依存していた。BSD/macOS sed はこれらを解釈せず**無警告で失敗**するため、機能が当該プラットフォームで恒久的に不作動になる。倒れる向きが fail-safe (安全側) だと CI も緑のまま (macOS leg は `continue-on-error`) で、しかも WARNING の reason が環境起因の失敗を「Issue 起票者の不備」として誤帰属した。**このリポジトリは `stat` / `date` / `wc` / `rm` / `realpath` / `md5sum` について既に BSD 分岐を持っており、`sed` の GNU 拡張だけが未整備だった** (plugins/rite 配下 1,135 箇所の sed 使用で本 2 行のみ)。同クラスは過去に `hooks/review-result-save.sh:356` でも実害を出している。教訓: production script で `\b` / `\|` を書かない。必要なら `sed -n -E` (ERE) へ移す (テストランナーは既に ERE を使っている)。

2. **Markdown の block 構造を壊す挿入 (散文契約)**: 「all of the following conditions」を要求する条件表の**行と行の間**に空行 + blockquote を挿入した結果、表がそこで閉じて 3 番目の AND 条件が blockquote の lazy continuation として平文に吸収された。raw markdown を読む LLM 実行者には 3 条件に見えるが、レンダを読む人間には 2 条件 gate に見える。既存パターン (表 → 空行 → `> **Reference**:` 注記) から逸脱した位置に注記を置いたことが原因。**契約 test は表の「内容」を pin するが「連続性」は pin しないため素通りする**。

3. **散文契約 pin が同一ファイル内の別行にも一致する (test 検出力)**: `grep` ベースの散文契約 pin で、needle が守りたい行だけでなく同一ファイルの別行 (E2E 最小化表のセル / Reference 中の言及) にも一致し、**守るべき記述を反転させても suite が green のまま**になる mutant が 16 本中 10 本生存した。兄弟 reason の片方だけが完全 literal でもう片方が裸単語、という非対称が典型。対策は (a) 行頭アンカー付きの行全体 literal、(b) `assert_grep_in_section` で節にスコープを切る、(c) 一致行数が 1 であることを検査する `assert_grep_unique` 相当の wrapper。**pin を書いた suite 自身が冒頭コメントでこの教訓を明記していても、全 pin へは適用されないことがある**。

4. **同一契約の複数 site 転記漏れ (Asymmetric Fix Transcription の再発)**: 条件表を更新したのに直下の判定フロー図が旧分岐のまま / template の 2 コピー (full mode と verification mode) の片方だけが表を欠く / reason 表と実装の割り当てが drift、が同時に発生した。**「同一 invariant の対称位置」には散文の図・テンプレートの複製・reason 表も含まれる**。しかも drift の複製側は既存 pin が片方だけで満たされるため機械検査が効かない。

5. **fail-safe の向きが consumer ごとに反転する設計の危うさ**: レーン判定では `full` = フル装備 = 安全側だが、並列実装ゲートでは `full` = 並列許可 = 攻撃側になる。この非対称を散文で説明したうえで、判定キーの「言い換え」(`complexity=` の存在 ≡ `FALLBACK` の不在) を括弧書きで添えたところ、marker を一切出さない失敗経路 (`helper_failed`) で 2 つの述語が非等価になり、攻撃側へ倒れる読みが成立した。**言い換えは経路が増えたときに真理値が崩れる**。

6. **診断 reason の粒度と前提の実測**: 「この値は必ず存在するから欠落は常に異常」という前提で全 reason に WARNING を出す設計にしたが、実測すると母集団の 38% (60 件中 23 件) が当該値を持たず、WARNING が定常出力になって actionable なケースが埋もれた。**「必ずある」を根拠に fail-loud を強める前に母集団を実測する**。加えて sibling helper が全 fail-safe 経路で具体的 target を名指しする規約を持つのに、新規 helper では 1 経路にしか適用されていなかった。
