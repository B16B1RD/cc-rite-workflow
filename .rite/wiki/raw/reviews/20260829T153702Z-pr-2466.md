### Finding Patterns

cycle 1 の HIGH 指摘（static-contract テストの pin 欠落）を fix した差分（+14/-0）に対する差分スコープレビュー。指摘 0 件で mergeable に到達した。観測されたパターン:

1. **mutant kill が false kill でないことの確認手順**: `assert_grep_in_section` は section 見出しが見つからないと `empty section` として fail する。したがって mutation で assert が落ちたとき、**helper のメッセージが `pattern not found in section [...]` か `empty section` か**を読み分けないと、「pin が効いた」のか「節抽出が壊れただけ」なのかが区別できない。今回は前者であることを確認して FIXED と判定した。この読み分けは section 限定 assert の mutation 検証で常に必要。

2. **両方向の実測で vacuous assert を排除する**: (a) clean tree で PASS、(b) mutant で FAIL、の両方が揃って初めて「assert が実際に効いている」と言える。(a) 単独は `assert_not_grep` が `^` + bare `|` の ERE で常時 FAIL する形になっていないことを、(b) 単独は positive assert が vacuously green でないことを、それぞれ排除する。片方だけでは不十分。

3. **section 境界パターンの一意性は degrade 経路を決める**: `assert_grep_in_section` は start 未マッチ（空 section）は fail にするが **end 未マッチは検出しない**。したがって end に汎用の水平線（`^---$` 等、ファイル内に多数出現）を使うと、その 1 本が将来消えたとき awk range が EOF まで伸びて assert が**無言で file-wide に劣化する**。end も一意な見出しにしておくとこの degrade 経路が閉じる。start の一意性だけでは足りない。

4. **`assert_not_grep` の pattern は base 版の連続 literal を使う**: file-wide の否定 assert は pattern が広いと無関係な行を掴む。base 版にしか存在しない連続 literal（今回は 4 placeholder の禁止列）を使えば file-wide でも誤検出しない。事前に `grep -cF` で「base 版に対して 1 hit、HEAD に対して 0 hit」を確認しておくとよい。

5. **推奨事項の 3 分類は triage 経路を分ける**: `actionable`（follow-up 対応が妥当）と `boundary`（action 要否が判断できず user 判断を要する）は Phase 7 の AskUserQuestion / Decision Log 記録へ回り、`design_confirmation`（対応不要と reviewer 自身が結論）は件数表示のみ。reviewer 側で分類を明示しないと既定 `design_confirmation` に落ち、actionable な提案が記録されずに消える。

6. **class B 降格済み finding の再訴訟を禁じる**: 前 cycle に帰結クラス降格で non-blocking にした指摘は、次 cycle の解消検証の対象には含めるが「未解消でも blocking 再報告しない」を prompt で明示する。これがないと同一根拠で毎 cycle blocking が復活し、収束しない。
