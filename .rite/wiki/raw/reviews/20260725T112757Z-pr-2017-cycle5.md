### Finding Patterns

**レビューサイクルは「AC の達成」ではなく「レビュー対応で追加した足場」を対象に発散しうる**。本 PR は cycle 1 で Issue の受入基準 3 項目を達成し実測確認したが、cycle 2〜4 の指摘 9 件はすべて「前 cycle の修正が追加したテスト pin / コメント / 診断出力」を対象としていた。修正 1 件が新たなレビュー対象面を作るため、`fixed` 件数（4,2,3,4）だけを見ると収束しているように見えない。**サイクル数ではなく「指摘が production を対象にしているか」で収束を判断する**。

**finding の基準を prompt で明示すると発散が止まる**。cycle 5 では reviewer に「findings = production hook の実欠陥、または production のセキュリティコントロールが blocking gate（Linux CI・短い $TMPDIR・通常 cwd）で未 pin になっているテストギャップ。足場の異常環境下での堅牢性やコメントの言い回しは推奨事項へ」と明示した。結果、4 名全員が 0 findings で、それまで findings として上がっていた同種の観察は推奨事項に分類された。**基準が曖昧だと reviewer は安全側に倒して everything を blocking にする**。

**繰り返し挙がる推奨は「対応する」か「Decision Log に記録する」かを早めに決める**。同一の推奨（RITE_DEBUG による give-up 記録、`$TEST_REPO/src` の cleanup、`[^"]*` の fixture 前提）が 3 サイクル連続で挙がっていた。cycle 5 直前にまとめて対応したことで、最終サイクルの指摘対象から外れた。**推奨を放置すると毎サイクル再提出され、レビューコストが線形に増える**。

**mutation matrix は「生存した変異」の理由を個別に説明できて初めて完了する**。最終 cycle の test reviewer は 16 変異中 13 kill、生存 3 件について (a) decision-neutral な診断経路、(b) 既存 TC の意味を変えない cleanup、(c) Linux では空 target symlink を作成できず到達不能、と個別に実測で結論づけた。**生存＝カバレッジ欠落ではない**が、その判断には到達経路の実証が要る。
