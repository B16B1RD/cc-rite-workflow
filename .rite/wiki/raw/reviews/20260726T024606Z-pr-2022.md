### Finding Patterns

本 PR は「emitter が emit する marker 形式」「consumer がそれを照合する形式」「test がどちらを pin するか」の 3 者整合が主題。6 cycle 目のレビューで残った唯一の指摘も同じ構造だった: emitter は `[CONTEXT] REMOTE_BRANCH_*` を出し consumer は `[CONTEXT] ` 込みでアンカー照合するのに、test の assertion は prefix 抜きの marker 名だけを grep していたため、emitter から prefix を落とす退行がスイートを素通りする。

この repo で繰り返し現れる経験則:

1. **marker contract のテストは「emitter が出す literal 全体」を pin する**。marker 名だけを pin すると prefix / 区切り / アンカーの退行が漏れる。consumer 側の照合形式と bit-exact に揃えること。
2. **静的検査テストには positive control を付ける**（本 PR の cycle 2-4 でも同種の vacuous pass が繰り返し検出・修正された）。assertion が常に真になる形（否定表現の alternation に非否定 disjunct を混ぜる等）は mutation を投入して赤くなることを実測するまで信用しない。
3. **marker family の部分文字列衝突**: `REMOTE_BRANCH_DELETE_FAILED` は `BRANCH_DELETE_FAILED` を部分文字列として含む。非アンカー照合すると短い側のルールが先に一致して誤処方になる。`[CONTEXT] ` prefix 込みで一致させるのが構造的解。
4. **「marker 不在 = 成功」契約の非対称**: ローカル側は成功時も肯定 marker を出すのに、リモート側は成功時に何も出さない設計だと「成功」と「ブロック未実行」が区別できない。複数 reviewer が独立に同じ設計確認を挙げた（design_confirmation ×4）。
5. **`git ls-remote <pattern>` はスラッシュ境界の suffix 一致**であり完全一致ではない。`refs/heads/{branch}` を渡さないと入れ子 ref に誤ヒットして rc=0 になる（複数 reviewer が実測で確認）。
6. **多バイト文字に隣接する変数展開は必ず brace で閉じる**（`$var。` は非 UTF-8 ロケールで変数名を壊す）。macOS CI 回帰の実績あり（Issue #2008）。
