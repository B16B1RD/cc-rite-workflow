### Finding Patterns

- **5 世代の pin 強化が示したこと — 「散文を静的 pin で守る」は部分被覆では収束しない**: 合計下限 → セクションごとの下限 → 厳密等値+共起+denylist → セル分割の構造述語 → canonical 完全一致、と 5 世代を経た。最終世代の canonical 完全一致は**当てた行については**言い換え・極性反転・削除・並べ替えのすべてを捕捉する（実測で確認）。しかし**適用範囲が部分的**だと、未 pin の行に同じ穴が残る。実例: 8.0.3 の 4 データ行のうち canonical pin を当てたのは 2 行で、残り 2 行（うち 1 行は gate が存在する唯一の理由を担う「sentinel NOT found → ERROR」行）を pass へ反転しても 310/0 の完全緑だった。**pin の強度と適用範囲は独立の軸**であり、強度を上げても範囲が欠ければ守れない。

- **allowlist のトークンが escape hatch になる**: 層 2 の allowlist に `legitimately skipped` を含めると、ERROR 行を「Gate は legitimately skipped」へ反転する変異が allowlist を満たして通る。allowlist は「規約に沿っているか」を見るが「その行が正しい判定をしているか」は見ない。判定の向きを守りたい層では、allowlist ではなく**行の役割ごとの本数を厳密等値で固定する**（pass 行 N 本 / ERROR 行 M 本）方が確実。

- **pin を層で当てるか行で当てるかを意識する**: 個別行に canonical pin を足す修正は、その行しか守らない（8.0.3 に足しても 8.0.1・8.0.2 は露出したまま）。同型の表が複数あるなら、ループで全表に当たる層（`_g_spec` のような表ごとの期待値リスト）に 1 項目足す方が、抜けが構造的に生じない。

- **「全廃した」という表明は grep で裏を取ってから書く**: 「区間 anchor のハードコードを全廃（残存 0 件）」と commit message に書いたが、別の helper（`assert_grep_in_section`）経由で同じ range 形が 4 件残っていた。表明の検証は、自分が書き換えた箇所ではなく**表明が主張する性質**（この場合「range 形の区間指定が 1 つも無い」）に対して行う。

- **SoT の設計規則と実装が乖離したら、実装ではなく規則に例外条項を足す判断もある**: 「denylist ではなく allowlist で書く（現行表記への係留を避ける）」という規則を持つリポジトリで、canonical 完全一致 pin（＝最大限の係留）を導入した。実装が正しいなら規則側に「判定の向きを担う少数のセルは意図的に係留する」の例外を書くべきで、規則をそのままにすると次の保守者が「規則違反だから」と塞いだ穴を開け直す。

- **同一箇所を複数 reviewer が独立に指摘したら Confidence を上げる**: 本 cycle では F-01 を test + error-handling、F-02 を test + application + error-handling が独立に指摘した。単独指摘より優先度を上げる根拠になる。
