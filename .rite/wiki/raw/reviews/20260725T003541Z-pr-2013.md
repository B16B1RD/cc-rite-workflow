### Finding Patterns

クロスプラットフォーム（GNU/BSD）テスト移植 PR に固有の指摘パターンが 2 系統に集中した。

1. **ドキュメント SoT テンプレートと実コードの乖離**（HIGH）: 本体テストは 2 段階の canonical 化（`mktemp -d` → `cd && pwd -P`）に修正済みなのに、CONTRIBUTING.md の「新規テストひな形」は 1 段目のみのまま、コメントだけが 2 段構成を説明していた。テンプレートは複製起点なので、修正したばかりの移植性バグを再導入する経路が残る。**移植性修正 PR では「直したパターンを再生産するテンプレート/ひな形」を必ず同時に更新する**。3 レビュアーが独立に同一箇所へ収束した。

2. **新設した fail-closed ガードが診断出力を先食いする**（MEDIUM）: skip 会計の drift 検出 `exit 1` を失敗テスト一覧の出力より前に置いたため、drift と失敗が同時成立すると失敗ファイル名が消える。さらに新診断行が CI 側の job-summary grep パターンに未登録で、赤いジョブのサマリーが「全件 pass」と表示される。**fail-closed 経路を追加するときは (a) 既存の診断出力より後ろに置く (b) CI 側のログ抽出パターンにも同時に登録する**。

3. **緑化の正直さを最終行が打ち消す**（LOW-MEDIUM）: SKIP カウンタを導入して集計行には gated group 数を出したのに、最終行は無条件 `All tests passed!`。同 PR 内のもう一方のランナー（run-all.sh）は注記付きに直しており、**2 ランナー間の非対称**が残った。skip 可視化を入れるときは「成功メッセージ」まで含めて一貫させる。

4. **文書が暗黙に前提とする CI 構造の未確立**（MEDIUM）: 「blocking gate では fail させよ」という新規約を書いたが、CONTRIBUTING.md はクロスプラットフォーム matrix の存在自体を説明していなかった。規約を書くときは、その規約が依拠する前提（どの leg が blocking か）を同一文書内で確立するか、SoT へのポインタを張る。

補足（本 PR では非 blocking と判定した観察）: `continue-on-error: true` の job は workflow run conclusion では success に潰れるが **check run conclusion は failure のまま**であり、required status check として機能する（devops reviewer がリポジトリの API 実測 + 公式ドキュメントで確認）。「continue-on-error の job は required check にできない」という通説は `needs.<job>.result` / run conclusion についての話で、check run には当てはまらない。
