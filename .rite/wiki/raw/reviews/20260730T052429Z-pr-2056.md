### Finding Patterns

散文手順（LLM が runtime で読むワークフロー定義）のレビューでは、**実測アンカーを付けられるかどうかが reviewer 側の技量差として現れる**。同一の欠陥に対し、片方の reviewer は「prose-only の変更は構造的に実測不能」としてアンカー無しで報告し、もう片方は `grep` / `sed` による構造の実測（見出し順序・分岐条件・行の存在）をアンカーにして blocking として報告した。**散文でも「文書内の構造的事実」は実測できる** — 見出しの順序、分岐表の条件、特定文字列の有無、参照先の行番号は `grep -n` / `sed -n` で観測でき、それが `Verification: repro` の正当な実測になる。実測不能と決めつけると、同じ欠陥が cycle を跨いで non-blocking のまま滞留する。

- **指示の配置と実行地点の乖離**: 「後続ステップ X で生成するものに検査を適用せよ」を X より前のセクションに置くと、線形に実行する LLM は X の地点でそれを思い出さない。実行地点側に導線が無ければ、指示は書かれているのに一度も実行されない。検査の指示は**生成コードの直前**に置くか、実行地点側にポインタを張る。
- **承認ゲートを跨ぐ自動書き換え**: 差分表示 → ユーザー承認 → 適用 の順序を持つフローで、表示後・承認前に本文を自動付記すると、ユーザーが承認した内容と適用される内容が乖離する。「付記は書き換えである」と自ら明記した文書が、別の経路でその原則を迂回していないか確認する。
- **前提の誤りは結論が正しくても指摘に値する**: 「分解パスは見込み Complexity が L/XL のため 3 クラス全検査」という記述は、結論（全検査）が無条件なので挙動は正しいが、根拠（分解 = L/XL）が偽（分解推奨は 4 条件の OR）。後続の編集者が誤った根拠に基づいて範囲を狭める余地を残すため、挙動不変でも修正対象になる。
- **同一文書内の宣言と処理表の矛盾**: 「対象外」と宣言した領域について処理表が挙動を規定していると、実行者はどちらに従うか決められない。片方を削るか、例外として明記して両立させるかを選ぶ。仕様側が「検証はしないがマーカーは付ける」と定めている場合、削る側に倒すと仕様違反になるため、宣言側に例外を書くのが正しい。
- **自分が入れた修正が次 cycle の指摘を生む**: cycle 1 で追加した 1 行が、同 PR 内の SoT が明記する規約（`-R {owner_repo}` 必須）に違反していた。修正を入れる際は、同 PR 内で自分が書いた規約・警告文と矛盾しないかを確認する。
- **先行詞のない「同じ〜に載せる」**: 分岐表で「同じ AskUserQuestion に載せる」と書くとき、その先行詞となる質問が別条件でしか発生しないなら、その条件が成立しない入力では指示が宙に浮く。表の各行は独立に到達しうるため、他行への暗黙依存を書かない。
- **共有 SoT の予算は consumer 側の消費を勘定に入れる**: 「最大 4 件まで」のような上限を SoT に書く場合、その上限が「専用呼び出し前提」なのか「既存呼び出しへ畳み込む consumer 込み」なのかを明示しないと、畳み込む側で off-by-one になる。
