### Finding Patterns

インタフェースを差し替える修正の直後に出る指摘には固有の型がある:

1. **インタフェースを変えたら、そのインタフェースを名指しする全テキストが同時に腐る** — オプション名を変えた PR で、gate の ERROR 診断 2 箇所が旧オプション名と削除済み機構を案内したまま残り、5 レビュアーが独立に検出した。しかも診断どおりに操作すると helper が `unknown option` で落ちる非収束経路になる。**実装の grep だけでなく「そのシンボルを説明する散文」の grep を完了条件に入れる**（`grep -rn -- '--old-option' plugins/` が 0 件、のような機械条件）
2. **契約の数値を「N 種すべて X」の形で書くと、1 例外の追加で全箇所が同時に嘘になる** — reason を 1 つ足しただけで「全失敗経路で exit 0」が 3 箇所で偽になった。内訳表記（「N 種のうち M 種は X」）へ最初から寄せる
3. **bash の trap は foreground コマンドの完了まで遅延する** — この性質を知らずに「完了フラグを見てから分類する」と書くと、コマンド完了直後・フラグ代入直前の窓が残る。フラグではなく**結果そのもの**（成果物の実在）を確認するか、実行の事実を別フラグで持つ必要がある。「代入を前に動かす」では窓は閉じない
4. **テスト fixture の置き場所が実装の導出先と食い違うと assertion は恒真になる** — 実装が `${TMPDIR}` から導出するのに fixture を `mktemp -d` 配下に置くと、実装がどう振る舞っても fixture 側は残るため「削除しない」assertion が常に pass する。**fixture は実装が実際に触る場所に置く**
5. **skip を pass として記録すると、前提を満たさない run が検証済みと同じ見え方をする** — タイミング依存の窓を狙う test で「窓に入らなかったら pass」と書くと、退行注入時にも green のまま通る。skip 専用の計上か、窓の決定論化（通知ファイルのポーリング等）が要る
6. **テストコードは production の緩和策を継承しない** — production 側が symlink 追随を `set -C` で塞いでいても、テスト fixture が素の `: >` で共有 `${TMPDIR}` に固定名ファイルを作れば同じ攻撃面が開く。テストにも同じ緩和を適用するか、`TMPDIR` ごと隔離する
7. **機械可読 sentinel に「成功」と「対象が無かった」を同じ形で出すと、下流はどちらか判定できない** — 3 状態あるなら 3 状態を出す
8. **`Verification:` アンカーに生パイプや `=>` 欠落があると、実測済みの指摘が書式だけで non-blocking へ降格する** — 本サイクルで 3 件が該当した。ゲートは正しく警告を出すが分類は変えないため、書式は投入前に確認する
