### Finding Patterns

- **コメント内の「call site の全称・唯一性の主張」は 3 サイクル連続で再生産される**: 「この 2 field を env で渡す caller は X のみ」「以降の caller は番号を持たない」といった形は、同一 PR 内で call site を 1 つ増やしただけで偽になる。cycle 1 は skill 側の散文、cycle 2 も同じ散文、cycle 3 は hook 側のコメント、と場所を変えて同じ様式が出た。**再発しない形は「実態を正しく列挙し直す」ことではなく「列挙を持たない記述へ縮める」こと** (例: 「env override も flow-state 読み取りも無い更新経路では既定値へ巻き戻るため読み戻す」)。列挙を保つ限り、call site が増えるたびに次の cycle で偽になる。
- **診断メッセージは自分がリセットしない対象を名指ししてはいけない**: WARNING が「A / B / C を既定値へ倒します」と書いたが、実際に倒れるのは C だけで A / B は後段の env override / 別経路の上書きが最終値だった。しかもその WARNING が届く唯一の caller が A / B を渡す経路だったため、誤報が最も届く場所で起きていた。**メッセージを書く位置が値の確定前なら、確定しない対象は条件付きで書く**。
- **観測性の限界を書くときは call site の形式ではなく helper 自身の性質で説明する**: 「call site が `2>/dev/null` で捨てるから届かない」と書いたが、実際は退避形の call site も rc=0 の成功分岐で捨てるため届かない。call site の形式を数え上げる説明は (a) 数え間違える (b) 陳腐化する (c) follow-up Issue のスコープを no-op にする、の 3 つを同時に招いた。
- **否定 assertion (「〜が出ない」) は production の最頻状態で書く**: 「WARNING を誤報しない」を非既定値の fixture だけで検証すると、既定値状態 (production で最も多い) での誤発火 mutant が生存する。否定の検証は、その否定が最も破られやすい入力で行う。
- **mutation は適用前に「対象文字列がちょうど 1 回一致すること」を assert し、適用後に `bash -n` を通す**: 一致 0 回の mutation は「テストが弱い」と誤読され、構文を壊した mutation は「全 TC が Red」という無意味な結果を出す。どちらも mutation テストの結論を反転させる。
