### Finding Patterns

- **診断メッセージを 2 本に増やすと、両者の解説コメントの整合も検証対象になる**: 既存 WARNING の解説ブロックが `if`/`else` 全体を統べる位置にあると、`else` 側に新しい WARNING を足した瞬間そのブロックの記述が新 WARNING にも適用される。結果「rc は条件に使わない」という既存の断定が、rc を条件にする新分岐を「誤報」と宣言してしまった。分岐を足すときは、その分岐を覆っている既存コメントの射程を必ず読み直す。
- **コメントの例示は「一般命題が真になる側」から選ぶ**: 「個別 key の欠落は無警告」という一般命題は非必須 key では真だが、例示に必須 key を挙げたため例だけが反例になった。例示は命題の反例にならないものを選ぶ。
- **診断文の主語は、その文が発火する条件が保証している対象に限る**: 「値を carry-forward しました」と書いたが、発火条件は「parse が corrupt かつ .data が非空」だけで carry-forward が起きたことは保証していない。env override が渡る経路では実際に carry-forward された値が 0 件でも発火する。
- **同型の guard は同型に pin する**: python3 側の `|| _parse_rc=$?` は専用 TC で固定したのに、1 行下の jq 側 `|| parsed=""` は無防備だった。同じリスク構造を持つ guard が同一 diff 内に並ぶときは、片方だけ pin する非対称を作らない。
- **到達不能な防御コードはテストで殺せない — 削除が正しい対処**: mutation で生存した防御コードを「テスト不足」と読むと不要な TC が増える。到達可能な入力が構成できないなら、それは coverage hole ではなくデッドコード。
- **WARNING が断定した挙動は assert する**: 「sync_revision を 1 から採番し直します」と書いた分岐で、その sync_revision を検証する assertion が無かった。診断文が約束する挙動は、そのままテストの assertion にできる。
