### Finding Patterns

ワークフロー定義（skills/*.md の散文＋埋め込み bash）を変更する PR に固有の指摘パターンが 3 つ観測された。

1. **プレースホルダ置換マニフェストと実テンプレートの乖離**（HIGH、2 レビュアーが独立検出）。
   置換対象を列挙する散文（「これらをリテラル置換せよ」）と、実際のテンプレート中のトークン名が
   食い違うと、LLM が列挙側を権威として扱って未置換のまま人間へ出力する。特に「復旧手順」の
   コマンドで起きると、人間が実行しても無害な no-op になり、しかも rc=0・無出力で成功に見える。
   rite では新しいプレースホルダを導入する際、(a) テンプレート本体 (b) 直近の置換指示
   (c) Placeholder Legend の 3 箇所を同時更新しないと必ずこの乖離が生じる。
   命名規約（lowercase-snake）から外れた略記（{ROOT} / {SID}）は乖離の兆候として検出しやすい。

2. **新設 marker の retain 指示漏れ**（MEDIUM）。`[CONTEXT] KEY=value` marker を新設したとき、
   emit site は書くが「どこまで retain するか」の指示を更新し忘れるパターン。marker の消費地点が
   sub-skill 呼び出しを何度も跨ぐ場合（本件では最大 5 cycle 分）ほど脱落しやすく、脱落しても
   エラーにならず「注意行が出ない」という無音の劣化になる。marker を追加する PR では
   emit / retain 指示 / 消費側分岐表 の 3 点セットを検査するチェックが有効。

3. **ドキュメントの条件節に先行詞が無い**（MEDIUM、前 cycle からの未解消継続）。
   「provided either X succeeds」のような保証文で、either が指す 2 項が同一文書内で
   導入されていない状態。実装を知る書き手には自明でも、その文書だけを読む人間には
   保証条件を検証できない。とくに「本 PR が是正対象とした当の文」で起きると、
   是正前と同じ「読んでも真偽を確かめられない保証」に戻る。
