1. **実測アンカーの有無は指摘の質ではなく「実測を試みたか」で決まる**: cycle 1 で non-blocking だった `stop-loop-continuation-contract.md:19` の指摘が、cycle 2 で同じ reviewer が `RITE_STATE_ROOT` を隔離し `chmod a-w` で `_atomic_write` の mktemp を失敗させる repro を組んだことで blocking (HIGH) に昇格した。ドキュメント記述の指摘であっても、記述が主張する条件を実装側で反証できれば実測になる。「doc の指摘は実測できない」は多くの場合 思い込みで、条件を状態として再現できるかを先に問うべき。

2. **半端な固定化は無防備な軸を残す**: 人間に渡す復旧コマンドで `--session` により sid 軸を固定しながら、state root 軸を固定しないパターン。`resolve_state_root` は cwd へフォールバックするため、非 repo cwd で実行すると rc=0 で成功しながら別ファイルを作り、本来直すべき state は手つかずで残る。marketplace install ではコマンド文字列にプロジェクト参照が一切含まれず、新規端末の既定 cwd が `$HOME` になるため、空振りが例外ではなく既定経路になる。「1 つの軸を明示的に必須化した」ときは、同じ解決関数が持つ他の軸も同時に塞ぐ。

3. **2 軸の成否の組み合わせを散文で列挙すると象限を取りこぼす**: 「A が失敗 × B が失敗」「A が走る前に終了」の 2 つを挙げて網羅を宣言すると、「A が走って失敗 × B に到達せず終了」の象限が抜ける。しかもこの抜けた象限こそ「通知が一切出ない唯一の経路」であることが多い (B に到達しないと B が emit する marker が無く、その marker を条件とする注意行も出ない)。散文の場合分けは「失敗」と「未到達」を別軸として扱った時点で 2x2 になるので、列挙をやめて「A も B も消せていない (失敗したか、到達しなかったか)」と 1 条件に畳むと構造的に漏れが消える。

4. **SoT 委譲は委譲先の網羅性を担保しない**: 「正確な条件は X が single source of truth であり再掲しない」と委譲した先の場合分けが不完全だと、誤りが一次情報側に閉じ込められ、読者は必ずその不完全な記述に着地する。委譲を張るときは委譲先の網羅性を同時に確認する。

5. **canonical spec 文書の無留保な保証文**: 実装が best-effort (2 つの write のいずれか成功に依存) なのに spec 側が「〜が必要」と無条件で書くと、限界が仕様レベルで失われる。片方の caveat だけを書くと、読者は「留保は列挙し尽くされている」と合理的に推論するため、部分的な留保は無留保より誤解を生みやすい。
