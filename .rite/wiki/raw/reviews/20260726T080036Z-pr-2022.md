### Finding Patterns

- `git ls-remote <pattern>` は ref の先頭または任意の slash 境界からの tail 一致であり、`refs/heads/` を前置しても anchor されない。完全一致を得るには stdout の ref 名を別途照合する必要がある（実測: git 2.43.0、`refs/heads/target` が `refs/heads/wip/refs/heads/target` に一致して rc=0）。`--exit-code` は真に不在の ref に対しては rc=2 を返し、ガードとしては機能する。
- `git push origin --delete <shortname>` は remote の全 namespace に対して <dst> を解決するため、同名のタグを削除しうる（実測確認）。存在確認を `refs/heads/` 修飾で行いながら削除を非修飾で行うと、検証した ref 集合と削除する ref 集合が一致しない非対称が生まれる。破壊的操作は検証と同じ ref 修飾で行うこと。
- skill 手順書で emitter（bash）と consumer（散文の判定表）を分離する設計では、契約を「サイト列挙」で書くと退避サイト追加のたびに列挙更新漏れが起き、散文とコードの drift が再発する。契約は「性質」（begin/end で囲まれた区間は一律 data）で書く。
- テストが「artifact から literal 抽出して実行する」方式は、実装のコピーによる drift を構造的に防ぐ有効なパターン。一方で、consumer 側が新たに load-bearing 化した結合点（marker の scope フィールド、退避テキストのインデント）は、mutation を当てて実際に red になるか確認しないと pin されたつもりの vacuous な assertion になる。
- 判定表に recency（最終出現を採用）を導入すると、それまで stale success が偶然マスクしていた emitter 側の欠落経路が表面化する。片側（リモート）だけに「既削除 = 正常系」を実装すると、もう一方（ローカル）で同じ症状が再生産される。
