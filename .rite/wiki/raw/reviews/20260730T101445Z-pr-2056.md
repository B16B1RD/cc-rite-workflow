### Finding Patterns

- **fix は「クラス」で閉じないと次 cycle に鏡像が出る**: cycle 2 の指摘は、cycle 1 で追加した規定の**反対側**がそのまま指摘になったものが大半だった。`CONTRADICTED` にだけ WARNING を義務づけた → `UNVERIFIED` に無い、と指摘。Issue→PR 方向にだけ型限定を入れた → PR→Issue 方向が未限定、と指摘。**規定を片側に足したら、同じ軸の反対側が既に埋まっているかを同 cycle 内で確認する**。埋まっていなければ 1 本の規則へ畳んで単一定義にする。
- **観測可能性は判定の強さと同順に設計する**: 強い判定 (`CONTRADICTED`) ほど本文に痕跡を残さない選択肢を持ち、弱い判定 (`UNVERIFIED`) だけが WARNING を持つ、という逆転が 2 cycle 連続で別箇所に現れた。**非成功判定は 1 本の規則で一律に観測可能化し、理由欄を必須にして経路を分離する**（rc=0 の失敗と非ゼロ終了の失敗が同じマーカーに潰れるのを防ぐ）。
- **1 question に 2 決定を載せる符号化は成立しない**: AskUserQuestion の回答は 1 つなので、ある項目の 3 択と別項目の可否を同じ問いで決めることはできない。上限に当たったら**呼び出しを増やす**（上限は 1 呼び出しあたりの制約で総予算ではない）。相乗りさせると LLM が即興で符号化し、塞いだはずの経路が復活する。
- **reviewer の提案は実測で検証してから採用する**: `git log --grep` の散文衝突に対し reviewer は行頭アンカー化を提案したが、develop 全 340 番号で実測すると衝突 3 件を消す代わりに正当な解決 4 件を落とした。実装 commit も自 Issue を地の文で引くため、**一致位置では散文引用と実装 commit を区別できない**。提案が具体的な regex を含むときほど、採用前に全件で before/after を測る。
- **区別できないことが確定したら、その事実を規定として書き残す**: 「正規表現では区別できない。位置ベースの分岐を追加してはならない」と理由付きで明記しないと、次 cycle で同じアンカー案が再提案されて再測定のコストが繰り返される。
- **自分が追記した「設計判断」も同じ検査に掛ける**: PR 本文の判断リストは fix cycle ごとに増えるが、後続 cycle の fix が挙動を変えると即座に stale になる。fact-check 系の PR ではこれ自体が指摘対象クラスであり、実際 reviewer が実測 grep で検出した。
