### Finding Patterns

本 PR は「対話モードの AskUserQuestion 3 択を機械的停止へ統一」というワークフロー仕様変更。3 レビュアーとも AC-1〜AC-4 の充足・Non-Target 遵守・旧記述の残骸ゼロを実測で確認し、指摘は周辺の記述精度・観測性に集中した。抽出できた再発パターン:

1. **diagnostics を運ぶ経路にフィルタを挟むと、ロケール依存の原因行が消える**: helper stderr を capture して `neutralize_ctrl --keep-newline` に通す idiom は、0x80-0x9f をバイト単位で `?` 置換するため UTF-8 日本語診断が判読不能になる。「元は端末へ素通しで読めていた stderr」をフィルタ越しにする変更は観測性の退行になりうる。capture 側で `LC_ALL=C` を付けて ASCII に固定するのが定石。tempfile 捕捉済みで元々端末に出ていなかったサイト（hooks/ 配下の同 idiom 約 20 箇所）は差し引きプラスであり、同一視して retrofit してはならない。

2. **空値ガードを持つ生成側と、持たない消費側の非対称**: bash ブロック内で `[ -n "$session_id" ]` guard を持つ経路が、同じ値を `[CONTEXT]` marker として emit し、その消費側（人間向け復旧コマンドの placeholder 置換）には guard 指示がない、というパターン。空値が置換されると `--session --phase` のようにオプションが次のフラグを値として食い rc=1 で即失敗する。しかも空値になる根本原因（session 解決失敗）は、その復旧コマンドを提示する分岐の発火条件（state write 失敗）と重なるため、「最後の安全網が劣化した局面でだけ復旧手順が壊れる」形になりやすい。

3. **条件節の先行詞が同一ファイル内で解決できない**: 「provided either X succeeds」の either が指す 2 つの対象のうち片方が、そのドキュメント内で一度も言及されない。実装を読める人間には自明でも、docs 単独の読者には検証不能な保証になる。SoT を別ファイルに委譲している場合、委譲先の内訳不足がそのまま読み手の穴になる。

4. **失敗と未到達を別軸で区別した列挙は組み合わせが漏れやすい**: 「(1) 両方失敗 (2) 到達しなかった」という 2 件の列挙は、「実行して失敗 × その後未到達」の交差ケースを落とす。2 つの set が別々の Bash 呼び出しである以上、中間で turn が終わる状態は到達可能。列挙をやめて「消せていない（失敗したか、到達しなかったか）」と 1 文に畳むと漏れが構造的に消える。

5. **scope 判定の実務**: 実測アンカー（`Verification: repro`）を添えられた指摘のみが blocking となる実測必須ゲート下では、ドキュメント記述の曖昧さ（runtime 実測が原理的に困難）は non-blocking へ落ちる。レビュアー側は「実測できるものは必ず実測を添える」を徹底しないと、実質的な blocking 指摘がゼロになりうる。
