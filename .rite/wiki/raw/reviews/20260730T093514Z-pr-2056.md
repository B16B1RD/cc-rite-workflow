### Finding Patterns

- **SoT reference と consumer の責務分割ミス**: 新設した共有 reference に「検査ロジック」は集約できても、再入時ガード・注記の扱いといった「運用ルール」を consumer 側 (issue-edit/SKILL.md) に置いてしまい、もう一方の consumer (issue-create 5.1.1) が継承できない乖離が生じた。Issue 側が MUST で「同一 reference を参照し複製しない」と定めていても、reference に書かれていない規則は構造的に共有されない。**共有 SoT を新設するときは「どの規則が全 consumer に効くか」を節として明示的に切り出す**。
- **ツール上限を仕様が織り込まない**: AskUserQuestion の質問数上限 (4) と「ユーザー承認なしに書き換えない」MUST が組み合わさると充足不能になり、実装が degraded path (無承認の自動付記) を作って MUST を破った。**外部ツール制約を伴う MUST は、上限超過時の挙動まで仕様に書く**。
- **判定の強さと観測可能性の逆相関**: 最も強い判定 (CONTRADICTED) が stderr WARNING を要求せず、溢れ分は弱い判定 (UNVERIFIED) と同じマーカーで記録されるため、確定した矛盾が検証不能と区別できなくなる。**強い判定ほど永続かつ判別可能な記録を持たせる**。
- **PR 説明文の stale 化**: レビュー修正コミット (578598a5) で挙動を反転させたのに PR 本文の「設計判断」節が追随せず、squash merge 後の履歴に実装と正反対の記述が残る経路が成立した。**挙動を変える fix commit を打ったら PR 本文の該当記述も同 cycle 内で更新する**。
- **同一観測値が非互換な 2 処理へ写る**: `gh issue view {N}` の `url` が `/pull/` を返すという同じ観測を、片方は「PR として続行」、もう片方は「CONTRADICTED」に写す規定が同一ファイル内に併存した。分岐述語 (「Issue として引用した」) が bare `#N` について未定義だったのが原因。**同じ観測値を複数箇所で使うときは分岐述語を先に定義する**。
- **有効だった検証手法**: reviewer 側の裏取り指示 (reviewer-prompt-generator.md の追記) が実際に機能し、3 reviewer とも `gh issue view` / `git log --grep` / `gh api commits` を実行して仕様中の番号参照・stderr 文言・語境界 regex を実測で確認した。手順書の断定は「書いた通りに走らせて観測する」と検証できる。
