### Finding Patterns

hook の挙動を散文で記述する docs PR で、記述が実装の分岐を網羅しない誤りが 2 件検出された。共通パターンは「分岐の主経路だけを見て全称量化してしまう」こと。

1. **skip と fail を同一視した全称量化**: 「全同期成功時のみ前進する」と書いたが、実装には `_skip_progress=1` で transform を「実行せず飛ばすが `_xf_ok` は 1 のまま」という第 3 の状態がある。失敗（前進しない）と skip（前進する）を区別せずに書くと、劣化通知を見た運用者が「次回再試行される」と誤解する。散文で契約を書くときは、実装の boolean フラグが 2 値か 3 値かを先に確認する。

2. **fetch → PATCH を二分岐として書いた取りこぼし**: `wm_replica=absent` 短絡（round_trips=0）と通常経路（round_trips=2）の 2 分岐として記述したが、実装には `reason=no_comment` の初回検知（round_trips=1、PATCH なし、負キャッシュ書き込み）という第 3 の帰結がある。観測ラベル（`round_trips`）が取りうる値を grep で列挙すれば取りこぼしは機械的に検出できる。

3. **解除経路の断定と同一ファイル内の既存記述の矛盾**: 「only a successful replica creation clears」と断定したが、同ファイルの flow-state フィールド表が Issue 切替でも落ちると明記していた。同一文書内に同じ契約の記述が 2 箇所あるとき、新規追記側だけを書くと矛盾が入る。所有を既存の表へ委譲（ownership-only cross-reference）する方が安全。
