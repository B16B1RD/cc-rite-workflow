### Finding Patterns

cycle 4 の修正（TC-4.9b の状態ベース同期、degraded 案内の分離、`_gh_err_detail` 集約と `gh:` prefix、
jq stderr の capture、unknown_option / rc>=128 の assertion）は test reviewer が 10 種の mutation で
すべて「その assertion 自身に殺される」ことを実測し、cycle 2 / cycle 3 と同種の vacuous pass は
再発していないと確認された。cycle 5 で新たに出たのは以下。

1. **防御を producer 側だけに入れると consumer 側の述語が古いまま残る**: gh の stderr に sentinel 同形行が
   混じる経路に `gh:` prefix を入れたが、gate 側の述語は非アンカーの部分一致のままだった。より深刻なのは
   producer 側の別経路 — trap 設置前の exit 1 経路は引数値を診断へ echo back し、かつ真の sentinel を
   1 本も出さないため、引数に sentinel 同形文字列を入れると「その cycle で唯一の sentinel」が生まれる。
   **防御は producer と consumer の両側に同時に入れないと閉じない**。

2. **テストの述語が consumer の述語より強いと、テストが green でも何も証明しない**: negative control を
   行頭アンカー付きで書き、gate は非アンカーで読む — この非対称があると、テストは「gate が騙される形」を
   検出できない。テストの述語は consumer の述語と一致させる。

3. **rationale で正しく限定した条件が、派生文書へ転記される過程で落ちる**: 「count > 0 なら新規作成へ縮退」の
   限定が rationale だけに残り、派生 7 箇所すべてで無条件の主張になっていた。1 箇所は条件を反転した断定に
   なっていた。SoT を先に直し、派生をそれに揃える順序で作業する。

4. **`2>` と `2>>` を同一ファイルに混在させない**: O_TRUNC と O_APPEND が同一 pipeline で並行すると、
   後発の O_TRUNC 書き込みが先行 append を頭から上書きする。追記に揃えるなら直前に明示 truncate を置く。

5. **フォールバック値 `${var:-/dev/null}` は診断を無言で捨てる**: tempfile 確保に失敗すると原因文字列が
   全滅し、残る「対処」案内だけが特定の原因（認証）を名指しして operator を誤誘導する。

6. **case の `*)` arm を「意図した 1 ケース」に読み替えると将来の綴り誤りを吸収してしまう**: テーブル駆動の
   ループで未列挙の入力を `*)` が拾うと、エントリ追加時のタイポが別 gate の発火で緑になる。`*)` は fail に倒す。

7. **ラベルと assertion の不一致は将来の誤読の起点になる**: 「reason 別の診断を検査する」と名乗るラベルが
   実際には共通 marker しか見ていない。テスト名は実行可能な仕様として読まれる。
