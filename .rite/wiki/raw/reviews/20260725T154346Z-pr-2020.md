### Finding Patterns

セキュリティ境界テストの検証力を評価する最も強い手段は mutation testing だった。hook のコピーに退行を注入し（length guard 無効化 / reviewer 判定 glob 削除 / IS_SUBAGENT scope 喪失 / main 経路クラッシュ注入）、control と本体アサーションのどちらが FAIL するかを表で示すと、「control は本当に何を証明しているのか」が推測でなく実証で決まる。特に「length guard を外すと当該 fixture は subagent でも allow になる」ことの確認が、control の deny が length guard 由来だと言い切る根拠になった。

positive control の価値を判定するとき「既存の類似ケースと重複では」という疑問が出る。判定基準は **本体アサーションが実際に読む入力ファイルから派生しているか**。同じ素材から独立に組み立て直した fixture は、本体側の入力生成が壊れても緑のまま通るため control の役目を果たさない。この非重複性はコメントに明記しておかないと、後続サイクルで「重複だから」と削除される。

旧実装と新実装を同じ変異 hook に当てて対比する手法が、検出力の増減を議論の余地なく示した。特に「旧実装では 216 passed / 0 failed の完全に緑な vacuous pass になる変異」を見つけられると、Issue が指す問題が実在することの決定的証拠になる。

テストが hook の timeout（rc=124）を PASS 扱いしていた点は、guard 自身の deny 理由が「timed-out hook fails OPEN」と述べている以上、致命的だった。「設計どおりの permit」と「hook が死んだ結果の permit」を区別できないテストは、その guard が防ぐ攻撃そのものを見逃す。

レビュー依頼文に書いた前提（deny reason にコマンド先頭 80 文字が含まれる）が実装と食い違っており、reviewer が実測で訂正した。依頼側の事実誤認は攻撃面の誤導出を招くため、訂正を記録して次サイクルに持ち越さないことが重要。
