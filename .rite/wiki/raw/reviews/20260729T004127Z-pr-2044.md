1. **状態を「設定値との相対値」で符号化しない (最重要)**: 「発火済み」を `cycle_count > max_review_cycles` と表現したが、`max_review_cycles` は毎回 config から読み直される可変入力だった。上限を下げれば未発火の counter が発火済みと誤認され、上げれば発火済みが認識されない。**符号化に使う基準値が実行間で変わりうるなら、その符号化は状態を表せていない**。cycle 2 で `-ge` → `-gt` に直したのは境界の位置だけを直したもので、「可変値との比較で終端状態を表す」という根の構造は残っていた。同じ失敗クラスが 2 cycle 連続で別の形で出た。

2. **代替は「マーカーを足す」ではなく「マーカーを要らなくする」**: reviewer が提示した収束案は、発火時点で counter を 0 にリセットして override 自体を削除するもの。発火後は handoff が default-clear されて自動再入場経路が無いという既存の性質から、fire 時リセットでも自動継続は起きない。**新しい状態変数を導入する前に、既存の不変条件から「その状態を覚えておく必要があるか」を問う**。今回は覚える必要が無かった。

3. **1 つの set に不変条件を複数背負わせると、失敗時の開示が破綻する**: fire 分岐の単一の `flow-state.sh set` が handoff クリア・発火済みマーカー・AC-2 再開可能性の 3 つを同時に背負い、失敗時の WARNING が結果を一括して「安全側」と断じた。ブレーカーに対しては真だが AC-2 に対しては偽で、停止通知が「再実行すれば N cycle 回る」と虚偽を述べる。**1 つの操作が複数の契約を担うなら、失敗時の開示も契約ごとに分ける**。

4. **enum 値に接頭辞関係を作らない**: `failed-refire` が `failed-refire-nodiag` の厳密な接頭辞になっており、prose 照合（LLM の grep）が一致順で解決すると誤分岐する。「完全一致で照合せよ」という指示で守るのは弱い。**値の集合を相互に非接頭辞に設計する**か、そもそも値を増やさない。
