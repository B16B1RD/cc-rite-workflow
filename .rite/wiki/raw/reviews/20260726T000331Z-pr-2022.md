### Finding Patterns

- **exit code ガード導入時に「成功を表す marker」を置き忘れるパターン**: `git ls-remote` の rc を 3 分岐（存在 / 不在 / 判定不能）にして「不在」と「判定不能」には marker を付けたが、実際に状態を変更する「存在 → 削除実行」分岐だけ成否の marker を持たなかった。下流の完了報告が「marker が無い = 成功」と推論する契約だったため、削除失敗が完了として報告される false-success を新規に作り込んだ。**教訓: 状態変更を伴う分岐こそ失敗 marker が要る。marker が無いことを成功の証拠として扱う契約を書くときは、その分岐が本当に失敗し得ないかを確認する。**
- **emitter だけテストして consumer をテストしないパターン**: SKILL.md から bash block を literal 抽出して sandbox 実行するテスト（emitter 側）は 6 TC で厚く張られたが、同じ PR が新設した完了報告の判定ルール（consumer 側の散文）にはテストが 1 件も無かった。consumer ブロックを丸ごと削除する mutation でも全スイート green。**教訓: marker を新設する変更は emit 側と解釈側の両方を pin する。散文の判定ルールも `assert_grep_in_section` で機械検証できる。**
- **静的 grep テストが「修正前の一字一句」だけを pin して言い換えを通すパターン**: 「保証する」という literal の不在のみを検査していたため、「必ず残ることを保証します」への書き換えでテストが通った。**教訓: 禁止表現の不在ではなく、要求される性質（できないことの明示）を肯定形で assert する。**
- **周辺コードの stderr 捕捉規約から外れるパターン**: 同一ブロック 11 行上のローカル削除は `del_err=$(... 2>&1)` で原因を WARNING に含めるのに、新規追加した `git ls-remote` は `2>&1` で捨てて rc だけを出した。ユーザーに手作業を要求する唯一の経路なのに原因が伝わらない。**教訓: 新規コードは同一ファイル内の既存エラー処理規約を先に読む。**
- **レビュアー間で revert テストの解釈が割れるパターン**: 「結果は PR 前と同じ（既存問題）」と「その断定を書いた行は本 PR の + 行（新規）」で blocking 判定が分かれた。SKILL.md の documented な revert テスト手順（diff-line inspection: バグが `+` 行に依存するなら pass）に従うと後者。**教訓: revert テストは結果の同一性ではなく、documented された手順（diff 行の帰属）で判定する。**
