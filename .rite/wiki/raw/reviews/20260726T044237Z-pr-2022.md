### Finding Patterns

cycle 10（サーキットブレーカー発火 cycle）。指摘推移は 5→5→6→6→1→1→4→6→4→7。**収束しなかった**。

最大の知見は「**規約を新設すると、その規約自身の適用範囲を問う指摘が次 cycle に生まれる**」という構造。本 PR で marker 照合の規約を段階的に強化した結果、cycle ごとに次が出た:

1. prefix アンカーを導入 → 「行頭も要る」（行中の偽 marker）
2. 行頭一致を導入 → 「複数行 stderr の 2 行目は列 0 に着地するのでデリミタが要る」
3. `branch=` スコープを導入 → 「同一ブランチ再実行では branch= が一致するので recency が要る」
4. pin を 2 family に追加 → 「3 個目の family に pin がない」

いずれも指摘自体は正しく、runtime 実測を伴う。しかし規約の強度を上げるたびに「まだ塞げていない入力クラス」が可視化されるため、**LLM が解釈する散文を契約として扱う設計では、この階段に終端がない**。

派生する実務的な経験則:

- **規約を追加するときは、同一ファイル内の類似箇所すべてに適用したかを機械的に確認する**。「2 箇所に適用して 3 個目を落とす」は 3 cycle 連続で起きた。
- **規約の適用範囲を自己限定する書き方（「以下のルールで『X』と書いた箇所」）は、否定形（fallback）に届かない穴を作る**。肯定・否定の両方を明示的に含める。
- **pin は「section 内のどこかに文字列がある」形にすると弱い**。ルール単位・要素単位で個別に要求し、mutation で片方ずつ潰して確認する。
- **説明的な commit SHA 参照は永続成果物に残さない**（`comment-best-practices.md` の MUST）。テストコメントの「同じ規律」の根拠として SHA を貼ると、squash/rebase で意味を失う。
- **review-fix ループの終端判断**: AC が全充足済みで、指摘の主成分が「前 cycle の修正が作った / 規約の適用範囲」に移ったら、それはループが価値を生まなくなった合図。サーキットブレーカーはこの判断をユーザーに委ねるための仕組みで、機械的な cycle 数だけでなく**指摘の性質の変化**を観察材料として提示すべき。
