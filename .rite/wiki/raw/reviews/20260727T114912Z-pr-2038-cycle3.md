### Finding Patterns

cycle 3 の最重要指摘は、**cycle 2 の修正そのものがテストを恒真化していた**というもので、4 reviewer が独立に検出した。

**`grep` のパターンが `-` で始まると、それはオプションとして解釈される**。`assert_not_grep "$file" '-X PATCH'` は `grep -qE '-X PATCH' "$file"` に展開され、`-X` が matcher 指定オプションとして食われて rc=2（usage error）で終わる。`assert_not_grep` は非ゼロ rc を「anti-pattern 不在」と解釈するため、**禁止された呼び出しがログに実在しても常に PASS する**。cycle 2 で PATCH の呼び出し形を `--method PATCH` から `-X PATCH` に変えた際、assertion のパターンも機械的に置換したことで 4 本の negative control が同時に無効化された。

一般化すると: **assertion のパターンを変えるときは、そのパターンが「見つける」ことを positive control で確かめる**。negative assertion（〜が無いこと）は、検索が実行されなくても失敗しないため、パターン自体の破損を構造的に隠す。本リポジトリは以前 `positive control を付け vacuous pass を排除する` を規約化しているが、その規約が negative assertion 側に適用されていなかった。

**その他の再現した型**:

- **allowlist にしても「検査対象の抽出」が表記に係留していれば同じ穴が残る**。pass 行を英語リテラルで抽出して規約適合を判定する形は、和文で書くと分子と分母から同時に脱落して等値判定を通る。**抽出と判定の両方を表記非依存にする**必要がある。
- **「初期値が success を騙れない」という安全特性は、その初期値を観測するテストが無ければ守られていない**。初期値を success 値に書き換えても全 pass するなら、その特性は主張されているだけ。
- **signal 経路は「rc とエラー文が別途出る」と仮定されがちだが、trap が sentinel だけを出す実装では何も出ない**。gate が「別途 loud に出る」を pass の根拠にしていると、その根拠ごと崩れる。
- **同じ規則を適用する範囲を「指摘されたファイル」に閉じると、同じ PR 内の別ファイルに規則違反が新規に増える**。journal comment の除去が reference / helper には及び、同時に追加した test には及ばなかった。
- **引数を受け取る新設の信頼境界は、producer 側が既に持っている allowlist を継承する**。`OWNER/REPO` を受ける gate が形だけを見て 3 セグメントを通すと、gh が先頭をホスト名と解釈して別ホストへ送出しうる。
- **記録が成功している経路で「記録が失われた」と読める案内を出さない**。degraded 縮退は失敗ではなく縮退であり、共通の失敗案内を流用すると operator を不要な再実行へ誘導する。
