### Finding Patterns

1. **プレースホルダ規約が「同じセルに入る他のプレースホルダ」に及ばない** (CRITICAL、2 レビュアーが独立検出)
   構造化データ（GFM テーブル行）を生成させる指示で、セル破壊文字の禁止規約を 1 つのプレースホルダ（`{description}`）だけに書き、同じセルへ verbatim 埋め込みされる別のプレースホルダ（`{title}`）に及ばせていなかった。実コーパスに反例が 16 行（うち link text 由来 5 行）実在し、しかも破壊を検出する consumer が存在しない（孤児検出は link target の grep なのでセル構造に無依存、query 側は当該形式を parse しない）ため無検出で蓄積する。
   教訓: 「区切り文字と衝突する値の扱い」は placeholder 単位ではなく**セル単位／レコード単位の一般規約**として書く。禁止（omit）より**エスケープを正規形として固定**する方が、他の literal 一致規約（frontmatter との同値要求）と衝突しない。既存コーパスに慣習（`\|` エスケープ 14 行）があるなら、それを正規形として明文化する。

2. **形式を是正する指示が「その節が存在しない初期状態」を落とす** (MEDIUM)
   既存の実体（テーブル形式 index）に合わせて指示を書き換えた結果、主経路もフォールバックも「対象セクションが存在する」ことを前提にしてしまい、テンプレートから初期化された直後（当該セクション自体が無い）の分岐が消えた。改修前の指示はテンプレート実体に偶然一致していたため、これは是正 PR が持ち込んだ退行。
   教訓: 「実体に合わせる」是正では、**実体が複数世代ある**ことを確認する（成熟したリポジトリの実ファイル / テンプレート生成直後の初期ファイル）。同一 PR 内で片方の不在ケース（統計節）だけを明示ハンドリングして他方（一覧節）を落とすと非対称が残る。

3. **書き手の規約を変えたのに読み手の実装を確認していない** (MEDIUM)
   共有データ構造の writer 側の生成規約を新形式へ移したが、その構造を機械 parse する唯一の consumer は旧形式専用の regex のままだった。writer 側ドキュメントは consumer の動作を「使用する」と断定していたため、変更後は読み手未対応という要修正事実を隠す誤記述になった。
   教訓: 共有データ構造の形式を変える変更では、`Grep` で consumer を列挙して**実装が新形式を受理するか**を確認する。ドキュメントが consumer 動作を断定している箇所は、実装状態に合わせて限定するか caveat を付ける。

4. **形式移行の非対称が「機能の無音停止」を生む**（pre-existing として検出、別 Issue 起票候補）
   index を箇条書きからテーブルへ移行した過去の変更で reader 側が追随せず、結果として当該 query 機能が**全キーワードで 0 件を返し WARNING も出さない**状態が継続していた。候補 0 件を正常系として `exit 0` する設計のため、運用上まったく検知されない。
   教訓: 「候補 0 件」は「該当する知見が無い」と「parser が形式に対応していない」を区別できない。抽出器が 0 件を返したときに**入力に候補らしき行が存在するか**を別軸で確認して WARNING を出さないと、機能停止が正常系に化ける。
