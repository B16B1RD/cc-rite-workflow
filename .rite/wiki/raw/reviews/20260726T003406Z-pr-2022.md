### Finding Patterns

- **新設 marker 名が既存 marker を部分文字列として包含し、非アンカーな判定ルールに誤一致する**: `REMOTE_BRANCH_DELETE_FAILED` は `BRANCH_DELETE_FAILED` を含む。完了報告の判定ルールが「`BRANCH_DELETE_FAILED=1` のとき」と非アンカーで書かれていたため、リモート marker 行にローカル側ルールが先に一致し誤診断・誤処方になる。**教訓: marker を新設するときは既存 marker との部分文字列関係を確認する。判定ルールは `[CONTEXT] ` prefix 込みでアンカーするか、衝突しない名前空間を選ぶ。同じ PR で「family でスコープせよ」と規範を書きながら family 名前空間を侵す marker を足す、という自己矛盾が起きやすい。**
- **散文ルールの静的 pin が「marker 名の存在」止まりで「判定値」を pin しない**: `grep -q 'MARKER=1'` だけでは、そのルールの結論（未完了 ` ` / 完了 `x`）を反転させる mutation を素通しする。**教訓: (marker → 判定値) のペアで pin する。判定値そのものの literal（`` ` ` ``）は曖昧なので、未完了判定に固有の救済文言（「手動削除」等）を grep する方が堅い。**
- **正常系テストが「特定 marker の不在」しか見ず marker family 全体の不在を見ない**: 契約が「family 全体の不在 = 成功」なら、正常系でも family 全体の不在を assert しないと、成功時に失敗 marker を出す退行を通す。**教訓: 否定アサーションのスコープを契約のスコープに合わせる。**
- **negative control の precondition が、その TC が実際に依存する命題とずれている**: 「不在ブランチにも push が走る」ことを示す mutation TC が、precondition として「origin が到達可能」だけを assert していた。前段 TC の後始末（`|| true` で失敗を握り潰す）が失敗すると、mutant は別の理由で push を呼び TC は主張と異なる理由で PASS する。**教訓: non-vacuity を証明する TC ほど、その主張が依存する命題を明示的に assert する。前段の後始末を `|| true` で握り潰さない。**
- **診断メッセージ自身が rc を混同する**: production 側で「rc=2（不在）と rc=128（到達不能）を混同するな」と直した直後に、テストの precondition guard が同じ混同（一律「到達不能」と表示）をしていた。**教訓: 修正した設計原則をテストコード自身にも適用する。**
