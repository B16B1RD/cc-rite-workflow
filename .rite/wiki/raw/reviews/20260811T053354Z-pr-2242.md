### Finding Patterns

「fail-loud の網羅」を主張する変更で、**宣言（ドキュメントの契約表）と実装のズレが 2 件とも blocking として出た**。パターンとして繰り返し観測されたのは次の 3 つ。

1. **契約表に書いた出口が実装されていない**: DESIGN.md の fail-loud 表に「クロスフェードがシーン尺より長い → エラー終了」と書きながら、実装のガードは総尺しか見ておらず per-scene の比較が無い。エラーメッセージの文言だけが per-scene の意味を名乗っていた（`assemble.sh:57` — 3 レビュアーが独立に検出）。**契約表を書いたら各行に対応する実装位置を 1 対 1 で辿り直す**必要がある。網羅を主張する変更ほど、主張そのものが検査対象になる。

2. **エラー経路でのリソース解放漏れが exit code の到達を殺す**: フレームループ内の `fail()` は catch でメッセージを出すが、`finally` が子プロセス（ffmpeg）を解放しないため event loop が生き残りプロセスが終了しない。**「エラーメッセージが出る」と「エラー終了する」は別物**で、呼び出し側が `set -e` で待つ設計だと後者が欠けた瞬間に無限待機になる（`render.mjs:151`）。fail-loud の検証は「メッセージが出るか」ではなく「exit code が呼び出し元に届くか」で行う。

3. **同じ帰結に至る出口の取りこぼしはコメントの根拠にも現れる**: BGM 尺不足ガードの根拠コメントが実際には発行していない `-shortest` を理由に挙げており、同じ誤りが DESIGN.md にも転記されていた（`assemble.sh:88`）。**コメントの根拠は実際に発行するコマンドと突き合わせる**。

補助的な観測: 契約検証用の fixture（`no-scene-decl.html`）を追加しても、それを実行する経路を同時に作らないと「手動 1 回の観測」で終わり、契約が回帰しても検出できない。同じ PR 内の `check-determinism.sh` が AC-2 を再実行可能な退路に変換していたのに対し、AC-3 だけがその扱いを受けていない非対称になっていた。
