### Finding Patterns

本サイクルの blocking 指摘 2 件はいずれも「rite リポジトリ内部の参照が、ユーザープロジェクトへ丸ごと展開される配布テンプレートに流入する」「同一コミットが追加した新形式に、そのコミット自身が明文化した pin 原則が適用されていない」という 2 つのパターンに帰着した。

1. **配布成果物への内部参照の流入** (tech-writer, MEDIUM): `templates/wiki/*.md` は `/rite:wiki-init` が placeholder 置換または単純 cp でユーザープロジェクトへ展開する成果物であり、rite リポジトリ内の相対パス (`docs/SPEC.md`) や Issue 番号 (`#2053`) を書くと展開先で解決できない。さらに `SCHEMA.md` は説明的番号参照 lint の走査対象から意図的に外されているため、番号参照が lint の届かない場所に永続する。develop 時点で当該テンプレート 4 本にはこの種の参照が 0 件だったため、「配布テンプレートに内部参照を書かない」は暗黙の不変条件として成立していた。

2. **cp fixture の mutation coverage が実体変化で空洞化する** (test, MEDIUM): 配布テンプレートを `cp` して fixture にするテストは、テンプレートが**持たない**形式を pin できない。本 PR はこの原則を自ら明文化して TC-50b (literal fixture) を追加した一方、同じコミットが**追加した**テーブル構造には assertion を到達させておらず、ヘッダー列名の改称やテーブル節の全削除が suite 緑のまま通ることを実測で確認した (PASS:182 FAIL:0)。「実体を変えた側にも pin を足す」対称性が欠けると、原則の明文化が片側にしか効かない。

### 有効だった検証手法

- **mutation testing による pin 強度の実測**: `git worktree add --detach` で隔離した作業ツリーに変異 (`in_comment` 分岐の `next` 落とし / ヘッダー列名の改称) を注入し、どの TC が kill するかを baseline / merge base の両方で測った。「TC-50b は旧 TC-50 より鋭い pin である」「テーブル側には kill する TC が存在しない」という 2 つの結論が推測ではなく実測で確定した。
- **散文の実行契約を実データへ機械的に当てる**: ステップ 6 の同定述語・列切り出しアルゴリズムを、実 wiki ブランチの index.md 342 データ行に対して全件適用し前提の成立を確認した (ページリンク直後に非空白が来る行 0 件 / 行末パイプ欠落 0 件 / 区切り 6 個未満 0 件)。LLM が実行する散文手続きのレビューでは、実データ全件への適用が最も強い検証になる。
- **「コメントのみの変更」の機械的確定**: `git diff -U0` から `+/-` のコメント行を除外して出力ゼロを確認することで、`.sh` 3 ファイルの挙動不変を推測なしに示した。
