### Finding Patterns

前 cycle 指摘への fix を差分スコープで再レビューした結果、fix 自体が新しい欠陥を持ち込む型と、修正が指摘の要件を満たしていない型が明確に分かれた。

1. **行番号の名前空間を 2 つ混ぜた突合は、偽陽性と偽陰性を同時に生む**。unified diff の `@@ -old +new` から削除側の範囲を採って照合対象に加えると、それは修正前ファイルの採番である。呼び出し側の記録規約が「HEAD の行」であるとき、両者を OR で受ける実装は「HEAD で一切変更していない行を cite しても検証を通過する」経路を開く。検証機構がまさに反証すべき水増しを、機構自身が許すことになる。削除された行には HEAD 上の行が存在しないという非対称が根本にあり、片方の名前空間へ閉じるか、削除側の採番を規約として明文化するかのどちらかしか成立しない。5 レビュアーが独立に同一箇所へ収束した。

2. **散文の記述を section 限定 grep で pin しても、同じ literal が同一 section 内に複数あれば assertion は空振りする**。section 限定は必要条件であって十分条件ではない。pin したい主張が「A かつ B」の複合であるとき、単一 literal ではなく主張のペア（同一行に A と B が同時に出現する、または当該節にしか無い語）を条件にしないと、ミューテーションが生存する。加えて awk の区間抽出が「次の見出しで閉じる」ことを前提にしていると、対象節がファイル末尾まで続く構造では窓が意図の何倍にも広がる。本 PR では 2 件が同型で発生し、どちらも「テストは green のまま対象行だけ削除できる」ことを実測で確認した。

3. **既存の canonical テンプレートが名指しで禁じている形を、新規追加行が再導入することがある**。signal trap を 1 行に統合し個別の `exit` を持たせない形は、signal 受信時に処理が継続して後続のリダイレクトが state ファイルを空に truncate し、しかも rc=0 で成功として返る。「周辺に同じ形の既存 site があるから」は、既存 site を掃除しない理由にはなっても、SoT を明示参照しているファイルで新規に踏襲する理由にはならない。

4. **設計の転換は散文の追随を 3 箇所以上要求する**。判定粒度をファイル単位から hunk 単位へ変えたとき、helper 冒頭の契約コメント・rationale ドキュメント・テストのラベル語彙が同時にずれる。テストのヘッダだけが更新され実装側のヘッダが取り残される、という非対称が起きやすい。

5. **fail-loud の追加は marker まで揃えないと分類器から不可視になる**。skill 定義の評価順テーブルが marker ベースで fatal を判定する設計のとき、新設した失敗経路が素の非ゼロ終了で終わると、どの row にも一致せず失敗の理由が失われる。同一ブロック内の兄弟出口が marker を emit しているかどうかが、非対称の目印になる。
