### Finding Patterns

1. **ガードの「向き」を修正する fix は、逆向きの同じ失敗を作りやすい**: cycle 1 で「不足側で判定を降ろす」ことによる恒久無効化を撤去し、cycle 2 で「過剰側で判定を降ろす」ガードを足したところ、counter が実在数に追いつかない経路で**同じ恒久無効化を逆向きに再導入**した（2 reviewer が独立に repro 付きで検出）。向きを反転させる修正では、新しい向きで同じ failure mode が成立しないかを、旧 failure mode の再現条件をそのまま鏡像にして確認する。

2. **「原理的限界だから塞ぐな」と書いたコメントは、実測なしに書くと後任の修正を止める**: LC_ALL=C 除去の検出可否を「非 C locale なら捕まる」と書いたが、実機の ja_JP.UTF-8 も CI 一般の C.UTF-8 も同順で検出できず、en_US.UTF-8 を明示すれば塞げた。限界を主張するコメントは、主張そのものを実測してから書く。

3. **同一 commit 内で実装の役割を変えたら、その役割を明記した文書 3 箇所が同時に偽になる**: cycle 2 で `cycle_count` を「診断値のみ」から「過剰検出にも使う」へ広げた結果、cycle 1 で書いたばかりの SPEC / CONFIGURATION の記述が同じ PR 内で矛盾した。役割変更は grep 可能なキー名で全出現を洗ってから commit する。

4. **新設したガードのうち片方の分岐だけがテストで実行されない状態は、instrumentation で検出できる**: `--since` 非空の経路が hit 0 のまま全緑だった。分岐を足したら「両方の入力で実行されるか」を注入計測で確認する。

5. **`od -c` のアドレス列は 8 進なので `grep -c '033'` は偽陽性を生む**: `od -An -c` を使う。
