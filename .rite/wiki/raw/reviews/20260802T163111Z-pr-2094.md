### Finding Patterns

- **同一 PR 内でドキュメントと実装が矛盾するパターン**: 実装は正しいのに、同じ PR が追加した rationale 散文だけが古い/誤った系統図を主張する。tech-writer と prompt-engineer が独立に同一 file:line を検出した。SKILL.md は LLM が実行時に読む仕様であるため、散文の事実誤認は後続セッションの判断を誤らせる。散文で「〜だけが X を持つ」「どの経路でも Y されない」と全称・唯一性を断定する箇所は、必ず Grep で全 call site を列挙して裏取りする必要がある。
- **load-bearing なコードコメントに対応するテストが無いパターン**: コメントが 8 行かけて「A ではなく B と書く理由」を説明しているのに、A へ書き換えても全テストが通る。コメントで守っている不変条件は mutation テスト (隔離 worktree で該当行を書き換えてスイートを走らせる) で生存を確認しないと、リファクタで silent に失われる。
- **2 段ガードの片側だけがテストされるパターン**: `pr_number` と `loop_count` のように対称な 2 フィールドを独立した条件式で守るとき、テストが片方しか検証していないと他方のガード除去が無検知になる。対称なガードには対称なアサーションを置く。
- **非対称な観測性**: 同一関数内で、ある縮退経路は rc 付き WARNING を出し、新設した別の縮退経路は完全に沈黙する。fail-loud を規範とするプロジェクトでは、既存の隣接コードが持つ観測性の水準を新規コードでも維持する。
- **shell portability の repo 規約**: GNU 形式の `sed -i '<expr>'` は BSD sed (macOS) で失敗する。本 repo は awk read→transform→write→mv helper を規約として明文化しており、テストの fixture 改変でもこれに従う。
