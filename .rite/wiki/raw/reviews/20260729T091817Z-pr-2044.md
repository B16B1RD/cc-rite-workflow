### Finding Patterns

cycle 1 の 3 件はすべて解消されたが、**同じ欠陥クラスが同じ節の別トークンで再発**した。これが
本 cycle の最大の学びである。

**「参照が読み手の実行経路で解決できない」欠陥は 1 箇所直しても同型が残る**。cycle 1 では
`{ROOT}` / `{SID}`（置換マニフェストに載っていないプレースホルダ）を修正したが、同じ注意行
ブロックの数行下にある実在確認コマンドの `$root` / `<UUID>` は手つかずだった。`$root` は
「解決できなかった場合」の案内文でだけ代入される shell 変数で、値が得られた支配的経路では
一度も定義されない。結果、正しい値を持つ人間が実行しても guard が常に偽を返し、
「root か UUID が誤っている」と誤診される。**修正時は「同じ節にある同種のトークンを全部
数える」ことが必要**で、grep 対象を修正したトークン名に限定すると取りこぼす。

**3 レビュアーが独立に同一 file:line を検出した**（prompt-engineer / code-quality /
error-handling）。異なる専門レンズ（プロンプト品質・コード品質・エラー処理）から同じ箇所に
収束するのは、その欠陥が単一ドメインの問題ではなく「実行契約としての散文の破綻」である
兆候。severity boost（HIGH → CRITICAL）は妥当だった。

**ドキュメント側では「片方だけ直す」非対称が生まれやすい**。同一ファイルに並行する一般記述が
2 つあるとき（CONFIGURATION.md の :437「no automatic abnormal-exit mechanism」と :632
「except max_review_cycles」）、変更のトリガーになった方だけに carve-out を入れると、同じ
文書が自分の invariant を否定したまま残る。**同種の列挙（Exit paths テーブル・yaml コメント・
別ファイルの同型テーブル）を grep で数えてから直す**のが有効。

**「2 項を名指しした」だけでは条件節は検証可能にならない**。cycle 1 の指摘（either が指す
2 項が未導入）に対し 2 項を名指しする修正を入れたが、その 2 項が結論に繋がる前提
（`--handoff` を省いた set は handoff キーを削除する）は文書内で未定義のまま残った。
**同一クラスの再発**として tech-writer が再指摘している。参照の解決可能性は
「名前が出ているか」ではなく「読者がその文書だけで結論まで辿れるか」で判定する必要がある。

**SPEC.md の schema 表セル内に rationale を書くと、他文書との drift 面と自己矛盾面が同時に
増える**。:1373 のセルは 719 → 1983 文字に膨張し、無条件の安全性断定が同一ファイル :853 の
「例外がある」という記述と正面衝突した。schema 表は「セマンティクス」に絞り、設計理由は
SoT へ 1 行ポインタで委譲する方が drift も矛盾も減る。

### 実測必須ゲートの効き方（cycle 1 との比較）

cycle 1: 5 件中 2 件に `Verification:` アンカー。cycle 2: 6 件中 4 件。**レビュアーが実際に
bash を叩いて再現した指摘は blocking に昇格し、散文の読解上の欠陥（未解決の節参照・dead
marker）は non-blocking に留まる**という分離が 2 cycle 連続で観測された。ワークフロー定義 PR
では「実行して観測できる欠陥」と「読めば分かる欠陥」の境界が安定している。

なお cycle 1 で non-blocking だった 2 件（REFIRE retain 指示漏れ・rationale 肥大）は cycle 2
では指摘事項から推奨事項へ移った。**レビュアーが経路を追い直した結果 risk 評価を下げた**もので、
同一 finding の cycle 間での格下げは正常な収束の一形態。
