### Finding Patterns

本 cycle で最も重要な出来事は、**reviewer が前 cycle の自分の指摘を実測により撤回した**こと。
error-handling reviewer は cycle 3 で「EXIT のみの trap でも中断時に成功を返さない」と主張して
文書の記述を誤りだと指摘したが、cycle 4 で計測方法の誤りに気付いた — `kill -INT $$` を
スクリプト自身が実行すると bash の default disposition が即座に殺すため rc=130 になり、
主張が偽に見えていた。実際に問題になるのは **foreground child でブロック中に SIGINT が届く形**
(hook が `gh api` 待ちのときの Ctrl-C) で、その形では EXIT-only は rc=0 で後続命令まで継続実行する。

同 cycle で security reviewer は同じ箇所を逆方向から指摘した — TERM/HUP では EXIT-only でも
143/129 を返すので「INT/TERM/HUP で成功として報告される」という 3 signal 一括の主張は過度な
一般化である、と。2 人の実測は矛盾せず、**主張は SIGINT に限定すれば真**という形で解決した。

得られた教訓: **signal の挙動を検証するときは「どのプロセスがどの状態で signal を受けるか」まで
条件を揃える**。`kill -SIG $$` (自プロセスへ直接) と「foreground child 待ちの親へ外部から」は
bash の POSIX 準拠挙動が異なり、同じ trap 構成でも結果が反転する。片方だけで検証すると、
正しい記述を誤りと判定する (cycle 3) か、誤った一般化を見逃す (cycle 1-3) かのどちらかになる。

test reviewer は 77 mutant を投入して 57 kill / 20 生存を実測し、うち 6 本を equivalent と
確定させたうえで残り 14 本を pin 欠落として報告した。equivalent mutant を「生存したから穴」と
数えない規律が、指摘の精度を保っている。
