### Finding Patterns

- review-fix ループが同じ欠陥クラスを 3 cycle 連続で出したときは、修正を続けるより切り出す方が収束する。本 PR では (A)「新設した安全経路に有効な回帰 pin が無い」(B)「判定不能を正常系に丸める」の 2 クラスが cycle 2/3/4 で繰り返し出た。各 cycle の修正は正しかったが、修正が増やした表面積そのものが次 cycle の指摘を生んでいた（ステップ 5 の bash ブロックは 64 行 → 238 行）。
- Quality Signal 1 の判定は「同じ指摘文言が残っているか」ではなく「同じ性質の欠陥が同じ場所で繰り返されているか」で行う。fix が新たに生んだ指摘は SoT 上は新規扱いだが、**同じクラスが 3 cycle 続いたら収束していない**とみなすのが実態に合う。
- 検証コマンドの rc は「対象が無い」以外の意味も持つ。`git show-ref --verify --quiet` は ref 不在・refname 非合法・ref store 障害のいずれでも rc=1 を返す。`git check-ref-format` を足しても解消するのは構文起因だけで、「合法だが対象と別物の名前」（`origin/foo`）と ref store 障害は残る。rc の多義性は「1 つ検査を足せば閉じる」性質のものではない。
- 「この検査で塞いだ」と書くときは、塞げていない範囲も同じ場所に書く。塞げていない例を「塞いだ例」として列挙すると、次の保守者が再検証しなくなる。
- 静的 pin は literal の存在ではなく (a) 条件式そのもの (b) marker 名と判定値の連言 で書く。literal だけを要求する形は `if false` 化と判定値の反転の両方を素通しする。実行時 TC はそれらすべてを捕捉する。
- テストの抽出アンカーが片側のブロックしか覆っていないと、もう一方は何 cycle も無検証のまま進む。判定表に同じ marker literal が存在するため、ファイル全体を grep する静的 pin では emitter の消失を検出できない。
