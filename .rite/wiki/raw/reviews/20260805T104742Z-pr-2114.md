### Finding Patterns

**(1) 「機構を足して守った」ものは、その機構自身が次の未検査面になる**

cycle 1 で helper に `_undecidable` marker を新設したが、その marker を受ける consumer 側 (`{review_cleanup_check}`) は reason 非依存の flat 判定のままだった。結果、helper が「失敗ではない (failed=0)」と宣言した状態が完了報告では「残作業」として描画される。**新しい reason / marker / sentinel を足すときは、同じ commit で consumer 側の分岐表も更新する** — consumer が reason 非依存なら、reason を増やすこと自体が意味論の衝突を生む。同 repo には既に per-reason 表を持つ先例 (`{wiki_ingest_check}`) があり、機構はあるのに新 reason にだけ適用されていなかった。

**(2) fix で追加したコード自体に pin が付かない**

cycle 1 で helper 本体を 60 assert まで厚くした一方、その **唯一の呼び出し元** (`cleanup/SKILL.md` ステップ 6) を固定する層はゼロのままだった。呼び出しを PR 前の形へ戻しても全 114 test file が green。同様に、helper の stderr 転送 3 本のうち mkdir だけに pin が付き (cycle 1 の指摘対応で追加)、mv と rm は無検査のまま残った。**「指摘された 1 箇所」だけを塞ぐと、同じ性質の兄弟が無検査で残る** — 修正時は「この pin が守る対象の兄弟は何本あるか」を数えること。

**(3) 診断・防御の追加が platform 依存を持ち込む**

`timeout` (GNU coreutils) を bare で使った TC が macOS CI leg で rc=127 になり、hang の signature (rc=124) を原理的に出せなくなる。プロジェクトには portable な `_timeout` helper が既にあり、姉妹 suite は全て使っていた。同様に「GNU 環境では mv_failure 側に落ちる」というラベル自身が platform 限定を表明している assert が無条件評価されている。**新しい外部コマンド依存を TC に持ち込むときは、既存 suite が同じコマンドをどう呼んでいるか先に grep する。**

**(4) 「無限ループを防ぐ guard」の根拠が実は成立していない**
