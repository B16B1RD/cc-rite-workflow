### Finding Patterns

**helper の reason enum を散文で列挙すると drift 源になる**。`review-trend-divergence.sh` は 0 件系だけで `no_results_file` / `results_dir_missing` / `no_file_after_pin` / `run_boundary_unresolved` の 4 分岐を持ち、dir と pin の状態で決まる。散文が特定の reason 名を名指しすると、その分岐条件まで正しく書かない限り必ず不正確になる。**列挙しない**（「判定は結果が 3 件揃うまで降りる」等）のが構造的に安全。

**reviewer の実測が割れたときは、どちらの立場でも成立する記述へ倒す**。cycle 3 では tech-writer が「Issue #2127 の `lost=1` により実際の武装開始は head 5」と主張し、他 4 名が「5 件 fixture での helper 実測で head 4/5/6」と主張した。両者の差は「その run で結果が何件保存されたか」という、docs からは検証できない事実に帰着する。head 番号を名指ししない記述にすれば、どちらが正しくても成立する。tech-writer と error-handling の両者が独立に同じ回避策を推奨していた。

**cross-validation で 4 名が同一箇所を指摘したときは、内容が同じでも severity 判断は割れる**。cycle 3 の `need_3_cycles` 誤りは tech-writer が MEDIUM、test / error-handling が HIGH と評価した。統合では最高値を採るが、severity の差は「その誤りが読者をどこまで誤導するか」の見積もりの差であり、討論の材料になる。
