### Finding Patterns

**パッチを重ねると seam が増える** — cycle 4 の 7 件のうち 3 件は cycle 3 の修正が生んだ新規不整合だった。指摘 4→7 件へ増加し、収束していた流れが反転した。原因は個別指摘への局所修正を続けたことで、共有 SoT と consumer の間に「consumer 別の予算表」「consumer 委譲された溢れ規則」「consumer 固有の不変条件」という条件付きの分岐が積み上がったこと。

- **SoT を consumer 依存にすると seam が増える**: 「上限は consumer が既に使う質問数を差し引いた残枠」「溢れの扱いは consumer 側の規定に従う」のように SoT を条件付きにすると、各 consumer 側に対応する規定を書く義務が生まれ、書き漏れが新しい指摘になる。**SoT は単一の default を持ち、consumer 固有の事情は consumer 側の設計を変えて吸収する**ほうが総量が減る。
- **削除した規則を参照する記述が残る**: SoT から default rule を削除した同じ commit で、consumer 側にその default rule を根拠として引く文を追加していた。**SoT を書き換えたら、その SoT を引用している全箇所を grep して同期する**。
- **不変条件は成立する形で書く**: 「3.1 の diff と Phase 4.1 が書く body は同一」という不変条件を掲げながら、同じ節が承認後の本文書き換えを規定していた。両立しない不変条件を load-bearing と明記すると、後続の修正がそれを守ろうとして別の欠陥を生む。
- **同一表に直交軸を混ぜると転写漏れが起きる**: 「検査対象 0 件で silent skip」と「自己矛盾候補あり」は別軸なので優先規則が要る。片方の consumer にだけ規則を書くと、共有 SoT を参照する 2 consumer の挙動が主経路で分岐する。**優先規則は SoT に 1 箇所だけ書き、consumer からはポインタで指す**。
- **エラー分類は観測シグナルで分ける**: 「コマンド失敗 → UNVERIFIED」と「参照先が存在しない → CONTRADICTED」は帰結が正反対なのに、どちらも同じ非ゼロ終了で観測される。終了コードだけでは分類できないため、stderr の文言 (`Could not resolve`) のような判別子を条件列に明記する。判別子の無い分類表は、安全側でない方へ倒れる。
- **「提示する」と書いたら提示先を持たせる**: 訂正案を「提示する」と定めた処理が、合流先の経路に質問も出力欄も持たないと dead instruction になる。提示先が無いなら、既に出力する予定のもの (付記本文など) に載せる形へ設計を変える。
