### Finding Patterns

- **「否定表現の存在を肯定的に assert する」パターンは alternation に非否定語を混ぜると崩れる**: `grep -qE '保証されない|止められない|抑止できるのは'` の 3 つ目は、それ単体では肯定にも否定にもなり得ない断片。禁止されている過大主張を書いたままでもマッチするため、pin が当の違反に false confidence を与える。**教訓: 「性質 P を持つこと」を assert する alternation の各 disjunct が、単体で P を含意するか一つずつ確認する。含意しないものは disjunct にしない。**
- **`grep ... | head -1` は「先頭 1 行しか見ない」ことを assertion の抜け道にする**: 対象を複数行に分割するだけで検査を回避できる。**教訓: 「この宣言が存在すること」を pin するなら、宣言の単位（bullet 全体等）を抽出してから検査する。**
- **レビュアーが上限サイクルで判定を厳格化すると収束する**: cycle 5 では 5 名中 4 名が「マージ可」を出し、各自が前 cycle の推奨を「本 PR でブロックすべきか」で再判定して follow-up へ落とした。1 名だけが新規の false-negative を実測で見つけた。**教訓: サーキットブレーカー直前であることを reviewer に伝えると、Observed Likelihood Gate の判定が厳格化して真にブロックすべきものだけが残る。**
- **レビュアーが自分の前 cycle の前提を訂正した**: prompt-engineer は cycle 4 の design_confirmation（「リモート成功の marker 不在は同一セクション内で 3 対 1 の少数派」）を、実際には 2 対 2 であり同一 check 内のローカル側と同型だと訂正して取り下げた。**教訓: 「規約が割れている」という主張は、割れている両側を数え直してから出す。**
- **CI の赤を「本 PR の回帰か既存 flake か」で切り分ける**: `hooks tests` ワークフローが赤だったが、(1) 失敗テストが本 PR の変更 3 ファイルに含まれない、(2) 直前 5 コミットは success、(3) 同一 SHA の別ワークフローが同じスイートで success、(4) ログに `printf: write error: Broken pipe`、の 4 点から EPIPE flake と確定できた。**教訓: 赤を見たらまず「同一 SHA の他ワークフロー」と「直前コミットの同一ワークフロー」を比べる。2 レビュアーが独立に同じ診断へ到達した点も信頼度を上げる。**
- **`grep -q` + パイプの EPIPE は pipefail 下で偽の判定を生む**: `printf '%s' "$x" | grep -qF "$lit"` は `grep -q` が早期終了して printf が SIGPIPE を受け、pipefail でパイプライン status が 141 になり否定条件が誤成立する。here-string（`grep -qF "$lit" <<<"$x"`）にすれば起きない。**教訓: `grep -q` をパイプの終端に置かない。**
