### Finding Patterns

**定数の既定値を変更する PR では「数値の同期」より「数値から導出された散文の再計算」が主要な欠陥面になる**。本 PR は実装 3 サイト・テンプレート・docs 5 ファイルの数値同期を完全に達成し、機械検査 (新規テスト 49 assertions) も green だったが、レビューで検出された 7 件中 4 件が「5 から導出されていた散文を 15 基準で書き直す際に混入した off-by-one」だった。特に `max=N` が「N cycle を許容する」のか「N cycle で止める」のかという境界則が、同一文の前半と後半で食い違う形で 2 箇所に複製された (Asymmetric Fix Transcription が誤りの側に働いた形)。

**引き上げ根拠として引用するトラジェクトリの帰属を裏取りせずに書くと、日英 docs が別々の run を根拠として提示する状態になる**。本 PR では日本語 SKILL.md が既存 backtest fixture (#1701 期) を、英語 CONFIGURATION.md が新しい実測 run (#2126) を、それぞれ「15 を選んだ根拠」として引用した。前者は test ファイル自身が「収束していない run」とラベルしているもので、根拠として不適切だった。

**mutation testing なしでは「テストが green」と「テストが drift を検出できる」を区別できない**。3 名の reviewer が独立に mutation を投入し、31 mutant 中 27 撃墜 / 4 生存を実測した。生存した 4 件はすべて「英文散文の既定値」「半角スペース無しの日本語表記」という negative 検査パターンの穴で、positive count pin (`grep -c` による件数一致) を足すことで閉じられる。negative 検査だけで契約を守ろうとすると表記揺れの分だけ穴が残る。

**ERE の `?` を多バイト文字に掛けると LC_ALL=C で意図しない挙動になる**。`既定値? 5` は `値` を optional にする意図だったが、C ロケールではバイト単位評価となり「既定 5」を検出できない。`既定(値)? 5` のグループ化で解決する。現行環境 (ja_JP.UTF-8 / C.UTF-8) では未発現だが、CI ロケールの変更で silent に失効する。
