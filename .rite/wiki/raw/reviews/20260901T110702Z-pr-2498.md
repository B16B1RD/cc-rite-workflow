1. **非実測 non-blocking を毎 cycle 先回りで直すと、それ自体がループの燃料になる**:
   cycle 3 と cycle 4 の指摘はいずれも「直前 cycle の修正が触った行のコメント文言」に対するもので、
   パッチの重ね掛けが 2 cycle 続いた。非実測指摘には designated home（6.1.d の記録と cleanup が
   作る follow-up Issue）がある。sweep で消化すべき実質的な doc-sync gap と、cycle ごとに湧く
   文言の推敲は別物で、後者を先回りで直すと次 cycle のレビュー対象を自分で作ることになる。
   ループを止める操作は reviewer を減らすこと（品質を予算で縛る）ではなく、
   「本 PR が既に 2 回以上書き換えた行の文言推敲はスコープ外」と disposition を宣言すること。

2. **トレンド判定の「収束中」は降格政策を測っていることがある**: blocking 件数の推移は
   `3,0,0,0` で `converging_or_descending` と出るが、毎 cycle の指摘が class B 降格されている
   場合、この数列は「指摘が減った」ではなく「降格が効いている」ことの反映になる。
   ブレーカーの機械判定は残すべきだが、人間（orchestrator）側は
   「今 cycle の指摘は前 cycle の修正が原因か」を別途見る必要がある。

3. **「兄弟を統一する」修正は、統一すべき集合の境界を先に確かめる**: 診断ラベルを 3 箇所で
   揃えようとして、実際には性質の異なる 2 種類の境界（呼び出し側が引数を確定させる
   script → script 境界と、literal substitution が引数を壊しうる skill body → script 境界）を
   同じ語彙で塗り、到達可能な原因を候補から落とす over-fix になった。次 cycle で差し戻し。
   「3 兄弟」と数える前に、その 3 つを実在する site で名指しできるか確認する。

4. **差し戻しの検証は「導入 commit の親」と照合する**: 「develop と同一文言へ戻ったか」という
   検証指示は、対象の call site が develop に存在しない場合に成立しない（実際に reviewer が
   この誤りを訂正した）。差し戻し系の検証は当該 hunk を導入した commit の親を baseline にする。
   最も強い証拠は `git diff <導入 commit の親>..HEAD -- <file>` が空であること。

5. **Linux だけで緑にしても CI は通らない**: 2 cycle × 6 reviewer が全員 Linux でテストを実行し、

   直接 assert するテストでは fixture 側も `pwd -P` を通す。symlink 経由の `$TMPDIR` を
   Linux 上で人工的に作れば同条件を再現でき、修正が load-bearing かも実証できる。
