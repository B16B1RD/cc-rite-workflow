# レビュー結果: 同じ run で再開した後続 cycle の非実測指摘を NB sweep が取りこぼす

## 判定

mergeable（reviewer 3 名、XS/S 軽量レーン、ブロッキング 0 件、非ブロッキング 1 件）

## 変更の要旨

iterate の NB digest sweep は、再入ガードファイルが「あるだけ」で already_done として skip していた。同じ run の後続 cycle で新しいレビュー JSON に非実測指摘が出ても消化されずに残った。ガードファイルの 1 行目に sweep したレビュー JSON の basename を記録し、最新 JSON の basename と一致するときだけ skip するように変えた。範囲を持たない旧形式のファイルは skip しない。

## レビューで得た知見

- 再入ガードは「実行したか」ではなく「何を対象に実行したか」を記録しないと、対象が増えたときに古い完了記録が新しい対象を覆い隠す。範囲の単位は、処理本体が読む対象と同じ単位（ここではレビュー JSON）にそろえると、読み手と処理本体の判定がずれない。
- 最新ファイルを選ぶ規則（字句順の末尾か mtime 最大か）が複数箇所に複製されているとき、テスト fixture で字句順の末尾と mtime 最大を意図的に別ファイルにしておくと、選び方を取り違えた変異を検出できる。字句順と mtime 順が一致する fixture だけでは、どちらの規則でも green になる。
- 旧形式の行（2 行目の SHA）を「残すが新しくは足さない」ように書き手を変えたときは、形式を説明する schema 側にも「書き直しで残す」ことを書かないと、schema だけを見た保守者が行を落とす方向に誘導される（非ブロッキング指摘）。
- 同じ制約の根拠として挙げていた実測が、変更後の述語ではもう防がない状況を指していることがある。仕組みを変えたら、rationale に挙げた根拠が今もその仕組みの責任範囲にあるかを見直す。

## 非ブロッキング指摘

- tech-writer / MEDIUM: review-result-schema.md の再入ガード形式説明が、書き直し時に 2 行目 SHA を残す挙動を記述していない
