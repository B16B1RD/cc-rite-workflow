### Finding Patterns

bash テストで `var=$(cmd | jq -r '... // empty' 2>/dev/null)` を `set -euo pipefail` 下に置くと、jq が非ゼロ終了した時点で代入コマンドの終了ステータスがスクリプト全体を abort させる。`2>/dev/null` が診断も捨てるため、テストは fail 関数を呼ばずに出力ゼロで死ぬ。後段に置いた「想定外の出力形式」検出分岐は、不正 JSON のケースでは構造的に到達しない dead branch になる。runner が exit code ベースで集計していれば silent pass にはならないが、失敗の診断情報は完全に失われる。

否定アサーション（`!= "deny"` 等）に positive control を前置する際、control の派生元を「本体が実際に読む入力ファイルそのもの」にするのが load-bearing な設計判断だった。同じ素材から独立に作り直す形にすると、本体側の入力構築が壊れても control が green のまま通り、control の意味が失われる。

hook 契約の読み違いを防ぐには、同ファイル内の既存ヘルパー（この例では allow を `rc=0 かつ空出力` と定義する assert 関数）を正典として参照するのが確実。Issue 起票時の修正案が実装の実挙動と噛み合わないことがあり、実測（スタブ差し替え + mutation testing）で前提を確認してから設計を決める必要がある。
