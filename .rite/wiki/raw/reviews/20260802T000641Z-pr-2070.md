### Finding Patterns

5 サイクル・のべ 30 レビュアーで **0 件へ収束**した。指摘の総数は cycle ごとに 3 → 6 → 5 → 3 → 0 と単調には減らず、抽象度が一段ずつ上がりながら収束した点が特徴。

**収束の形: 実装 → テストの厳密さ → ドキュメントの正確さ → ドキュメントの出典表記 → 0**

- cycle 1-5 を通じて **実装本体 (helper のロジック) への指摘は 1 件も出ていない**。実装の正しさは毎サイクル、実データでの base 比較（develop 版と per-page hits がバイト一致）・契約経路の実測発火・敵対的入力・変異スイープで独立に再確認された。
- 指摘はすべて「実装は正しいが、その正しさを固定する仕組み（テスト・記述・出典）が片側だけ」という形だった。

**fix が新しい指摘を生む率は 4 サイクル連続で 20-33%。ただし内容の誤りは 1 回だけ。**

cycle 1 fix → cycle 2 で 1/4、cycle 2 → 3 で 1/5、cycle 3 → 4 で 1/3、cycle 4 → 5 で 0/0。持ち込んだ欠陥の内訳は「常時緑の dead assertion（BRE と ERE の取り違え）」「誤った前提での要検証注記」「出典を伴わない断定」「表の 1 行だけ pin」で、**いずれも修正の中身ではなく修正の書き方**だった。唯一「中身が誤り」だったのは cycle 2 の要検証注記（上流を読めば偽と分かる命題を未確認として提示した）。

### Process Observations

- **「修正した箇所を次サイクルの第一級レビュー対象に据える」運用が毎回機能した**。cycle 2 の最重要指摘（dead assertion）は、前 cycle で 0 件だった reviewer が最初に見つけた。「前回 0 件だったから浅くてよい」は成立しない。
- **変異検証を「そのテストが実際に使う経路で」行うことが決定的**。cycle 1 の失敗は、検証に素の grep（BRE）を使い、アサーション本体が使う `grep -qE`（ERE）と別コマンドだったこと。以後は隔離 worktree でスイート本体を変異下実行し、当該 assertion が FAIL することを目視する形に統一した。
- **レビュアー間で外部事実の読みが割れたら一次ソースで決める**。上流実装のグラフ構築モデルについて 2 名が別々の主張をし、実装を直接読んで片方が誤りと確定した。両者とも「上流を読んだ」形で提示するため、読み比べないと誤りが通る。
- **同一の疑問が複数レビュアーから独立に上がるのは、記述の曖昧さが実在する強いシグナル**。フィールドの母集団拡大について 3 名が独立に同じ確認を提起し、ユーザー確認へ回して決着させた。
