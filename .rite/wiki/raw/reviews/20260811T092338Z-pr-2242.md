### Finding Patterns

本 cycle の指摘は「検証層の削減が silent failure を再導入した」型に集中した。プロジェクト原則
(no speculative structure / fail-loud) に従ってガードを削る際、削除の可否判定に「Issue の
エラー表に載っているか」だけを使うと、**同じ PR の過去 cycle が実測を根拠に追加したガード**を
落とす。今回は `assemble.sh` の位置別マージン検査がそれで、削除により `-t` に過大値を渡した
ときの「exit 0 のまま素材を捨てた mp4」が復活した (3 reviewer が独立に同一箇所を指摘)。

繰り返し観測されたパターン:

- **入口検査を文字クラスの否定で書くと defect class を表現できない**: `case "$x" in ''|*[!0-9.]*|*.*.*)` は
  ドット単体 `.` を通す。「数値であること」は正規表現 (class predicate) で書く
- **解析的に算出した期待値を成果物の実尺として報告する**: 照合しないまま完了行に出すと、
  成功メッセージ自体が誤情報の発生源になる (期待 6.000s / 実測 2.066667s)
- **ffmpeg は入力が退化しても exit 0 で完走する**: 「崩れれば ffmpeg 側のエラーとして現れる」は
  フレームレート不一致では成立するが (exit 234)、xfade の offset 崩壊では成立しない。
  「ffmpeg が弾いてくれる」という前提はガード削除の根拠にならない
- **契約 MUST に自動 pin が無い**: fixture を置くだけで実行経路が無いと、契約ガードを変異させても
  検証コマンドが green のまま通る (mutation 実験で確認)
- **文書が実装より強い保証を主張する**: 削減時に fail-loud 表だけ同期し「検査していないこと」節を
  更新しないと、未検査項目が機械検査されると誤読される
