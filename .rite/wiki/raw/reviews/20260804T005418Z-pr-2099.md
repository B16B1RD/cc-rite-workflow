### Finding Patterns

1. **代理値を捨てる修正は、その代理値が担っていた「暗黙のガード」も同時に捨てる**: cycle 1 で
   run 境界を counter から実データ pin へ移した際、旧実装の配列スライスが counter=0 で構造的に
   空集合を返していた事実（＝発火不能という副次的保護）を見落とし、pin 不在経路で counter=0
   でも全件を読んで発火する退行を入れた。代理値を廃止するときは「その値が偶然満たしていた
   invariant」を列挙し、新実装で明示的に再現するか意図的に捨てるかを決めること。

2. **縮退方向が機構内で一貫していないと、1 経路だけが逆向きに倒れる**: helper 本体は全経路
   「判定不能 → 不発火（安全側）」で統一されているのに、新設した pin だけが「書けなければ
   全件読み（＝誤発火側）」へ倒れていた。新しい入力経路を足すときは、既存機構の縮退方向を
   1 文で言えるか確認し、その向きに合わせる。

3. **sed の文字クラスは値域の実例で検算する**: `[a-z_]*` で reason を抽出したが、実装が返す
   値のうち `need_3_cycles` だけが数字を含み、最頻経路で無言に切り詰められた。抽出パターンを
   書いたら、生成側が返しうる**全値**を列挙してパターンに通すこと（enum が文書化されている
   なら機械的に検算できる）。

4. **同一 PR 内で assert の粒度を揃える**: 同じ cycle で追加した stderr assert のうち、一部は
   WARNING 本文を pin し、一部は marker 語 `WARNING:` だけを見ていた。粒度の非対称は
   レビューで必ず指摘され、弱い側が dead assertion になる。

5. **中和・正規化のような「無くても緑」の防御は、専用の破壊テストが無い限り必ず dead surface になる**:
   制御文字中和を追加したが、それを外してもスイートは全 PASS。防御コードを足したら、その防御が
   守る攻撃入力を fixture 化して同じ commit で pin する。

6. **fixture が production の命名形を 1 つでも欠くと、その形に依存する契約が全部 unpin になる**:
   collision-resolved 名（`{ts}~{hex}`）を fixture が生成しないため、`LC_ALL=C` ソート順に
   依存する 2 つの独立した契約（要素順 / 境界選別）がどちらも locale 変更で壊れても緑のままだった。
