### Finding Patterns

このリポジトリで繰り返し観測される 4 パターンが今回も再現した。

1. **静的 pin の tautology / mutation 非感応**（最頻出）。「旧形状の不在」を pin する形は、旧形状がそもそも base に存在しない場合に追加時点から一度も失敗しえない。今回も `NONBLOCKING_LOOKUP=done` の出現数 0 を pin したが、develop 側に当該文字列は 1 件も無く base 上でも green だった。また「区間内リテラルの出現数を等値で pin する」形は、live な述語を差し替えつつ同区間に散文を 1 行足すと相殺されて素通りし（false negative）、逆に gate 無変更の散文追加で失敗する（false positive）。**pin すべきは出現数ではなく live な述語そのもの**（`**Check**: .*<sentinel>` のような load-bearing 行の存在）。

2. **`grep -F` の部分一致に依存した到達性 pin は、コメントアウトを検出できない**。行頭に `# ` を足しても部分一致は成立し、コメントアウト行は同じ fence 内に留まるため fence 検査も通る。到達性を pin するなら行頭 anchor 付き ERE（`^[[:space:]]*<literal>`）が必要。

3. **caller 契約違反と IO 失敗を同一条件に潰すと、契約違反が非ブロッキング経路で無音になる**。`[ ! -s "$file" ]` は「ファイル不在（caller が Write を実行しそこねた = 定義バグ）」と「存在するが空（IO 失敗）」を区別しない。同じ helper 内で placeholder residue は `exit 1` にしているのに本条件だけ非ブロッキング、という内部非対称が発生しやすい。**兄弟 helper が同一条件をどう扱っているかを必ず突き合わせる**。

4. **SoT を更新したら consumer を grep で洗い出す**。「記録先 3 経路 → 4 経路」の変更で SoT と同一ファイル内の別行を含む 6 箇所が旧値のまま残り、うち 1 箇所は SoT と正面から矛盾する断定文（「唯一の永続チャネル」）になった。列挙・件数・「唯一の〜」型の断定は SoT 変更時の必須 grep 対象。

加えて、**gate の入力に使う機械可読 control line は、その値を作る引数側で完全性を担保する必要がある**。改行を含む値を無検証で sentinel に埋め込むと、完全な形の偽 sentinel を生成できてしまう（denylist gate では防げず、allowlist または制御文字 reject が要る）。同種の gate を既に allowlist へ移行済みの兄弟 helper がある場合、新規 helper だけ移行前パターンで書かれる drift が起きやすい。

**update-in-place コメントの lookup に author 条件を入れていないと、marker を模倣した第三者コメントに PATCH 先を奪われる**。前方一致化は引用返信（`> ` 前置）しか塞がない。
