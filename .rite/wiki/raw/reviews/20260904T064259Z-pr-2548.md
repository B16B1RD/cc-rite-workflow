### Finding Patterns

このリポジトリで繰り返し観測された 2 つの型が本 cycle でも出た。

1 つ目は「検出 arm を追加したが、その arm が scanner の scan roots の外しか捕捉しない」型。positive control（samples 配列）は arm 単体との照合なので通るが、全木走査は 1 度も当該 arm を発火させない。arm を足すときは positive control の pass ではなく、**修復前 tree に対する per-arm ヒット数**で「その arm が実際に働くか」を測る必要がある。scan roots の宣言と arm が拾おうとする対象ファイルの所在が食い違っていないかを、arm 追加時に必ず突き合わせる。

2 つ目は「プレースホルダで復元した番号が、同じ画面内の未変更の裸番号と矛盾する」型。番号トークン（`#NNNN`）だけを検出文法の対象にしていると、`#` を伴わない裸番号（`/rite:open 1234`、`feat/issue-1234-add-auth`）は検査の外に残る。片側だけをプレースホルダへ寄せると、レンダリング結果が破綻したまま検出ゲートは green になる。番号を含む表示テキストを修復するときは、同一表示単位（同じターミナルカード・同じ scene）の全番号を 1 度に見る。

補足として、正規表現 arm を「開き括弧 + 空白 + 小文字」のような広い形で書くと bash subshell（`if ( set -C; ...`）に大量誤検出する。狭めた arm を入れたら、その狭め自体を negative assertion で pin する（広い形に戻すと落ちることを実測で確かめる）と、後からの再拡大が全木走査の「residue found」ではなく arm の退行として現れる。
