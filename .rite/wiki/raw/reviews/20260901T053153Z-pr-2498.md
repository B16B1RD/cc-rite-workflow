### Finding Patterns

SKILL.md のインライン bash を helper へ抽出する refactor で、**抽出そのものが新しい失敗モードを作る**パターンが集中して出た。

1. **プロセス境界の新設が silent failure を生む**: インライン bash を helper へ移すと「helper が起動しない」経路（usage error / rc=127 / plugin_root 未解決置換）が新規に生まれる。呼び出し側が rc を捨てると marker が 1 本も出ず、消費側の判定表が「marker 不在 = 成功」と読む設計なら未実行が完了と報告される。3 名の reviewer が独立に検出。抽出元の中に「内側の helper に対して rc を marker へ変換する」ガードが既にあったのに、自ら新設した外側の境界には持ち上げていなかった。
2. **fail-loud の追加が正規経路を壊す**: helper に引数の必須検証（usage error）を足すと、抽出前は正常に処理していた入力（Issue 番号未識別など、スキルが公式にサポートする状態）が marker なしで落ちる。fail-loud は呼び出し側の消費規則とセットで設計しないと挙動退行になる。
3. **新規 marker が消費側の family glob に取り込まれる**: 消費側が `PREFIX_*` の glob で marker family を scope している場合、同 prefix の新 marker（`--dry-run` 用など）を足すと判定表のどの行にも一致せず fallback にも落ちない未定義状態を作る。コメントで「family を分離している」と書いても、消費側の scope 規則が glob なら分離は成立しない。
4. **件数だけの pin は配線を守らない**: 抽出の完了ゲート（「SKILL.md に削除処理の bash が残っていない」）を helper 呼び出しの件数で pin すると、呼び出しの引数を literal へ潰す変異が素通りする。引数がガードを駆動する入力である場合、件数の pin は「配線は検査済み」という false confidence を生む。mutation で 3 変異すべてがスイート全体 green だった。
5. **テストが本番の走らせる形を走らせない**: helper の単体テストが全起動で optional 引数（`--state-root`）を明示的に渡すと、本番が通る唯一の経路（既定解決）が 1 度も実行されない。同様に、分類の主経路（`in_worktree` arm）を生成しないテストは、その arm の実装を丸ごと未検査のまま通す。
6. **行頭アンカーの regex が実コードを見落とす**: 静的検査で `^[[:space:]]*git worktree remove` のように行頭アンカーを使うと、`if cmd; then` / `|| cmd` の位置にある実行行に一致しない。抽出前のコードに当てても 1 件しか一致せず、ゲートが検査したつもりの対象を最初から見ていなかった。
7. **配布物に存在しないスキル名を現在形で書く**: helper の docstring が「A と B の双方から呼ばれる」と書いたが B は未実装。Issue 本文では可能形 + Sub 番号で hedge されていた表現が、配布される docstring で断定形に変わっていた。
