### Finding Patterns

ワークフロー定義（LLM 向け散文手順）に「検証手順」を新設する PR で、**手順が処方する検証コマンド自体が、その手順が防ごうとしている失敗モードを検出できない**という自己言及的な欠陥が最上位の指摘になった。2 名のレビュアーが独立に同一 file:line を検出した。

- **処方コマンドの判別能力を実測する**: `gh issue view {N}` は PR 番号を渡してもエラーにせず PR を解決して成功で返す（`state=MERGED` / `url=.../pull/{N}` が返る）。一方 `gh pr view {N}` は Issue 番号に対し `Could not resolve to a PullRequest` で正しく失敗する。この非対称性のため「`gh issue view` の title を照合する」という手順は PR/Issue 番号混同を検出できない。本リポジトリでは squash merge により PR タイトルが Issue タイトルから派生するため title はほぼ同一になり、照合が空振りする。判別には `state`（`MERGED` は PR 固有値）か `url` のパスセグメント（`/pull/` vs `/issues/`）か `gh api repos/{o}/{r}/issues/{N} --jq '.pull_request'` の非空判定を使う必要がある。
- **worked example は必ず実行して裏取りする**: reference 中の具体例（commit / PR / Issue 番号）の記述自体は正しくても、その例に対して処方手順を実際に走らせると手順の欠陥が露呈することがある。ドキュメントの「記述の正しさ」と「手順の有効性」は別軸。
- **SoT 宣言と実体の乖離**: 「語彙は X が SoT であり再定義せず転用する」と宣言しながら、独自の意味列を持つ表を同一ファイルに置くと再定義になる。判定「ラベル」を借りるのと判定「根拠」を借りるのは別物であり、根拠が異なるなら宣言側でその旨を明示しないと、SoT を読みに行った保守者が対応しない定義を受け取る。
- **プロジェクト規約の数値上限は lint 対象外でも適用される**: Simplification Charter の「Issue / PR 番号の本文引用は 1 ファイル 1 件まで」は `number-reference-check.sh` の走査対象（CHANGELOG 2 種 + lint/SKILL.md）外のファイルでも適用される。機械検出されないことは適用除外を意味しない。
- **指示の配置と実行地点の乖離**: 「後続ステップ X で生成するものに検査を適用せよ」という指示を、X より前のセクションに置くと、線形に実行する LLM は X の地点で検査を思い出さない。検査の指示は実行地点（生成コードの直前）に置くか、実行地点側にポインタを張る必要がある。
- **AskUserQuestion の質問数上限は consumer 間で共有される**: 共有 reference が「最大 4 件まで」と定めても、既存の確認呼び出しへ畳み込む consumer では既存の質問数を差し引いた残りが実効上限になる。SoT 側の上限が「専用呼び出し前提」か「共有呼び出し込み」かを明示しないと超過する。
- **承認と適用の内容一致**: 差分表示 → 承認 → 適用の順序を持つフローで、差分表示後・承認前に本文へ自動付記すると、ユーザーが承認した内容と適用される内容が乖離する。付記するなら差分を再描画するか、付記箇所を承認の確認に列挙する。
