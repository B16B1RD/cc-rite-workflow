### Finding Patterns

**発火条件と回復条件が同一の状態変数に依存する委譲設計は、回復経路が構造的に成立しない**: 本 PR は「flow-state に worktree 記録が無い（`in_worktree_unrecorded`）」を委譲モードの発火条件とし、回復手段として「main checkout での再実行」を案内した。しかし再実行時も flow-state は空のままなので同じ検出 helper が `none` を返し、委譲した項目に到達しない。委譲・遅延・後回しの設計を入れるときは「委譲を受け取る側が、委譲した事実を機械可読な担体（manifest / state ファイル）で受け取れるか」を必ず確認する。人間宛ての散文だけが担体になっている委譲は回復不能。3 名の reviewer（役割の異なる prompt-engineer / tech-writer / test）が独立に同一の欠陥へ到達した = 設計レベルの欠陥は役割横断で検出される。

**prose-driven skill のテストは marker 名の在処ではなく指示語を pin しないと、指示の反転が素通りする**: `assert_grep` で `CLEANUP_DELEGATED=1` の存在だけを見るテストは、ガードの削除は検出するが「実行しない」→「通常どおり実行する」の反転を検出しない（mutation 実測で 4 サイト反転しても全 assert green）。prose が実装本体である skill では、指示語そのものが pin 対象。

**新設した marker には排他性の negative control が要る**: 「この marker を emit してよいのは 1 箇所だけ」「このガードを持つのは 3 ステップだけ」という排他性は、`grep -c` による件数固定でしか pin できない。存在 assert だけでは marker の漏出（別 arm からの emit）やガードの混入（state 系ステップへの誤挿入）を検出できず、いずれも受入基準を丸ごと無効化しうる。

**「構造的に不可能」という前提は形態を特定して書く**: harness の worktree 隔離ガードは「Bash 呼び出しのコマンド文字列に直接 `cd` / `git -C` が現れる形」を拒否するが、helper スクリプト内部の `cd` は拒否しない（実測）。「構造的に拒否される」と一般化して書くと、自動化可能な操作を恒久的に人手へ委ねる設計判断が固定される。
