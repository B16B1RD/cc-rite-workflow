**A. 検出層・検証層の「列挙」は必ず漏れる**
- stage 1 の装飾対応を bold 限定（`\*{0,2}`）で書いたら、バッククォート・全角コロン・三重アスタリスク・underscore が漏れて無音降格が残った。**正規化**（文字クラス + 全角記号の吸収）に書き換えて解消
- 教訓: 「特定の形を列挙して拾う」設計は、列挙を 1 つ足すたびに同じレビューが再発する。文字クラスで吸収する形にすると打ち止めになる

**B. 検証層を hard fail にすると「救おうとした対象より大きなもの」を落とす**
- 記録欠落を検出する gate を hard fail にしたら、記録の欠落を理由に**保存そのものが中止され blocking findings まで失われた**（既存テスト 5 件の失敗で発覚）
- さらに型 check を id gate の後ろに置いたため、非配列で `length` が非 0 になる値（`"abc"`→3 / `3`→3 / `{"a":1}`→1）が件数を水増しし、「非ブロッキング」と 3 箇所に明記した契約が**型によって hard fail に化けた**
- 教訓: advisory なデータの欠陥で primary なデータを巻き添えにしない。gate の順序は「型 → 内容」で、型崩れを内容の欠陥として誤診断させない

**C. SoT の例が SoT の enforcer を通らない**
- canonical JSON 例に足した id `F-02b` が、同じファイルが定める書式規則 `^F-[0-9]{2,}$` に違反していた。write 側はこの例を「真実の源」として参照するため、写すと永続 JSON が保存されず既定構成で hard fail する
- **4 reviewer が独立に検出**。どちらのファイルを単独で読んでも見つからず、「例を validator に流す」実測でのみ判明した
- 教訓: canonical 例を持つ SoT には「例が自身の enforcer を通る」fixture を置く。これは規則と例のどちらを読んでも検出できない欠陥クラス
