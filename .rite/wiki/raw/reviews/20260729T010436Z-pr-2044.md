### Finding Patterns

cycle 3 で機構を「削除」した結果の取りこぼしが 4 件。削除は追加より安全に見えるが、削除固有の失敗モードがある。

1. **機構を削除したら、その機構を名指しする散文を全部消す（最大の型）**: cycle 3 で「ステップ 0.6 の発火後再実行 override」を実装ごと削除したのに、それを参照する散文が 3 箇所（同一ファイルの hard invariant ブロック・設計判断、および別ファイルの spec）に残った。同一ファイル内で「override を持たない」と「override が counter をリセットする」が共存する自己矛盾になり、隣接する 2 bullet が互いに排他的な機構を主張する状態まで生じた。4 レビュアー全員が独立に検出。**削除した識別子（`override` / 機構名）で grep して 0 件になるまで掃く**のが唯一の防御。追加時の「新語彙で grep」より、削除時の「旧語彙で grep」のほうが漏れやすい。

2. **削除は下流の条件式も孤児にする**: override を消したことで、それに依存していた注意行の付加条件（`RESET=failed-refire`）が主経路を外した。発火時の phase は fix なので、発火 set 失敗後の再実行は resume 判定となり reset ブロックに入らず `RESET=none` になる。結果、review を 1 回も回さずに即再発火する当の invocation で注意行が付かない。**削除した分岐に条件が依存していないか**を、条件側から逆に辿る。

3. **`2>&1` capture は「rc≠0 のときだけ表示」と組むと成功時の診断を握り潰す**: helper が rc=0 のまま WARNING を出す経路（破損 state のデフォルトマージ等）があると、リダイレクトが無かった頃には届いていた診断が消える。**capture 導入は観測性の向上とは限らない** — 表示条件を rc に紐付けた瞬間、rc=0 の診断は捨てられる。診断の emit は if/else の外に置き、rc とは独立に surface する。

4. **手順書に書くコマンドは、同じ手順書が約束する他の経路を壊さないか確認する**: 手動リセット手順に `--phase pr` を書いたが、3 行下で「`/rite:recover` でも再開できる」と約束していた。recover は phase で routing するため `pr` は別コマンドへ飛ぶ。**運用コマンドを文書に書くときは、その副作用が同一文書の他の記述と両立するかを確認する**。
