### Finding Patterns

前 cycle の 8 指摘は全て解消。しかし **「穴を塞ぐために書いたテスト自身に、同じ型の穴が再発した」** という最も重い教訓が出た。

1. **テストを新設したら、そのテスト自身をミューテーションで検証する — 例外なく**（F-01 CRITICAL）
   前 cycle で「アサートが意図より広くマッチする」穴（成功行のサフィックス）を見つけて `assert_line_matches` で塞いだ。ところが**同じファイルの別のアサート**（失敗ファイル名）が、runner の `=== Running: X ===` 進捗行にマッチしていた。この進捗行は結果に関係なく必ず出るため、失敗リストがファイル名を出さなくなっても 4 assertions が永久に green。しかも守るべき軸はまさにそれ（TC-4 のコメント自身が「ファイル名を出す行が消えるのを防ぐ」と書いている）。
   前 cycle で 3 種のミューテーションを回したが、**修正した箇所（成功行）しか検証しなかった**のが直接の原因。
   → **規則: ミューテーションは「今直した箇所」ではなく「そのテストが守ると主張する全アサート」に対して回す。** アサートごとに「これが守る挙動を壊したら赤くなるか」を 1 つずつ確認する。文字列マッチは特に、runner が別の目的で同じ文字列を出していないか grep する。

2. **`set -euo pipefail` 下の `$(cmd | grep ...)` は、マッチなしでスクリプトごと落とす**（F-02）
   `line=$(printf '%s\n' "$OUT" | grep -F "$needle" | tail -1)` は grep の rc 1 が pipefail で伝播し、代入の失敗が errexit を起こす。直後に書いた `[ -z "$line" ] && fail "..."` は**到達不能な dead branch** になり、needle が消えたとき（=そのテストが守る regression が起きたとき）だけ診断が消える。
   → **規則: 「マッチしないこと」が正常系にありうる grep は `{ grep ... || true; }` で局所的に無害化し、空判定を次行で必ず assert する。** `|| var=""` で代入全体を握るのは、`tail` や `printf` の失敗まで飲むので不可。

3. **「N 象限を pin した」と言うとき、軸の直交性を確認する**（F-03）
   「4 象限（失敗 × drift）」と称したが、`failure × 正しくカウントされた skip` のセルが無く、各 TC のサンドボックスに合成ファイルが 1 個しかないため**ファイル横断の積み上げ**（`SKIPPED=$((SKIPPED + file_skips))`）が一度も実行されない。結果 5 種のミューテーションが生存した。
   → **規則: 「象限」を主張するときは、各軸の値が独立に変化するケースを列挙して埋める。** 集計ロジックを pin するなら入力を複数にする。

4. **自分が課した規則は、同じ PR が触った全箇所に適用したか grep する**（F-05）
   規則 6 に「capability probe には blocking gate の floor を付けよ」と書いた同じ PR が、触った 3 つの `command -v jq` gate に floor を付けていなかった。文書・規則・実装の 3 者で契約が食い違う状態。
   → **規則: 規約を新設したら、その規約が適用されるべき箇所を機械的に列挙して差分を確認する。**

5. **複製を強制する機械的検査を入れたら、その契約を文書化する**（F-04）
   `_timeout` は 6 ファイルに inline 複製され、TC-7 が byte-identity を、TC-8 が guard 存在を強制する。しかし CONTRIBUTING は「`_test-helpers.sh` が提供し source 時に abort する」としか書いておらず、6 分の 1 の経路しか説明していない。文書だけを読んで `_test-helpers.sh` を直したコントリビューターは TC-7 で落ちる。
   → **規則: 機械的検査が「複数箇所の同時変更」を要求するなら、その要求を文書に書く。** floor 値のハードコード位置（下げるとき触る場所）も含めて書く。

6. **予約グリフ / 予約文字列を導入したら、その制約を明示する**（F-06）
   `⏭️` はマーカーとして導入したが、実装は各テストの stdout+stderr **全体**を `grep -c` するため、被テストスクリプトがこのグリフを出しただけでスイート全体が落ちる。実在の供給源（`backfill-sub-issues.sh:171`）があり、それを実行するテストが 1 本追加された瞬間に発火する。しかも失敗メッセージは無関係な自分のサマリ行を疑わせる。
   → **規則: 「この文字列/グリフはスイート横断で予約」という制約は、導入と同時に文書化する。**

### 討論フェーズの記録（矛盾 1 件）

application が `_timeout` の perl シムについて「GNU timeout 2s vs シム 27s」と報告したが、orchestrator が再現したところ **GNU timeout も 27s**（trap TERM を持つ子は、グループ送信でも TERM を無視すれば待つ）で数値は不正確だった。しかし**別のケース（孤児が stdout を保持）では GNU 3s vs シム 30s** となり、中核の主張（deadline がプロセスグループに効かない）は実在を確認。
→ **教訓: reviewer の数値主張は再現してから採否を決める。** 数値が誤っていても中核の欠陥は実在しうるので、「数値が違う＝指摘ごと棄却」にしない。severity は発火経路の有無（現行コーパスでは全 background job が trap で回収済み）で follow-up に調整した。
