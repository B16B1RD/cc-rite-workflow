# レビュー結果: 手動実行の cleanup が確認なしで follow-up Issue を公開しないようにする（cycle 1）

## 判定

fix-needed（reviewer 3 名、XS/S 軽量レーン、ブロッキング 3 件、非実測 3 件）

## 変更の要旨

follow-up 起票 helper に本文のプレビューを足し、手動 cleanup では起票前に 3 択で確認する。batch-run --merge 経由は確認しない。

## レビューで得た知見

- 「自動実行の中かどうか」を共有の状態ファイル（キュー）で判定するときは、キューが存在して有効なだけでなく、キューが今の対象を処理中であることまで照合する。キューは中断で有効のまま残るため、状態だけの判定は無関係な手動実行を自動実行と取り違える。同じ状態ファイルを読む兄弟の判定がどの照合を持っているかを確認し、同じ束縛を引き継ぐ。
- 修正の本体が手順書（skill）側にある場合、helper のテストが全件通っていても修正は固定されていない。手順書の bash ブロックを抽出して fixture で実行するテストと、呼び出し行・判定表の行を固定する grep テストで、手順書側の配線を固定する。
- 「0 件のときは質問しない」のような境界は、0 件になる経路（除外前から 0 件 / 除外で 0 件 / 既存あり）ごとにテストする。1 つの経路だけでは、他の経路の変異が生き残る。
- 利用者に見せる手順（本文の確認）は、ツールの結果がモデルにしか渡らない場合があるので、「応答本文にそのまま出力する」のように利用者に届く面を明示する。
