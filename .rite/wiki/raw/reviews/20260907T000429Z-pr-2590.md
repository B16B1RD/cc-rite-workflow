- **Type**: review

### Finding Patterns

新しい報告欄（テンプレート内の 1 セクション）を複数 orchestrator に横展開する変更で、3 系統の系統的欠落が同時に起きた。

1. **規範文の主語と実装の集合がずれる**: 「orchestrator が転記する」と書いた文が対象 skill を 4 つ列挙したが、欄を実装したのは別の 3 つだった（過剰 2・欠落 1）。規範文を書き換えるときは、その文が量化する対象集合を実装側で機械的に数え（`grep -c` で欄の実在を全 skill 分カウント）、文と一致させる。英日ペアがある文書では両方を同時に直さないと乖離する。

2. **正常経路にだけ欄を足し停止・失敗経路を落とす**: 同一 skill 内で完了報告 2 本には欄を足し、停止報告 1 本には足さない抜けが起きた。停止経路こそ「ユーザーが操作しない限り残り続ける警告」が出る出口であり、同じ skill の停止経路の bash が実際にその種の WARNING を emit していた。報告テンプレートを増やす変更では全出口の sentinel を列挙してから網羅を確認する。

3. **静的契約テストの presence-only assertion が N 本のテンプレを守れない**: `assert_grep '^欄名:$'` は 1 件でも match すれば PASS するため、複数テンプレを持つファイルで片方から欄が消えても green のまま。同一 PR 内で 1 ファイルだけ件数 pin を持ち他が持たない非対称が生じた。プレースホルダの pin も、そのプレースホルダが「定義表」「規則の散文」「テンプレート本体」の 3 役で出現する場合、テンプレート本体から消えても他 2 つで充足するため検出できない。複数テンプレを守るには件数 pin を、欄とプレースホルダの対応を守るには隣接行の pin を使う。

補足: 件数 pin は「削除」しか検出せず「欄なしの新経路追加」は素通りする。この非対称は静的契約の限界として明示的にコメントで人手ゲートに倒すのが現実的。
