### Finding Patterns

**revert が正しい修正であることの検証は、revert 後に「元の記述が実装と一致するか」を実装側から辿り直して行う**: cycle 2 で導入した機構を revert した際、3 名の reviewer が独立に「revert 方向は正しい」と判定した根拠は、prose を読み比べたのではなく実装（detect helper の分岐条件、ステップ 5 の record 呼び出し、consumer の bypass 条件）を端から端まで辿り直したことにある。revert の妥当性は「前の状態に戻した」ことではなく「戻した先が実装と一致する」ことで決まる。

**手動回復コマンドは実行される場所を限定しないと連鎖が自分を壊す**: 委譲案内に `git worktree remove --force '{path}' && git worktree prune && git branch -D {branch}` を書いたが、この案内は定義上その worktree 内にいるセッションへ出力される。実行すると remove が cwd を消し、prune が rc=128 で連鎖を止め branch -D に到達しない。しかも worktree が消えた時点で遅延回収の反復対象が失われ、ブランチが dead-letter に戻る。同ファイルの既存 sibling はすべて「別セッションを閉じたあと」「sandbox 外のシェルで」の限定句を持っていた — 新設分だけが規約を落としていた。**回復コマンドを書くときは、既存 sibling がどんな限定句を持っているかを先に読む**。

**件数固定の negative control は「追加」を捕まえるが「移設」は捕まえない**: `grep -c` による出現数固定は marker の増殖を検出するが、同じ marker を別の分岐へ移す変異は総数が変わらないため素通しする。排他性を pin したいなら「どこに在るか」も別 assert で固定する（範囲抽出 + 出現数 0 の negative control）。テストのコメントが「排他性そのものを pin する」と宣言していても、実際に pin しているのは総数だけということがある。
