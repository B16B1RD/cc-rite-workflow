### Finding Patterns

前 cycle の修正が新たに導入した欠陥を 3 件検出した。修正が指摘を消すのではなく「指摘の形を変える」典型が 2 系統で現れている。

1. **セーフティネットの発火条件を、守りたい対象ではなく手近な代理値で書くと、守るべき経路でだけ無効化される**: 前 cycle で「index.md を読めたのにエントリを 1 件も認識できない = 検出失敗」ガードを追加したが、その発火条件を index.md 自身の内容ではなく stdin (pages_list) の非空性に置いた。ところが手順書側は「pages_list が空でもこのステップは skip するな」と明示的に定めており、ガードが無効化される経路とガードを必要とする経路が完全に一致していた。application と error-handling の 2 名が独立に同一 file:line を検出している。**precondition は守る対象と同じものを測る**。代理値は「たまたま相関している間だけ」正しい。

2. **1 箇所の記述を実装へ揃えると、同じファイル内の別定義と新たに矛盾しうる**: 前 cycle で SPEC の helper 説明に「テーブル / 箇条書きを行単位で判別」と書いたが、同じ SPEC 内の index.md 定義行は「OKF 箇条書き」のままで、SPEC 単体では「なぜ箇条書きと定義したファイルにテーブル判別が要るのか」が解けない状態になった。develop 版にはテーブルへの言及自体が無く、矛盾は修正の + 行が新規に作った。**記述を実装へ揃えるときは、その記述が依拠している別の定義も同時に見る**。

3. **rationale の退避規約は、修正時に最も破られやすい**: 前 cycle で追加した設計根拠の段落が references/ 側とほぼ逐語で二重化していた。指摘へ答えようとして手順書本体に説明を足すのは自然な反応だが、プロジェクト規約は「実行時に必要な情報は本体、根拠は references へ 1 行ポインタ」を要求している。
