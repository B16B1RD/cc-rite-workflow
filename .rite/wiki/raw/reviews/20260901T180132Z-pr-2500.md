### Finding Patterns

cycle 3 の blocking 1 件は全レビュアー一致で FIXED。blocking 推移は 6 → 3 → 1 → 2。増加分の 2 件は
**security reviewer を cycle 4 で初めて起動したことによる新規検出**であり、収束の反転ではない。

1. **レビュアー選定の判定自体を毎 cycle 回さないと、cap 由来の除外が恒久化する**。security は cycle 1 で
候補数が cap を超えたため正当に除外されたが、cycle 2/3 では候補が cap 以内だったにもかかわらず選定
判定を回していなかった。結果、6 レビュアーが 3 cycle にわたって見逃していた CRITICAL を cycle 4 の
初回起動が即座に検出した。**「前 cycle で除外した」は次 cycle の除外理由にならない** — 差分スコープは
調査範囲の限定であって選定手続きの省略ではない。

2. **quote と `--` は argv 分割にしか効かない。展開はパース時に終わっている**。指摘対象は
`--branch "{branch_name}"` の形で、`{branch_name}` に第三者が制御する `headRefName` が literal
substitute される経路。二重引用符は「単語分割とグロブを止める」だけで、コマンド置換 `$(...)` /
バッククォートはその内側でも展開される。helper 側の全ガード（デリミタ検査・値の妥当性検査）は
**展開後の値**にしか走らないため、防御線として機能しない。値をテンプレートへ埋める設計では、
「引用符で囲んだから安全」は成立しない。

3. **`git check-ref-format` は shell metacharacter を弾かない**。裏取りの実測:
`git check-ref-format 'refs/heads/feat/issue-2493-$(id)'` は **rc=0**。バッククォート形も `$IFS` も rc=0 で、
rc=1 になるのは空白を含む場合など ref 名として不正なときだけ。「git 側が名前を検証しているから
安全な文字しか来ない」という前提は誤り。防御は charset 束縛（`^[A-Za-z0-9._/-]+$`）を自分で書くか、
シェル変数へ受けてから渡すか。

4. **CRITICAL は受け入れる前に自分で裏取りする**。本 cycle の CRITICAL は 2 つの主張の連言
（(a) 部分一致条件を満たす head 名を第三者が作れる / (b) その値がテンプレート内で展開される）だった。
両方を独立に実測してから受理した。連言で成り立つ指摘は、片方が偽なら全体が偽になるため、
severity が高いほど分解して検算する価値がある。

5. **finding ID をコメントに残さない**。テストの assertion に `（F-18 と同じ盲点）` と書くと、その ID は
