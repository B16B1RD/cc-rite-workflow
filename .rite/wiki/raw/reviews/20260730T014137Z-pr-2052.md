### Finding Patterns

1. **機構の前提が overclaim だと、その上に建てた分岐・移行・退避のすべてが不要になる**（CRITICAL、3 レビュアーが独立に「過剰設計」と判断）
   「1 つのファイルに 2 形式が混在すると構造が崩壊する」という前提で移行装置を作ったが、GFM のテーブルは最初の非テーブル行で終端するため、テーブルブロックと箇条書きブロックが別ブロックとして共存しても双方正しく描画される（実測: `gh api --method POST /markdown` で td=5 かつ ul=1）。崩壊するのはテーブルの**内側**に挿入した場合だけで、限定を落とした過大主張が装置全体の唯一の正当化になっていた。
   教訓: 「壊れる」を根拠に機構を足す前に、**壊れ方を実測して限定条件を特定する**。限定を落とした主張は、それに依存する設計を丸ごと不要にする。レンダラの挙動は API を叩けば数分で確定できる。

2. **退避規則は判定キーから除外しないと分岐を永久ラッチさせる**（CRITICAL の構成要素）
   「移送できない行はファイル内に残す」と規定したが、判定キーが「旧形式行の有無」だったため、残した行が次サイクル以降も条件を成立させ続け、通常経路へ永久に到達しなくなる。
   教訓: 意図的に残すデータを作る規則を書いたら、**それが自分の分岐条件を再成立させないか**を必ず確認する。残すなら判定キーから明示的に除外する。

3. **手順の実行順序は依存関係で決める。列挙順が依存順と逆だと成果物が壊れる**（CRITICAL の構成要素）
   分岐表で「移行 → 節の用意」と並べたが、移行は移送先テーブルの存在に依存する。順序が逆だとヘッダ行がデータ行の後に置かれ、GFM ではヘッダより上の行はテーブルにならず全行がカタログから消える（実測 td=0）。
   教訓: 分岐表に手順名を並べるときは**依存グラフのトポロジカル順**にする。「用意 → 使用」の順序は自明に見えて逆順を書きやすい。

4. **分岐表の各行は手順の集合として対称にする**（CRITICAL の構成要素）
   ある分岐の適用手順欄に「既存行の更新」を書き忘れると、その分岐に落ちるリポジトリでは更新が永久に実行されず、代わりに新規追加が走って同一キーの行が二重化する。しかも重複を拾う検出器が無い（孤児検出は `sort -u` で重複を潰し、統計突合は条件付き skip）。
   教訓: 分岐表を書いたら**列（手順）× 行（分岐）の行列として埋め漏れを確認**する。「この分岐では起こらない」と思った手順が本当に起こらないか、上流の判定を追って確認する。

5. **位置ベースの操作は既に崩れているデータに対して未定義になる**（HIGH、3 レビュアーが独立検出）
   行の同定をキー一致にして「誤爆を防ぐ」と書いても、同定後の**列の特定**を位置で行えば、既に列がずれている行（実データで 298 行中 16 行）では誤ったセルを破壊する。改修前の指示はセパレータキー（区切り文字以降を上書き）= 位置非依存だったため、位置依存への退行だった。
   教訓: 構造化データの部分更新は**行全体の再生成**に置き換えるほうが単純で安全。列の数え方が不要になり、既存の壊れた行も更新のたびに漸次是正される。

6. **形式を宣言している箇所は「実行時に読まれる参照チェーン」まで含めて洗う**（CRITICAL、2 レビュアーが独立検出）
   書き手の規約とテンプレートを是正しても、実行 LLM が同一セッションで読む共通参照（構造契約表）が旧形式を宣言していると、誤誘導が残る。自分の修正で「成果物本文の宣言は判定根拠にしない」と無効化した誤誘導と同種のものが、参照側には無効化されずに残っていた。
   教訓: 形式変更時は「その形式を宣言している箇所」を grep するだけでなく、**skill が実行時に読み込む参照ファイル**も対象に含める。SoT 列で自分が変更したファイルを名指ししている表は特に危険。

7. **同一 run で配られる成果物同士の整合を確認する**（HIGH、2 レビュアーが独立検出）
   初期化スキルが同じ実行で 2 つのテンプレートを展開する場合、片方だけ是正すると受け取ったユーザーは矛盾する 2 文書を同時に得る。
   教訓: テンプレートを変えたら、**同じ初期化 run で配られる他のテンプレート**を列挙して整合を取る。

8. **false positive を除去すると、それが覆い隠していた検出器の欠陥が露出する**（討論で non-blocking と合意）
   テンプレートからサンプルリンクを含む HTML コメントを削除したところ、孤児検出の enum が `true` → `index_empty` に変化した。原因は helper が全文を grep しており、コメント内の placeholder パスを「登録済みページ」と誤認していたこと。つまり従来の健全な結果は phantom に支えられていた。
   教訓: 挙動変化を見たら**どちらが正しいか**を先に決める。phantom を復活させて緑を維持するのは、検出器の「走査不能」と「真に 0 件」の混同を覆い隠す行為であり anti-pattern。正しい挙動を採り、露出した検出器の欠陥は別 Issue に切り出す。

9. **修正が 2 cycle 連続で新たな指摘を生んだら、作り込みではなく削減を検討する**
   cycle 2 の 7 件中 6 件、cycle 3 の 6 件中 4 件が直前の修正が生んだものだった。3 レビュアーが独立に「過剰設計」と判断し、同一の最小解に収束した。
   教訓: fix-introduced 指摘の比率と集中箇所を cycle ごとに数え、**停止条件を事前に宣言**しておく。過半が同一機構に集中したら、その機構を削る方向を第一候補にする。仕様が択一で提示した選択肢を両方実装していないかを確認する。
