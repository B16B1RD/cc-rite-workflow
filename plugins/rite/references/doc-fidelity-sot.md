# 文書整合・SoT 規則（Documentation Fidelity Gate の個別条件）

> **SoT scope**: `agents/_reviewer-base.md` の Documentation Fidelity Gate が参照する、個別の検出条件と是正条件の一覧。reviewer は diff が散文・列挙・表・コメント・参照・件数・復旧手順に触れたとき該当節を Read し、発見は `Likelihood-Evidence` に「どの記述が」「どの実装・SoT と」食い違うかを書く。書き手（実装者・fix）は同じ条件を変更前の自己点検に使う。

共通の型: **主張を書き換える・実装を動かす・列挙を増減する、のいずれかをしたら、同じ主張を持つ全 site を数え、実装の実値と突き合わせる**。名前の類似や記憶は根拠にならない。

## 1. 伝播（変更した事実を持つ全 site を掃く）

- **検索語は概念で選ぶ**: 旧語彙の grep だけでは足りない。旧定義が真だった前提・言い換え語・語順違い・総称表現・別言語版（日英ペア）・別ファイル種別（`.sh` コメント、tests）まで掃く。pathspec で `*.md` に限定しない。完了検査は旧表現でなく「主張した概念」の逆引きで行い、hit した各 site を読む。
- **対象は live な記述に限る**: 現在形・行番号付き・手順として読まれる記述を直す。CHANGELOG・移行ガイド・retired 節の歴史記述は据え置く。同名でも別 artifact（新旧 hook 等）の記述は一括置換せず区別する。
- **移設・削除・rename の後始末**: 旧パス、旧ステップ番号、旧関数名、削除シンボル名、削除した識別子を指す表現を全文 grep する。削除は inbound 参照（行番号 citation を含む）を削除前に数える。機構を削除したら、それに依存していた条件式・enum・rationale が孤児化していないか条件側から逆に辿る。
- **列挙の増減**: 要素を足す・消す・reason を追加するときは、同じ集合を列挙する全 site（表、ツリー、ヘッダ、スキーマ、docs/SPEC.md の別表、エラー表、テストコメント）を grep で洗い、共有述語が新要素にも成立するか個別に確認する。番号付きリストへ挿入したら他ファイルの序数参照（「ルール N」「手順 1〜N」）を確認する。
- **鏡像・複製**: SoT を編集したら複製表・mirror 文書・canonical snippet（依存する前提注記を含む）を同コミットで同期する。複製 N 箇所の照合は目視でなく固定文字列の計数で行う。
- **対称更新**: stale 参照の掃除は「hit した行」「その行が参照する SoT」「直下の例示」を同時に直す。片側だけの更新は内部矛盾を作る。

## 2. 単一の正本（二重定義を作らない）

- 同じ規則・列挙・判定式・復旧手順・表を複数箇所に書かない。本文 1 箇所 + 他は要約とリンクにする。判定式の写しは書き直さず正本へのポインタにする。
- 複製が正当な場合（consumer が異なる）は、どれが canonical かを明示し、規則変更時に全 site を更新する。
- 概数を公開する文書は派生値（%・倍率）を書かない。手書きの件数 counter は drift 源なので、grep で実在検証できる step 列挙に置き換える。増え続ける corpus の実測値は絶対値でなく下限 + 条件で書く。
- 別文書の内部ステップ番号を参照しない。実体名 + SoT への相対リンクにする。

## 3. 主張の射程を実装に合わせる

- 全称・否定・限定の主張（「全て」「唯一」「構造的に不可能」「呼ばない」「作らない」「のみ」）は、実装の全経路・全 caller・全分岐（選言の全枝、else 側を含む）を数えてから書く。分岐前に無条件で走る処理まで数える。
- 「N 箇所」「N 種」「caller は X」は書く前に実装を `grep -c` で数える。集合の一致は件数でなく識別子集合の差分（`comm -3` 等）で確認する。
- 説明文は実装の条件式から書き起こす。因果句（「〜のため」）は新ケースに接続する前に、その制御が実際に効く範囲を読んで確かめる。拒否・復旧・診断の文言は、その文言に至る条件をコードで追ってから書く。呼び先が返す exit code は測ってから診断に書く。
- 挙動を変えた修正は、その挙動を断定する散文（「silent」「同一」「常に」）を同じ diff で直す。修正を説明する文も修正本体と同じ厳しさで読む。
- 実測に基づく保証は測った範囲だけ書く。未確認は「未確認」と書き、観測できない値は `_TBD_` でなく `N/A` + 代替手法で記録する。実在しない consumer や宣言を現在形で語らない。予防的ガードの理由は将来 consumer が入ったときの保護として書く。

## 4. 完了検査・検証スクリプト

- 検証スクリプトの exit 0 が「一致を確認した」のか「skip / 未解決を含む」のかを区別できるようにする（別 rc か 2 段判定）。lint が緑でも、検出器の非検出範囲を規約遵守の根拠にしない。実測した非検出形は Known boundary として明記する。
- 掃引は検索一致でなく操作単位（実際に何を変える site か）で分類する。復旧案内は「回復不能」判定も含め、回復側セッションで分岐が発火するかから辿り直す。
- 実測値（件数・passed 数・行数）は fix のたびに最終 HEAD で取り直し、測定条件（プラットフォーム、母集団）を明記する。

## 5. Markdown と参照の機械的な崩れ

- GFM table: セル内の raw pipe（regex・code span 内を含む）は `\|` にする。table 内に HTML コメントを挟まない。崩れの確認は `awk -F'|'` でセル数を測る。
- 相対リンクは、参照元の depth ごとに解決して存在を確認し、anchor は GitHub slug を再計算して一致を確かめる。clickable なリンクの depth 誤りは drift、bare inline-code の plugin-root 相対表記は慣習であり drift ではない。
- 見出しを rename したら TOC anchor と inbound 参照（below / 下記 等の位置含意を含む）を再計算する。節を常時表示から条件付きに変えた場合も同じ。
- 行番号参照の禁止表記（括弧、`L<n>`、`file:n`、散文、`Line n`、`~` 接尾辞）は全形式を scan する。

## 6. 外部事実・SoT 衝突

- 外部ツールの仕様・回避策は要約でなく公式原文（必要なら issue tracker）で照合し、出典・確認日・再検証手順を添える。
- Issue 本文と canonical SoT が同じフィールドで衝突したら canonical 側を採り、blocker として表面化する。同一判断に別規則が競合するときは勝者を選ばず、2 つの文面を人間に示す。
- 配布物の rationale は、開発リポジトリの実データ分布を根拠にしない（配布先で検証できない）。
