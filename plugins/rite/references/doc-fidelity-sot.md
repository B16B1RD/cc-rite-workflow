# 文書整合・SoT 規則（Documentation Fidelity Gate の個別条件）

> **SoT scope**: `agents/_reviewer-base.md` の Documentation Fidelity Gate が参照する、個別の検出条件と是正条件の一覧。reviewer は項目 11 の発火時に該当節を Read し、発見は `Likelihood-Evidence` に「どの記述が」「どの実装・SoT と」食い違うかを書く。帰結クラスと severity は `agents/_reviewer-base.md` の「手順書・仕様書ドメイン Finding Gate」で判定し、字面整合だけの不一致を blocking にしない。発火条件は同ファイル Documentation Fidelity Gate の項目 11 を正とする。

共通の型: **主張を書き換える・実装を動かす・列挙を増減する、のいずれかをしたら、同じ主張を持つ全 site を数え、実装の実値と突き合わせる**。名前の類似や記憶は根拠にならない。

## 1. 伝播（変更した事実を持つ全 site を掃く）

- **検索語は概念で選ぶ**: 旧語彙の grep だけでは足りない。旧定義が真だった前提・言い換え語・語順違い・総称表現・別言語版（日英ペア）・別ファイル種別（`.sh` コメント、tests）まで掃く。pathspec で `*.md` に限定しない。完了検査は旧表現でなく「主張した概念」の逆引きで行い、hit した各 site を読む。
- **対象は live な記述に限る**: 現在形・行番号付き・手順として読まれる記述を直す。CHANGELOG・移行ガイド・retired 節の歴史記述は据え置く。同名でも別 artifact（新旧 hook 等）の記述は一括置換せず区別する。
- **機構削除の孤児化**: 機構を削除したら、それに依存していた条件式・enum・rationale が孤児化していないかを条件側から逆に辿る（旧語彙の sweep と削除時の inbound 参照は gate 項目 1・10 が正本）。
- **列挙の増減**: 要素を足す・消す・理由コードを追加するときは、同じ集合を列挙する全 site（表、ツリー、ヘッダ、スキーマ、仕様書・設計文書内の別表、エラー表、テストコメント）を grep で洗い、共有述語が新要素にも成立するか個別に確認する。番号付きリストへ挿入したら他ファイルの序数参照（「ルール N」「手順 1〜N」）を確認する。
- **鏡像・複製**: SoT を編集したら複製表・mirror 文書・canonical snippet（依存する前提注記を含む）を同コミットで同期する。複製 N 箇所の照合は目視でなく固定文字列の計数で行う。
- **対称更新**: stale 参照の掃除は「hit した行」「その行が参照する SoT」「直下の例示」を同時に直す。片側だけの更新は内部矛盾を作る。

## 2. 単一の正本（二重定義を作らない）

- 同じ規則・列挙・判定式・復旧手順・表を複数箇所に書かない。本文 1 箇所 + 他は要約とリンクにする。判定式の写しは書き直さず正本へのポインタにする。
- 複製が正当な場合（consumer が異なる）は、どれが canonical かを明示し、規則変更時に全 site を更新する。
- 概数を公開する文書は派生値（%・倍率）を書かない。手書きの件数 counter は drift 源なので、grep で実在検証できる step 列挙に置き換える。増え続ける corpus の実測値は絶対値でなく下限 + 条件で書く。

## 3. 主張の射程を実装に合わせる

- 全称・否定・限定の主張（「全て」「唯一」「構造的に不可能」「呼ばない」「作らない」「のみ」）は、実装の全経路・全 caller・全分岐（選言の全枝、else 側を含む）を数えてから書く。分岐前に無条件で走る処理まで数える。
- 「N 箇所」「N 種」「caller は X」は書く前に実装を `grep -c` で数える。`grep -c` は一致した行数であり、1 行に複数回出る語は `grep -o | wc -l` で数える。集合の一致は件数でなく識別子集合の差分で確認する（`comm -3` は両入力を `sort` してから使う）。
- 説明文は実装の条件式から書き起こす。因果句（「〜のため」）は新ケースに接続する前に、その制御が実際に効く範囲を読んで確かめる。拒否・復旧・診断の文言は、その文言に至る条件をコードで追ってから書く。呼び先が返す exit code は測ってから診断に書く。
- 挙動を変えた修正は、その挙動を断定する散文（「silent」「同一」「常に」）を同じ diff で直す。修正を説明する文も修正本体と同じ厳しさで読む。
- 実測に基づく保証は測った範囲だけ書く。未確認は「未確認」と書き、観測できない値は未記入の placeholder でなく `N/A` + 代替手法で記録する。実在しない consumer や宣言を現在形で語らない。

## 4. 完了検査・検証スクリプト

- 検証スクリプトの exit 0 が「一致を確認した」のか「skip / 未解決を含む」のかを区別できるようにする（終了コードを分けるか、一致 / 未解決の 2 段階で報告する）。lint が緑でも、検出器の非検出範囲を規約遵守の根拠にしない。実測した非検出形は 既知の非検出範囲として明記する。
- 掃引は検索一致でなく、実際に何を変える箇所かで分類する。復旧案内は「回復不能」判定も含め、復旧を実行するセッションで分岐が発火するかから辿り直す。
- 実測値（件数・passed 数・行数）は fix のたびに最終 HEAD で取り直し、測定条件（プラットフォーム、母集団）を明記する。

## 5. Markdown と参照の機械的な崩れ

- GFM table: セル内の raw pipe（regex・code span 内を含む）は `\|` にする。table 内に HTML コメントを挟まない。崩れの確認は、`\|` を除いた未エスケープの `|` の数を行ごとに数え、全行で同数か確かめる（`awk '{gsub(/\\[|]/,""); print gsub(/[|]/,"|")}'`）。
- 相対リンクは、参照元ごとの `../` の段数で解決して存在を確認し、anchor は GitHub の slug 規則（小文字化、句読点の除去、空白を `-` に、非 ASCII 文字は残す、重複には `-1` を付ける）で再計算して一致を確かめる。clickable なリンクの段数誤りは指摘対象、bare inline-code の plugin-root 相対表記は慣習であり指摘対象ではない。
- 見出しを rename したら TOC anchor と inbound 参照（below / 下記 等の位置含意を含む）を再計算する。節を常時表示から条件付きに変えた場合も同じ。

## 6. 外部事実・SoT 衝突

- 外部ツールの仕様・回避策は要約でなく公式原文（必要なら issue tracker）で照合し、出典・確認日・再検証手順を添える。
- Issue 本文と canonical SoT が同じフィールドで衝突したら canonical 側を採り、その衝突を blocking の指摘として報告する。
- 配布物の rationale は、開発リポジトリの実データ分布を根拠にしない（配布先で検証できない）。
