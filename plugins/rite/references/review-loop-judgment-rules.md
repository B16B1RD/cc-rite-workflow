# レビュー・修正ループの判断規則

review ⇄ fix ループで繰り返し発散・空転しやすい判断を、「条件 → 期待結果」の形で集約した共有規則です。iterate・fix・pr-review が読む入口で、各スキルは自分の節だけを参照します。

- 既存の機構（breaker、停滞診断 [review-stagnation.md](review-stagnation.md)、採否ゲート）が機械的に扱う内容は重複して書きません。ここは機構が判断できない場面で従う規則です。停止・離脱の出口はこの文書では新設せず、既存の出口に合流します。
- 別 Issue 化・却下・持ち越しなど外部へ書く処分は、採否ゲートの出口（file / record / fix / hold）の候補にします。どの出口になるかはゲートの V/C/T 判定が決め、ここでは分類だけで出口を決めません。`gh issue create` を直接実行したり、台帳へ直接書き込んだりしません。scope 内の根因は同 cycle で完成させ、scope 外のものだけをゲートに載せます。
- 規則は上限・予算で品質を妥協しません。切る対象は発散・空転であり、収束に向かう実サイクルではありません。

## 1. fix: 修正の適用と検証

| 条件 | 期待結果 |
|---|---|
| commit message に「X を Y に置換」「全置換」と書く | 書く前に X のリテラルを `git grep` し、同 PR の全ファイルで残存 0 を機械確認する。目視で宣言しない |
| 片側の分岐の自己矛盾を直した | 同じ理由が成立する反対分岐（失敗・increment 側）を対で確認し、ブロック内の全分岐に適用して閉じる |
| over-match 指摘で記述を厳密化する | 実装が許容する全正当形状（生成側が作る名前変種を含む）を再 Read する。元の拘束を落とさず連言で足す |
| 同一行に指摘が集中した、または同じ機構へパッチを重ねている | パッチを重ねず 1 回の書き換えに統合し、既存の述語へ寄せる。述語が代理指標（相関が切れる条件の列挙が既存パッチ一覧と一致する）なら述語自体を是正する |
| テスト以外の検証機構・lint を足す | 次 cycle のレビュー面が増える。追加より削除・集約で応じ、fix 後は変更ファイルに既存の検出器を全てかけ直す。error path を足す fix の回帰テストは Error-Path Gate を優先し、削らない |
| reviewer の推奨値（ID・名前）を採用する | 採用前に既存との衝突を grep する。suggestion 欄のパッチは走らせて検証してから採る |
| consumer に新しい入力を足す | 全 producer 経路が値を運べるか確認する。値域は設計意図でなく producer の実出力から引く。表示用の表から再構成せず、producer 保存の正本を渡して既定値で補完しない。停止条件は「判定に要る本文が無い」ことだけにする |
| 読み側に「この種類の行も候補にする」を足す | 入力を消す側（孤児回収・退避判定）も同種の行を持つファイルを保持するか確かめる |
| 位置・時刻・名前など衝突しうる自然キーで map を引く、または記録の同定キーを決める | 別物を巻き込まないよう、記録を生んだ文脈の全キー（run・commit・cycle）で一意にする。同一 HEAD の再実行を前回記録と一致させない |
| 新しい再入経路・戻り経路・state 操作を足す | 兄弟経路の再入防止を移植し、counter を進めない戻り経路には終端条件を置く。既存 state との組合せを実入口から試し、停止ヒントは受理状態でのみ出す |
| ループの途中に段を足す | 終端を指す指示を全箇所更新する。まだ作られていないのが正常な保存先ディレクトリの不在は異常扱いにしない。次レビュー開始の可否を確認する |
| テストの検査（pin）を強める | 強めた側が自分で変異を 1 回当てる。前 cycle で生存した変異は修正後のテストへ同形で当て直す |
| 検証コマンドを記録・実行する | `env -u` で ambient なセッション変数を外して CI と同条件にし、PATH 等の環境依存値を埋め込まず hook 環境で再実行できる形にする |
| 同機序の複数指摘が出た | 個別 guard を増やさず、参照実装へ畳んで宣言を削除する |
| 終了条件の件数・終端状態を扱う | 観測時点を揃える（分類時の件数と対応後の未処理件数を混ぜない）。終端状態は到達事実で記録し、可変上限との境界比較で代用しない |
| 修正の完了を宣言する | 自然な workflow 経路での発火実績を確認する。reviewer が示した再現手順があれば先にそれで流す |
| 不明な点に対して断定を書く | 断定の根拠を同 cycle で用意する |
| 隣接分岐が WARNING を出すのに 1 枝だけ無言 | 沈黙の非対称を残さない |
| 「別 Issue で」と委譲したくなる | 別 Issue 化・scope 上の必然・機械化条件が揃わない限り、同 cycle で完成させる。揃った場合はゲートの file 候補にする |
| 全域 grep・「旧表記ゼロ」の受入条件 | 意図的な残存（凍結ファイル・歴史記録・同期 invariant）の除外リストを cycle 間で引き継ぎ、内訳付きで達成報告する |
| 「N 箇所で同期が必要」と指摘された | 同期の前に revert で N を減らせるか（動作中か・scope 内か）を問う。PR が持ち込んだ重複は本 PR で対称に直し、base 由来のものだけをゲートの file 候補にする |
| 大規模 rename で callee→caller の drift が 1 件見つかった | 全 callee × 全 caller の cross-product grep をその場で実行する |

## 2. iterate: 収束の読み方

| 条件 | 期待結果 |
|---|---|
| blocking 件数が増えた | 発散かどうかの判定は breaker に任せる。ここでは、件数が下降していても降格が効いているだけか、前 cycle の修正由来かを別途見る。個別対処でなく構造の見直しを優先する |
| 収束を判定する | 件数でなく、指摘が散文・文面の層へ上がったかで読む。severity でなく層（挙動 / 検出力 / 文面）で判断する。停止が必要なら停滞診断の見直しと既存の停止 sentinel に合流する |
| 指摘の性質が実装誤りから検証資産の不足へ移った | 本 PR が持ち込んだ経路の検証不足は本 PR で直す（New Error-Path Regression Gate は current-PR が対象）。base 由来の不足だけをゲートの file 候補にする |
| 同一の推奨が non-blocking として繰り返し出る | 5.S の non-blocking sweep で消化する対象とする。毎 cycle 1 件出る non-blocking は収束の見かけを保つだけで、閉じた状態ではない |
| 収束局面で reviewer が 0 件を返す | 正常終了として受容し、捏造した指摘で埋めない |
| ループを止めたい | reviewer の数を削らない。採否ゲートで行き先（修正・別 Issue・記録）を変える |
| cycle 間で判定が逆転した方針判断が出た | 新 cycle の判定を自動採用せず、双方の根拠を実行して決着を試みる。決着しない場合のみ question_resolution の規則に従う |
| CI の赤 job を判断入力にする | 失敗 step を特定する。test 実行前（checkout 等）の失敗は再実行で切り分け、suite 全体時間に起因する timeout は本 PR の指摘にしない。他 OS の job も読み、base で green なら PR 起因として直す |
| 全体テストが無関係に落ちた | 別セッションによる実リポジトリ state の汚染を疑い、退避して単独実行する |
| 同じ調査推奨が複数 cycle で繰り返された | 指摘へ昇格させる信号として扱う |
| 収束を報告する | 主題の収束と、fix 自身が持ち込んだ churn を分けて報告する |

## 3. pr-review: 採否と集約

| 条件 | 期待結果 |
|---|---|
| reviewer の評価が割れた、または全員が一致した | 多数決にしない。各主張が測った経路を突合し、未測定の経路は統合側が実機で再現する。合意は同じ側だけを読んだ結果かもしれず、実測の代わりにならない |
| reviewer の数値・外部事実・外部ツール挙動（hook timeout 等）の主張 | 再現または一次ソース（実装・公式 docs）で確認してから採否を決める。数値が誤りでも中核の欠陥は実在しうる |
| reviewer の regression 帰属（PR 由来 / pre-existing）の主張 | `git show <base>:file` で独立に検証する。revert test は行単位でなく PR 全体で判定する。受入条件がファイル全体の無矛盾を要求する場合は PR 内修正を許容する |
| reviewer 間の矛盾 | 双方が引用する既存記述が現在も成立するかを grep で確認してから重み付けする。決着は 5.2 の手順（debate・確認）に従う |
| 同じ疑問を複数 reviewer が独立に挙げた | 記述の曖昧さの信号として仕様確認に回す。reviewer が挙げる「仕様への疑問」は実ファイルで裏取りしてから採否を決める |
| reviewer 推奨の対象が先行 Issue で Non-Target と明示されている | 実行前に `git log` と Issue で確認する。消費側手順書の Non-Target は挙動が壊れていないことを確認し、ゲートの file 候補（別 Issue）にする |
| 「accepted trade-off」を理由に指摘を却下する | 正当化の射程が当該 site を含み、かつ修正が trade-off を取り崩す場合に限る |
| 推奨事項・スコープ外の候補を却下する | 宣言で終えず、判定記録に REJECT と V/C/T の根拠（変異と結果を含む）を書いてゲートに渡す。verdict と出口はゲートが決める。blocking 指摘の却下は Rejection Evidence Gate に従う |
| 1 件の記載漏れ報告 | 全 site の走査要求として読み、修正は本 diff に閉じる。「N 箇所」の宣言は Grep の hit 数と照合する。実装者の根拠の検証と結論の検証は別軸で行う |
| 前 cycle で任意と判断した論点 | 理由なく blocking へ格上げしない |
| 指摘が scope 内かを判定する | 基準は cycle diff でなく PR diff とする。base に存在しない行は何 cycle 目でも scope 内。incremental review が決めるのは読み直すファイルだけで、scope ではない |
| scope 外の同期 drift | ゲートの file 候補（別 Issue）にし、後続の最小 PR で解消する |
| 直前に merge された PR が確立した規約を後続 PR が破る | review 時に直近 merged PR の規約を参照する |
| 配布境界の指摘が実測手段を持たず降格しそう | 捨てずに、判定記録へ根拠と V/C/T を書いてゲートに渡す。verdict と出口はゲートが決める |
| 指摘を FIXED と判定する | 目視・self-claim でなく、実ファイルの grep 等の機械証拠で行う。`bash -n` は構文の確認にしかならず、挙動の証拠にはならない |
