# スキル・散文手順の書き方

SKILL.md・references・agent 定義など、LLM が読んで実行する散文を書く・直す・レビューするときの条件表。書き手は着手前に該当節を読み、自分の変更を見直すときの観点としても使う。reviewer の実行時には読まれない。`skill-diet-method.md` が「削る手順」を扱うのに対し、本ファイルは「書く・直すときに守る条件」を扱う。

各項目は条件と期待結果を示す。「→」を使う項目は、左が条件、右が期待結果である。確かめ方を「grep」「テスト」などと明記した項目は、その手段で検査できる。

## 1. 配置と順序

- 「後続ステップで生成するものに検査を適用せよ」のような指示 → 生成地点より後ろ（実行地点）に書く。前に書くと、実行時に適用されないことがある。
- 手順を書き終えたら → 実フローの制御構造（迂回分岐・承認ゲート・未生成の対象・中断・再開）と突き合わせ、すべての経路が前提ステップを通ることを確かめる。
- 「提示する」「報告する」と書く → 提示先（質問・出力欄）を同じ文に持たせる。無ければ既存の出力に載せる設計にする。
- 節を飛ばす分岐が後続の必須値を渡す → 値の定義を分岐の文に書く。飛ばされる節の中に置かない。
- 項目に工程を足す → 項目全体を実行順（入力確保 → 検査 → 停止・回復 → 次工程）に並べ直す。
- 検査や停止条件を持つ既存の段落がある → 新しい検査は独立節にせず、その段落へ統合する。同じ段落を通る他の経路にも自動で効く。
- 「上記」「次の」など位置で指す語を含む列挙文へ節を差し込む → 指示先がずれる。語を足して直さず、節の順序を元に戻す。
- 解決手順（placeholder の解決など）が最初の使用より後ろにある → リテラルのまま実行される。使用の直前で解決する。
- 変更が分岐表の行条件を動かす → 否定側の行・要約文・それを pin するテストを同時に直す。分岐表の判定キーは 1 観測量に統一し、直交する軸は表外に出す。表は「列 × 手順」で埋め漏れを確かめる。

## 2. 規範文の強さと衝突

- 新しい MUST / MUST NOT を書く → 書く前に同一ファイル内の既存の禁止文・許可文を grep し、衝突を確かめる。新しい規則が同じ段落の既存禁止に打ち消されないかも確かめる。
- 強さが矛盾する → 緩い側を強めず、強い側の適用範囲を絞る。矛盾が成立するケース数を数えてから直す。
- 呼び出し側が SoT（「してよい」）より厳しい制約（MUST）を新設しない。
- 禁止規則が自 workflow と衝突する → 例外条項を足さず、禁止対象の述語（性質）を言い換える。
- 規範文を新設する → 支配範囲の全行へ再適用するか、適用範囲を狭める（既定は狭める）。同一ファイルの類似箇所にも自己適用し、機械的に確かめる。
- 「〜に限る」と限定する文を足す → 限定の外に落ちる正当な指摘・経路を先に列挙する。
- 強調（太字・MUST）は命令本体に集中させる。設計上の理由は本体に書かず、同梱 `references/` に置いて `rationale:` ポインタで示す（`skill-diet-method.md` §1）。変更の経緯は commit / PR に書く。指示を強める場合は、LLM が実際に実行する側（closed enumeration・template）にも反映する。rationale 層だけの強化は効かない。
- 優先規則（A が B に常に優先する、など）を決める → 優先されない側が負ける場面（B が必要な場面）が残る。選ばなかった側の扱いも SoT に書く。
- 優先順位の宣言は、表・散文・コードのどの形式の記述にも効くように書き、表だけに限定しない（ステップ側の散文との衝突を解く）。

## 3. 限定・修飾・述語

- 同格の主張が並ぶ → 修飾は集合単位でかける。非対称が事実の差から来る場合だけ対称化せず書き分ける。
- 限定句は原因と対処の説明にだけかける。「停止する」など全体への指示は限定の外に置く。
- 「〜しない」と否定する文には、否定が成り立つ経路を限定する句を入れ、隣の経路では該当する場合があることを添える。
- 同じ契約を複数箇所に書く → 最も限定的な表現に揃え、無限定な一般化を避ける。述語を散文化するときは、母集団を先に束縛し、依存関係（A かつ C）を落とさない。
- 「専用」「全て」「必ず」など絶対化語彙で置換 fix を書かない。所有格・限定形で並列性を示す。
- OR 条件の要約は「・」で並べず「いずれか」と書く。論理式の日本語書き起こしは、正本の括弧構造を括弧で保ち、AND / OR を「かつ」「または」に固定する。正本で optional な要素は「省略可」と明示する。
- 因果節を 2 つ並べた 1 文を避け、ケースごとに文を分ける。値の列挙は括弧に入れ子にせず、独立した文にする。
- 「同じ会話に限る」のような限定 → 実行者が確かめられる観測対象と、読めないときの行き先を併記する。
- 述語の評価レベル（サイト単位か効果単位か）が曖昧 → 明示する 1 文を添える。
- 散文で機械的述語を定義した → 字義どおりのプローブを実データ全件に当てて確かめる。
- 「同形」「同じ」と書くコメント → 一致する範囲を限定し、その範囲を変異テストで固定する。
- 既存の術語の動詞を別の意味に流用しない。新しい意味には別の語を立てる。「追加」と「置換」を 1 つの動詞にまとめない。

## 4. 列挙・件数・参照

- 散文で call site・件数・分岐を列挙する → 条件へ変換して書く。列挙を保つ文は、書き直しが収束しない。
- helper の内部分岐（reason enum など）や可変長引数の要素を、散文・呼び出し側メッセージで名指し列挙しない。
- 規則は転写せず 1 行ポインタで共有する（要約は情報が落ちる）。SoT をポインタ化する前に指し先の完全性を確かめ、撤去の完了は grep の残存 0 件で判定する。
- 規則とその反例を同じ diff で導入しない。
- 用語を統一する → 単語単独でなく、文脈の類義語群を最初の grep で同時に列挙して一括で直す。
- step 参照は、見出し名 + ステップ番号の絶対形で書く（「次のステップ」のような相対形を避ける）。同一ファイルで「ステップ N」が 2 つの番号体系を指す場合は、項目名を添える。手順の実行順を指す参照は絶対形、文書内の配置を指す参照（「上の表」など）は相対表現で書く。
- sub-phase（8.0.1 など）を足す → 親（8.0）の見出しも存在させる。中間ステップを削除したら、番号の振り直しと順序 N への参照を確かめる。
- 識別子・構造ラベルを消す → 同一ファイル内に dangling 参照が無いことを、消す前の grep と消した後の 0 件で確かめる。
- 新設 placeholder と既存の shell 変数が名前を共有しない。共有する場合は区別を注記するか、別名にする。
- 単一の `{number}` が複数の実体（issue と PR）を指しうる → `{issue_number}` / `{pr_number}` に分離する。
- placeholder は、実行主体が解決手段を持つファイルにだけ伝播させる（agent 定義は除外）。診断文には placeholder（`{plugin_root}` など）を書かない。診断を読む人の側では解決されないため、そのまま表示される。
- 後段 bash が参照する placeholder は、入力の生値でなく、選択処理が確定させた最終値を指す。出所を導入文に書く。ある呼び出しの変数を別の Bash 呼び出しが参照する場合は、同じ呼び出しで出力するか、既存の resolver を実行する定義に揃える。
- 引数を導入した → その skill を invoke する全分岐（修復・再試行・handoff）に同じ引数を付ける。
- 複数コマンドの引数表記 → 各 SKILL.md の argument-hint と既存の正典を事前に grep して揃える。
- 新しいコピーを書く前に、同じ idiom の全サイトを `git grep` で列挙し、最終更新を `git log -G` で確かめてから写す。

## 5. rationale ポインタと SoT

- `rationale: <path>#<anchor>` は、bare 形式に統一する（markdown link や混在形式を避ける）。ポインタ行は単独行にし、anchor が見出しに解決することを退避後に機械的に確かめる。見出しをリネームするとポインタが無音で死ぬので、リネームするときは参照を grep する。
- ポインタ方式では、本体とポインタ先の両方を同時に直す。述語を変えるときは、`rationale:` でリンクする参照先を先に更新する（参照先が旧規則だと agent は旧規則を採る）。
- ポインタ先は、anchor が解決するだけでなく、必要な内容を実際に含むかを個別に確かめる。
- ケース分岐の規則は、実行時に注入される本文に書く。rationale へ退避すると、実行時に参照できる規則の集合が変わる。
- 汎用契約の表には経路固有の step 番号・reason 集合を書かず、下位節へ委譲する。同一文書に正典記述があるフィールドは、条件を書き直さず所有を委譲する。分岐表がある手順の本文規範は、表へ委ねる 1 文にする。
- 修飾を N 箇所へ展開するときは、機構の詳細を SoT ポインタ 1 箇所に集約する。
- 行動指示と帰結の記述を 1 文に混載せず、帰結は SoT 表へのポインタ 1 行にする。
- 「N 種を禁止し、行き先を示す」規則は、禁止と行き先を 1 つの対リストに畳む。
- 同じ戻り値への処理（再試行・停止）を、表と段落の 2 か所に書かず 1 か所に置く。
- SoT は単一の既定値にする。consumer 固有の事情は consumer 側の設計で吸収し、条件分岐を SoT に積まない。
- 共有 reference を新設する → 全 consumer に効く運用ルールも節として切り出す。
- 手順を要約した別ファイル（括弧書き・案内文）は、手順書の工程追加に追従し忘れる。手順を変えたら、要約側と、それを pin するテストを検索して同時に直す。
- SKILL.md の bash ブロックを helper へ移す → ブロック内コメントが持っていた手順情報（再実行手段・placeholder の出所）を LLM が失う。散文側へ残す。
- SKILL.md に新しい節を足すときは、同一ファイル内の類似ブロックの記法に合わせる。

## 6. 実装の裏づけと到達可能性

- 「N iteration で force-exit」のような safeguard の散文 → counter・分岐の実装を探す。無ければ散文を削除するか実装する。
- 「機械的」「強制」と謳う散文 → 対応する hook / script の検出が grep で見つからなければ、prose-only として扱う。
- 未実装の原則は曖昧に宣言せず、未定義であることを Note で明示する。
- opt-in flag は、実装と同時に call site へ配線する。
- 到達不能になる変更（早期 return の追加、分岐の削除）は、同じ commit で下流の分岐・参照・fallback を畳む。その行だけが持っていた情報（手順・保護文）は、生きた経路へ移す。
- 到達不能に見える分岐を削る前に、入力の流れ先（catch-all）の診断が正しいかを確かめる。削除コストがガードの改変なら、散文を緩めるなど別の最小手を探す。テストが届かない fail-loud 分岐は、後段の既存 fail-loud に委ねて削ってよい。
- 簡素化の後は「この防御は今も到達可能か」を問い、到達不能なガードを消す。
- 冪等ガードの根拠は、同じ cycle の別修正で偽になっていないか確かめ、実際に効く経路を根拠に書く。
- 構造的に不可能と書く場合は、拒否される形態を実測で特定し、その形態だけを書く。機構の配線状況（誰がどこで強制するか）は説明の誤りが入れ替わるので、判定に必要な事実だけを残す。
- 記録義務を課す前に、記録先を読む consumer が実在することを grep で確かめる。受け皿を新設できないなら、義務ごと撤回して follow-up にする。
- bash 実装を散文化する簡素化では、旧実装の閾値・例外条件を、前後で突き合わせる。
- 手順を外部スクリプトへ移す → 移した値を読む全経路（通常・中断・取消・再開）で、取りうる値の範囲を列挙する。移設で入った厳格な検査が正常な経路を落とすなら、検査を足して塞がず外して直す（空値が正常な引数は、渡されたことだけを要求する）。
- 一度も代入されない可能性のある変数（helper 呼び出しの結果や placeholder の値）を `${var:-}` で既定化すると、失敗が無言になり完了報告が誤報になる。この場合はリテラル置換のみを正規経路とする（trap の cleanup は対象外。`bash-trap-patterns.md` に従う）。
- 「検出と消費」が同じ phase にある → 同一 Bash invocation に物理統合する（sentinel emit より優先）。

## 7. 診断・案内文言

- 診断の主語と射程は、発火条件が保証する対象に限る。確定前の値を断定せず、捕捉した診断値の出し分岐まで設計する。
- WARNING を追加する → 発火条件が縮退のみか、テストで pin されるか、stderr が届く経路かを同時に決める。
- 兄弟 WARNING は、条件節の有無を突き合わせ、変数束縛で複製を消す。診断の射程は戻り値の粒度（全ケースの共通部分）に揃える。
- 中立ラベルを原因断定ラベルに改名する前に、helper 実装まで遡って流入しうる原因を列挙する。
- 診断を原因別の群に分ける → 後段の群は前段が通ったときだけ評価する。1 行が 2 つの原因を兼ねる場合は、両方の原因を併記する。
- 診断の目的が切り分けなら、外部入力を埋め込まず、行番号だけを報告する。
- runtime 診断は、見る場所（ファイル・行・reason 名）だけを示し、原因の分類は SoT に持たせる。
- 既存 reason を新しい失敗経路へ流用する → reason 一覧の説明・ACTION と契約文書を広げて grep で同期する。共通の診断 helper に新経路を載せたら、見出し・行ラベル・冒頭コメントに残る旧経路名を洗う。
- 診断は全経路を包含する文言にする。上限付き WARNING を指すなら、残件数を明示する。
- 同一レポート内の 2 行は、定義位置でなく描画位置を主語に書き、別ステップの出力と誤読させない。
- 共有パスの進捗・status 表示は、合流する全経路で真となる中立語（「処理済み」など）にする。本文と Placeholder Legend を同期する。常時出す完了文に空集合の除外（「failed 扱いを除き」）を置かず、条件付きの専用行に閉じる。
- 停止の見分けは、stderr の先頭一致でなく、行の有無で書く。判別文字列の衝突も確かめる。
- 恒久規範の理由を、現時点の欠陥への断定に置かない（置くなら、その欠陥を扱うテストの名前または SoT の節への参照を添える）。
- 「A を却下して B を採用」と書く → 却下理由が B にも成り立たないかを、書き終えた直後に再検査する。成り立つなら理由から外し、犠牲を明記する。

## 8. 復旧・再実行の案内

- 復旧案内は、エラー出力だけで実行できること。新しい失敗 reason を既存の行へ束ねたら、行ごとに復旧手順が実行可能かを確かめ、必要なら行を分ける。
- 診断が先頭数行しか出さない → 「診断の行を直す」と書かない。再実行を禁止するなら、解除条件を添える。
- 拒否文が案内する修復手段は、拒否と同じ述語を持つこと。
- 何も変更しないまま、同じ入力で毎回同じ分岐に入る → 同種の他の分岐と同様に、そこから抜ける手順を書く。抜ける手順の破壊性（rm など）は、分岐の設計判断に揃える（元に戻せる退避で見送る分岐なら、削除でなく `mv` での退避を案内する）。
- 再実行の案内には、再実行の範囲と、保持する初回判断を同じ文で書く。通常経路で強制している検査も範囲に含め、再試行の上限も書く。重複を除かない追記を含む手順では、既に成功していた場合を先に分けてから再実行させる。
- 互いに独立した条件（例：入力の欠落と権限の不足）が増えても、組み合わせごとに分岐ラベルを増やさない。1 つのテンプレートに、条件ごとに任意で埋める欄を持たせる。場合分けを増やしたら、ケースごとに「何が出て何が出ないか」を書く。
- 失敗の判定は、失敗理由を個別に列挙せず、「解決できない」の単一クラスの述語で書く（仕様側の列挙も同時に更新する）。エラーの終着では、止める原因だけを列挙し、それ以外は上限付きの「直して再実行」で受ける。上限と、直せない原因の終着も書く。
- 他のスキルから読まれる reference へ回復規定を移す → 回復手順の所在をリンクで辿れるようにする。
- 利用者の承認を挟んで内容を自動で書き換える手順 → 「書き換え後も承認済みの内容と同じ」といった不変条件を掲げず、書き換えた差分を再表示して承認を取り直す。再表示は再実行と読まれないよう、表示するものと行う処理を分けて書く。承認に戻って繰り返す手順の終了条件は、本文中の目印文字列でなく、session の状態に持つ。
- `AskUserQuestion` の 4 問上限を理由に、承認外の経路を作らない（呼び出しを増やすか、最終問に溢れ分を載せる）。

## 9. 変更時の自己適用と検算

- 規約・lint rule を新設する PR → 最初にその PR 自身の diff（lint script を含む）へ適用して、self-violation を検算する。
- 散文の修正を書く → 是正文の上下 5 行と転送先を読み、置換後の文を単独で読み直す。新しい制御フローは、載せる面を先に列挙してから書く。
- コメントの誤りを直す → 主張を強めず、弱めるか削る。仕組みを細かく語るコメントは検証すべき主張を増やすので、短く圧縮し、根拠はテストの名前への参照で示す。
- 動作の契約を変える変更 → 冒頭の要約段落も書き換える。コメント内の件数（「N 箇所中 M 箇所」など）は変更で陳腐化するので、相対的な表現に置き換える。
- 「正本に準拠」と注記する変更 → リンクのパス・命名規約・件数表記まで、準拠先の同種の記述と一致させる。比較対象には、対象箇所と詳しさ（全文を載せるか、要点だけか、委譲先を指すだけか）が同じ記述を選ぶ。
- 同じ PR で、別の場所へ誘導するだけの短い案内文を複数作る → 目印に使う接頭辞（marker）を全案内文で文字列として一致させる。新しい reference 名は、事前に grep して概念衝突を確かめる。
- 新設セクションへ言語統一ルールを適用する → 見出しだけでなく、定型ラベル・凡例・注記にも同じ規則を適用する。同 scope の Hint / Warning は、既存の多数派の言語に揃える。
- 圧縮を目的とする変更の受入条件は、変えてはならない範囲とスコープ制約から逆算する。目標値と実際の着地点を併記する。
- 圧縮・再編のあと → heading level の飛び（h2 → h4 など）を awk で機械検出する。行数制約を理由に MUST-execute の list を inline に詰めて scannability を損なわない。
- LLM にリテラルで渡す bash は、構文有効性（`; then` の隣接など）をテストで検証する。
- 番号付きリストは、項目の間にインデントしていないブロック（コードフェンスなど）を挟むとそこで切れ、後ろのリストは最初の項目の番号から始まる。全項目を `1.` と書くと、そこで 1 から数え直しになる。番号で参照する場合やブロックを挟む場合は、実際の順の番号を書く。
- prompt 内の numbered list は、全 step に同じ粒度の動作詳細を対称に置き、自明を理由に省略しない。
- GFM のセルを壊す文字の規約は、placeholder 単位でなく、全経路の親に置く。表のセルに複雑な jq pipe を埋めず、散文の指示でフィルタを書く。
- CHANGELOG の項目は、commit 件名の内部用語でなく、利用者に見える効果を主語に書く。
- 現在の実行に効かない記述は、削除・書き直し・変更なしの 3 択で判定し、その記述を読む側を grep で確かめる。構造を平坦にする変更で消すときは、経緯の注記・同期保守のための情報・機能の記述の 3 つに分類してから消す。
- 検出を避けるために崩した記入例の書式 → 退避である旨と、実際の正しい記入形式を併記する。
- verbatim 実行の指示と placeholder の置換必須が矛盾する → 「placeholder のみ置換可」の carve-out を明記する。
- 制約が生成テンプレート向けなら、生成物に載る fence の中にも書く（fence の外は生成器しか読まない）。
- 最初から順に実行する手順に、条件付きの Phase を足す → `(Optional)` / `(On Demand)` と冒頭契約の例外を明記する。
- 提示順のルールを計画テンプレートへ足す → `depends_on` 列の有無を確かめ、plain list なら独立ブロックとして提示する。
- 人間確認箇所の洗い出しは、ツール名だけでなく、選択肢提示の見出し・問いかけの文末も列挙して掃引する。
