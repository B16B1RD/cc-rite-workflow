# テストの pin・mutation 設計原則

テスト（特に bash テスト・散文契約の静的 pin）を**書く側**と**レビューする側**が共通で読む規則集。
各行は「条件 → 期待」の形で書く。判定の軸は 1 つ: **その実装が壊れる最も起こりやすい形で、このテストは落ちるか**。

呼び出し元: `skills/issue-implement/SKILL.md`（5.0.F テスト規律）/ `agents/test-reviewer.md`（Step 3）。
節構成と配線の契約テスト: `hooks/tests/test-pin-mutation-principles-contract.test.sh`。

用語: **pin** = 挙動・文言・件数を固定するテスト assert。**positive control** = 検査が空振りしていないことを示す、必ず成立する対照入力。
**negative control** = 検査が拒否すべき入力。**mutation** = 実装を意図的に壊した版（mutant）。**生存** = mutant でもテストが緑のまま。

## 1. 基本手順（pin を書くとき）

| 条件 | 期待 |
|------|------|
| 既存の実装に pin を足す | 書く前に mutation を当て、素通りしたときだけ pin を足す（要否と有効性を分離する）。実装より先にテストを書く TDD では、Red（先に落ちること）の確認がこの役を担う |
| pin を足した | 対象を壊す mutation を実測して落ちることを確認する。確認していない kill 主張（「この変異で落ちる」というコメント）は書かない。書いてあって未確認ならコメントから撤去する |
| 修正を入れた | 修正全体を戻すと落ちるだけでは各行が固定されたとは言えない。修正の行ごとに mutation を入れる |
| 同一方針で複数経路を直した | 各経路の修正を単独で戻す mutation でそれぞれ落ちることを確認する |
| pin を足す・深める | 述語・配置・routing・副作用・到達の 5 軸で mutation を当てる。既存 literal は残し、極性（肯定/否定）まで固定する |
| 回帰テストを書く | 修正前コードに当てて落ちることを確認する（grep token は修正パス固有 literal にする）。直らない失敗の確認には修正前版でも同じ実行を回して再現する対照を示す |
| 防御・guard・fail-loud 分岐を足した | 分岐ごとに失敗を起こすテストを同じ変更で足す。guard を壊す mutation で落ちることを測る。到達入力を構成できない防御は、テスト不足でなくデッドコードとして扱う |
| 新規 lint・検出 helper | 中核ロジックを no-op にした mutation で落ちる TC を持つ。検出分岐を足したら分岐ごとのヒット数を修復前の tree で測り、0 なら、その分岐を削るか走査の起点を広げる |
| 「X を守る」と書いた assert | X を壊す変異で落ちることを実測する。assert 名・TC 名は実際に強制する範囲と同じ広さで書き、実際の強さ（例: `-ge 1` で確かめているのに「3 回」と名付ける）・方向・順序を名乗り過ぎない |

## 2. 空振りを防ぐ（positive / negative control）

| 条件 | 期待 |
|------|------|
| 「出ない／呼ばれない／作られない」を assert する | 同じ fixture・同じ経路で「出る」ことを示す positive control を先に置く。sandbox の依存不足・早期 exit・ログが書かれない走行で素通りしやすい |
| 否定 assert が上流の早期 exit・ゲートの後ろにある | ゲート条件を洗い出し、経路を通過した証拠（到達マーカーを記録する stub + 陽性対照）を pin する |
| 無出力が正常な契約 | 非空チェックを「動作している」ことの証明に使わない。control を別に置く |
| 警告のみ・rc=0 の helper を pin に使う | 対象の実在確認と警告 grep の 2 段で塞ぐ。縮退動作と正常動作が同じ rc なら経路固有 marker の不在を pin する |
| 負例 fixture | 修正前・guard なしなら通ってしまう入力を選ぶ。複数の検証に掛かる値は避け、検証したい分岐だけが拒否する値にする |
| 拒否側 pin を足した | 受理側（弾いてはいけない正当入力）も同時に固定する。入力を狭める変更には「弾かれる側の正当入力」fixture を 1 本入れる |
| 禁止文・否定 pin を書く | 許可語彙の denylist を対で置き、対象行の件数を先に確認する。失敗理由（0 件／2 件以上／残存）を切り分けて出す |
| 負の pin を足す | 回避策が逃げる positive 側も同時に pin する。到達して落ちうるか変異で確認する |
| 実装変更で到達不能になった否定 assert | 常時緑なので削除する |
| 自分が echo した文字列を自分で grep している | self-grep tautology。被テスト側の実出力を検査する |
| 期待値に `.*` を含める／assert に使われない診断変数がある | `.*` は未検証と同義。固定するか削除するかの二択にする |
| fixture 書換え・前提を作る操作の後 | 狙った前提が成立したこと自体を assert する。ただし前提を壊す mutation が無い恒真 assert はコメントで足りる |
| `\|\| true` や stderr 握りつぶしでテスト対象を呼ぶ | exit code を assert する。stderr 握りつぶし + exit 未検査 + 事前 = 事後の期待値が揃うと、スクリプトが動かなくても PASS する。変化する値を assert する |

## 3. 文字列・正規表現 pin の精度

| 条件 | 期待 |
|------|------|
| 文言を前方一致で pin する | 接頭辞が短いほど付け足し変異を通す。行末まで完全一致（`grep -qxF` 等）にする。「行まるごと」を名乗る照合は行全体一致 |
| ファイル全体への grep で pin する | 対になる記述箇所（強制用と診断用など）の片方が残れば緑になる。pin 対象を 1 箇所に絞り、一意な行まで狭める |
| 散文と同居する行を pin する | コマンド span に絞り、引数の出どころまで固定する。折り返された散文は空白正規化して文全体を `grep -F` |
| 出現数を数える | `grep -c` は行数で出現数ではない。同一行に複数あり得るなら `grep -o \| wc -l`。`-ge N` は片側 mutation を隠すので `-eq N`。count の注記に対象 literal を書くと注記自身が N+1 個目になる |
| 出現回数 pin（count=2 等） | 一意な行を消しても、同じ語を含む別の行（おとり）が残れば件数が合って素通りする。出力する側・読む側・実行を促す行を独立に pin する |
| 閾値・下限を置く | 実数に近い値（1 件の欠落を捕まえる値）にする。閾値ちょうどの入力 fixture を置く |
| grep の方言 | `grep -E` に BRE の選択記号（バックスラッシュ + パイプ）を渡すと literal 化し、否定の pin は緑のまま、肯定の pin は赤のままになりやすい（対象に literal のパイプがあれば一致する）。パイプを含む文字列（markdown の表の行など）を ERE に渡すと、空の枝ができて全行に一致し恒真になる実装がある（GNU grep。空の枝の扱いは未規定で、エラーにする実装もある）。ERE の対にならない `)` も実装により扱いが異なる（GNU grep は literal、エラーにする実装もある）。helper の方言を確認する |
| 部分文字列 grep（`grep -ci stop` 等） | `nonstop` や否定形にも一致する。境界例で確かめる。停止語は続行語の不在も確認する |
| 述語を広げた／狭めた | 肯定・否定の両例で実測する。alternation は各枝を単独 grep し、quantifier 境界・flag ごとに positive test を置く |
| テキスト検査の対象に残骸が入りうる | `__pycache__` や古い生成物を事前に整える。大小のみ違う fixture ファイル名は macOS の既定のファイルシステムでは同一ファイルになる |
| コメントに同じ token が残る | token を独立 grep する pin は、実コードを消してもコメントで PASS する。実コード行に絞った結合 regex にする |
| `awk -v` で範囲 pattern を渡す | backslash がエスケープとして処理され pattern の意味が変わる（範囲が早く閉じる、end が一致せず末尾まで走るなど）。`ENVIRON` か meta なしの pattern を使う |
| section / flip-flop 抽出 | start は code 行専用 prefix でアンカーし、end も文書内で一意な見出しにする。抽出が空（pattern 未検出）か範囲が空かを切り分ける。両端アンカーを検査し、閉じの消失は rc に反映する |
| `sed` / `awk` で mutation を作る | quote で silent に失敗しうる。適用前に一致が丁度 1 件であることを確認し、適用後に該当行を表示して `bash -n` で構文を確かめる |
| 検出器が抽出する対象 | 既存の書き方の完全一致でなく性質（形）で抽出し、一致例・非一致例の両側 fixture で固定する。エンジンが複数（sed / awk / Python）なら各エンジンに自己テストを置く |
| 手書きで写した定義（regex・集合） | 両側から集合を取り出し一致を test で固定する。別実装が同じ判定を持つなら実物同士を同じ入力集合で突合する |
| grep 系 assert の対象が markdown | 括弧書き・限定句・補足句まで literal に含めて pin する。`.*` で繋ぐと補足句が固定されず狭める書換えが緑になる |
| 否定文の pin | 否定語まで固定し、反転する mutation で落ちることを確認する。否定語 + 動詞の検出は副詞挿入・改行・強調記号を通す窓を命令・助動詞の否定に限って与える |

## 4. 対称・横展開・件数

| 条件 | 期待 |
|------|------|
| 対称な 2 経路（通常経路と回復経路、通常 commit と merge commit 等）を持つ実装 | pin も両側に置く。片側しか実行しない pin は退行を検出できない（片側ずつ外す mutation で生存する） |
| N 箇所へ同じ修正を展開した | 適用箇所数 = pin 箇所数を完了条件にする。N 個の系統に規約を適用したら N 個すべてを pin する |
| 新規 TC を足す | sibling TC の共通 helper・fixture の形・variant 数と命名に揃える。sibling が固定する列・値の集合を継承し、自分だけ弱い集合を選ばない |
| 同一 invariant を表す 3 site（一覧・実装・コメント） | 同期更新ルールを 1 行で明文化する。値を足したら限定句・固定 regex・assert ラベルを同一 commit で揃える |
| 期待値を片側から抽出する symmetry pin | 両側同時 drift は固定されない。2 値を同一視する正規化をしたら前提を別 assert で固定する |
| 2 実装が「同一定義」を宣言する | 両実装の regex literal をバイト比較する test と対にする |
| helper へ共通化した | helper 単体 test に加え caller 側の routing・引数 wiring も pin する。呼出件数だけの pin は引数 wiring を守らない |
| 新しい出力フィールド・marker | producer の emit だけでなく consumer（表なら各行）を行単位で pin する。marker は payload まで完全一致で、producer と consumer を対にする |
| OR 接続の拒否条件・連言 | 項ごとにその項だけで拒否される case を置く。受理側は片項だけ外した入力で pin する |
| 母集団に対する `all()`／全称契約 | 複数要素 fixture で pin し、代表 1 値でなく全ての分岐の値をループで固定する |
| 掃き出し（sweep）の完了検証 | 抽出と同じ grep を使わない（死角が継承され残存ゼロが偽になる）。対象の性質から独立に検証する |
| 同一 1 文への drift 修正が繰り返された | 逐語 pin を足さず、詰め込んだ構造を箇条書きに分割する |
| 複数の test が同じ形を持つ | 共通 helper 化を検討する |

## 5. fixture 設計

| 条件 | 期待 |
|------|------|
| fixture を作る | 本番で普通に起きる state（レビュー履歴あり・実データの逸脱）を入れる。テンプレートでなく生成器の実出力から作り、書き込み元が同時に書く全フィールドを揃える |
| 境界を検証する | 境界ちょうど・直下・直上の入力を置く。上限と下限は別 fixture（区間制約は下限を破る fixture と上限を破る fixture を別々に） |
| 選択規則（最新・先頭・優先順） | 規則を区別できる fixture（字句順と更新時刻が食い違う、先頭は marker なし・2 つ目に marker）で書く。同順位を決める入力（更新時刻など）は値を互いにずらし、順位が一意に決まるようにする |
| 省略時・既定値の TC | 既定値と他値で結果が分かれる入力で書く。既定値と同値の assert / 等価変異は強化とみなさず、テスト名を実態に合わせて付け替える。本番の引数形（既定値を解決する経路）を通すテストを 1 本置く |
| fixture helper が入力を既定値へ正規化する | 対象の分岐に届かない。state を直接書き換える fixture にする |
| 2 つの候補値が同じ fixture | 参照先を区別できない。旧値と新値を分離して識別力を持たせる |
| 重複排除・集計 | 入力に重複を実在させる。対象と対象外が混在する fixture でも件数を固定する |
| 一時 repo | 実 repo と同じ追跡除外（ツールの作業ディレクトリなど）を入れる。git 失敗は `&&` 連結か `rev-parse` で捕捉する。`\|\| continue` でツール欠落を握りつぶさず即 exit 1 |
| control の作り方 | 本体 assert が食う入力ファイルそのものから 1 変数だけ差し替えて派生させる。別 TC に control が住むなら両 TC が同じ mock 定義を共有し続けることを保つ |
| cwd 依存の挙動 | cwd をテスト側で固定する（`cd / && run ...`）。linked worktree 依存は linked worktree fixture でしか pin できない |
| 特殊文字・実運用形式の値 | 述語の境界文字（`-` `/` `$` バッククォート）を含む実運用形式の値を 1 ケース足す。path traversal 拒否は着地先が実在する id で書く |
| 外部ツールの入力仕様 | 公式原文で確かめ、fixture は実際に届く形で組む。技術主張は sandbox で実 ref を仕込み rc と副作用を観測して裏取りする |

## 6. stub・shim・mock

| 条件 | 期待 |
|------|------|
| 失敗を注入する | PATH 先頭に fake binary（`mv` 等）を置く（`chmod -w`・`chattr` は root・FS 依存）。shim は対象呼出しだけ選択的に失敗させ他は実バイナリへ `exec` 委譲（実体パスは shim 前に `command -v` で捕捉）。引数分岐の shim で「無引数のみ exit 1」等を作る |
| 同じコマンドを複数回呼ぶ手順 | 失敗注入は呼出回数ごとに分ける。1 経路だけ失敗させる差替え + 差替えなし対照実行をセットにし、TC 名は強制範囲と同じ広さにする |
| gh・外部 CLI の stub | 本番 CLI と同じ入力軸（URL・`--jq`）を区別する。`--jq` を無視せず実 jq で fixture JSON を評価する。引数の個数・順序は argv 完全一致で要求する。絞り込みフラグは stub が守る |
| 書込系 subcommand の不呼出を pin する | 記録 stub を使い、スタブ呼出ログの全行が読取であることを allowlist で検査する。複数行引数（GraphQL mutation）は改行を正規化してから行単位 denylist に掛ける |
| 絶対パス呼出しの helper | PATH 注入が効かない。sandbox の plugin root に記録用 mock を置き、受領 payload を観測する |
| stub が引数（フィルタ式）を無視する | その処理はテスト外れになる。fixture に非対象要素を混ぜる |
| mock の intercept | mktemp 等は `TMPDIR` 有無の両形に対応する分岐にする。mock への marker 追加は事後 `sed -i` でなく mock 定義へ直接書く |
| stub の結果返却 | stdout で返し、失敗時は原因を残す。出力を足したときに他 assert が空振りしないか確認する |
| 縮退した mock | 他の分岐の到達不能を隠す。同一 fixture で正常走行を先に回して helper 到達を assert し、mock を正常動作に戻してから失敗走行を回す |
| `output=$(hook を source する helper ...)` | source した hook が親に残す変数はサブシェルで消える。hook は直接起動する。helper の `fail` を `$()` 内で呼ぶとカウンタ加算も消える |

## 7. 失敗経路・停止・skip

| 条件 | 期待 |
|------|------|
| 停止・失敗を検証する | 終了コードだけでなく理由出力（経路固有の診断 marker）まで assert する。同じ exit code を返す gate が複数あるなら exit + 固有文言の対で固定する |
| 非ブロッキング契約（exit 0 always） | 末尾 `exit 0` を削除する mutation で立証し、`\|\| true` で捨てずに終了コードを assert する |
| 失敗経路のテスト | 有効入力・実際の解決処理で副作用境界（外部への書込 0 回）まで到達させる。正常に解決する処理の停止分岐は、解決に失敗する処理を置いた一時 tree に script を複製して git 管理外 cwd から実行する |
| 「止まる」と「通る」 | 原因状態をループで回して止まること、解除後に通ることを両方検査する。コメントの主張はループ範囲に限る |
| 終了コードで使い分ける新規の失敗分岐（例: 1 は再生成、2 は即停止） | rc は非ゼロでなく完全一致で固定する |
| 停止条件を絞る・引数を必須化する | 全コマンドを列挙し直し、空値で続行していた正常経路が無いか確認する。fail-loud の OR 分岐は各側をテストする |
| 無音失敗を可視化する WARNING 修正 | その防御自体の失敗パスをテストし、同じ PR で mutation 確認する。WARNING は対象パスを含むこと・corrupt 入力で出ることを別 fixture で pin する。書込不可 state の検査は root では skip になる |
| テスト自体の skip | 集計されない skip 形態（exit 0 で抜ける、`pass '...skipped'`）を既存パターンから grep で特定してから規約化する。環境の能力を調べて skip する場合は、skip で検査が丸ごと消えないよう、CI を止める側の検査に権限に依存しない失敗誘発（存在しないパスへの書込など）で下限を残す。前提は uid の値で推測せず、実際に書き込みを試して確かめる。skip を持つ TC は skip 側に固定して mutation を当て、素通り（カバレッジ 0）を検出する |
| `id -u` 等の gate で root 環境が skip になる | pin が失われる。gate の外にも下限を置く |
| 環境値から前提を導出する（`$TMPDIR` 長など） | 下限値を assert する。CI を止める検査は失敗にし、それ以外は skip にする |

## 8. mutation の実測と報告

| 条件 | 期待 |
|------|------|
| mutation を当てる（実装者） | 検証対象の artifact から導出し、作業ツリーでその場で変異させる。戻しは `git checkout` でなく文字列置換で行い、`git diff` が変異前と同じ状態に戻ったことを確かめる |
| mutation を当てる（reviewer） | レビュー対象の working tree は変更しない。`agents/_reviewer-base.md` の Mutation experiments の手順に従い、使い捨ての detached worktree で行う |
| 赤にならない | pin の不備より先に mutation が効いたか（一致件数・構文・到達）を疑う。「到達して落ちうるか」を実証してから結論にする |
| mutation が生存した | テストを足す前に届かない理由を実測する。生存 mutant は 1 件ずつ到達経路を実証して説明できて完了。等価変異は分けて数える |
| mutation の報告 | 生存 mutation の列挙を本体にし、投入した mutant の一覧を報告に残す。clean tree の PASS と mutant の FAIL は別の欠陥を排除するので両方向測る |
| 入力値・正規化との相互作用 | テスト入力値が変異の落ち方を変えて assert の単独検出力を奪っていないか確かめる。production の正規化処理（`tr`/`sed`）との相互作用も実測する |
| 正規化の除外境界・選択肢 | 境界ごと（単/二重引用・backslash・行継続）に 1 本ずつ弱める mutant を当て、恒等関数 mutant だけで済ませない |
| 位置固定（前方一致・最終行等値）の述語 | 位置だけを崩す mutation で識別力を確認する |
| load-bearing な空白・コメント | mutation fixture の空白は test 内の grep で自己検査（その空白が残っているかを pin）し、formatter による剥離を防ぐ。コメントが守る不変条件は mutation で生存を確認する |
| 「戻らない」契約 | 戻り先に成功側の内容（おとり）を置くテストでしか固定できない。契約の入口（キー欠落・型違い）ごとにおとりを置く |
| signal handler・trap | EXIT trap だけで rc/副作用が満たされるなら、handler 削除 mutant を落とすために `trap -p` 等を assert する |
| 計算量・計時の修正 | 旧実装を参照に境界入力で突合する。計時テストは最悪形（因子の積で決まる。最長入力とは限らない）を定数から組み立て、遅い経路に到達したことを判定理由（出力メッセージなど）で assert し、閾値は性質（タイムアウト等）から決める |
| 外部 reviewer の指摘と自分の repro が逆 | 平均せず差分（句読点や空白の位置など 1 文字の違い）を特定する |

## 9. 散文契約・手順書の pin

| 条件 | 期待 |
|------|------|
| 散文を契約として grep pin する | 見出しラベルや語彙でなく operative な文（判定値・識別子）を狙う。weakened probe（意味を弱めた文）に一致しないことを negative control として課す |
| 手順書の bash 文を検証する | 期待文字列を照合するのでなく、抽出して実行し、プレースホルダー置換後の rc と marker を assert する。fixture は各ケース自前、失敗 stub は PATH 置換。プレースホルダを一律にチェックアウト内パスへ置換すると checkout 外を指す block を検出できない |
| 手順書が「保存 commit から読み戻す」等と述べる | helper の終了コードでなく保存された commit から読み戻す。検査成功と問題検出は別観測として扱う |
| 手順書の分岐と案内の対応 | 案内文の有無でなく見出し配下の配置で固定する。順序は節を切り出して行番号を取り、欠落を空値で先に数えてから比較する |
| 同型の案内が複数箇所にある | 全箇所を固定する（案内文中のコマンド部に bash の `$'...'` 形式が現れない、といった静的 assert）。引用なし案内も同欠陥なので、`$` やバッククォートを含む値の fixture で printf の `%q` による escape と二重引用符を区別する |
| 「全条件」「全て」を名乗る診断文・コメント | 連言を数えて全部挙げ、欠けた条件で落ちる記録でテスト固定する。主張が名指す入力を実装に通してから書く |
| 「直し方」の文言 | 故意に読み違えた操作を実行し、後段の検査が拒否するか実測する |
| 受入条件が文言の複数要素を要求する／帰結が 2 節（出す + 扱う） | 要素ごと・節ごとに pin を置く。静的 pin の grep は節限定にする |
| 文字列が残らない型の受入条件 | grep 0 件だけでは再追加を止められない。固定テストの要否を判断する |
| 例（canonical example）を持つ単一の正本文書 | 例を実際に検査する側（lint や hook など）へ流す fixture を置く。受入条件の再現手順はテスト suite に直接 pin する |
| 手順の dead 化 | 入口検証を足したら旧 guard と ERROR 文言に依存する方針・テストが死文化しないか確認する |

## 10. 環境・移植性・移設

| 条件 | 期待 |
|------|------|
| path 出力を比較する | fixture root は生成直後に `pwd -P` で正規化する（`TMPDIR` 末尾 slash も同様）。被テストが `cd -P` で出すなら期待値も `cd -P` 側で作る。片辺だけ `resolve()` を掛けず `readlink` で link 文字列を pin する |
| 文字列比較・ソート | `LC_ALL=C` を固定する。エラーメッセージの grep は locale 依存で dead assertion 化するので、rc か肯定結果を assert する |
| GNU/BSD・awk 実装差 | 移植性修正は gawk/mawk/bwk の 3 実装 + no-op 変異で load-bearing を確認し、旧実装を凍結して比較する。fixture 自身がその差異に依存しないか確認し、観測点を 2 系統に分ける |
| CI でだけ落ちる／ローカルで再現しない | 関連スイートだけでなく CI が回す範囲で検証する。隣接 git 操作へ identity フラグ（`-c user.email` 等）を揃える。評価したい条件を `next`/`exit` より前で出力して CI 実機で観測し、未観測の原因を書かない。CI が赤いときは失敗名に加え実行されたテスト件数を確認する（中断を疑う） |
| helper・bash block を別ファイルへ移設した | 移設前後でテストの検査数が無言で減っていないか、変更していない test も含めファイル別・全集計形式で base と比較する。減った検査は運んでいた契約を明示ケースに戻す。移設手順の鮮度は placeholder 置換後の bash と helper 本体の diff で測る |
| 振る舞い保持の refactor／委譲 | 原実装を参照に同入力で出力をバイト比較して立証する。観測は外部から見える全 channel（rc / stdout / stderr / file / commit body）で行う。bash 修正は修正前相当との A/B 実測で示す |
| 判定式・検出式を変えた | 式の断片で repo 全体を grep し、全スイートを実行してから push する。過去の実コマンドを新旧 guard に再生し、差分が意図形だけかを測る |
| 新しい検査 regex | 修正前コードに当てて一致件数が期待どおりか確認する（本来 N 件が 1 件なら対象を見ていない） |
| 共有 assert helper を source する | 独自の pass/fail カウンタを持つスイートでは FAIL が終了コードに反映されないことがある。summary 行は `$(basename "$0")` で自己参照する |
| base を取り込んだ | 他ブランチの取り込みでテスト名やテスト番号が衝突したら、それらから作る作業 dir 名も機械検証し直す |
| テストの `/tmp` 直書きを禁じる lint | `*/tests/*` を除外していると再発が不可視になる。走査を広げるか、除外理由を記録して棚卸しする |
| 新規 bash test を書く | 既存の bash テストを 1 つ以上読んで慣用パターンを確認する |
