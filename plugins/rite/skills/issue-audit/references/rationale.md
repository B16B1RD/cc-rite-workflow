# /rite:issue-audit — 設計理由

`skills/issue-audit/SKILL.md` から退避した rationale。本体は該当箇所に `rationale: references/rationale.md#<anchor>` の 1 行ポインタだけを残す。分岐表・marker・bash ブロックは本体と helper の docstring が SoT であり、ここへ複製しない。

## scope

採否判定の helper とゲートは、1 つの PR の 1 つの根因について、起票するかどうかをその時点で決める。そこで決めた結果が Issue 群として積み上がったときに初めて見えるものがある。

- 同じ根因が別々の PR から別々の Issue として起票されている
- follow-up の follow-up が何世代も続き、元の契約から離れていく
- 本文の受入条件が、その後の実装とずれたまま残っている
- 誰も手を付けないまま時間だけが経っている

本スキルはこの層だけを担う。入力を既存の記録に限っているのは、ここで新しいレビュー指摘を生むと、監査そのものが次の Issue の供給源になり、減らすべき連鎖を自分で伸ばしてしまうからである。

## rule-not-judgement

`/rite:issue-cancel` は「起動は人間の明示指示に限る」と定めている。やらないと決めるのは要件側の判断であり、実装側の観測からは導けないからである。本スキルの処分はこの規則と衝突しない。本スキルは中止を判断しない。すでに記録された事実に採否規則を当てはめた結果だけを実行する。

- 重複: `follow-up` ラベルを持ち、本文の先頭行が同じ根因キーの marker である Issue が 2 件以上ある。ラベルと先頭行は follow-up を起票する helper が既存の照合に使う条件と同じで、ラベルを付けられない第三者が本文に marker を貼っても重複は成立しない
- 解消済み: base branch へ merge された PR が `Closes` と書いている、または判定記録が `present=false` と記録している
- 不採用: 判定記録が V=C=T=false と理由を記録している

判断を要するもの（同じ根因かどうか、系譜の各世代が必要かどうか、方向をどう直すか）は提案に留め、人間か次の作業に委ねる。この境界は散文ではなく helper の構造で守る。`dispose` は Issue 番号を受け取らず、処分対象を自分で再計算する。そのため、提案として読んだ内容が処分に紛れ込む経路がない。

処分に使うのは、消えない場所にある根拠だけである。レビュー中の判定記録（sweep / triage）は PR の後片付けで削除され、残るのは follow-up の記録だけになる。そこで close コメントには、根拠をファイル名・判定行・マーカーの形で逐語に写す。ローカルの記録が消えたあとでも、Issue 上で処分の理由を追える。

人間が reopen した Issue と、別のセッションが claim している Issue は、規則に当たっても処分しない。reopen は「閉じない」という明示の判断であり、claim 中の Issue を閉じると、並行して動いている作業を壊すからである。
