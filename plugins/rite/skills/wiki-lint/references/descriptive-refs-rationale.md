# 番号参照の検出 — 設計根拠

`hooks/scripts/wiki-lint-descriptive-refs.sh`（wiki-lint ステップ 7.5）の設計の背景。comment-journal の P5/P6 は廃止済みで、Wiki の番号参照カウンタは本 helper。
**検出文法の SoT は `hooks/scripts/number-reference-check.sh`**、本文抽出（走査範囲と除外）の SoT は helper 冒頭であり、本ファイルは「なぜその形なのか」「なぜ代替案でないのか」を収める。

## helper へ切り出した理由

ステップ 7.5 は当初 SKILL.md 内の grep pipeline だった。検出を裸の `PR #N` / `Issue #N` へ広げた時点で除外が 5 種必要になり、
`bash-heaviness-check.sh` の LINE_THRESHOLD も超えた（拡張前から超えており `MIN_SIGNALS=2` 未達で finding 化はされていなかったので、これは決め手ではない）。決定的だったのは、**Markdown fence の中に置かれたロジックには mutation test が届かない**こと
（fence 内を差し替える mutant を生成できないため、検出規則が壊れても緑のまま通る）。sibling helper 5 本が既に同じ形なので、新しい構造の導入ではない。

## 検出文法を持たず委譲する

Wiki の番号は `number-reference-check.sh` が定義する文法で数える。本 helper が独自の regex を持つと、
文法が 2 箇所に住み、片方が動いたときにもう片方が黙って古くなる。本 helper の仕事は
「Wiki の永続成果物を SoT に照らして測る」ことなので、その SoT のコピーを抱えるのは目的と矛盾する。

helper に残るのは**本文抽出**だけ — frontmatter の `sources:` ブロック、コードフェンス、
インラインコードスパンのマスク、TODO/FIXME、`index.md` のサマリー列抽出。抽出した行を委譲先へ渡し、
返ってきた findings の行数を hits とする。委譲先の exit code は 0/1/2 の clean/hit/error 信号で
件数ではないため、hits の算出に使ってはならない（使うと 1 ページの hits が最大 1 に潰れ、
指標の意味が「hit 行数の合計」から「hit を持つページ数」へ無言で変わる）。

委譲した文法が持つ性質は 3 点ある。

- **キーワードを伴わない裸の番号トークンも対象になる**。参照キーワードを要求する文法は
  「キーワードのない番号は正当な文脈が多すぎる」という理由で裸形を落とすが、
  SoT 側は 3-4 桁という桁数で範囲を絞っており、その絞りが「正当な文脈」の大半
  （箇条番号・少数の列挙）を先に落とす
- **1-2 桁と 5 桁以上は対象外**。上流トラッカの id や列挙条件は Wiki 散文に残る。
  範囲の判定を手書き grep で行うとこの境界とずれるため、判定にも同じ委譲先を使う
- **`drift-check-ignore` 行は Wiki 本文でも免除される**。検出器自身の fixture 向けの opt-out であり、
  **Wiki ページで使ってはならない** — 書いた瞬間そのページが本指標から外れる

## 走査範囲 — どこを見て、どこを意図的に見ないか

検出規則と同じくらい重要なのが「どのファイルを対象にするか」で、範囲の外にあるものは指標に一度も現れない。
本検出器の範囲は次のとおり。**見ないファイルはいずれも意図的な除外**であり、未実施の残債ではない。

| 対象 | 判断 |
|------|------|
| `pages/**`（走査する。`## ソース` 節を含む） | Why 散文そのもの。指標の中核。**`## ソース` 節も除外しない** — bullet の表示テキストは読者が読む散文であり、そこに番号があれば Wiki の中の番号である。出典の受け皿は隣のリンク先パスで、そちらは `#` を持たないため文法に一致せず、表示テキストを直してもリンク先は動かない |
| `index.md`（走査する。エントリごとのサマリーのみ） | サマリーはページ frontmatter の `description` と同源の散文。`/rite:wiki-query` の Pass 1 もこれをキーワード照合に使う（テーブル形式・箇条書き形式のどちらでも）。いずれの形式でも「読み手が Why を取りに行く面」であり永続成果物として SoT の適用スコープに入る |
| `log.md`（走査する） | ingest / lint イベントの台帳で、読み手が「いつ何が入ったか」を取りに行く永続成果物。各エントリは raw ファイルパスを併記しており、そこに出典がある以上、散文側の番号は重複であって追跡可能性の担保ではない。**append-only は ingest / lint が log を書く経路の契約**（追記のみ、過去エントリを書き換えない）であって、過去エントリを番号規則の対象外にする宣言ではない |
| `raw/**`（走査しない） | レビュー / fix の生ログ = provenance 資料。番号は出典そのもので、Why の代替として貼られたものではない。文法には一致するためパス単位で除外する（実測 1,400 **ファイル**超。他行の hits とは単位が異なる。review / fix サイクルごとに増えるため厳密値は持たない） |
| `SCHEMA.md`（走査しない） | スキーマ定義で散文を持たず、実測 0 hits。対象化しても指標は動かない |

`index.md` と `log.md` は helper が**自力で読む**。stdin の `pages_list` へ足す形にすると、LLM が substitute を忘れた回が
「走査しなかった」ではなく「指摘が無かった」として通過し、本検出器が塞ごうとしている盲点そのものを再導入する。
stdin から渡す経路も完全一致で受理するが（重複は畳む）、届くかどうかを stdin に依存させない。
`log.md` では自力読出が唯一の経路でもある — ステップ 2.2 の `pages_list` は `pages/` 配下しか列挙しない。

<a id="pages-list-unchanged"></a>

**ステップ 2.2 の `pages_list` を変えない理由**: `pages_list` はステップ 3 / 4 / 5 / 6.2 / 7 が共有する入力で、
ステップ 5（孤児検出）は `pages_list` の各ページが index 登録集合に含まれるかを見る（`pages_list ∖ index 登録ページ`）。
`index.md` は自分自身に登録されないため、`pages_list` に足すと index.md 自身が未登録として孤児 +1 になる。
ステップ 4（陳腐化）は frontmatter `generated.at` を要求するが、index.md はそれを持たないため「generated.at フィールドが存在しません」の
WARNING skip が 1 件増える。helper 側で完結させれば他カテゴリの入力はバイト同一のまま保たれ、非回帰が測定ではなく**構成**で保証される。

### `index.md` のサマリー抽出

エントリ行の判定は `](pages/...)` リンクの有無で行い、**行単位**でテーブル形式と OKF 箇条書き `* [title](pages/...) - desc` の
両方を受ける。テーブルは列数不問（サマリー列の位置と列数をヘッダー行から導出する）。`templates/wiki/index-template.md` と
wiki-ingest ステップ 6 はどちらもテーブル形式を**指示**しており、現行の wiki ブランチもテーブルで維持されている。
一方、箇条書きテンプレートが配布されていた期間に初期化された bundle の index.md は箇条書きのまま残り、移行を促す producer も存在しない。つまり箇条書きは
放っておけば消える残滓ではなく、テーブルと併存し続ける。どちらか一方専用にすると、そうした bundle で検出が無言で 0 件へ倒れる。
ファイル単位で形式を判定しないのは、ingest がテーブル行を追記しても節の外の旧箇条書き行を削除も移送もしない以上、
混在が「起きうる」ではなく**そうした bundle が到達する終端状態**だから。なお本リポジトリの wiki ブランチでは箇条書き形式の
index.md は観測されておらず、両形式対応は外部 bundle に対する防御的サポートである。

`index.md` の走査では **HTML コメントブロックを行の分類より前に落とす**（`^[[:space:]]*<!--` で開始、`-->` を含む行で終了）。
箇条書きテンプレートが配布されていた期間の `index-template.md` の前文はコメント内に箇条書きの記法例を含み（現行テンプレートでテーブル形式へ差し替えた際に
この記法例コメントは削除されたが、それ以前に初期化された bundle の index.md には残る）、落とさないと記法例が
実エントリとして数えられて、下の検出失敗ガード（`entries == 0 && linkrows > 0`）がそれらの index.md では
恒久的に発火しなくなる。
開始側に行頭 anchor を付けるのは、サマリー本文中に `<!-- ... -->` を**引用している実エントリ行**を落とさないため
（実測: 現行 index.md に該当行が 2 件あり、anchor 無しだと該当 2 行分 hits が減る（実測時 230 → 228。index.md は ingest ごとに増えるため絶対値はスナップショット））。

`|` で split する前に **3 種のマスク**を通す。1 つでも欠けると現行 index.md の列数不一致は 0 件にならない。
下記の実測行数は **ingest のたびにエントリが増えるため下限**として読むこと（`log.md` / `raw/**` の行数と同じ性質で、
厳密値は持たない）。荷重を担っているのは「どのマスクも 0 行ではない」ことであって絶対値ではない。

- **インラインコードスパンのマスク** `` gsub(/`[^`]*`/, "_", …) ``: バッククォート内の素のパイプ（実測 27 行以上）を潰す。列数維持の支配項で、E4 の検出側除外と split 前処理の二役を兼ねる
- **エスケープ済みパイプのマスク** `gsub(/\\\|/, "_", …)`: サマリー列に書かれた `\|`（実測 3 行以上 = ``awk -F'\|'`` 型の説明文）を潰す
- **リンクスパンのマスク**: リンクテキストに**素のパイプ**を含むページタイトル（実測 9 行以上 = `O_CREAT|O_EXCL` 型）を潰す

ヘッダー行にはコードスパンとエスケープ済みパイプの 2 種を適用する。ヘッダー判定は `](pages/...)` を含む行を
除外するため、リンクスパンのマスクはヘッダーでは不要。ヘッダー側だけ raw のまま split すると
列数が水増しされ、全データ行が「ヘッダーと列数が違う」として skip される。

サマリー列の位置はヘッダー行から決め、ヘッダーを検出できないテーブル行は**既定列を当てずっぽうで読まずスキップする**。
既定列を当てると、見出し語が `サマリー` から drift しただけで別列を黙って走査し hits が無言で 0 に倒れる
（位置固定の列パースが列の増減で silent no-op に倒れるのと同じ失敗形。`/rite:wiki-query positional-parse-row-count-guard` で参照）。
列数がヘッダーと異なる行も同様にスキップする（誤検出で件数を膨らませない）。箇条書き形式は列を持たないためヘッダー不在の影響を受けない。

エントリ行を判定するリンク regex は、同じ `index.md` を読む `wiki-lint-orphans.sh` と**同一定義**にする
（`./pages/` / `../pages/` 形式も受ける）。片方だけ狭いと、その形式の index で本 helper だけが無言で 0 件に倒れ、
orphans 側は正常に処理し続けるため他カテゴリからも異常が見えない。

**スキップした行は stdout の `descriptive_refs_skipped_rows` に載せる**。stderr の WARNING だけでは
ステップ 9 の note 条件（`descriptive_refs_read_errors > 0`）を通らず、部分欠損した集計が注記なしで
「実測済み」としてレポートに載ってしまう。helper が pages 側で明示的に閉じている失敗モードと同じ穴を
index 経路にだけ残さないための措置。**行単位の値を `descriptive_refs_read_errors` へ混ぜてはならない** —
`read_ok=io_error` の判定は「読めなかったファイル数 == 走査母数」というファイル単位の算術で、
行単位の値を足すと 1 行のスキップが index.md 全体の読出失敗として扱われ、その時点の index.md の hits が丸ごと落ちる。

ガードの発火条件を「全行 skip（`parsed == 0`）」にしないのは、記法例コメントを落とした後の canonical な
`index.md` では `parsed == 0` が「形式 drift」と「まだ登録が無いカタログ」を区別できないため。両者を分ける
材料はリンク形状の行の有無（`linkrows`）にしかない。記法例コメントを落とす規則自体の理由は上記の
HTML コメントブロック除去の段落を参照。

<a id="entries-zero-guard"></a>

**エントリ 0 件ガードの発火条件を `index.md` 自身の内容で決める理由**: 「リンク形状の行（`](`）が 1 行以上あるのに、
そのリンク先が `pages/` と認識できない（`entries == 0`）」だけを検出失敗とし、リンク行が 1 行も無い index は
静かに 0 件として落とす。前者は**形式 drift**（実測 230 hits 以上が丸ごと落ちる状態）、後者は**まだ登録が無いカタログ**で、
両者を分ける材料は index.md の中にしかない。判定材料に散文の箇条書き / テーブル行を含めないのは、実エントリを
持たない手書き index（「- 準備中」等）を検出失敗として誤計上しないため。
**stdin（`pages_list`）の非空性を条件にしてはならない** — ステップ 2.2 は `pages_list` が空でも本ステップを実行する
契約（wiki 初期化直後 / `git ls-tree` 失敗時に index.md の指摘を落とさないため）であり、そこを条件にすると
**ガードが無効化される経路とガードを必要とする経路が完全に一致する**。precondition は守りたい対象と同じものを
測る必要があり、相関しているだけの代理値を使うと「相関が切れる場所＝守るべき場所」で沈黙する。

**END の未閉鎖検査を `in_comment` / `infence` の 2 ラッチに限る理由**: 本文フィルタは他に 2 つのラッチを持つが
（`infm && insrcblk` = frontmatter の `sources:` ブロック、`insrc` = `## ソース` 節）、どちらも `index.md` では
**ラッチを立てる producer が存在しない**。実測: `index-template.md` と live `index.md` のいずれにも `sources:` /
`## ソース` は 0 件で、live 側はそもそも frontmatter を持たない（`infm` が立たないので `insrcblk` に到達しない）。
ingest の index 更新もこの 2 つを書かない。**検査を足すか否かを分ける判別子は「`index.md` 経路に producer が実在するか」の一点**である。
HTML コメントは、箇条書きテンプレートが配布されていた期間に初期化された bundle の index.md 前文と
手書き index という**現存する producer** を持ち、閉じ忘れが実際に到達しうる（開始側の行頭 anchor により、
ingest がサマリー列へ書き込む引用はラッチ対象外）。コードフェンスは index 経路の producer を持たないが、
ページ本文と共有するフィルタの一部としてもともと同一の END 検査に同居している（判別子が決めるのは
**これから検査を足すか**であって、既存の同居を解くことではない）。到達しない状態に検査を足すと、
正常形（末尾がソース節の手書き index）を検出失敗として誤計上する側のリスクだけが増える。
`index.md` に `sources:` / `## ソース` を書く producer が生まれたときに、この 2 ラッチへ検査を足す。

Wiki ページの番号参照カウンタは本 helper が `git show` で担う。comment-journal の P5/P6 は廃止済み。`separate_branch` では Wiki ページの実体は wiki ブランチにあり、dev checkout の `.rite/wiki/` は gitignore されたローカル置き場になる。

**E5（TODO / FIXME）の適用単位はページと index で異なる**。ページは行単位で落とす（従来どおり）が、index はサマリーを
抽出したあと、コードスパンのマスク後に判定する。フィルタ段で落とすとエントリ行が `entries` にも計上されないまま消え、
END の分母（エントリ行数）が実体からずれる。副次的に、コードスパン内に**引用された** TODO は E4 のマスクで無効化されるため
index では hit として残る（引用は主張ではない）。

E5 は**意図的除外**であって抽出失敗ではないため `descriptive_refs_skipped_rows` には載せない。載せると
「形式が変わって列を読めなかった」欠損と「規約どおり除外した行」が同じ 1 つの signal に潰れ、
このカウンタの存在理由（部分欠損を注記なしで「実測済み」と読ませない）を損なう。E1-E4 と同じく、
除外そのものは surface しない。

`separate_branch` で wiki ブランチの ref 自体が解決できない場合は、`index.md` を「不在」ではなく**読出失敗**として扱う。
`git cat-file -e` は「ref が無い」と「ref 内に path が無い」をどちらも rc=128 で返すため、畳むと壊れた ref が
静かな 0 件になり、`pages_list` も空だと stderr すら出ないまま「実測済みの 0 件」として通る。

<a id="exclusions"></a>

## 除外の実測根拠

| 除外 | 実測 | 判断 |
|------|------|------|
| E1 frontmatter `sources:` ブロック | frontmatter 散文に本物の参照 22 件 | frontmatter 全体を落とすと 22 件が盲点になるため `sources:` ブロックのみへ限定。ref 値はファイルパスで番号規則に一致しないため、除外自体は防御的 |
| E3 コードフェンス / E4 スパン | — | 引用されたコマンド・regex の中の番号はリテラルであって主張ではない。E4 は削除ではなく `_` 置換（削除するとスパンの前後が連結して行の意味が変わり、`index.md` では列構造まで崩れる） |
| E5 TODO / FIXME | — | 前方追跡の番号は「これから対応する先」であって過去の出典ではない。SoT も同じ行を除外する |

いずれの除外もその範囲内では再発が見えなくなる。だから範囲は最小限に切る。

**`## ソース` 節は除外しない（E2 を置かない）。** 節を provenance ラベルの置き場と見なして丸ごと落とすと、
Wiki の番号のほぼ全量が指標の外に出る — 節を持つページは 306 / 310 で、除外が指標のほぼ全面を覆う。
その状態の検出器は「除外の外は clean」としか報告できない。
bullet の表示テキストは読者が読む散文であり、そこに番号があれば Wiki の中の番号である。
出典は隣のリンク先パスが持ち、そちらは `#` を持たないため文法に一致しない — 表示テキストを直しても
リンク先集合は不変で、provenance は失われない。節スコープと見出し接尾辞許容の各規則は、
節そのものを落とさない以上そもそも要らない。除外の識別子は E1 / E3 / E4 / E5 の 4 つで、
番号を詰めないのはテストと本文が既に名指ししている意味を保つため。

## 検出器を 1 本に保つ

Wiki の番号参照カウンタは本 helper だけ（wiki ブランチを読み、ファイル単位で hits を集計する）。
comment-journal の P5/P6 は廃止済み。文法は `number-reference-check.sh` に委譲するため、
番号の定義そのものはリポジトリ全体で 1 箇所にある。
